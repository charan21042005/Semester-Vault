# UNIT I — PART 4: CAP Theorem & Trade-offs

## 🎬 First, Forget the Word "Theorem"

Imagine we have a MongoDB application. At the beginning, everything is simple:

```
              APPLICATION
                   │
                   ↓
              MongoDB
                   │
                   ↓
                Server
```

> One server. Life is peaceful. 😄

But our application becomes extremely popular. We now need multiple machines:

```
                  APPLICATION
                       │
             ┌─────────┼─────────┐
             ↓         ↓         ↓
          Server 1  Server 2  Server 3
             │         │         │
             └─────────┼─────────┘
                       ↓
                    DATA
```

Why? Because we learned in Part 2 that modern systems may need:

```
huge scale
high availability
distributed operation
horizontal scaling
```

> So now our database is distributed. And that creates a new problem.

---

## 1. The Problem CAP Is Trying to Explain

Imagine:

```
       Server A                  Server B
          │                         │
          │                         │
          └────── NETWORK ──────────┘
```

Both servers are supposed to communicate. Server A has some data. Server B has some data. They need to communicate so that the distributed system behaves properly.

**But what if...**

### 💥 THE NETWORK BREAKS?

```
       Server A          ❌          Server B

        DATA                       DATA
          │                          │
          └──────── X ──────────────┘
                 Network failure
```

Now Server A and Server B cannot communicate with each other. This is called a **Network Partition**.

> And this is where CAP becomes important.

---

## 2. What Does CAP Stand For?

> 🔥 This is an absolute must-know.

```
C → Consistency
A → Availability
P → Partition Tolerance
```

**CAP = Consistency + Availability + Partition Tolerance**

> But these words sound abstract. Let's understand each one separately.

---

## 3. C — CONSISTENCY

Don't think of consistency as simply: *"The database has correct data."* CAP consistency has a more specific meaning.

Think of two database nodes:

```
             Database
             /      \
            ↓        ↓
        Server A   Server B
```

Suppose the current value is `Balance = ₹1000`. Now we update it: `₹1000 → ₹500`.

> If the system provides CAP-style consistency, a successful read should not give you an outdated value after the update has become visible according to the system's consistency guarantee.

A simplified mental model:

```
Before:
A → ₹1000
B → ₹1000

        UPDATE

After:
A → ₹500
B → ₹500
```

### 🧠 Think:

> Consistency = everyone sees the appropriate/latest agreed value according to the system's consistency guarantee.

For our beginner mental model, think:

```
C
↓
"Don't give me stale/inconsistent data."
```

---

## 4. A Simple Real-Life Analogy

Imagine you and your friend maintain the same attendance sheet. Initially: `Rahul → Present`. You change it: `Rahul → Absent`.

> Your friend should eventually know the same updated state according to the system's consistency guarantee.

If you ask your friend *"What's Rahul's status?"* and he still says *"Present"* while your update should already be visible — you have a consistency problem.

---

## 5. A — AVAILABILITY

Now imagine one of the servers is having trouble. The system should still respond to requests.

```
          Application
               │
       ┌───────┴───────┐
       ↓               ↓
    Server A        Server B
       ❌               ✅
                       │
                       ↓
                    Response
```

Even if Server A is unavailable, Server B can potentially respond.

> **Availability** means the system continues responding to requests.

For our mental model:

```
A
↓
"Give me a response."
```

> The key idea is system remains operational and responds, subject to the system's defined guarantees.

---

## 6. Real-Life Analogy for Availability

Imagine a college has two admission counters: **Counter A** and **Counter B**.

Counter A closes. If Counter B continues serving students:

```
Counter A ❌

Counter B ✅
   ↓
Students still get service
```

> That's the idea of availability. The service doesn't completely stop just because one component has failed.

---

## 7. P — PARTITION TOLERANCE

> This is probably the most misunderstood one.

Let's look again:

```
       Server A          Server B
          │                 │
          X ← NETWORK →     X
```

Suppose the network between them fails. That's a **Partition**. The two parts of the distributed system cannot communicate properly.

> **Partition Tolerance** means: the distributed system continues operating despite a network partition between nodes.

Think:

```
P
↓
"Even if communication between nodes breaks,
the distributed system must tolerate that partition."
```

---

## 8. Real-Life Analogy

Imagine two college campuses:

```
Campus A                    Campus B

Students                    Students
   │                           │
   └────── Internet ───────────┘
                  ❌
             connection lost
```

The campuses can no longer communicate. A partition has occurred.

> The question becomes: How should each side behave while communication is broken? And that's where the CAP trade-off appears.

---

## 9. Put C, A and P Together

```
              CAP
               │
       ┌───────┼────────┐
       ↓       ↓        ↓
       C       A        P
       │       │        │
 Consistency Availability Partition
                       Tolerance
       │       │        │
       ↓       ↓        ↓
  Correct/    System   Survive
  consistent  responds network
  view        requests partition
```

At this point you might think: *"Okay, let's just choose all three."* And here's where the famous CAP idea comes in.

---

## 10. 🔥 The CAP Theorem

### ⭐ Exam Definition

> The CAP theorem states that a distributed data system cannot simultaneously guarantee Consistency, Availability, and Partition Tolerance during a network partition.

> This is the important sentence. But I want you to understand the reason, not just memorize it.

---

## 11. Why Can't We Have Everything During a Partition?

Imagine:

```
             DATABASE
             /      \
            ↓        ↓
        Server A   Server B
            \        /
             \      /
              NETWORK
                 ❌
```

The network has broken. Server A receives:

```
Update:
X = 100
```

But Server B cannot communicate with A. Now someone asks Server B: *"What is X?"*

> What should B do? It has two broad choices.

---

## 12. Choice 1 — Prioritize Consistency

Server B could say: *"I cannot safely guarantee the correct/current value because I can't communicate with the other side."*

> So it may refuse/delay the operation rather than return potentially stale data.

```
Network partition
       ↓
Cannot coordinate
       ↓
Protect consistency
       ↓
Some requests may not be served
```

Here:

```
Consistency ✅
Partition Tolerance ✅
Availability ❌
```

This is commonly described as: **CP**

---

## 13. Choice 2 — Prioritize Availability

Alternatively, Server B could continue responding even though it cannot communicate with Server A.

```
Network partition
       ↓
Communication unavailable
       ↓
Still respond to requests
       ↓
Availability maintained
```

But now B might return information that is not consistent with the latest state elsewhere. Conceptually:

```
Consistency ⚠️
Availability ✅
Partition Tolerance ✅
```

This is commonly described as: **AP**

---

## 14. So What About CA?

You might ask: *"What about C + A?"*

Conceptually, **C + A** can be achieved if you don't have to tolerate network partitions. For example, imagine a non-distributed/single-node system where the partition scenario isn't applicable.

> But in a genuinely distributed system where network partitions are a possibility, you cannot guarantee all three simultaneously during the partition.

> 🔥 This is an important nuance.

Don't memorize: *"CAP says you can only ever have two of the three."* That's an oversimplification.

A better exam statement is:

> "During a network partition, a distributed system must trade off consistency and availability."

---

## 15. THE MOST IMPORTANT CAP PICTURE

> Memorize this:

```
                   CAP
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
     CONSISTENCY AVAILABILITY PARTITION
                              TOLERANCE
          │         │         │
          └─────────┼─────────┘
                    ↓
             NETWORK PARTITION
                    │
            ┌───────┴────────┐
            ↓                ↓
           CP               AP
            │                │
     Consistency        Availability
     prioritized        prioritized
     during partition   during partition
```

---

## 16. Let's Make CP Feel Real

Imagine a banking-like operation. Account balance = ₹10,000. Now someone withdraws ₹8,000.

> You don't want another server to simultaneously tell someone "Balance = ₹10,000" if that would violate the system's required consistency.

So during a network problem, the system may prefer: *"Wait / reject / don't serve this operation"* rather than risk inconsistent data.

```
Partition
   ↓
Protect consistency
   ↓
Potentially sacrifice availability
   ↓
CP
```

---

## 17. AP Feels Different

Imagine something like a social-media "like" counter. Suppose Post likes = 10,000. A user clicks Like. One server updates: 10,001. Another server temporarily still sees: 10,000.

> During a network partition, the system may prioritize: "Keep serving users." The count may temporarily differ across nodes and converge later depending on the system's design.

```
Partition
   ↓
Keep responding
   ↓
Potential temporary inconsistency
   ↓
AP
```

---

## 18. ⚠️ This Does NOT Mean AP Systems Are "Bad"

> Absolutely not. This is an application requirement decision.

For some applications: **Availability > immediate consistency** might be acceptable.

For others: **Consistency > continuous availability** might be more important.

> That's why CAP is about trade-offs. Your syllabus explicitly calls out "CAP Theorem and their trade-offs."

## 21. 🔥 CP vs AP

> This is exam gold.

| CP | AP |
|---|---|
| Consistency + Partition Tolerance | Availability + Partition Tolerance |
| Prioritizes consistent data during partition | Prioritizes continued responses during partition |
| Some requests may be rejected/delayed | System may return temporarily inconsistent/stale data depending on design |
| Useful when consistency is critical | Useful when availability is critical |

### The Easiest Memory Trick:

```
CP
C = Consistency
P = Partition tolerance

AP
A = Availability
P = Partition tolerance
```

> The P is common because in a distributed system, the network partition is the problem we're dealing with.

The trade-off is:

```
C  ←→  A
```

## 22. A Very Important Nuance About MongoDB

Since this is a MongoDB course, you might be tempted to write: *"MongoDB is AP."*

> ⚠️ Don't memorize that as a blanket statement.

Modern MongoDB has configurable deployment/consistency behavior and supports replica sets, read/write concerns, transactions, etc.

So for this course, the useful lesson is:

> "CAP helps us understand the consistency/availability trade-offs that arise in distributed database systems."

> We'll understand MongoDB's actual architecture and replication behavior later in Part 6. That way, when we eventually discuss MongoDB replica sets, you won't be blindly labeling MongoDB "AP" or "CP."

## 26. 🎯 Exam Answer — 2 Marks

**What is CAP theorem?**

> "CAP theorem states that during a network partition, a distributed database system cannot simultaneously guarantee both consistency and availability while also tolerating the partition. Therefore, it must trade off consistency and availability."

---

## 27. 🎯 Exam Answer — 5 Marks

**Explain CAP theorem.**

> A strong answer structure:

CAP stands for:

- **Consistency** — clients receive data satisfying the system's consistency guarantee.
- **Availability** — the system continues responding to requests.
- **Partition Tolerance** — the system continues operating despite network communication failures between nodes.

> The CAP theorem states that in a distributed system, when a network partition occurs, it is not possible to simultaneously guarantee both consistency and availability while tolerating that partition.

Therefore, systems commonly make a trade-off:

```
CP → Consistency + Partition Tolerance
AP → Availability + Partition Tolerance
```

> The appropriate choice depends on application requirements.

> 🔥 That's a very good 5-mark answer.

---

## 28. 🎤 Viva Round

**Q1. What does CAP stand for?**
Consistency, Availability, Partition Tolerance.

**Q2. What is consistency?**
It means the system provides data according to its specified consistency guarantee, avoiding unacceptable conflicting/stale views.

**Q3. What is availability?**
The system continues responding to requests.

**Q4. What is partition tolerance?**
The ability of a distributed system to continue operating despite a network partition between nodes.

**Q5. What is a network partition?**
A failure in communication that separates parts of a distributed system so that nodes cannot properly communicate with each other.

**Q6. What is CP?**
Consistency + Partition Tolerance.

**Q7. What is AP?**
Availability + Partition Tolerance.

**Q8. Does CAP mean a database can only ever have two properties?**
Not exactly. The important point is that during a network partition, a distributed system must trade off consistency and availability.

> 🔥 That's a much better answer than the common oversimplification.

# UNIT I — PART 5: NoSQL Data Models

> Your syllabus specifically names four: Key-Value database, Column-oriented database, Document database, Graph database.
>
> This part is very important, because until now we've repeatedly said: *"NoSQL isn't one database. It is a family of different data models."*
>
> Now we're finally going to see what those models actually look like.

---

## 1. First: What Does "Data Model" Mean?

Forget databases for one minute. Suppose I give you a bunch of information:

```
Rahul
21
CSE
Python
8.5
```

There are many ways to organize that information.

**Way 1**

```
101 → Rahul
102 → Priya
103 → Arjun
```

**Way 2**

```
Student {
    name: Rahul,
    age: 21,
    branch: CSE
}
```

**Way 3**

```
Rahul → CSE → Database
```

> They're all representing data. But they're organizing it differently. That organization approach is the basic idea of a **Data Model**.

### ⭐ Simple Definition

> A data model defines how data is structured, stored, represented, and related within a database system.

Think:

```
DATA
  ↓
How do we organize it?
  ↓
DATA MODEL
```

---

## 2. Why Does NoSQL Have Multiple Models?

> This is the beautiful part.

Different applications have different types of data.

**Application A** — Needs: `User ID → User information`

> A key-value model can be extremely natural.

**Application B** — Needs: huge analytical datasets, rows/columns grouped for distributed processing

> A column-oriented model can be useful.

**Application C** — Needs:

```
Product
 ├── name
 ├── price
 ├── specifications
 └── reviews
```

> A document model can be natural.

**Application D** — Needs:

```
Person → FRIEND → Person
Person → WORKS_AT → Company
Person → LIVES_IN → City
```

> A graph model becomes very natural.

So:

```
                 NoSQL
                   │
       "Different problems need
        different data models"
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
 Key-Value      Column      Document
                               │
                               ↓
                            MongoDB

                   Graph
```

> 🔥 That's why there isn't one universal NoSQL structure.

---

## 3. MODEL 1 — Key-Value Database

Let's start with the simplest possible model. Imagine a dictionary.

```
KEY → VALUE
```

```
101 → Rahul
102 → Priya
103 → Arjun
```

Here: `101 = key`, `Rahul = value`

---

## 4. Visualize Key-Value

Imagine a giant cupboard. Every drawer has a unique label:

```
        KEY-VALUE STORE

┌───────────┬──────────────────┐
│ Key       │ Value            │
├───────────┼──────────────────┤
│ user101   │ Rahul            │
│ user102   │ Priya            │
│ user103   │ Arjun            │
│ user104   │ Karthik          │
└───────────┴──────────────────┘
```

You know the key. You use it to find the value. Conceptually:

```
GET user101
      ↓
    Rahul
```

---

## 5. The Core Idea of Key-Value

Think: *"Give me a key, and I'll give you the corresponding value."*

```
KEY
 ↓
LOOKUP
 ↓
VALUE
```

> This makes key-value databases especially attractive for fast lookups by key.

---

## 6. Real-World Example — User Session

Suppose a website needs to remember a user's login session.

```
session_9283 → user_101
session_9284 → user_205
session_9285 → user_317
```

When the user sends `session_9283`, the system quickly retrieves `user_101`.

Another example: `user101 → shopping_cart_data`

Another: `product500 → product_information`

> The model is extremely straightforward.

---

## 7. What Can the Value Be?

> This is where it gets interesting.

The value doesn't necessarily have to be a simple string. Conceptually:

```
user101
   ↓
{
   name: "Rahul",
   age: 21,
   branch: "CSE"
}
```

So: `KEY → VALUE`, where the value can itself be a more complex object/data structure, depending on the database.

---

## 8. Strengths of Key-Value Databases

**⭐ Very simple model**

```
key → value
```

**⭐ Fast key-based access** — If you know the key, retrieval can be very efficient.

**⭐ Easy to scale for suitable workloads** — Key-value systems are commonly used in distributed architectures.

**⭐ Useful for caching/session-like workloads** — Typical examples include:

```
Caching
Sessions
User preferences
Fast lookups
```

---

## 9. Limitation of Key-Value Model

Suppose you have `user101 → Rahul` and ask: *"Give me all users whose age is greater than 20."*

> The key-value model isn't naturally centered around querying arbitrary fields inside the value.

Its strength is:

```
KNOWN KEY
   ↓
VALUE
```

not necessarily:

```
Complex relationships
        ↓
Arbitrary analytical queries
```

> So the data model should match the access pattern.

## 12. Traditional Row Thinking

Suppose we have:

| 101 | Rahul | CSE | 8.5 |
| 102 | Priya | ECE | 9.1 |
| 103 | Arjun | CSE | 8.2 |

Traditional row-oriented thinking is roughly:

```
Row 1
→ 101, Rahul, CSE, 8.5

Row 2
→ 102, Priya, ECE, 9.1

Row 3
→ 103, Arjun, CSE, 8.2
```

---

## 13. Column-Oriented Thinking

Now imagine organizing the data by columns:

```
ID
│
├── 101
├── 102
└── 103

Name
│
├── Rahul
├── Priya
└── Arjun

Branch
│
├── CSE
├── ECE
└── CSE

CGPA
│
├── 8.5
├── 9.1
└── 8.2
```

Conceptually:

```
COLUMN
   ↓
Values for that column
```

> The database is optimized around a column-oriented representation.

---

## 14. Why Would We Want This?

Imagine we have 10 million students and the question is: *"Calculate the average CGPA."*

We only need `CGPA`. We don't necessarily need name, address, phone, branch, email, etc.

> A column-oriented approach can be highly useful for workloads that operate on selected columns across very large datasets.

---

## 15. Column-Oriented Databases and Analytics

This gives us an important connection:

```
Huge dataset
      ↓
Need analytical operations
      ↓
Often access selected columns
      ↓
Column-oriented model can be useful
```

Typical use cases can include:

```
analytics
large-scale data processing
aggregation-heavy workloads
distributed data storage
```

---

## 16. A Famous Example

One well-known NoSQL column-family database is **Apache Cassandra**.

```
Cassandra
   ↓
Column-family / wide-column database
```

Another example often discussed in this family is **HBase**.

> For our syllabus, the important thing right now is recognizing the column-oriented / column-family model.

---

## 17. ⚠️ Important Terminology

You may see terms such as:

```
Column-oriented
Column-family
Wide-column
```

> These are related concepts, but database systems can implement them differently. So don't blindly assume every "column database" is identical.

For your Unit I foundation:

> "Column-oriented NoSQL systems organize data around columns/column families and are particularly suited to certain large-scale distributed and analytical workloads."

> That's the useful level for now.

### 🧠 Column Model Memory Trick

Think:

```
Rows → records

Columns → attributes grouped together
```

So:

```
KEY-VALUE
→ lookup by key

COLUMN
→ work efficiently with column-oriented data
```

---

## 18. MODEL 3 — Document Database

> 🔥 NOW WE COME HOME.

This is the model you already met in Part 3. Because: **MongoDB = Document-oriented NoSQL database.**

---

## 19. What Is a Document Model?

Instead of splitting information into rigid rows and columns, we can represent a record as a document.

```json
{
    "name": "Rahul",
    "age": 21,
    "branch": "CSE",
    "cgpa": 8.5
}
```

Think:

```
DOCUMENT
   │
   ├── name → Rahul
   ├── age → 21
   ├── branch → CSE
   └── cgpa → 8.5
```

---

## 20. Documents Can Be Rich

A document can contain:

```json
{
    "name": "Rahul",
    "age": 21,

    "skills": [
        "Python",
        "Java",
        "MongoDB"
    ],

    "address": {
        "city": "Hyderabad",
        "country": "India"
    }
}
```

Now we have:

```
Document
│
├── Simple fields
│
├── Array
│
└── Nested document
```

> 🔥 This is one of the major strengths of document-oriented modeling.

---

## 21. Why Is Document Model Useful?

Think about an e-commerce product.

A laptop might have: `name`, `price`, `brand`, `RAM`, `storage`, `processor`

A shirt might have: `name`, `price`, `brand`, `size`, `material`, `color`

A phone might have: `name`, `price`, `brand`, `camera`, `battery`, `screen`

> Different products can have different attributes. A document model can represent these varying structures naturally.

```
Product
│
├── Laptop document
│
├── Shirt document
│
└── Phone document
```

---

## 22. Document Database = MongoDB

Now lock this into your brain:

```
NoSQL
  │
  ↓
Document Model
  │
  ↓
MongoDB
```

So if an exam asks *"Which NoSQL model does MongoDB use?"* — answer immediately: **Document-oriented model.**

---

## 23. MODEL 4 — Graph Database

Now we're going to think completely differently.

Imagine: `Rahul` has `friend → Priya`. Priya: `works_at → ABC Company`. Rahul: `lives_in → Hyderabad`.

Now visualize:

```
Rahul
  │
  │ FRIEND
  ↓
Priya
  │
  │ WORKS_AT
  ↓
ABC Company

Rahul
  │
  │ LIVES_IN
  ↓
Hyderabad
```

> This is a graph.

---

## 24. What Is a Graph Database?

A graph database represents data using:

**Nodes** — Represent entities.

```
Person
Company
City
Product
```

**Edges** — Represent relationships.

```
FRIEND
WORKS_AT
LIVES_IN
BOUGHT
FOLLOWS
```

So:

```
NODE ──RELATIONSHIP──> NODE
```

---

## 25. Real-World Example — Social Network

Imagine:

```
        Priya
       /     \
   FRIEND   FRIEND
     /         \
  Rahul       Arjun
    |
  FRIEND
    |
  Karthik
```

> The important information isn't just "Who is Rahul?" It's "Who is Rahul connected to?" and "Who are Rahul's friends' friends?"
>
> That's where graph databases become very natural.

---

## 26. Graph Database Use Cases

> Graph databases are particularly useful when relationships are central to the problem.

**Examples:**

**Social networks** — `Person → follows → Person`

**Recommendation systems** — `User → bought → Product`

**Fraud detection** — `Account → transfers_to → Account`

**Knowledge graphs** — `Person → works_at → Company`, `Company → located_in → City`

> The relationships themselves become first-class data.

---

## 27. Famous Graph Database

A well-known example is **Neo4j**.

```
Neo4j
  ↓
Graph Database
  ↓
Nodes + Relationships
```

---

## 28. 🔥 Now Compare All Four

> This is where everything becomes crystal clear.

| NoSQL Model | Basic Idea | Think Of | Typical Strength |
|---|---|---|---|
| Key-Value | Key → Value | Dictionary | Fast key-based lookup |
| Column-Oriented | Data organized around columns/column families | Large analytical dataset | Large-scale distributed/analytical workloads |
| Document | Documents containing fields/values | JSON-like record | Flexible application data |
| Graph | Nodes + relationships | Network | Relationship-heavy data |

---

## 29. The Most Important Visual

> I want you to see the four models simultaneously.

```
                         NoSQL
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ↓                  ↓                  ↓
   KEY-VALUE           COLUMN              DOCUMENT
        │                  │                  │
        ↓                  ↓                  ↓
   key → value       column-oriented     document
                                            │
                                            ↓
                                         MongoDB


                           GRAPH
                             │
                             ↓
                     nodes + relationships
```

---

## 30. Same Student — Four Different Models

> This is a fantastic way to understand data models.

Suppose: `Rahul, 21, CSE, 8.5`

**Key-Value**

```
student101 → Rahul's data
```

**Column-oriented**

```
Name   → Rahul
Age    → 21
Branch → CSE
CGPA   → 8.5
```

with data organized around column structures.

**Document**

```json
{
    "name": "Rahul",
    "age": 21,
    "branch": "CSE",
    "cgpa": 8.5
}
```

**Graph**

```
Rahul ──STUDIES──> CSE
  │
  └──HAS_CGPA──> 8.5
```

> Same underlying information. Different model. 🔥 This is the essence of NoSQL data modeling.

---

## 31. How Do I Choose the Model?

> This is where we move from memorization to engineering thinking.

Ask: *"What does my application naturally care about?"*

**If you need:** `KNOWN KEY → VALUE` — Think: **Key-Value**

**If you have:** Large-scale data + Column-oriented analytical access — Think: **Column-oriented / Column-family**

**If you have:** Flexible records + Nested structures + Arrays + Application-oriented data — Think: **Document**

**If you have:** Complex relationships + Connections are central — Think: **Graph**

---

## 32. 🔥 Decision Tree

```
                  WHAT IS MY DATA LIKE?
                           │
            ┌──────────────┼──────────────┐
            ↓              ↓              ↓
        Key lookup?    Flexible records? Relationships?
            │              │              │
            ↓              ↓              ↓
       KEY-VALUE       DOCUMENT         GRAPH
                           │
                           ↓
                        MongoDB
```

And if the workload is heavily based around large-scale column/column-family access:

```
Large distributed / analytical workload
                 ↓
        COLUMN-ORIENTED
```

> These are examples of systems associated with different NoSQL models.

## 35. 🎯 Exam Definitions

**Key-Value Database**

> "A key-value database stores data as pairs consisting of a unique key and its associated value."

**Column-Oriented Database**

> "A column-oriented or column-family database organizes data around columns or column families and is commonly used for large-scale distributed workloads."

**Document Database**

> "A document database stores data as documents containing field-value pairs, often supporting nested structures and flexible schemas."

**Graph Database**

> "A graph database represents entities as nodes and relationships between entities as edges."
