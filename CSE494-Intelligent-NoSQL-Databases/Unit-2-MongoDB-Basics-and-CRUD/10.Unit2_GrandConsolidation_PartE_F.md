### 1. What is a MongoDB database?

**Strong answer:**

> A MongoDB database is a logical container that organizes collections of related documents. A database contains one or more collections, and each collection contains BSON documents.

The hierarchy is:

```
MongoDB deployment
      ↓
Database
      ↓
Collection
      ↓
Document
      ↓
Fields
```

> MongoDB documentation describes databases and collections as organizational structures for documents.

🔥 **Trap**

Don't say:

> "A MongoDB database is a table."

Wrong.

---

### 2. What is a collection?

> A collection is a group of MongoDB documents.

It is roughly analogous to a table in SQL, but it is not identical because MongoDB documents can have flexible structures and nested data.

Example:

```
collegeDB
   ↓
students
   ↓
documents
```

**Killer addition:**

> A collection can contain documents with different sets of fields because MongoDB has a flexible document model.

---

### 3. What is a MongoDB document?

> A document is MongoDB's basic unit of data storage.

Example:

```json
{
    "name": "Rahul",
    "age": 21,
    "branch": "CSE",
    "cgpa": 8.7
}
```

Documents are stored using BSON.

They can contain:

```
fields
arrays
embedded documents
nested structures
```

> MongoDB explicitly identifies documents as its basic unit of data storage.

---

### 4. What is BSON?

BSON stands for:

```
Binary JSON
```

It is the binary serialization format MongoDB uses for documents.

Its major advantage is that it supports richer native data types than standard JSON, including types such as:

```
ObjectId
Date
Decimal128
Binary
Int32
Int64
Timestamp
```

> MongoDB's BSON documentation lists these richer BSON types and their semantics.

**Killer line:**

> JSON-like syntax is convenient for humans, but BSON is the underlying document representation used by MongoDB.

---

### 5. What is `_id`?

> `_id` is the unique identifier of a document in a standard MongoDB collection.

If the application does not provide `_id`, the MongoDB driver automatically generates one, commonly an `ObjectId`.

MongoDB also creates a unique index on `_id`.

Think:

```
_id
 ↓
identity of document
```

---

### 6. What is ObjectId?

> `ObjectId` is a BSON type commonly used for MongoDB document identifiers.

It is:

```
12 bytes
```

and contains components including:

```
4-byte timestamp
5-byte random value
3-byte counter
```

> ObjectIds are approximately ordered by creation time, but not perfectly chronological. MongoDB explicitly warns that they are not guaranteed to be monotonic.

🔥 **Viva trap**

Don't say:

> "ObjectId is exactly the creation timestamp."

❌ Wrong.

It contains timestamp information, but it is not simply a timestamp.

---

### 7. What is CRUD?

CRUD means:

```
C → Create
R → Read
U → Update
D → Delete
```

MongoDB's core CRUD operations include methods such as:

```
insertOne()
insertMany()

find()
findOne()

updateOne()
updateMany()

deleteOne()
deleteMany()
```

> MongoDB defines CRUD as operations for creating, reading, updating and deleting documents.

---

### 8. Difference between `insertOne()` and `insertMany()`?

`insertOne()` inserts one document.

```js
db.students.insertOne({
    name: "Rahul"
})
```

`insertMany()` inserts multiple documents.

```js
db.students.insertMany([
    { name: "Rahul" },
    { name: "Priya" }
])
```

So:

```
insertOne()
     ↓
one document

insertMany()
     ↓
multiple documents
```

---

### 9. What happens if `_id` is not provided during insertion?

> MongoDB generates an `_id` automatically, commonly using an `ObjectId`.

Example:

```js
db.students.insertOne({
    name: "Rahul"
})
```

becomes conceptually:

```json
{
    "_id": "ObjectId(...)",
    "name": "Rahul"
}
```

The `_id` must be unique within the collection.

---

### 10. Difference between `find()` and `findOne()`?

**`find()`**

Returns a cursor for documents matching the query.

```js
db.students.find({
    branch: "CSE"
})
```

It can return multiple documents.

**`findOne()`**

Returns one matching document.

```js
db.students.findOne({
    branch: "CSE"
})
```

Mental model:

```
find()
   ↓
potentially many

findOne()
   ↓
one
```

---

### 11. What is a query filter?

> A filter specifies which documents should match.

Example:

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8 }
})
```

The filter says:

```
branch = CSE
AND
cgpa >= 8
```

Think:

> Filter = WHICH documents?

---

### 12. What is projection?

> Projection controls which fields are returned.

Example:

```js
db.students.find(
    { branch: "CSE" },
    {
        name: 1,
        cgpa: 1,
        _id: 0
    }
)
```

Here:

```
First object
 ↓
filter

Second object
 ↓
projection
```

This distinction is extremely important.

---

### 13. What is the difference between `$gt` and `$gte`?

```
$gt
 ↓
greater than

$gte
 ↓
greater than or equal to
```

Example:

```js
{
    cgpa: { $gt: 8 }
}
```

means:

```
CGPA > 8
```

while:

```js
{
    cgpa: { $gte: 8 }
}
```

means:

```
CGPA >= 8
```

Likewise:

```
$lt  → less than
$lte → less than or equal
```

---

### 14. How do you perform an AND condition?

MongoDB can express simple AND conditions by placing multiple fields in the same filter.

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8 }
})
```

This means:

```
branch = CSE
AND
cgpa >= 8
```

> MongoDB also supports explicit logical operators such as `$and`.

---

### 15. How do you perform an OR condition?

Use `$or`.

```js
db.students.find({
    $or: [
        { branch: "CSE" },
        { branch: "ECE" }
    ]
})
```

Conceptually:

```
condition A
   OR
condition B
```

---

### 16. Difference between `$set` and `$inc`?

**`$set`**

Assigns a value.

```js
{
    $set: {
        cgpa: 9.0
    }
}
```

Meaning:

```
cgpa → 9.0
```

**`$inc`**

Changes a numeric value by a specified amount.

```js
{
    $inc: {
        views: 1
    }
}
```

Meaning:

```
views → views + 1
```

So:

```
$set → assign
$inc → increment/decrement
```

---

### 17. What are `$push` and `$pull`?

They are commonly used for arrays.

**`$push`**

Adds an element.

```js
{
    $push: {
        skills: "MongoDB"
    }
}
```

**`$pull`**

Removes matching array elements.

```js
{
    $pull: {
        skills: "MongoDB"
    }
}
```

Mental model:

```
$push
 ↓
ADD

$pull
 ↓
REMOVE
```

---

### 18. Difference between `updateOne()` and `updateMany()`?

`updateOne()` updates at most one matching document.

```js
db.students.updateOne(
    { branch: "CSE" },
    { $set: { department: "CS" } }
)
```

`updateMany()` updates all matching documents.

```js
db.students.updateMany(
    { branch: "CSE" },
    { $set: { department: "CS" } }
)
```

> MongoDB documents these methods separately according to whether one or multiple matching documents are updated.

---

### 19. Difference between `deleteOne()` and `deleteMany()`?

**`deleteOne()`**

Deletes one matching document.

```js
db.students.deleteOne({
    name: "Rahul"
})
```

**`deleteMany()`**

Deletes all documents matching the filter.

```js
db.students.deleteMany({
    branch: "CSE"
})
```

⚠️ **Killer trap:**

```js
db.students.deleteMany({})
```

means:

> Delete all documents in the collection.

So always inspect the filter first.

---

### 20. What is upsert?

`upsert` means:

> Update if a matching document exists; otherwise insert a new document.

Conceptually:

```
Find match
   │
 ┌─┴─┐
YES  NO
 │    │
 ↓    ↓
UPDATE INSERT
```

For example:

```js
db.students.updateOne(
    { studentId: "STU001" },
    { $set: { name: "Rahul" } },
    { upsert: true }
)
```

If `STU001` doesn't exist, MongoDB can insert a document based on the operation.

### 21. What is data modeling in MongoDB?

Data modeling is:

> The organization of data and the relationships between related entities in the database.

> MongoDB's flexible model allows documents in one collection to have different fields or even different types for a field, although applications generally still maintain an intentional common structure.

The key principle:

> Data that is accessed together should generally be stored together when that fits the workload.

---

### 22. What is embedding?

> Embedding means storing related information inside the same MongoDB document.

Example:

```json
{
    "name": "Rahul",

    "address": {
        "city": "Jalandhar",
        "state": "Punjab"
    }
}
```

Here:

```
student
   └── address
```

is embedded.

Good candidates often include related, bounded data that is commonly retrieved with the parent.

---

### 23. What is referencing?

> Referencing means storing related data separately and linking documents using identifiers.

Example:

```json
{
    "studentId": "STU001",
    "courseId": "CSE401"
}
```

The related student and course documents exist separately.

> References are useful for situations such as high-cardinality relationships, complex many-to-many relationships, or independently managed data. MongoDB's modeling documentation explicitly discusses these considerations.

---

### 24. Embedding vs Referencing — the killer viva

If examiner asks:

> "Which is better, embedding or referencing?"

Never answer:

> "Embedding is better."

or:

> "Referencing is better."

Both are bad answers.

Say:

> "Neither is universally better. The choice depends on access patterns, relationship cardinality, document growth, update frequency, duplication, and whether the related data is independently managed. If related data is usually accessed together and is bounded, embedding can be advantageous. For high-cardinality, independently managed, or complex relationships, referencing may be more appropriate."

🔥 That's a viva-quality answer.

---

### 25. How do you model 1:1, 1:M and M:M relationships?

**1:1**

Example:

```
Student → Passport
```

Can often be embedded if closely associated.

**1:M**

Example:

```
User → Posts
```

Could be embedded if the number is bounded and posts are accessed with the user, or referenced if the child side grows substantially.

**M:M**

Example:

```
Students ↔ Courses
```

Often needs references or an intermediate relationship collection such as:

```
enrollments
```

> MongoDB explicitly supports modeling one-to-one, one-to-many, and many-to-many relationships through embedding or referencing.

### 26. What is an index?

> An index is a special data structure that helps MongoDB execute queries more efficiently.

Without an appropriate index, MongoDB may need to scan every document in a collection.

> With an appropriate index, MongoDB can reduce the amount of data it needs to scan. MongoDB's standard indexes use a B-tree structure.

Analogy:

```
Book
 ↓
Index
 ↓
Find page quickly
```

Database:

```
Collection
 ↓
Index
 ↓
Find relevant data
```

---

### 27. Why shouldn't we create indexes on every field?

Because indexes aren't free.

They:

```
consume storage
+
require maintenance
+
can slow writes
```

Every insert/update may need index maintenance.

> MongoDB explicitly warns that excessive indexes can degrade performance, especially in write-heavy workloads.

So:

> Create indexes based on actual/common query patterns.

---

### 28. What is a compound index?

> A compound index contains multiple fields.

Example:

```js
db.students.createIndex({
    branch: 1,
    cgpa: 1
})
```

This creates an index over:

```
branch
+
cgpa
```

Field order matters.

MongoDB can use the prefixes of compound indexes.

For example:

```js
{
    branch: 1,
    cgpa: 1,
    age: 1
}
```

has index prefixes beginning with:

```
branch
```

and:

```
branch + cgpa
```

but not simply:

```
cgpa
```

as the leading prefix.

---

### 29. What is `explain()`?

> `explain()` helps us understand how MongoDB executes a query.

Example:

```js
db.students.find({
    branch: "CSE"
}).explain("executionStats")
```

It can provide information such as:

```
winning plan
nReturned
totalDocsExamined
totalKeysExamined
executionTimeMillis
```

> MongoDB's explain output is specifically intended to help analyze query plans and execution statistics.

### 30. What are COLLSCAN, IXSCAN, and a covered query?

🔥 This is the final boss question.

**COLLSCAN**

Means:

> Collection scan.

MongoDB scans documents in the collection to find matches.

**IXSCAN**

Means:

> Index scan.

MongoDB scans index keys to identify relevant records.

**Covered query**

> A covered query is one where the index contains all the fields needed to answer the query and return its projected results, so MongoDB can satisfy the query from the index without examining collection documents.

Conceptually:

**NORMAL:**

```
INDEX
 ↓
FETCH DOCUMENT
 ↓
RESULT
```

**Covered:**

```
INDEX
 ↓
RESULT
```

> MongoDB explicitly defines covered queries in terms of the index containing the fields needed by the query and being able to return the result without scanning the collection.

## ⚔️ BONUS KILLER VIVA — "WHY?"

These are the questions that separate memorization from understanding.

### Q31. Why does MongoDB use BSON instead of simply JSON?

**Answer:**

> Because BSON provides a binary representation and supports additional data types that JSON doesn't natively represent, such as `ObjectId`, `Date`, `Decimal128`, binary data, and specific integer types.

### Q32. Why is MongoDB called schema-flexible?

> Because documents within a collection do not have to contain exactly the same fields, and field types can differ between documents.

But:

> Schema-flexible does not mean schema design is unnecessary.

> MongoDB's documentation explicitly describes this flexible model while still recommending intentional modeling and, where needed, validation.

### Q33. Why is embedding sometimes faster?

> Because related information can be retrieved from the same document rather than requiring separate document lookups.

> MongoDB's modeling principle is to store data together when it is accessed together, where appropriate.

### Q34. Why can referencing be better?

> Because embedding everything can cause:

```
huge documents
+
duplication
+
unbounded growth
+
difficult updates
```

> References can separate independently managed or high-cardinality data.

### Q35. Why can indexes make writes slower?

> Because when a document is inserted or updated, MongoDB may also need to maintain the relevant indexes.

So:

```
More indexes
   ↓
Potentially better reads
   +
More write/index maintenance
```

> MongoDB explicitly notes this trade-off.

## 🧠 THE 10 MOST DANGEROUS UNIT II TRAPS

Mate, memorize these traps more than the definitions.

### 🚨 TRAP 1

> "NoSQL means no SQL."

❌ Wrong.

NoSQL is commonly interpreted as:

> Not Only SQL

### 🚨 TRAP 2

> "MongoDB stores JSON."

Too simplistic.

Better:

> MongoDB works with JSON-like documents at the interface level and stores documents using BSON.

### 🚨 TRAP 3

> "MongoDB has no schema."

❌ Wrong.

Better:

> MongoDB has a flexible schema model, but applications should still intentionally design document structures and can use validation where needed.

### 🚨 TRAP 4

> "Embedding is always better."

❌ Wrong.

Choice depends on workload and relationships.

### 🚨 TRAP 5

> "Referencing is MongoDB's version of SQL JOIN."

Not exactly.

Referencing is a data modeling technique.

> MongoDB can use operations such as `$lookup` when cross-collection querying is required, but referencing itself isn't a direct equivalent of a SQL JOIN.

### 🚨 TRAP 6

> "More indexes = faster database."

❌ Absolutely not.

Indexes improve suitable reads but add storage and write-maintenance costs.

### 🚨 TRAP 7

> "`$set` replaces the entire document."

❌ No.

It updates the specified field(s).

But if you `$set` an entire embedded object, that field's previous object value can be replaced.

### 🚨 TRAP 8

> "`deleteMany({})` deletes the collection."

❌ No.

It deletes all matching documents.

The collection itself remains.

To remove the collection:

```js
db.students.drop()
```

### 🚨 TRAP 9

> "ObjectId is the exact creation time."

❌ No.

It contains timestamp information and is approximately ordered by creation time, but isn't perfectly chronological.

### 🚨 TRAP 10

> "COLLSCAN automatically means the query is bad."

Not necessarily.

On a tiny collection, a collection scan may be perfectly reasonable.

The real question is:

> Is the execution plan appropriate for the workload and data size?

That's why we analyze `explain()` rather than judging from one word alone.

## 🏆 WHAT TO WRITE IN AN EXAM VS WHAT NOT TO WRITE

This is the final sharpening.

### Question: "What is an index?"

❌ **Weak**

> Index makes database fast.

✅ **Strong**

> An index is a special data structure that improves the efficiency of query execution by allowing MongoDB to locate relevant data without scanning the entire collection when an appropriate index exists. However, indexes consume storage and add write-maintenance overhead.

### Question: "What is data modeling?"

❌ **Weak**

> Data modeling means creating collections.

✅ **Strong**

> Data modeling is the organization of data and relationships between related entities. In MongoDB, the design should be based on application access patterns, including decisions about embedding versus referencing and appropriate indexes.

### Question: "Embedding vs referencing?"

❌ **Weak**

> Embedding is faster and referencing is slower.

✅ **Strong**

> Embedding stores related data inside the same document and is useful when related data is commonly accessed together and has manageable growth. Referencing stores related data separately and is useful for high-cardinality, independently managed, or complex relationships. The choice depends on workload and access patterns.

## ⚔️ 7. THE MOST IMPORTANT DIFFERENCES

### `find()` vs `findOne()`

```
find()
→ multiple matching documents / cursor

findOne()
→ one matching document
```

### `insertOne()` vs `insertMany()`

```
insertOne()
→ one document

insertMany()
→ multiple documents
```

### `updateOne()` vs `updateMany()`

```
updateOne()
→ at most one matching document

updateMany()
→ all matching documents
```

### `deleteOne()` vs `deleteMany()`

```
deleteOne()
→ one matching document

deleteMany()
→ all matching documents
```

### `drop()` vs `deleteMany({})`

This one is very important.

```js
db.students.deleteMany({})
```

means:

> Delete all documents.

But:

```js
db.students.drop()
```

means:

> Remove the entire collection.

So:

```
deleteMany({})
        ↓
documents gone
collection remains

drop()
        ↓
collection gone
```

And the three that students commonly confuse:

> Common identifier type containing timestamp-related information.

> MongoDB's BSON reference documents these types and their distinctions.

## 🥊 11. EMBEDDING VS REFERENCING — FINAL DECISION TABLE

| Question                              | Embedding                | Referencing                    |
|------------------------------------------|-----------------------------|-----------------------------------|
| Related data accessed together?           | ✅ Strong candidate          | Possible                          |
| Small bounded data?                        | ✅                           | Possible                          |
| High-cardinality relationship?             | Usually less suitable       | ✅                                 |
| Unbounded growth?                           | Risky                        | ✅ Better candidate                |
| Data independently managed?                  | Usually less suitable       | ✅                                 |
| Complex M:M?                                  | Usually difficult           | ✅                                 |
| Avoid extra reads?                             | ✅                           | ❌ potentially                     |
| Avoid duplication?                              | Sometimes harder            | ✅                                 |
| Single-document atomicity useful?                | ✅                           | May require multi-document work   |

> MongoDB's guidance emphasizes relationship type, cardinality, growth, duplication, and access patterns rather than prescribing one universal strategy.

## 13. SINGLE VS COMPOUND INDEX

### Single

```js

    email: 1
})
```

For queries primarily involving:

```
email
```

### Compound

```js
db.students.createIndex({
    branch: 1,
    cgpa: 1
})
```

For query patterns involving multiple fields.

Remember:

> Field order matters.

Compound indexes support queries involving their index prefixes.

## 🧠 14. THE INDEX TRADE-OFF

Never write:

> "Indexes always improve database performance."

Instead:

```
INDEX
 ↓
Potentially faster suitable reads
 +
Storage cost
 +
Write/update maintenance
```

> MongoDB explicitly notes that indexes improve query performance but add cost to write operations because indexes must be maintained.

## 🔥 15. COLLSCAN VS IXSCAN

This needs to be instant.

### COLLSCAN

```
Collection
    ↓
scan documents
```

### IXSCAN

```
Index
  ↓
scan index keys
  ↓
relevant documents
```

> MongoDB's explain output identifies `COLLSCAN` when the query planner selects a collection scan and `IXSCAN` when it selects an index scan.

## 16. FETCH

You may see:

```
IXSCAN
   ↓
FETCH
```

Think:

```
IXSCAN
 ↓
find relevant index entries

FETCH
 ↓
retrieve the actual documents
```

This is normal for many indexed queries.

## 🔥 17. COVERED QUERY

The ideal mental picture:

**Normal**

```
INDEX
 ↓
FETCH
 ↓
DOCUMENT
 ↓
RESULT
```

**Covered**

```
INDEX
 ↓
RESULT
```

> MongoDB says that when an index covers a query, the query can be answered using only index keys and does not need to examine collection documents; explain output shows an `IXSCAN` not descending from a `FETCH`.

## ⚔️ 21. WHAT TO WRITE VS WHAT NOT TO WRITE

### "What is MongoDB?"

❌ **Don't write:**

> MongoDB is a database where we store JSON.

✅ **Write:**

> MongoDB is a document-oriented NoSQL database that stores data as BSON documents organized within collections.

### "What is BSON?"

❌ **Don't write:**

> BSON is JSON.

✅ **Write:**

> BSON stands for Binary JSON and is MongoDB's binary serialization format for documents, supporting additional data types such as ObjectId, Date and Decimal128.

### "What is embedding?"

❌ **Don't write:**

> Embedding is putting tables inside tables.

✅ **Write:**

> Embedding stores related data within the same MongoDB document, which can be beneficial when the related data is commonly accessed together and has manageable growth.

### "What is referencing?"

❌ **Don't write:**

> Referencing is like a foreign key exactly.

✅ **Write:**

> Referencing stores related entities separately and links them using identifiers, making it suitable for independently managed, high-cardinality, or complex relationships.

### "What is an index?"

❌ **Don't write:**

> Index makes query fast.

✅ **Write:**

> An index is a data structure that can improve query execution by allowing MongoDB to locate relevant data more efficiently, at the cost of additional storage and write-maintenance overhead.

## 🧠 22. UNIT II — 15 DEFINITIONS TO MEMORIZE

These are your exam-ready definitions.

**1. Database**

> A logical container that organizes related MongoDB collections.

**2. Collection**

> A group of MongoDB documents, conceptually similar to a relational table but with a flexible document model.

**3. Document**

> MongoDB's basic unit of data storage, represented using BSON.

**4. BSON**

> Binary JSON, MongoDB's binary serialization format for documents.

**5. CRUD**

> Create, Read, Update and Delete operations on data.

**6. Projection**

> Selection of which fields should be returned from matching documents.

**7. Data Modeling**

> The organization of data and relationships according to application requirements and access patterns.

**8. Embedding**

> Storing related data inside the same document.

**9. Referencing**

> Storing related data separately and connecting it through references.

**10. Index**

> A data structure that improves efficient query execution for supported query patterns.

**11. Single-field Index**

> An index built on one field.

**12. Compound Index**

> An index built on multiple fields in a specified order.

**13. COLLSCAN**

> An execution-plan stage representing a collection scan.

**14. IXSCAN**

> An execution-plan stage representing an index scan.

**15. Covered Query**

> A query whose conditions and returned fields can be satisfied entirely using an index without examining collection documents.
