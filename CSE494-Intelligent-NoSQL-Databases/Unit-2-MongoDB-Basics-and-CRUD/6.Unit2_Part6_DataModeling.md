# UNIT II — PART 6: DATA MODELING IN MONGODB

## 1. 🧠 First — What Exactly Is Data Modeling?

Very simple definition:

> Data modeling is the process of deciding how data is organized, stored, and related inside a database.

> MongoDB's documentation similarly defines data modeling around the organization of data and the links between related entities.

Imagine we're building a college application.

We have:

```
Student
Course
Department
Address
Professor
```

The question isn't merely:

> "What data do I have?"

The real question is:

> "How should I arrange this data inside MongoDB documents and collections so my application can efficiently use it?"

That's data modeling.

---

## 2. 🧩 SQL Thinking vs MongoDB Thinking

This is where your Part 2 / Unit I knowledge becomes useful.

In a relational database, we'd naturally think:

```
Students table
Courses table
Departments table
Addresses table
```

and connect them using:

```
Primary Key
Foreign Key
JOIN
```

MongoDB gives us a different design mindset.

Instead of automatically separating everything, we ask:

> What data is usually accessed together?

> MongoDB's current modeling guidance emphasizes structuring data around the application's data access patterns—data that is accessed together is often a candidate for being stored together.

That sentence is **VERY** important.

---

## 3. 🔥 The Golden MongoDB Modeling Question

Before designing a collection, ask:

> "When my application needs X, what information does it usually need at the same time?"

Suppose an e-commerce application displays:

```
Product
 ├── name
 ├── price
 ├── brand
 └── recent reviews
```

If the product page almost always needs the recent reviews too, keeping those frequently accessed reviews with the product can make sense.

Instead of forcing the application to repeatedly fetch related information from another collection, MongoDB can model the data together.

So:

```
Application query
       ↓
What data is needed together?
       ↓
Design document around that access pattern
```

---

## 4. 🧠 MongoDB's Flexible Schema

You've already learned:

> MongoDB is schema-flexible.

That means documents in a collection aren't required to have exactly the same fields, and even a field's data type can differ between documents.

Example:

```json
{
    "name": "Rahul",
    "branch": "CSE",
    "cgpa": 8.5
}
```

Another:

```json
{
    "name": "Priya",
    "branch": "ECE",
    "cgpa": 9.1,
    "scholarship": true
}
```

Both can exist in:

```
students
```

But **STOP**.

This doesn't mean:

> "Throw random fields everywhere."

😂 Absolutely not.

Flexible schema means:

> The database gives you flexibility; you still have to design intelligently.

> MongoDB itself recommends planning the data model before production-scale use.

---

## 5. 🧠 The Three-Step Modeling Mindset

A very useful MongoDB design process is:

```
1. Identify application workload
          ↓
2. Map relationships
          ↓
3. Choose appropriate design pattern
```

> MongoDB's documentation describes essentially this schema-design process: identify workload, map relationships, then apply suitable design patterns.

Let's unpack it.

---

## 6. 🧩 Step 1 — Identify Workload

Suppose we're designing:

```
ONLINE SHOP
```

We need to know what users actually do.

Maybe users frequently:

```
View product
View product reviews
Search products
Place order
View order
Update address
```

Those are our **workloads / access patterns**.

Don't design the database first and then wonder how the application will use it.

Instead:

```
Application requirements
        ↓
Queries + writes
        ↓
Data model
```

This is one of the biggest differences in MongoDB schema design compared with the traditional mindset of simply normalizing everything first.

---

## 7. 🧩 Step 2 — Identify Relationships

Now ask:

> How are these entities related?

For example:

```
Student → Address
```

Maybe:

```
One student
     ↓
One address
```

That's:

```
1 : 1
```

Another:

```
Student → Courses
```

One student may take multiple courses:

```
One student
     ↓
Many courses
```

That's:

```
1 : M
```

And:

```
Students ↔ Courses
```

One student takes many courses, and one course has many students.

That's:

```
M : M
```

> MongoDB supports modeling one-to-one, one-to-many, and many-to-many relationships using either embedded data or references.

---

## 8. 🔥 Step 3 — Decide: EMBED or REFERENCE?

🔥 This is the **heart** of MongoDB data modeling.

When two pieces of data are related, you generally have two major choices:

```
RELATED DATA
     │
     ├── EMBED
     │
     └── REFERENCE
```

> MongoDB explicitly supports both approaches.

And now we're going to understand them from absolute zero.

---

## 9. 🧠 EMBEDDING

Embedding means:

> Store related data inside the same MongoDB document.

Example:

```json
{
    "_id": 101,
    "name": "Rahul",

    "address": {
        "city": "Amritsar",
        "state": "Punjab",
        "pincode": "143001"
    }
}
```

Here:

```
Student
  │
  ├── name
  │
  └── address
        ├── city
        ├── state
        └── pincode
```

The address is **embedded** inside the student document.

> MongoDB describes embedded documents as related data stored within the same document structure.

---

## 10. 🔥 Why Is Embedding Powerful?

Imagine the application wants:

> "Show me Rahul's profile and address."

With embedding:

```
ONE document
      ↓
Student + Address
      ↓
ONE read
```

Conceptually:

```json
{
    "name": "Rahul",
    "address": {
        "city": "Amritsar",
        "state": "Punjab"
    }
}
```

Everything is already together.

> MongoDB notes that embedding can let applications retrieve related data in a single database operation and can support atomic updates to that single document.

---

## 11. 🎒 Think of Embedding Like a Backpack

This analogy will help.

Imagine Rahul carries:

```
Rahul's backpack
 ├── Student ID
 ├── Notebook
 ├── Calculator
 └── Water bottle
```

Everything Rahul frequently needs is inside Rahul's backpack.

Similarly:

```
Student document
 ├── name
 ├── branch
 ├── address
 └── contact
```

The related information travels together.

That's embedding.

---

## 12. 🧩 Another Embedding Example — Employee

Suppose:

```json
{
    "_id": 501,
    "name": "Arjun",
    "department": "Engineering",

    "contact": {
        "email": "arjun@example.com",
        "phone": "9876543210"
    }
}
```

We could have:

```
employees
    ↓
one document
    ↓
employee information
    +
contact information
```

If the application normally displays them together, embedding can be a natural design.

---

## 13. 🧠 One-to-One Relationship With Embedding

Let's formalize it.

Suppose:

```
User
  ↓
exactly one
  ↓
Address
```

That's:

```
1 : 1
```

We can model:

```json
{
    "_id": 101,
    "name": "Rahul",

    "address": {
        "street": "Main Road",
        "city": "Amritsar",
        "state": "Punjab"
    }
}
```

> MongoDB's own one-to-one example uses this basic pattern: a parent document containing its related address document.

---

## 14. 🧩 One-to-Many With Embedding

Now:

```
Student
   ↓
many
   ↓
Phone numbers
```

We could model:

```json
{
    "_id": 101,
    "name": "Rahul",

    "phoneNumbers": [
        "9876543210",
        "9123456780"
    ]
}
```

Or:

```
Student
  │
  └── phoneNumbers
        ├── number 1
        └── number 2
```

This is a one-to-many relationship represented using an array.

> MongoDB documents one-to-many embedded models where related child data is naturally viewed in the context of its parent.

---

## 15. 🔥 Embedding Objects in Arrays

It gets even more powerful.

Suppose a student has multiple addresses:

```json
{
    "_id": 101,
    "name": "Rahul",

    "addresses": [
        {
            "type": "home",
            "city": "Amritsar",
            "state": "Punjab"
        },
        {
            "type": "hostel",
            "city": "Chandigarh",
            "state": "Punjab"
        }
    ]
}
```

Now:

```
Student
  │
  └── addresses[]
        │
        ├── address object
        └── address object
```

This is still embedding.

---

## 16. 🧩 This Is Where Part 4 Connects

Remember we learned:

```
"address.city"
```

for nested querying?

Now you understand why that exists.

Suppose:

```json
{
    "name": "Rahul",

    "address": {
        "city": "Amritsar"
    }
}
```

We can query:

```js
db.students.find({
    "address.city": "Amritsar"
})
```

The data model:

```
Student
   ↓
embedded address
   ↓
city
```

and the query:

```
"address.city"
```

are directly connected.

That's why MongoDB's document model, CRUD, and data modeling shouldn't be studied separately.

---

## 17. 🧠 REFERENCING

Now let's flip the design.

Instead of:

```
Student
  └── Address embedded
```

we create separate documents.

**`students`**

```json
{
    "_id": 101,
    "name": "Rahul"
}
```

**`addresses`**

```json
{
    "_id": 501,
    "studentId": 101,
    "city": "Amritsar",
    "state": "Punjab"
}
```

Here:

```
Student
   │
   │ studentId / reference
   ↓
Address
```

The related data is stored separately.

> MongoDB calls this a reference: one document stores a link to another document, commonly using the referenced document's `_id`.

---

## 18. 📚 Think of Referencing Like a Library Card

Imagine a library.

You don't carry the entire book inside your student ID card.

Your card simply contains:

```
Book ID → 501
```

The actual book exists somewhere else.

Similarly:

```
Student
   ↓
addressId: 501
   ↓
Address document
```

The student document says:

> "The related address is over there."

That's referencing.

---

## 19. 🧩 Embedded vs Referenced — Visualize It

**EMBEDDING**

```
students
   │
   └── Rahul
        │
        └── address
             ├── city
             └── state
```

Everything together.

**REFERENCING**

```
students
   │
   └── Rahul
        │
        └── addressId: 501
                     │
                     ↓
                 addresses
                     │
                     └── _id: 501
                         city
                         state
```

Data separated.

---

## 20. 🔥 Why Would We Reference?

Imagine a company has:

```
10 million employees
```

and every employee document embedded a giant department document.

You could end up duplicating the same department information many times.

For example:

```
Employee 1 → Engineering department data
Employee 2 → Engineering department data
Employee 3 → Engineering department data
...
Employee 100000 → Engineering department data
```

If department information changes frequently, updating all those copies becomes painful.

A reference can instead look like:

```
Employee
   ↓
departmentId: 50

Department
   ↓
_id: 50
name: Engineering
```

Now the department information exists in one place.

> MongoDB recommends considering references when embedding would cause significant duplication without enough read-performance benefit, when relationships are complex, or when child data grows very large.

---

## 21. 📝 Embedding vs Referencing

This table is gold, mate.

| Factor                             | Embedding             | Referencing                        |
|-------------------------------------|------------------------|--------------------------------------|
| Data location                       | Same document          | Separate documents                   |
| Related data retrieved together     | Excellent              | Requires additional access           |
| Read simplicity                     | Usually simpler        | More application/query work          |
| Duplication                         | Possible               | Reduced                              |
| Frequently changing shared data     | Can be problematic     | Often better                         |
| Large/growing child data            | Can become problematic | Often better                         |
| Complex relationships               | Less suitable          | Often better                         |
| Atomic single-document update       | Strong advantage       | May require multiple operations      |

> MongoDB's best-practice guidance similarly favors embedding when related data belongs together, is commonly queried together, or forms a contains/has-a relationship; references become more attractive for high-cardinality children, unbounded growth, large combined size, heavy write patterns, or independently existing child data.

---

## 22. ⚠️ Here's the BIGGEST Misconception

Do **NOT** memorize:

> "Embedding is good."
>
> "Referencing is bad."

**No.**

The correct answer is:

> Choose embedding or referencing based on the application's access patterns, relationship characteristics, update behavior, data growth, and duplication trade-offs.

> MongoDB explicitly frames the choice around how the application queries and returns related data.

That is the mature answer.

---

## 23. 🧠 When Should I EMBED?

Think:

### EMBED when...

**1. Related data is frequently accessed together**

Example:

```
Product
 + basic information
 + recent reviews
```

If the page always displays them together:

```
Product page
    ↓
Product + recent reviews
    ↓
ONE read
```

Embedding can make sense.

**2. The relationship is naturally "contains"**

Example:

```
User
 └── Address
```

or:

```
Order
 └── ShippingAddress
```

or:

```
Student
 └── ContactInformation
```

These are natural candidates for embedding.

> MongoDB specifically identifies "has-a" / "contains" relationships as common embedding scenarios.

**3. Related data doesn't grow without bounds**

This is important.

Suppose:

```
User
 └── 3 phone numbers
```

Fine.

But:

```
User
 └── 100 million messages
```

💀

That's obviously not a good giant embedded array.

> MongoDB documents have a 16 MiB maximum BSON document size, so unbounded growth is a major reason not to embed everything.

---

## 24. 🔥 When Should I REFERENCE?

Think:

### REFERENCE when...

**1. Child data has high cardinality**

Example:

```
University
   ↓
millions of students
```

Don't shove millions of students into one university document.

Reference them.

**2. Data grows without bounds**

Example:

```
User
   ↓
Messages
```

Messages can continue forever.

Better:

```
users
messages
```

with references.

**3. Child can exist independently**

Suppose:

```
Customer
Order
```

Orders are their own important entities.

A separate `orders` collection can make more sense.

**4. Data changes frequently**

Suppose 50,000 documents all duplicated:

```
departmentName: "Engineering"
```

and department information changes frequently.

Updating all copies creates extra write work.

A reference may be preferable.

> MongoDB's best-practice guidance explicitly lists frequent updates, unbounded growth, high cardinality, and independently existing child data as factors favoring references.

## 25. 🧩 One-to-One — Embedding vs Reference

Suppose:

```
User ↔ Profile
```

**Embedded**

```json
{
    "_id": 101,
    "username": "rahul",

    "profile": {
        "age": 21,
        "city": "Amritsar"
    }
}
```

Good when:

> User and profile are almost always accessed together.

**Referenced**

```json
// users
{
    "_id": 101,
    "username": "rahul",
    "profileId": 501
}
```

```json
// profiles
{
    "_id": 501,
    "age": 21,
    "city": "Amritsar"
}
```

Potentially useful when:

> Profile is large, independently managed, or accessed separately.

## 26. 🧠 One-to-Many — Embedding

Example:

```
Author
  ↓
Books
```

If an author has a small, bounded number of books and the application normally displays them together:

```json
{
    "_id": 1,
    "name": "Author A",

    "books": [
        {
            "title": "Book 1",
            "year": 2024
        },
        {
            "title": "Book 2",
            "year": 2025
        }
    ]
}
```

> MongoDB's one-to-many embedded model specifically gives this kind of pattern.

---

## 27. 🔥 One-to-Many — Referencing

But suppose:

```
Publisher
   ↓
100,000 books
```

You don't want:

```js
publisher: {
    books: [
        100000 objects...
    ]
}
```

Instead:

```json
// publishers
{
    "_id": 50,
    "name": "ABC Publications"
}
```

```json
// books
{
    "_id": 501,
    "title": "MongoDB Basics",
    "publisherId": 50
}
```

Another:

```json
{
    "_id": 502,
    "title": "Database Systems",
    "publisherId": 50
}
```

Now:

```
Publisher 50
    │
    ├── Book 501
    ├── Book 502
    ├── Book 503
    └── ...
```

> MongoDB documents this referenced one-to-many pattern specifically as useful when embedding would repeat information such as publisher details across many book documents.

---

## 28. 🔥 Many-to-Many

Now the big one.

Suppose:

```
Students ↔ Courses
```

A student can take many courses:

```
Rahul
 ├── DBMS
 ├── DSA
 └── AI
```

But each course has many students:

```
DBMS
 ├── Rahul
 ├── Priya
 ├── Arjun
 └── ...
```

That's:

```
M : M
```

This can become complicated very quickly.

> MongoDB supports multiple modeling patterns for many-to-many relationships, and references are often useful when the relationship is complex or the data has high cardinality.

---

## 29. 🧠 Why Many-to-Many Is Tricky

Imagine embedding all courses inside every student:

```
Rahul
 └── DBMS
 └── DSA
 └── AI

Priya
 └── DBMS
 └── DSA
 └── AI
```

Now course information may be duplicated.

Or embed all students inside every course:

```
DBMS
 ├── Rahul
 ├── Priya
 └── Arjun
```

Now student information may be duplicated.

So references can become more attractive:

```
students
    ↓
course IDs

courses
    ↓
student IDs
```

Or use a separate relationship/enrollment collection depending on the workload.

The key is:

> Many-to-many relationships require more careful modeling.

## 30. 🔥 The "Access Together" Principle

Let's make this extremely practical.

Suppose we have:

```
Order
 ├── orderId
 ├── date
 ├── customer
 └── items
```

When the user opens an order, they almost always need:

```
Order
+
Items
```

So:

```
Order
 └── items[]
```

is a natural embedded model.

Example:

```json
{
    "_id": 1001,
    "customerId": 501,

    "items": [
        {
            "productId": 10,
            "name": "Keyboard",
            "quantity": 2,
            "price": 2499
        },
        {
            "productId": 20,
            "name": "Mouse",
            "quantity": 1,
            "price": 999
        }
    ]
}
```

One order document contains the information required to display the order.

That's data modeled around access patterns.

## 31. 🧠 Why MongoDB Likes Denormalization

Remember Unit I?

We talked about:

```
Relational → normalization
MongoDB → often denormalized
```

Now you can actually understand what that means.

**Normalized style**

```
orders
   ↓
order_items
   ↓
products
```

Separate entities.

**Denormalized style**

```json
orders
   ↓
{
   "customer": {...},
   "items": [
      {...},
      {...}
   ]
}
```

Related information brought together.

> MongoDB documentation notes that denormalized models can let applications retrieve related data in a single operation and avoid some cross-collection joins.

---

## 32. ⚠️ But Denormalization Creates a Trade-Off

Suppose:

```
Product
name = Keyboard
price = 2499
```

and we copy product information into 10,000 orders.

Then:

```
Keyboard
price = 2499
```

is duplicated many times.

Now price changes.

**Which copies should change?**

That's the consistency problem.

So:

```
Embedding
   ↓
faster/easier reads
   +
possible duplication
```

while:

```
Referencing
   ↓
less duplication
   +
more work to retrieve related data
```

This is the fundamental trade-off.

> MongoDB's documentation explicitly discusses duplication versus read performance when deciding how to link related data.

---

## 33. 🔥 A VERY Important Real-World Trick

Sometimes you don't have to choose "pure embedding" or "pure referencing."

You can combine them.

Suppose:

```
Product
```

has:

```
5 most recent reviews
```

The application wants those frequently.

But there are:

```
100,000 total reviews
```

A possible design is:

```
products
   │
   ├── basic product data
   │
   └── recentReviews[]
```

and:

```
reviews
   │
   └── all reviews
```

So:

```
Frequently needed data
       ↓
Embedded

Large complete dataset
       ↓
Referenced/separate
```

> MongoDB itself gives this kind of recent-reviews pattern as a schema design example.

This is called **strategic denormalization** rather than blindly duplicating everything.

---

## 34. 🧠 Data Modeling and Atomicity

Here's another powerful connection.

> MongoDB writes are atomic at the single-document level.

Suppose:

```json
{
    "_id": 101,

    "balance": 5000,

    "transactions": [
        "..."
    ]
}
```

If an operation modifies multiple fields within this same document, the single-document write is atomic.

That means the changes happen together rather than leaving the document halfway updated.

This is another reason embedding can be powerful.

If data belongs together and needs to change together:

```
same document
     ↓
single atomic write
```

---

## 35. ⚠️ But References Can Require Multiple Operations

Suppose:

```
users
orders
payments
```

are separate collections.

Updating related data may involve:

```
Operation 1 → users
Operation 2 → orders
Operation 3 → payments
```

Now multiple documents/collections are involved.

> MongoDB supports transactions when atomicity across multiple documents/collections is required, but a good schema can often reduce the need for them by keeping closely related data together when appropriate.

So another modeling question becomes:

> Do these pieces of data need to change together atomically?

If yes, embedding can sometimes be a very attractive design.

---

## 36. ⚠️ Data Modeling Is NOT "Put Everything Inside One Document"

This is probably the biggest beginner trap.

Someone learns:

> "MongoDB likes embedded documents."

Then creates:

```
University
 └── 100000 students
      └── 500 courses
           └── 1000000 enrollments
```

😂

**No.**

The document would become enormous, hard to update, and potentially violate MongoDB's document size limit.

Remember:

> Embed related data that belongs together and is reasonably bounded.

Not:

> Embed literally everything.

> MongoDB documents have a 16 MiB BSON document limit.

---

## 37. 🧠 A Decision Tree

When you're designing a MongoDB relationship, ask:

```
                 Related data?
                      │
                      ↓
          Is it usually accessed together?
                 /          \
               YES           NO
                │             │
             EMBED?        REFERENCE?
                │             │
                ↓             ↓
       Is the data bounded?  Is it large?
          /       \            │
        YES       NO           │
         │         │           │
      EMBED     REFERENCE   REFERENCE
```

Then additionally ask:

```
Does it change frequently?
Does it grow without bounds?
Is it independently useful?
Is duplication acceptable?
Does it need atomic updates?
```

That's the real decision-making process.

---

## 38. 📝 Exam-Quality Definition

If they ask:

> What is data modeling in MongoDB?

A strong answer:

> Data modeling in MongoDB is the process of organizing documents, collections, and relationships according to the application's data access patterns. MongoDB supports flexible schemas and allows related data to be modeled either by embedding it within documents or by referencing documents stored separately.

That is much better than:

> "Data modeling means creating tables."

😂 That's SQL thinking.

---

## 39. 📝 Embedding — Exam Definition

> Embedding is a MongoDB data-modeling technique in which related data is stored inside the same document, typically using nested documents or arrays. It can simplify reads and allow related information to be retrieved in a single database operation.

---

## 40. 📝 Referencing — Exam Definition

> Referencing is a MongoDB data-modeling technique in which related data is stored in separate documents or collections, with one document storing a reference such as the related document's `_id`.
