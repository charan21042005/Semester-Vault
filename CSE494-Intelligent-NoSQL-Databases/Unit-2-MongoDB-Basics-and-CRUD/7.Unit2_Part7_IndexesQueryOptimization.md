# UNIT II — PART 7: INDEXES & QUERY OPTIMIZATION ⚡

## 1. 🔥 The Problem: What Happens With 10 Million Documents?

Imagine:

```
students
   │
   ├── Document 1
   ├── Document 2
   ├── Document 3
   ├── ...
   └── Document 10,000,000
```

Now execute:

```js
db.students.find({
    email: "rahul@example.com"
})
```

MongoDB needs to locate Rahul.

> Without an appropriate index, MongoDB may need to inspect documents across the collection — a **collection scan** (`COLLSCAN`). With an appropriate index, it can use an **index scan** (`IXSCAN`) to narrow the search.

And THAT is the problem indexes solve.

---

## 2. 🧠 First: What Is an Index?

Forget MongoDB for 30 seconds.

Imagine a textbook with:

```
1000 pages
```

You want:

> "Where is the chapter about databases?"

You could:

```
Page 1 → no
Page 2 → no
Page 3 → no
...
Page 700 → found
```

Painful.

But the textbook has an index:

```
Database .......... 245
MongoDB ............ 380
SQL ................ 410
NoSQL .............. 450
```

You immediately jump to the relevant location.

MongoDB indexes work on the same broad principle.

> An index is a separate data structure that helps MongoDB locate relevant documents without scanning the entire collection.

---

## 3. 🧩 The MongoDB Picture

**Without index:**

```
Query
  ↓
Collection
  ↓
Document 1 → check
Document 2 → check
Document 3 → check
Document 4 → check
...
Document 10,000,000 → check
```

**With index:**

```
Query
  ↓
INDEX
  ↓
Find relevant keys
  ↓
Relevant documents
```

So:

```
NO INDEX
Query → scan collection

INDEX
Query → index → relevant documents
```

That is the entire fundamental idea.

---

## 4. 🔥 A Real-World Example

Suppose:

```json
{
    "_id": "ObjectId(...)",
    "name": "Rahul",
    "email": "rahul@gmail.com",
    "branch": "CSE"
}
```

and we frequently search:

```js
db.students.find({
    email: "rahul@gmail.com"
})
```

We can create:

```js
db.students.createIndex({
    email: 1
})
```

Now MongoDB has an index on `email`.

> MongoDB recommends indexes for fields used repeatedly by application queries.

---

## 5. 🧠 `createIndex()`

The fundamental syntax:

```js
db.collection.createIndex({
    field: 1
})
```

For example:

```js
db.students.createIndex({
    email: 1
})
```

The:

```
1
```

means **ascending** index order.

You can also specify:

```js
db.students.createIndex({
    email: -1
})
```

for **descending** order.

> For a single-field index, the direction generally doesn't change whether equality queries can use the index; direction becomes particularly important when dealing with compound indexes and sort patterns.

---

## 6. 🧩 What Exactly Is Stored in an Index?

Suppose we have:

```
students

Rahul  → email = rahul@gmail.com
Priya  → email = priya@gmail.com
Arjun  → email = arjun@gmail.com
```

An index conceptually maintains something like:

```
email index

arjun@gmail.com  → document
priya@gmail.com  → document
rahul@gmail.com  → document
```

> The index contains indexed field values plus information allowing MongoDB to locate the corresponding documents.

> MongoDB indexes are specialized data structures; its standard indexes use a **B-tree** structure.

You don't need to implement the B-tree yourself.

Just understand:

```
INDEX
 ↓
organized searchable structure
 ↓
fast lookup
```

---

## 7. ⚠️ Why Don't We Just Index EVERYTHING?

Excellent question.

Because:

> Indexes are not free.

Suppose:

```
students
```

has:

```
10 million documents
```

and we create indexes on:

```
name
email
age
branch
cgpa
city
phone
...
```

Every time a document is inserted or updated, MongoDB may also need to update the relevant indexes.

So:

```
More indexes
     ↓
Potentially faster reads
     +
More storage
     +
More write/update overhead
```

> MongoDB explicitly warns that indexes improve reads but add overhead to writes because indexes must also be maintained.

So:

> Don't create indexes randomly.
>
> Create them based on actual query patterns.

## 11. 🔥 MongoDB Automatically Indexes `_id`

Remember `_id` from Parts 2 and 3?

> MongoDB automatically creates a unique index on `_id` when the collection is created. That index enforces uniqueness of `_id`, and you cannot drop it.

So conceptually:

```
students
   │
   ├── _id index        ← automatic
   │
   └── your indexes     ← you create
```

For example:

```js
db.students.getIndexes()
```

will show an index corresponding to:

```
_id_
```

---

## 12. 🧠 Why Is `_id` Indexed?

Imagine:

```js
db.students.findOne({
    _id: ObjectId("...")
})
```

Because `_id` is unique and indexed:

```
_id
 ↓
at most one document
```

This is also a good example of **high selectivity**.

---

## 13. 🔥 What Is Selectivity?

This is an important query-optimization concept.

Suppose:

```
1,000,000 documents
```

Query:

```
{ email: "rahul@gmail.com" }
```

Maybe:

```
1 matching document
```

That's **highly selective**.

But:

```
{ branch: "CSE" }
```

might match:

```
300,000 documents
```

That's **less selective**.

> MongoDB defines query selectivity in terms of how well a predicate filters documents; highly selective queries match a relatively small proportion of the collection.

Think:

```
HIGH SELECTIVITY
 ↓
few documents match

LOW SELECTIVITY
 ↓
many documents match
```

---

## 14. 🧠 Why Does Selectivity Matter?

Suppose:

```
1,000,000 students
```

Query:

```
{ _id: "..." }
```

returns:

```
1 document
```

The index is extremely useful.

But:

```
{ gender: "M" }
```

might return:

```
500,000 documents
```

The index may not provide as much benefit because a huge portion of the collection still needs to be considered.

> MongoDB notes that low-selectivity queries may perform no better, and sometimes can perform worse, with an index than with a collection scan.

So:

> Indexing a field doesn't automatically guarantee a faster query.

That sentence is important.

---

## 15. 🔥 Compound Index

Now things get interesting.

Suppose our application frequently queries:

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gt: 8.5 }
})
```

We're querying:

```
branch
+
cgpa
```

We can create a **compound index**:

```js
db.students.createIndex({
    branch: 1,
    cgpa: 1
})
```

> A compound index contains multiple fields in one index. MongoDB recommends compound indexes when queries commonly use multiple fields.

---

## 16. 🧩 Visualize a Compound Index

**Single:**

```
Index
 ↓
branch
```

**Compound:**

```
Index
 ↓
branch
 +
cgpa
```

Conceptually:

```
(CSE, 8.2)
(CSE, 8.5)
(CSE, 9.1)
(ECE, 8.8)
(ECE, 9.2)
...
```

MongoDB can use this organized structure to support suitable queries.

---

## 17. 🧠 Why Does Index Order Matter?

This is very important.

Suppose:

```js
db.students.createIndex({
    branch: 1,
    cgpa: 1
})
```

The order is:

```
1st → branch
2nd → cgpa
```

It's **not equivalent** to:

```js
db.students.createIndex({
    cgpa: 1,
    branch: 1
})
```

for all query patterns.

> MongoDB states that field order in compound indexes affects which queries the index supports.

---

## 18. 🔥 Compound Index Prefixes

Suppose:

```js
db.students.createIndex({
    branch: 1,
    cgpa: 1,
    age: 1
})
```

Think:

```
branch
branch + cgpa
branch + cgpa + age
```

These are the index's **prefixes**.

> MongoDB compound indexes can support queries using prefixes of the indexed fields.

So:

```
{ branch: "CSE" }
```

can be supported by the index.

And:

```js
{
    branch: "CSE",
    cgpa: { $gt: 8 }
}
```

can also make use of the compound index.

But a query only on:

```
{ age: 21 }
```

doesn't have the same useful prefix relationship because `age` is not the beginning of the index.

---

## 19. 🧩 The Left-Prefix Idea

Imagine:

Index:

```
A → B → C
```

Then useful prefixes are:

```
A
A + B
A + B + C
```

Not:

```
B
C
B + C
```

as equivalent prefix usage.

So:

```
{branch}
{branch, cgpa}
{branch, cgpa, age}
```

fit the beginning of:

```
branch → cgpa → age
```

This is one of the most important compound-index concepts.

---

## 20. 🔥 ESR — Equality, Sort, Range

Now we're getting into actual query optimization.

MongoDB documents the **ESR** guideline:

```
E = Equality
S = Sort
R = Range
```

A common pattern is:

```
Equality → Sort → Range
```

when designing compound indexes for appropriate queries.

Example query:

```js
db.movies.find({
    rated: "PG",
    released: { $gt: ISODate("2000-01-01") }
})
.sort({
    title: 1
})
```

Conceptually:

```
Equality
rated = PG
    ↓
Sort
title
    ↓
Range
released > date
```

A corresponding index might be structured around:

```
rated → title → released
```

> MongoDB's documentation gives this exact style of reasoning for ESR.

Don't worry if ESR feels advanced right now.

Just remember:

> Compound-index field order matters, and ESR is a useful guideline for choosing that order.

## 21. 🧠 Query Optimization

Now we can finally define it.

> Query optimization is the process of making database queries execute more efficiently, reducing the amount of data MongoDB must process.

> MongoDB specifically identifies indexes, projections, and query limits as major tools for improving query performance and reducing resource usage.

So:

```
Query Optimization
       │
       ├── Appropriate indexes
       ├── Selective filters
       ├── Projection
       ├── limit()
       └── Analyze with explain()
```

---

## 22. 🧩 Optimization Technique #1 — Index the Fields You Query Frequently

Suppose application repeatedly executes:

```js
db.users.find({
    email: "..."
})
```

Create:

```js
db.users.createIndex({
    email: 1
})
```

Simple.

---

## 23. 🧠 Optimization Technique #2 — Use Projection

Suppose the document is huge:

```
Student
 ├── name
 ├── address
 ├── history
 ├── certificates
 ├── projects
 ├── skills
 ├── ...
```

But your application needs only:

```
name
cgpa
```

Instead of:

```js
db.students.find({
    branch: "CSE"
})
```

use:

```js
db.students.find(
    { branch: "CSE" },
    {
        name: 1,
        cgpa: 1,
        _id: 0
    }
)
```

> Projection reduces the fields returned to the client. MongoDB includes projection as one of its core query-optimization techniques.

---

## 24. 🔥 Optimization Technique #3 — `limit()`

Suppose you need:

> Top 10 students.

Don't retrieve:

```
1,000,000 students
```

and throw away 999,990 in application code.

Instead:

```js
db.students.find()
    .sort({ cgpa: -1 })
    .limit(10)
```

> MongoDB notes that limiting results reduces resource usage, including network resources.

---

## 25. 🧠 Optimization Technique #4 — Good Filtering

Suppose:

```js
db.students.find({
    _id: ObjectId("...")
})
```

This is highly selective.

Versus:

```js
db.students.find({})
```

which asks for everything.

So:

```
Specific filter
      ↓
fewer documents
      ↓
less work
```

```
explain()
```

Suppose:

```js

})
```


## 28. 🧠 The Three Important Stages

When reading an explain plan, three terms are particularly useful for beginners:

```
COLLSCAN
IXSCAN
FETCH
```

> MongoDB documents these execution stages explicitly.

Let's destroy the confusion.

---

## 29. 🔥 COLLSCAN

Means:

```
Collection Scan
```

MongoDB is scanning the collection.

Conceptually:

```
Query
 ↓
COLLSCAN
 ↓
Document 1
Document 2
Document 3
...
```

If you expected an index to help but see:

```
COLLSCAN
```

that's something worth investigating.

> MongoDB notes that filter/sort operations showing `COLLSCAN` may benefit from an appropriate index.

---

## 30. 🧠 IXSCAN

Means:

```
Index Scan
```

MongoDB is scanning an index.

Conceptually:

```
Query
 ↓
IXSCAN
 ↓
Index
 ↓
relevant keys
```

That's generally what we hope to see when an appropriate index is useful for the query.

---

## 31. 🧩 FETCH

Sometimes MongoDB uses the index to identify candidate documents and then retrieves the actual documents.

Conceptually:

```
IXSCAN
   ↓
find relevant document locations
   ↓
FETCH
   ↓
retrieve documents
```

So:

```
IXSCAN → identify
FETCH  → retrieve
```

This is why an index scan doesn't necessarily mean MongoDB never touches the actual collection documents.

---

## 32. 🔥 `docsExamined`

This is a very useful metric.

Suppose:

```
nReturned = 5
docsExamined = 500,000
```

That's suspicious.

You returned:

```
5
```

but examined:

```
500,000
```

documents.

That's a lot of work.

> MongoDB recommends comparing `totalDocsExamined` with `nReturned` to identify inefficient filtering/index use.

---

## 33. 🧠 `keysExamined`

Similarly:

```
keysExamined
```

tells us how many index keys were examined.

Suppose:

```
keysExamined = 5
docsExamined = 5
nReturned = 5
```

That's pretty efficient.

But:

```
keysExamined = 500,000
docsExamined = 500,000
nReturned = 5
```

means the index isn't filtering very effectively.

---

## 34. 🧩 The Dream Scenario

Suppose:

```
nReturned = 5
docsExamined = 5
```

That's beautiful.

MongoDB found and examined roughly only the documents it needed.

Conceptually:

```
1,000,000 total
       ↓
Index
       ↓
5 relevant
       ↓
5 examined
       ↓
5 returned
```

That's what good selectivity and indexing can help achieve.

## 35. 🔥 Covered Query

Now we're entering one of the coolest index concepts.

> A **covered query** is a query where MongoDB can satisfy the query entirely from the index without fetching the actual documents. MongoDB requires the queried fields and returned fields to be available in the index, subject to coverage conditions.

Example index:

```js
db.students.createIndex({
    branch: 1,
    name: 1
})
```

Query:

```js
db.students.find(
    { branch: "CSE" },
    { name: 1, _id: 0 }
)
```

The index contains:

```
branch
name
```

The query needs:

```
branch → filter
name   → result
```

And `_id` is explicitly excluded.

So MongoDB can potentially answer the query from the index itself.

---

## 36. 🧠 Why Is a Covered Query Powerful?

Normal:

```
Query
 ↓
Index
 ↓
Document
 ↓
Return fields
```

Covered:

```
Query
 ↓
Index
 ↓
Return fields
```

No document fetch required.

> MongoDB notes that querying only the index can be faster because index keys are generally smaller than the full documents they catalog.

---

## 37. 🧩 Another Example

Index:

```js
db.products.createIndex({
    category: 1,
    name: 1
})
```

Query:

```js
db.products.find(
    { category: "Laptop" },
```

The index has:

```

name
```

Filter:

```
category
```

Output:

```
name
```

So the index contains everything needed.

## 38. ⚠️ But `_id` Can Ruin Coverage

Remember:

> MongoDB returns `_id` by default

So if your index doesn't include `_id`, a projection like:

```js
{
    name: 1
}
```

still requests `_id`.

For a covered query, explicitly exclude it:

```js
{
    name: 1,
    _id: 0
}
```

> MongoDB's covered-query documentation specifically highlights this requirement when `_id` isn't included in the index.

That's a beautiful connection back to Part 4.

## 40. 🧠 What About Arrays?

> Indexes can also be built on array fields, producing what MongoDB calls a **multikey index**.

For example:

```json
{
    "name": "Rahul",
    "skills": [
        "C++",
        "Python",
        "MongoDB"
    ]
}
```

You could create:

```js
db.students.createIndex({
    skills: 1
})
```

> MongoDB can use a multikey index for queries involving array fields.

But there are important limitations, including limitations around covered queries involving array fields.

Don't worry about the deeper multikey rules yet — the important Unit II idea is:

> MongoDB indexes can support array-field queries, and those indexes become multikey indexes.

## 41. 🧩 Indexing Strategy — Don't Guess

Here's the proper workflow:

```
Application
    ↓
Identify common queries
    ↓
Observe actual workload
    ↓
Create appropriate indexes
    ↓
Run queries
    ↓
explain()
    ↓
Analyze performance
    ↓
Remove unnecessary indexes
    ↓
Repeat as workload changes
```

> MongoDB recommends identifying common query patterns, creating indexes to support them, analyzing their effectiveness, and periodically reviewing unused/unnecessary indexes.

That's much better than:

> "Let's put an index on every field."

😂 No.

## 45. 🧩 A Subtle Point: MongoDB Has a Query Optimizer

You don't normally tell MongoDB:

> "Use this index!"

> MongoDB's query planner generally chooses an appropriate index for a query.

You can inspect the chosen plan with `explain()`. In special cases, you can use `hint()` to force a particular index, typically for testing or specific troubleshooting scenarios.

So:

```
Normal
Query
 ↓
MongoDB optimizer
 ↓
Choose plan
```

and:

```
hint()
```

is something you use deliberately, not casually.

If you run:

```js

```

don't think:

## 49. 🔥 One Major Trade-Off

Indexes improve:

```
READ
 ↓
faster query execution
```

But can hurt:

```
WRITE
 ↓
insert/update/delete must maintain indexes
```

So:

```
INDEX
 ├── 👍 faster reads
 ├── 👍 better query execution
 ├── 👎 storage cost
 └── 👎 write/update maintenance
```

This is one of the most important database engineering trade-offs.

## 52. 📝 The Most Important Index Concepts to Remember

Mate, if I strip this entire part down to the core combat arsenal:

**Index**

> Separate data structure that helps MongoDB locate documents efficiently.

**`createIndex()`**

```js
db.students.createIndex({
    email: 1
})
```

**Single-field index**

> one field

**Compound index**

```js
db.students.createIndex({
    branch: 1,
    cgpa: 1
})
```

**Selectivity**

> How effectively does the query reduce the number of matching documents?

**COLLSCAN**

> Collection scan

**IXSCAN**

> Index scan

**`explain()`**

> Show me how MongoDB executed the query.

**Covered query**

> Query can be satisfied entirely from index.

**Major trade-off**

> Indexes
> ↑ read performance
> ↓ write performance / storage overhead
