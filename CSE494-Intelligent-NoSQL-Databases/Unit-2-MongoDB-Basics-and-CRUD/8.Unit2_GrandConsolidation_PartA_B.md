## 1️⃣ DATABASE → COLLECTION → DOCUMENT

Let's start from the foundation.

Imagine we're building a college system.

We create:

```
collegeDB
```

Inside it:

```
collegeDB
│
├── students
├── teachers
├── courses
└── departments
```

Each of those is a **collection**.

Inside `students`:

```
students
│
├── Document 1
├── Document 2
├── Document 3
└── Document 4
```

A document could be:

```json
{
    "name": "Rahul",
    "age": 21,
    "branch": "CSE",
    "cgpa": 8.7
}
```

So:

```
MongoDB
   ↓
Database
   ↓
Collection
   ↓
Document
   ↓
Fields
```

### SQL Comparison

| SQL         | MongoDB    |
|--------------|-------------|
| Database     | Database    |
| Table        | Collection  |
| Row          | Document    |
| Column       | Field       |
| Primary key  | `_id`       |

> This is a conceptual mapping, not a claim that MongoDB collections and SQL tables behave identically.

## 2️⃣ DOCUMENT → BSON

Now here's something extremely important.

We write MongoDB documents using JSON-like syntax:

```json
{
    "name": "Rahul",
    "age": 21,
    "cgpa": 8.7
}
```

But MongoDB actually stores documents using:

```
BSON
```

**BSON = Binary JSON**

And BSON gives MongoDB richer data types than ordinary JSON.

For example:

```js
{
    name: "Rahul",
    age: 21,
    active: true,
    skills: ["C++", "Python"],
    address: {
        city: "Jalandhar"
    },
    createdAt: new Date()
}
```

Here we have:

```
String
Number
Boolean
Array
Embedded Document
Date
```

And MongoDB also has types such as:

```
ObjectId
Decimal128
Int32
Int64
Binary
Regex
Timestamp
Null
```

So remember:

```
MongoDB document
       ↓
JSON-like syntax
       ↓
BSON internally
```

## 3️⃣ `_id` — THE IDENTITY OF A DOCUMENT

When we insert:

```js
db.students.insertOne({
    name: "Rahul",
    branch: "CSE"
})
```

MongoDB automatically gives it an `_id` if we don't provide one.

Conceptually:

```json
{
    "_id": "ObjectId(...)",
    "name": "Rahul",
    "branch": "CSE"
}
```

Think:

> `_id` = identity card of the document.

> MongoDB creates a unique index on `_id` by default.

We manipulate data.

That's CRUD:

## 5️⃣ CREATE

**Insert one**

```js
db.students.insertOne({
    name: "Rahul",
    branch: "CSE",
    cgpa: 8.7
})
```

Break it:

```
db
 ↓
current database

students
 ↓
collection

insertOne()
 ↓
insert one document

{ ... }
 ↓
document
```

**Insert many**

```js
db.students.insertMany([
    {
        name: "Rahul",
        branch: "CSE",
        cgpa: 8.7
    },
    {
        name: "Priya",
        branch: "ECE",
        cgpa: 9.1
    }
])
```

So:

```
insertOne()  → one document
insertMany() → multiple documents
```

---

## 6️⃣ READ

Now suppose we already have:

```json
{
    "name": "Rahul",
    "branch": "CSE",
    "cgpa": 8.7
}
```

We want to retrieve it.

**Everything**

```js
db.students.find()
```

or:

```js
db.students.find({})
```

Both conceptually mean:

> Give me all matching documents.

**Find CSE students**

```js
db.students.find({
    branch: "CSE"
})
```

Meaning:

```
branch == "CSE"
```

**Find students with CGPA > 8.5**

```js
db.students.find({
    cgpa: { $gt: 8.5 }
})
```

`$gt`:

> greater than

**Find CGPA >= 8**

```js
db.students.find({
    cgpa: { $gte: 8 }
})
```

**Multiple conditions**

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8 }
})
```

Conceptually:

```
branch = CSE
        AND
cgpa >= 8
```

---

## 7️⃣ PROJECTION

Suppose the document contains:

```json
{
    "name": "Rahul",
    "age": 21,
    "branch": "CSE",
    "cgpa": 8.7,
    "phone": "..."
}
```

But we only want:

```
name
cgpa
```

We can project:

```js
db.students.find(
    { branch: "CSE" },
    { name: 1, cgpa: 1, _id: 0 }
)
```

Now you're saying:

> Find CSE students, but only show their name and CGPA.

Important distinction:

```
FILTER
↓
Which documents?

PROJECTION
↓
Which fields?
```

This distinction is very important.

---

## 8️⃣ SORT + LIMIT + SKIP

Suppose we want highest CGPA first:

```js
db.students.find().sort({
    cgpa: -1
})
```

Remember:

```
1  → ascending
-1 → descending
```

**Top 3:**

```js
db.students.find()
    .sort({ cgpa: -1 })
    .limit(3)
```

Pagination can use:

```js
.skip(10)
.limit(10)
```

Meaning:

> Skip first 10, then give next 10.

## 9️⃣ UPDATE

Now Rahul's CGPA changes.

We use:

```js
db.students.updateOne(
    { name: "Rahul" },
    { $set: { cgpa: 9.0 } }
)
```

Think:

```
FILTER
   ↓
find Rahul
   ↓
MODIFY
   ↓
set cgpa = 9.0
```

### `$set`

`$set` means:

> Set this field to this value.

It can also create the field if it doesn't already exist.

---

## 🔟 `$inc`

Suppose:

```
{
    views: 100
}
```

We want:

```
100 → 101
```

Use:

```js
db.products.updateOne(
    { name: "Keyboard" },
    { $inc: { views: 1 } }
)
```

`$inc` = increment.

It can also decrement:

```js
{ $inc: { views: -1 } }
```

## 1️⃣1️⃣ ARRAYS — `$push` and `$pull`

Suppose:

```json
{
    "name": "Rahul",
    "skills": ["C++", "Python"]
}
```

Add Java:

```js
db.students.updateOne(
    { name: "Rahul" },
    { $push: { skills: "Java" } }
)
```

Now:

```
["C++", "Python", "Java"]
```

Remove Python:

```js
db.students.updateOne(
    { name: "Rahul" },
    { $pull: { skills: "Python" } }
)
```

## 1️⃣2️⃣ UPDATE MANY

Suppose every CSE student gets a department field:

```js
db.students.updateMany(
    { branch: "CSE" },
    { $set: { department: "Computer Science" } }
)
```

Difference:

```
updateOne()
    ↓
at most one matching document

updateMany()
    ↓
all matching documents
```

## 1️⃣3️⃣ DELETE

Remove one:

```js
db.students.deleteOne({
    name: "Rahul"
})
```

Remove all matching:

```js
db.students.deleteMany({
    branch: "CSE"
})
```

And here's your dangerous command:

```js
db.students.deleteMany({})
```

That means:

> Delete every document in the collection.

🔥 Golden rule:

> **FILTER FIRST, THEN MODIFY OR DELETE.**

Before executing:

```
deleteMany(...)
```

always ask yourself:

> "Exactly which documents am I targeting?"

## 1️⃣6️⃣ DATA MODELING

Data modeling means:

> Designing how data and relationships are organized inside the database.

> MongoDB has a flexible schema, meaning documents in one collection don't necessarily need exactly the same fields or data types. But that doesn't mean we should randomly structure everything. MongoDB recommends designing around application workload and access patterns.

The central question becomes:

> What data is usually accessed together?

MongoDB's core modeling principle is essentially:

```
DATA ACCESSED TOGETHER
          ↓
STORE TOGETHER
```

when that design makes sense for the workload.

---

## 1️⃣7️⃣ EMBEDDING

Suppose a student has one address.

Instead of:

```
students
addresses
```

we can put the address inside the student:

```json
{
    "name": "Rahul",
    "branch": "CSE",

    "address": {
        "city": "Jalandhar",
        "state": "Punjab",
        "pincode": "144001"
    }
}
```

This is:

```
Embedding
```

The related information lives inside the same document.

---

## 1️⃣8️⃣ WHY EMBED?

Imagine the application displays:

```
Student Profile
+
Address
```

every time.

Why make multiple database operations?

Store together:

```
Student
 ├── Name
 ├── Branch
 └── Address
      ├── City
      ├── State
      └── Pincode
```

One document gives you everything.

> Embedding can also make related single-document updates atomic.

## 1️⃣9️⃣ REFERENCING

Now imagine:

```
University
   ↓
Millions of students
```

Or:

```
Publisher
   ↓
Thousands/millions of books
```

You probably don't want one giant publisher document containing every book.

Instead:

```json
{
    "_id": 101,
    "name": "Penguin"
}
```

and books:

```json
{
    "title": "Book A",
    "publisherId": 101
}
```

This is:

```
Referencing
```

The related data lives separately and documents contain references to one another.

---

## 2️⃣0️⃣ EMBEDDING VS REFERENCING

This is one of the most important Unit II comparisons.

| Embedding                                | Referencing                              |
|--------------------------------------------|---------------------------------------------|
| Related data inside document               | Related data in separate documents           |
| Fewer reads for together-accessed data     | May require additional reads/operations      |
| Good for bounded related data              | Good for large/unbounded relationships       |
| Convenient when data belongs together      | Useful when data exists independently        |
| Can improve read performance               | Avoids excessive duplication                 |
| Single-document atomicity advantage        | Multi-document work may need transactions    |

> MongoDB explicitly recommends considering access patterns, duplication/update frequency, and relationship characteristics when deciding.

## 2️⃣3️⃣ NOW THE DATABASE BECOMES HUGE

Imagine:

```
students
   ↓
100 students
```

`find()` is fine.

But now:

```
students
   ↓
10 million documents
```

Query:

```js
db.students.find({
    email: "rahul@gmail.com"
})
```

Without a suitable index, MongoDB may need to scan many/all documents.

That's where:

```
INDEXES
```

come in.

> MongoDB indexes are separate data structures designed to make query execution more efficient. Without an appropriate index, MongoDB may scan the collection. MongoDB indexes use B-tree structures for standard indexes.

## 2️⃣5️⃣ SINGLE FIELD INDEX

Suppose users frequently search by email.

Create:

```js
db.students.createIndex({
    email: 1
})
```

Now MongoDB has an index on `email`.

## 2️⃣6️⃣ COMPOUND INDEX

Suppose our common query is:

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8 }
})
```

We could consider:

```js
db.students.createIndex({
    branch: 1,
    cgpa: 1
})
```

That's a:

```
Compound index
```

An index over multiple fields.

And here's the important part:

> Order matters in compound indexes.

> MongoDB can use compound-index prefixes, so the beginning fields of the index matter when determining which query shapes it supports.

---

## 2️⃣7️⃣ INDEX ≠ FREE SPEED

This is extremely important.

People think:

```
More indexes
     ↓
More speed
```

❌ Wrong.

Actually:

```
More indexes
     ↓
Faster suitable reads
     +
More storage
     +
More index maintenance during writes
```

Every insert/update may need corresponding index maintenance.

> MongoDB therefore recommends creating indexes around actual/common query patterns rather than indexing everything.

## 2️⃣8️⃣ QUERY OPTIMIZATION

Now we're at the final stage of Unit II.

Suppose this query is slow:

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8 }
})
```

We ask:

> Why is it slow?

We investigate using:

```js
.explain("executionStats")
```

For example:

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8 }
}).explain("executionStats")
```

Now MongoDB tells us about the query execution plan.

## 2️⃣9️⃣ COLLSCAN VS IXSCAN

These two should become automatic in your brain.

### COLLSCAN

```
COLL
 ↓
scan documents
 ↓
check each document
```

Means:

> Collection scan.

### IXSCAN

```
INDEX
 ↓
find relevant keys
 ↓
retrieve relevant documents
```

Means:

> Index scan.

So:

```
COLLSCAN → "I searched the collection."

IXSCAN   → "I used an index."
```

## 3️⃣0️⃣ IMPORTANT `explain()` METRICS

You may encounter:

```
nReturned
totalDocsExamined
totalKeysExamined
executionTimeMillis
```

Think:

**`nReturned`**

> How many documents actually came back?

**`totalDocsExamined`**

> How many documents did MongoDB inspect?

**`totalKeysExamined`**

> How many index keys did it inspect?

**`executionTimeMillis`**

> How long did execution take according to the reported execution statistics?

The goal is generally to reduce unnecessary work, not blindly optimize around one number.

---

## 3️⃣1️⃣ SELECTIVITY

Another important concept.

Suppose:

```
10 million documents
```

Query:

```
_id = "something"
```

Maybe only one document matches.

That's **highly selective**.

But:

```
gender = "Male"
```

might match millions.

That's **less selective**.

So:

```
HIGH SELECTIVITY
        ↓
small fraction matches

LOW SELECTIVITY
        ↓
large fraction matches
```

> MongoDB notes that highly selective predicates generally make indexes more useful, while low-selectivity predicates may provide less benefit.

---

## 3️⃣2️⃣ COVERED QUERY

This is a beautiful concept.

Suppose we have:

```js
db.students.createIndex({
    email: 1,
    name: 1
})
```

And query:

```js
db.students.find(
    { email: "rahul@gmail.com" },
    { name: 1, _id: 0 }
)
```

The index contains:

```
email
name
```

And we're asking only for:

```
email
name
```

with `_id` excluded.

> MongoDB may be able to answer the query entirely from the index without fetching the actual documents.

That's:

```
Covered query
```

Conceptually:

```
Normal:

INDEX
 ↓
DOCUMENT
 ↓
RESULT


Covered:

INDEX
 ↓
RESULT
```

> A covered query is one where the index contains the fields needed by the query and projection, allowing MongoDB to avoid scanning the collection documents.

## 1️⃣ THE MASTER SQL → MONGODB MAP

This is the first table I want permanently burned into your brain.

| Relational / SQL          | MongoDB                          |
|-----------------------------|-------------------------------------|
| Database                    | Database                            |
| Table                        | Collection                          |
| Row                           | Document                            |
| Column                        | Field                                |
| Primary Key                   | `_id`                                |
| JSON-like record               | BSON document                       |
| INSERT                         | `insertOne()` / `insertMany()`       |
| SELECT                          | `find()` / `findOne()`               |
| UPDATE                          | `updateOne()` / `updateMany()`       |
| DELETE                           | `deleteOne()` / `deleteMany()`       |
| WHERE                             | Query filter                        |
| SELECT specific columns           | Projection                          |
| ORDER BY                          | `sort()`                            |
| LIMIT                              | `limit()`                            |
| OFFSET                              | `skip()`                             |
| Index                               | Index                                |
| JOIN-like relationship               | Referencing / `$lookup` later        |
| Nested related data                   | Embedded document                    |
| Multiple related values                | Array                                |
| Query optimization                      | Indexes + `explain()`                |

> MongoDB officially defines CRUD as create, read, update and delete operations, with `insertOne()`/`insertMany()`, `find()`, `updateOne()`/`updateMany()`, and `deleteOne()`/`deleteMany()` forming the core methods.

**MongoDB:**

gives:

the database/collection becomes actually populated.

is a table.

**MongoDB:**

```
students
```

is a collection.

```
students

id | name  | branch | cgpa
--------------------------------
1  | Rahul | CSE    | 8.7
```

**MongoDB**

```json
{
```

## 4️⃣ ROW vs DOCUMENT

This is a conceptual mapping, not an exact structural equivalence.

**SQL row:**

```
1 | Rahul | CSE | 8.7
```

**MongoDB document:**

```json
{
    "_id": 1,
    "name": "Rahul",
    "branch": "CSE",
    "cgpa": 8.7
}
```

But MongoDB documents can go much deeper:

```json
{
    "name": "Rahul",

    "address": {
        "city": "Jalandhar",
        "state": "Punjab"
    },

    "skills": [
        "C++",
        "Python",
        "MongoDB"
    ]
}
```

That's one of MongoDB's major differences.

## 5️⃣ SQL INSERT → MongoDB CREATE

**SQL:**

```sql
INSERT INTO students
(name, branch, cgpa)
VALUES
('Rahul', 'CSE', 8.7);
```

**MongoDB:**

```js
db.students.insertOne({
    name: "Rahul",
    branch: "CSE",
    cgpa: 8.7
})
```

**Multiple:**

**SQL:**

```sql
INSERT INTO students VALUES (...), (...);
```

**MongoDB:**

```js
db.students.insertMany([
    {
        name: "Rahul",
        branch: "CSE"
    },
    {
        name: "Priya",
        branch: "ECE"
    }
])
```

> MongoDB's insert methods can create the collection if it doesn't already exist.

## 6️⃣ SQL SELECT → MongoDB FIND

This is one of the most important mappings.

**SQL:**

```sql
SELECT *
FROM students;
```

**MongoDB:**

```js
db.students.find()
```

**SQL:**

```sql
SELECT *
FROM students
WHERE branch = 'CSE';
```

**MongoDB:**

```js
db.students.find({
    branch: "CSE"
})
```

So:

```
SQL WHERE
   ↓
MongoDB filter document
```

---

## 7️⃣ SQL WHERE WITH COMPARISON

**SQL:**

```sql
SELECT *
FROM students
WHERE cgpa > 8.5;
```

**MongoDB:**

```js
db.students.find({
    cgpa: { $gt: 8.5 }
})
```

Translation:

```
>   → $gt
>=  → $gte
<   → $lt
<=  → $lte
=   → equality / $eq
!=  → $ne
```

For example:

```js
{ cgpa: { $gte: 8 } }
```

means:

> CGPA greater than or equal to 8.

---

## 8️⃣ SQL AND → MONGODB MULTIPLE CONDITIONS

**SQL:**

```sql
SELECT *
FROM students
WHERE branch = 'CSE'
AND cgpa >= 8;
```

**MongoDB:**

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8 }
})
```

That's an implicit AND.

You can also explicitly use:

```js
db.students.find({
    $and: [
        { branch: "CSE" },
        { cgpa: { $gte: 8 } }
    ]
})
```

Usually the first form is cleaner when straightforward equality/range conditions can be expressed directly.

---

## 9️⃣ SQL OR → MONGODB `$or`

**SQL:**

```sql
SELECT *

WHERE branch = 'CSE'
OR branch = 'ECE';
```

**MongoDB:**

```js
db.students.find({
    $or: [
        { branch: "CSE" },
        { branch: "ECE" }
    ]
})
```

Mental translation:

```
SQL OR
 ↓
$or
```

Very useful.

## 1️⃣1️⃣ SQL SELECT COLUMNS → MONGODB PROJECTION

```
    ↓

    ↓
```

This distinction is gold.

## 1️⃣5️⃣ SQL UPDATE → MongoDB UPDATE

**SQL:**

```sql
UPDATE students
SET cgpa = 9.0
WHERE name = 'Rahul';
```

**MongoDB:**

```js
db.students.updateOne(
    { name: "Rahul" },
    { $set: { cgpa: 9.0 } }
)
```

The structure is beautiful:

```
updateOne(
    FILTER,
    MODIFICATION
)
```

or:

```
                 updateOne
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
       FILTER              UPDATE
          ↓                   ↓
   "Which document?"     "What change?"
```

## 1️⃣6️⃣ SQL UPDATE MULTIPLE → `updateMany()`

**SQL:**

```sql
UPDATE students
SET department = 'Computer Science'
WHERE branch = 'CSE';
```

**MongoDB:**

```js
db.students.updateMany(
    { branch: "CSE" },
    {
        $set: {
            department: "Computer Science"
        }
    }
)
```

Difference:

```
updateOne()
→ at most one matching document

updateMany()
→ all matching documents
```

> MongoDB documents the same distinction explicitly.

**Multiple:**

## 1️⃣8️⃣ THE DEADLY EMPTY FILTER

**SQL:**

```sql
DELETE FROM students;
```

means:

> Delete all rows.

**MongoDB equivalent:**

```js
db.students.deleteMany({})
```

means:

> Delete all documents.

So:

```
{}
```

as a filter means:

> No filtering condition.

> MongoDB's documentation confirms that `deleteMany({})` targets all matching documents, while `deleteOne({})` deletes the first document returned by the collection.

🔥 Therefore:

```
{}
```

is harmless in:

```
find({})
```

because it means:

> show everything.

But dangerous in:

```
deleteMany({})
```

because it means:

> delete everything.

## 1️⃣9️⃣ SQL PRIMARY KEY → `_id`

**SQL:**

```sql
id INT PRIMARY KEY
```

**MongoDB:**

```json
{
    "_id": "ObjectId(...)"
}
```

> MongoDB automatically creates a unique `_id` index for each collection, and duplicate `_id` values are rejected.

You can also explicitly provide:

```json
{
    "_id": "STU001",
    "name": "Rahul"
}
```

But then:

```
STU001
```

must be unique within that collection.

## 2️⃣0️⃣ SQL NORMALIZATION vs MONGODB MODELING

This is where you should not blindly translate SQL design into MongoDB.

Imagine SQL:

```
STUDENT
---------
student_id
name
branch

ADDRESS
---------
address_id
student_id
city
state
```

Relational thinking often separates related data into tables and uses keys.

MongoDB may instead embed:

```json
{
    "_id": 101,

    "name": "Rahul",

    "branch": "CSE",

    "address": {
        "city": "Jalandhar",
        "state": "Punjab"
    }
}
```

That's:

```
Embedding
```

The important question is:

> What does my application read and update together?

Not:

> "How do I blindly convert every SQL table into a MongoDB collection?"

## 2️⃣1️⃣ INDEX MAPPING

**MongoDB:**

But again:

## 2️⃣2️⃣ QUERY OPTIMIZATION

SQL developers may use:

```sql
EXPLAIN
```

MongoDB uses:

```js
.explain()
```

Example:

```js
db.students.find({
    branch: "CSE"
}).explain("executionStats")
```

You investigate the execution plan.

Look for concepts such as:

```
COLLSCAN
IXSCAN
FETCH
nReturned
totalDocsExamined
totalKeysExamined
executionTimeMillis
```

The idea is:

```
Query
 ↓
Execution plan
 ↓
What work did MongoDB perform?
 ↓
Can an index or better query shape reduce unnecessary work?
```

## 2️⃣3️⃣ THE BIG SQL → MONGODB TRANSLATION EXERCISE

Let's say your professor gives:

> Find the top 3 CSE students having CGPA ≥ 8.5 and display only their names and CGPA, highest CGPA first.

### SQL thinking

```sql
SELECT name, cgpa
FROM students
WHERE branch = 'CSE'
AND cgpa >= 8.5
ORDER BY cgpa DESC
LIMIT 3;
```

### MongoDB thinking

First:

**FILTER**

```js
{
    branch: "CSE",
    cgpa: { $gte: 8.5 }
}
```

Then:

**PROJECTION**

```js
{
    name: 1,
    cgpa: 1,
    _id: 0
}
```

Then:

**SORT**

```js
{ cgpa: -1 }
```

Then:

**LIMIT**

```
3
```

**Final:**

```js
db.students.find(
    {
        branch: "CSE",
        cgpa: { $gte: 8.5 }
    },
    {
        name: 1,
        cgpa: 1,
        _id: 0
    }
)
.sort({
    cgpa: -1
})
.limit(3)
```

🔥 This is exactly the kind of translation ability I want you to develop.
