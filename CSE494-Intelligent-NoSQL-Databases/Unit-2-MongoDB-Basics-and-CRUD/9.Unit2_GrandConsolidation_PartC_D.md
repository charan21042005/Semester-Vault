## PHASE 2 — ENTER OUR DATABASE

Run:

```js
use collegeDB
```

Then:

```js
db
```

You should see:

```

```

### What just happened?

We haven't started creating tables or anything.

We've simply said:

> "From now on, `db` refers to `collegeDB`."

So when we write:

```
db.students
```

MongoDB interprets it as:

```
collegeDB
   ↓
students
```

## PHASE 3 — CREATE COLLECTION

We can explicitly create:

```js
db.createCollection("students")
```

Then:

```js
show collections
```

You should see:

```

```

Now our structure is:

```
MongoDB Server
      ↓
  collegeDB
      ↓
  students
      ↓
  documents
```

### But remember something important

We don't necessarily have to explicitly create the collection.

If we instead did:

```js
db.students.insertOne({
    name: "Rahul"
})
```

MongoDB can create the collection as part of the insertion if it doesn't already exist.

So:

```
createCollection()
```

and:

```
insertOne()
```

are not the same operation.

## PHASE 21 — NESTED UPDATE

Suppose Rahul moves from Jalandhar to Delhi.

We don't want to replace the whole address.

We want:

```
address.city
```

only.

Use:

```js
db.students.updateOne(
    {
        name: "Rahul"
    },
    {
        $set: {
            "address.city": "Delhi"
        }
    }
)
```

This is important.

Compare:

**Safe targeted update**

```js
{
    $set: {
        "address.city": "Delhi"
    }
}
```

with:

**Potentially destructive replacement of the embedded object**

```js
{
    $set: {
        address: {
            city: "Delhi"
        }
    }
}
```

The second form replaces the `address` value with the new object, so fields such as `state` could disappear.

🔥 This is exactly why understanding the document structure matters.

## ⚠️ PHASE 23 — THE DANGEROUS DELETE

Imagine you accidentally write:

```js
db.students.deleteMany({})
```

What does `{}` mean?

```
NO FILTER
```

Therefore:

```
deleteMany({})
     ↓
ALL DOCUMENTS
```

🔥 Never casually execute destructive commands.

The safe mental procedure is:

```
1. Write the filter.
2. Run find(filter).
3. Inspect the results.
4. Only then update/delete.
```

For example:

```js
db.students.find({
    branch: "CSE"
})
```

If the result is exactly what you expect:

```js
db.students.deleteMany({
    branch: "CSE"
})
```

That habit will save you from disasters.

## PHASE 25 — WHEN WOULD WE REFERENCE?

Now imagine:

```
University
   ↓
Courses
```

A course could be associated with thousands of students.

Instead of putting huge student lists inside every course document, we may use references.

For example:

```json
{
    "_id": "CSE101",
    "name": "Database Systems"
}
```

Student:

```json
{
    "name": "Rahul",
    "enrolledCourseIds": [
        "CSE101",
        "CSE205"
    ]
}
```

Now the documents refer to other documents.

That's:

```
REFERENCING
```

### 🧠 THE DECISION

When designing MongoDB data:

Ask:

```
Are these pieces of data
usually accessed together?
        │
       YES
        ↓
   Consider embedding
```

But:

```
Is the related data huge,
unbounded, independently managed,
or shared heavily?
        │
       YES
        ↓
   Consider referencing
```

This is not an absolute law. Workload and access patterns determine the design.

## PHASE 29 — NOW WE TEST PERFORMANCE

This is where the practical becomes query optimization.

Run:

```js
db.students.find({
    branch: "CSE"
}).explain("executionStats")
```

> MongoDB's `executionStats` verbosity executes the winning plan and reports statistics such as `nReturned`, `totalKeysExamined`, `totalDocsExamined`, and execution time.

### 🔎 WHAT ARE WE LOOKING FOR?

Suppose we see:

```
COLLSCAN
```

Think:

> MongoDB scanned the collection.

Conceptually:

```
Document 1 → check
Document 2 → check
Document 3 → check
...
Document 10,000,000 → check
```

Not necessarily disastrous for every query, but potentially expensive at scale.

> MongoDB's documentation describes `COLLSCAN` as a collection scan and `IXSCAN` as an index scan.

---

## PHASE 30 — AFTER INDEXING

Suppose we have:

```js
db.students.createIndex({
    branch: 1
})
```

Then run:

```js
db.students.find({
    branch: "CSE"
}).explain("executionStats")
```

The winning plan may now include:

```
IXSCAN
```

Potentially with:

```
FETCH
```

depending on the query and index.

Conceptually:

**Before**

```
COLLECTION
   ↓
COLLSCAN
   ↓
many documents examined
```

**After**

```
INDEX
   ↓
IXSCAN
   ↓
relevant keys
   ↓
FETCH
   ↓
documents
```

> MongoDB's explain documentation specifically identifies `COLLSCAN` and `IXSCAN` in execution plans and describes how index use can reduce unnecessary document scanning.

## PHASE 31 — READ THE NUMBERS

Suppose you see:

```
nReturned: 5

totalDocsExamined: 100000

totalKeysExamined: 0
```

That should make you think:

> "I'm returning only 5 documents but examining 100,000 documents."

Potentially inefficient.

Now suppose after indexing:

```
nReturned: 5

totalDocsExamined: 5

totalKeysExamined: 5
```

Much more targeted.

Don't obsess over exact numbers in tiny datasets, though. A small collection may execute quickly even without an index.

The important learning is:

```
How much work
did MongoDB perform
to produce the result?
```

## PHASE 32 — COVERED QUERY

Now imagine:

```js
db.students.createIndex({
    email: 1,
    name: 1
})
```

And:

```js
db.students.find(
    {
        email: "rahul@gmail.com"
    },
    {
        name: 1,
        _id: 0
    }
)
```

The index contains:

```
email
name
```

The query needs:

```
email
name
```

and explicitly excludes `_id`.

So MongoDB may be able to satisfy the query using only the index.

Conceptually:

```
                 NORMAL
                   ↓
INDEX → FETCH DOCUMENT → RESULT


                 COVERED
                   ↓
INDEX → RESULT
```

> MongoDB describes a covered query as one where the index can both match the query and return the required results without examining collection documents; the explain plan has an `IXSCAN` not descended from a `FETCH`.

## ⚔️ PRACTICAL GOLDEN RULES

### Rule 1

Always know which database you're currently using.

```js
db
```

### Rule 2

Before modifying data, inspect the filter.

```js
db.students.find({
    ...
})
```

Then update/delete.

### Rule 3

Don't confuse filtering and projection.

```js
find(
    FILTER,
    PROJECTION
)
```

### Rule 4

Don't confuse `$set` with replacing an embedded object.

```js
$set: {
    "address.city": "Delhi"
}
```

targets one nested field.

### Rule 5

Don't create indexes blindly.

> Indexes improve suitable reads but consume resources and require maintenance for writes.

### Rule 6

Use `explain()` to investigate query execution.

Not:

> "I think this query is fast."

But:

> "Let's see what plan MongoDB actually used."

> MongoDB explicitly recommends `explain()` for understanding query plans, index usage, and documents/index keys examined.

---

## 🧠 THE ONE QUESTION THAT CONNECTS EVERYTHING

Imagine I ask:

> "Why did we create an index?"

You shouldn't answer:

> "Because indexes make queries fast."

That's incomplete.

The impressive answer is:

> "We create an index based on common query patterns so MongoDB can locate relevant data more efficiently instead of unnecessarily scanning large portions of a collection. We can use `explain("executionStats")` to inspect the selected execution plan and metrics such as documents examined and index keys examined."

That's the difference between:

```
MEMORIZING MONGODB
```

and:

```
UNDERSTANDING MONGODB
```

### STEP 4 — SHOULD WE EMBED ALL STUDENTS IN COURSE?

Could we write:

```
   ↓
```

### STEP 5 — ENROLLMENT COLLECTION

We can model the relationship separately:

```js

    enrolledAt: new Date()
}
```

Now:

```
   ↓

   ↓
```

### STEP 6 — WHY THIS IS POWERFUL

Enrollment itself has information:

```

course
semester
grade
date
status
```

So enrollment isn't merely a relationship.

It's an entity containing relationship-specific data.

That's a strong reason to give it its own collection.

### STEP 7 — CREATE ENROLLMENT

```js
db.enrollments.insertOne({
    studentId: "STU001",
    courseId: "CSE401",
    semester: "Fall 2026",

    enrolledAt: new Date()
})
```

### STEP 8 — FIND COURSES FOR A STUDENT

```js
db.enrollments.find({
    studentId: "STU001"
})
```

We get enrollment records.

Then the application can resolve the referenced courses.

This is the conceptual difference:

```
Embedding:
Student document already contains course information.

Referencing:
Student/enrollment document points to course data.
```

### STEP 9 — FIND STUDENTS IN A COURSE

```js
db.enrollments.find({
    courseId: "CSE401"
})
```

Again, references allow us to model the many-to-many relationship without forcing all relationship data into one enormous document.

> MongoDB provides aggregation stages such as `$lookup` for querying normalized data across collections.

### STEP 10 — UPDATE GRADE

Beautiful example of why enrollment deserves its own document.

What queries happen frequently?

Therefore:

and:


Potentially, if we commonly query by both:

```js

```

Again:

> Indexes follow workload.

Notice something.


Why?

Because:

```

usually retrieved with customer information,

```

> Embedding is often suitable for related data that is queried together.

### STEP 2 — RESTAURANT

```json

```

```json
    "name": "Paneer Tikka",

    "price": 220,

    "available": true
}
```

Now we have a reference:

```
restaurantId
```

because menu items belong to restaurants and may be independently queried.

### STEP 4 — ORDER

Now things become interesting.

Suppose Rahul orders:

```
Paneer Tikka × 2
Biryani × 1
```

Should we simply store:

```json
{
    "itemIds": [
        "ITEM001",
        "ITEM002"
    ]
}
```

Maybe.

But there's a major issue.

What if the menu price changes tomorrow?

Suppose:

```

Tomorrow:
Paneer Tikka = ₹280
```

An old order should still say:

```
Paneer Tikka
₹220
quantity 2
```

not suddenly become ₹280.

So the order should store the relevant purchase-time information.

### STEP 5 — EMBED ORDER ITEMS

We can design:

```js
{
    _id: "ORD001",

    customerId: "CUS001",

    restaurantId: "REST001",

    items: [
        {
            itemId: "ITEM001",
            name: "Paneer Tikka",
            price: 220,
            quantity: 2
        },

        {
            itemId: "ITEM002",
            name: "Chicken Biryani",
            price: 280,
            quantity: 1
        }
    ],

    total: 720,

    status: "PLACED",

    orderedAt: new Date()
}
```

🔥 This is a hybrid design.

We reference:

```
customerId
restaurantId
```

but embed:

```
order items
```

inside the order.

### WHY?

Because an order is a historical record.

We want:

```
Order
 ↓
exact items
 ↓
exact prices
 ↓
exact quantities
```

at the time of purchase.

This is a classic case where strategic denormalization/embedding can preserve the data needed by the order itself.

> MongoDB's modeling guidance emphasizes considering how data is queried together and whether duplicated data changes frequently before choosing embedding versus references.

## 🧠 THE GOLDEN DECISION TREE

When an exam gives you a modeling problem, think:

```
             RELATED DATA?
                  │
                  ↓
       Is it normally accessed
             together?
            /        \
          YES         NO
           │           │
           ↓           ↓
      Consider       Consider
      EMBEDDING      REFERENCE
           │
           ↓
     Does it grow
      without bound?
       /       \
     YES       NO
      │         │
      ↓         ↓
 REFERENCE   EMBEDDING
```

Then consider:

```
High cardinality?
Frequent independent updates?
Shared data?
Complex many-to-many?
Independent existence?
```

If yes, referencing becomes more attractive.

If:

```
Contains/has-a?
Queried together?
Updated together?
Bounded growth?
```

embedding becomes attractive.

This is a guideline, not a rigid law.

## 🔥 THE BIGGER LESSON — EMBEDDING + REFERENCING CAN COEXIST

This is something I really want you to understand.

A real MongoDB application doesn't have to be:

```

```

or:

```
ONLY REFERENCING
```

It can be:

```
Customer
 ├── addresses[]          ← embedded
 │

Order
 ├── customerId           ← reference
 ├── restaurantId         ← reference
 │
 └── items[]              ← embedded
```

This is called a **hybrid approach** conceptually.

And often that's exactly what good schema design looks like.

## ⚡ SCENARIO COMPARISON — WHAT IF WE USED THE WRONG MODEL?

This is where viva questions become interesting.

### E-commerce

If we put millions of reviews directly inside a product document:

```
Product
 └── reviews[]
       ↓
    10 million
```

🚨 Problem:

> The embedded data can grow without bounds.

Referencing becomes more appropriate for such high-cardinality/unbounded data.

### University

If we put every enrolled student inside every course:

```
Course
 └── students[]
```

and every student inside every course:

```
Student
 └── courses[]
```

you now have duplicated relationship state that can become difficult to maintain.

A dedicated enrollment/reference model can be cleaner for complex many-to-many relationships.

### Food delivery

If an order only stores:

```json
{
    "itemId": "ITEM001"
}
```

and always looks up the current menu item price:

```
Today's price
```

you risk losing the historical purchase price.

That's why storing relevant purchase-time item information inside the order can be a sensible denormalization strategy.
