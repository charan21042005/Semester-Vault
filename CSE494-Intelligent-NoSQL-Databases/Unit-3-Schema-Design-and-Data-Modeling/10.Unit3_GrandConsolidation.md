# PART A — COMPLETE REVISION OF PART 1 → PART 9

## 1️⃣ Schema-less / Flexible Schema

### What is a schema?

A schema describes:

```
What fields exist?
What types do they have?
What structure do they follow?
What rules apply?
```

Traditional relational databases generally enforce a predefined table structure.

MongoDB instead gives us a flexible document model.

Example:

```json
{
    "name": "Rahul",
    "age": 21,
    "branch": "CSE"
}
```

Another document could contain:

```json
{
    "name": "Priya",
    "age": 20,
    "branch": "ECE",
    "scholarship": true
}
```

MongoDB doesn't require every document to have exactly the same fields by default.

But:

```
Flexible schema
       ≠
No schema
       ≠
Random data
       ≠
No validation
```

The better exam statement is:

> MongoDB uses a flexible schema model in which documents in the same collection do not have to follow an identical structure by default. Schema validation can be used when stronger consistency is required.

> MongoDB explicitly describes schema validation as useful when an application has a defined structure, while noting that validation itself can remain flexible and need not cover every field.

**Golden line:**

> MongoDB gives you freedom from a rigid schema, not freedom from good schema design.

## 2️⃣ Workload & Access Patterns

This is probably the most important conceptual shift in the entire unit.

A beginner asks:

> "What entities do I have?"

A MongoDB designer asks:

> "What does my application frequently do with this data?"

Suppose we're designing Amazon-like e-commerce.

Entities:

```
Customer
Product
Order
Payment
Address
Review
```

That's not enough.

We need to ask:

```
What does the user frequently read?

What does the application frequently update?

Which data is retrieved together?

Which data changes independently?

How large can each relationship become?
```

> MongoDB's schema-design process explicitly starts with identifying the application's workload and then mapping relationships.

### Example

Suppose:

```
Customer → Address
```

Application usually displays:

```
Customer name
+
Address
```

together.

Embedding may be ideal:

```json
{
    "name": "Rahul",
    "address": {
        "city": "Amritsar",
        "state": "Punjab"
    }
}
```

Why?

One document gives us everything.

## 3️⃣ Embedding vs Referencing

This is the heart of MongoDB data modeling.

### EMBEDDING

Put related data inside the same document.

```json
{
    "name": "Rahul",

    "address": {
        "city": "Amritsar",
        "pincode": 143001
    }
}
```

> MongoDB describes embedded data as related data stored in a single document structure, allowing related information to be retrieved in one database operation and updated atomically at the document level.

Think:

```
PARENT
  │
  ├── child
  ├── child
  └── child
```

### REFERENCING

Store related data separately and connect it using IDs.

**`students`**

```json
{
    "_id": 101,
    "name": "Rahul",
    "addressId": 501
}
```

**`addresses`**

```json
{
    "_id": 501,
    "city": "Amritsar",
    "pincode": 143001
}
```

> MongoDB references are links between documents stored separately, and applications resolve those references when related data is needed.

## 4️⃣ One-to-One

One entity relates to exactly one other entity.

```
User ───── Profile
```

Examples:

```
Student ─ Passport
Employee ─ Locker
Building ─ Address
User ─ Profile
```

### Embedded:

```json
{
    "_id": 101,
    "name": "Rahul",

    "passport": {
        "number": "P12345",
        "country": "India"
    }
}
```

Good when passport information is usually retrieved with the student.

> MongoDB specifically demonstrates embedded 1:1 relationships as a way to retrieve connected information in a single read.

### Referenced:

**`students`**

```json
{
    "_id": 101,
    "name": "Rahul",
    "passportId": 501
}
```

**`passports`**

```json
{
    "_id": 501,
    "number": "P12345",
    "country": "India"
}
```

Use reference when the related entity has a sufficiently independent lifecycle/access pattern.

---

## 5️⃣ One-to-Many

One parent has many children.

```
Department
     │
     ├── Student
     ├── Student
     ├── Student
     └── Student
```

Examples:

```
Author → Books
Customer → Orders
Course → Lessons
Department → Students
Country → Cities
```

### Embedded 1:M

```json
{
    "_id": 1,
    "name": "India",

    "cities": [
        "Delhi",
        "Mumbai",
        "Amritsar"
    ]
}
```

Great when the "many" side is:

```
reasonably bounded
usually viewed with parent
part of parent's lifecycle
```

> MongoDB's embedded 1:M examples use this exact idea: related child information is retrieved with the parent in a single operation.

### Referenced 1:M

For something like:

```
Customer → Orders
```

we don't want:

```js
{
    customerId: 101,

    orders: [
        1001,
        1002,
        1003,
        ...
        999999
    ]
}
```

That could become an unbounded array.

Instead:

**`customers`**

```json
{
    "_id": 101,
    "name": "Rahul"
}
```

**`orders`**

```json
{
    "_id": 1001,
    "customerId": 101,
    "total": 2500
}
```

Now orders can grow independently.

## 6️⃣ Many-to-Many

Now things become interesting.

```
Student ←────→ Course
```

One student can take many courses.

One course can have many students.

### Option 1 — Embedded

Possible for small/bounded cases.

```json
{
    "_id": 101,
    "name": "Rahul",

    "courses": [
        {
            "id": 501,
            "name": "MongoDB"
        },
        {
            "id": 502,
            "name": "Cloud Computing"
        }
    ]
}
```

But now course information might be duplicated across many students.

### Option 2 — References

```json
{
    "_id": 101,
    "name": "Rahul",

    "courseIds": [501, 502]
}
```

and:

```json
{
    "_id": 501,
    "name": "MongoDB"
}
```

Better when the entities are independently queried or maintained.

> MongoDB recommends considering references for complex many-to-many relationships and when related entities are queried independently.

## 7️⃣ Relationship Collection

This is where our university example became powerful.

```
students
courses
enrollments
```

**Student:**

```json
{
    "_id": 101,
    "name": "Rahul"
}
```

**Course:**

```json
{
    "_id": 501,
    "name": "MongoDB"
}
```

**Relationship:**

```json
{
    "_id": 10001,
    "studentId": 101,
    "courseId": 501,
    "semester": 5,
    "grade": "A",
    "attendance": 92
}
```

Look at this.

The relationship itself contains:

```
semester
grade
attendance
```

🔥 Therefore the relationship is no longer just:

```
Student ↔ Course
```

It has its own data.

That's a strong reason to model the relationship separately.

## 8️⃣ Best Practices

Let's compress Part 7.

### Rule 1 — Design around workload

```
Application
     ↓
Queries + updates
     ↓
Schema
```

Not:

```
Entities
 ↓
Random collections
```

> MongoDB recommends designing based on application operations and how related entities are actually used.

### Rule 2 — Embed when

```
read together
bounded
same lifecycle
updated together
contains relationship
```

### Rule 3 — Reference when

```
high cardinality
unbounded growth
independent access
frequent independent updates
complex relationships
duplication becomes expensive
```

> MongoDB's current best-practices guidance gives essentially this same split.

### Rule 4 — Avoid unbounded arrays

Bad:

```js
{
    userId: 101,

    followers: [
        // potentially millions
    ]
}
```

Potentially enormous document.

Better:

```
relationships collection
```

with:

```json
{
    "followerId": 201,
    "followingId": 101
}
```

### Rule 5 — Remember 16 MiB

> MongoDB documents must be smaller than 16 MiB.

Therefore:

```
Embedding
   ↓
Document grows
   ↓
Could become too large
   ↓
Consider referencing
```

### Rule 6 — Duplication isn't automatically bad

This is a HUGE MongoDB mindset shift.

Traditional normalization says:

> Avoid duplication.

MongoDB says:

> Duplication can be intentional if it improves the application's workload.

For example:

```
Order
 └── priceAtPurchase
```

We can store:

```json
{
    "productId": 501,
    "productName": "Laptop",
    "priceAtPurchase": 75000
}
```

Even if current product price later becomes:

```
80000
```

the historical order should still say:

```
75000
```

That's intentional duplication.

> MongoDB's guidance explicitly says duplication can improve reads, but frequently changing duplicated data increases maintenance cost.

## 9️⃣ Schema Validation

Flexible schema doesn't mean uncontrolled schema.

We can define:

```js
validator: {
    $jsonSchema: {
        // ...
    }
}
```

For example:

```js
required: [
    "name",
    "age",
    "cgpa"
]
```

and:

```js
age: {
    bsonType: "int",
    minimum: 17,
    maximum: 30
}
```

and:

```js
branch: {
    enum: ["CSE", "ECE", "EEE", "MECH"]
}
```

So:

```
Flexible schema
       +
Validation
       ↓
Flexibility + data quality
```

# PART B — THE EMBEDDING VS REFERENCING DECISION MATRIX 🔥

This is probably the most useful table in the entire unit.

| Situation                                        | Prefer      |
|-------------------------------------------------------|----------------|
| Data usually read together                               | Embed          |
| Small bounded child data                                    | Embed          |
| Same lifecycle                                                | Embed          |
| Updated together                                                | Embed          |
| Contains relationship                                             | Embed          |
| Need single-document atomic update                                  | Embed          |
| Child has high cardinality                                             | Reference       |
| Child grows without bound                                                | Reference       |
| Child queried independently                                                | Reference       |
| Child changes frequently independently                                       | Reference       |
| Complex many-to-many                                                            | Reference       |
| Duplication becomes expensive                                                     | Reference       |
| Data has independent lifecycle                                                       | Reference       |

These aren't absolute laws.

They're decision guidelines based on workload. MongoDB's documentation emphasizes that the correct choice depends on application queries and access patterns.

```

```

```
DEPARTMENT
------------------
department_id

```

SQL:

```
STUDENT.department_id
        ↓
```

MongoDB could be:

**`students`**


```json
{
    "_id": 10,
    "name": "CSE"
```

If department information needed with the student is small and stable:


```
SQL mindset:
```

Let's pretend you're asked:

Application needs:


Application frequently needs:

```
1. Get student profile
2. Find student's department

7. View course enrollment
```

### Step 3 — Entities

```
Student

Course
Enrollment
```

### Step 4 — Relationships

```
Department 1 ─── M Student

Student M ─── M Course

Student + Course
      │
      ▼
Enrollment
```

### Step 5 — Design

**`departments`**

```json
{
    "_id": 10,
    "name": "Computer Science"
}
```

**`students`**

```json
{
    "_id": 101,
    "name": "Rahul",
    "departmentId": 10
}
```

**`courses`**

```json
{
    "_id": 501,
    "name": "MongoDB",
    "credits": 4
}
```

**`enrollments`**

```json
{
    "_id": 10001,
    "studentId": 101,
    "courseId": 501,
    "semester": 5,
    "grade": "A",
    "attendance": 92
}
```

### Step 6 — Indexes

Because we frequently search:

```
students.departmentId
enrollments.studentId
enrollments.courseId
```

we create appropriate indexes.

```js
db.students.createIndex({ departmentId: 1 })

db.enrollments.createIndex({ studentId: 1 })

db.enrollments.createIndex({ courseId: 1 })
```

Now our design becomes:

```
University
│
├── departments
│
├── students
│     └── departmentId
│
├── courses
│
└── enrollments
      ├── studentId
      └── courseId
```

🔥 This is actual schema design.

# PART G — 30 BEST UNIT III VIVA QUESTIONS 🔥

### 1. What is schema-less architecture?

> MongoDB is better described as schema-flexible; documents need not have an identical structure by default.

### 2. Does MongoDB have schemas?

> Yes, MongoDB allows flexible schemas and can enforce validation rules when needed.

### 3. What is data modeling?

> Organizing data, relationships, and document structures to efficiently support application requirements and workloads.

### 4. What is an access pattern?

> The way an application commonly reads, writes, updates, or queries data.

### 5. Why are access patterns important?

> Because MongoDB schema design should be optimized around how the application uses data.

### 6. What is embedding?

> Storing related data inside the same MongoDB document.

### 7. What is referencing?

> Storing related data separately and connecting documents using references such as IDs.

### 8. What is the main advantage of embedding?

> Related data can often be retrieved in a single operation and updated atomically within the document.

### 9. When should you reference?

> When related data has high cardinality, grows without bounds, is independently queried/updated, or complex relationships make embedding unsuitable.

### 10. What is a 1:1 relationship?

> One entity is related to one entity.

### 11. Give examples.

```
User → Profile
Student → Passport
Building → Address
```

### 12. What is 1:M?

> One parent is associated with many children.

### 13. Example?

```
Department → Students
Customer → Orders
```

### 14. What is M:M?

> Many records on one side can relate to many records on the other.

Example:

```
Student ↔ Course
```

### 15. Why are M:M relationships difficult?

> Because relationships can become large/complex and the relationship itself may contain data.

### 16. What is a relationship document?

> A separate document representing the connection between two entities.

Example:

```json
{
    "studentId": 101,
    "courseId": 501,
    "grade": "A"
}
```

### 17. What is an unbounded array?

> An array that can grow indefinitely or without a practical upper limit.

### 18. Why are unbounded arrays dangerous?

> They can cause large documents, memory/performance issues, and potentially hit MongoDB's 16 MiB document limit.

### 19. Is duplication always bad?

> No.

Intentional duplication can improve read performance and preserve historical values.

### 20. What is denormalization?

> Structuring data so related information is duplicated or combined to optimize application access.

### 21. What is normalization?

> Separating data into distinct structures to reduce duplication and maintain independent entities.

### 22. What is single-document atomicity?

> A write to one MongoDB document is atomic; either the document update succeeds as a whole or doesn't.

### 23. What is schema validation?

> Rules used to enforce desired structure and content constraints on documents.

### 24. What is `$jsonSchema`?

> MongoDB's JSON Schema-based validation mechanism.

### 25. What does `required` mean?

> The listed field must exist.

### 26. What does `bsonType` mean?

> The required BSON type of a field/document.

### 27. What does `enum` do?

> Restricts a field to allowed values.

### 28. `validationLevel` vs `validationAction`?

```
validationLevel
→ how validation applies

validationAction
→ what happens when validation fails
```

### 29. Does validation guarantee uniqueness?

> No.

Use a unique index.

### 30. What is the golden rule of MongoDB schema design?

🔥

> Design your schema around your application's access patterns and workload.

# PART H — COMMON EXAM TRAPS 🚨

### ❌ "MongoDB has no schema."

Say:

> MongoDB uses a flexible schema and supports optional schema validation.

### ❌ "Always embed because MongoDB is document-oriented."

Wrong.

Use workload-based reasoning.

### ❌ "Always normalize like SQL."

Wrong.

MongoDB often intentionally denormalizes.

### ❌ "Always reference many-to-many."

Not necessarily.

Depends on size, access pattern, duplication, and whether the relationship has its own attributes.

### ❌ "More collections = bad MongoDB design."

Not automatically.

References and separate collections can be perfectly appropriate.

### ❌ "Embedding means no duplication."

Not necessarily.

Embedded data can itself represent intentional denormalization.

### ❌ "Schema validation makes MongoDB relational."

No.

You can enforce data-quality rules without turning MongoDB into a relational database.

### ❌ "Unique is part of `$jsonSchema`."

For MongoDB uniqueness, use a unique index.

# PART I — WHAT TO WRITE VS WHAT NOT TO WRITE

This is your exam-writing strategy.

**Question:**

> Explain embedding and referencing in MongoDB.

**Good answer:**

> Embedding stores related data inside the same MongoDB document. It is suitable when related data is commonly accessed together, bounded in size, and shares a lifecycle. It reduces the number of read operations and supports atomic updates at the document level.
>
> Referencing stores related data in separate documents or collections and links them using references such as IDs. It is suitable when related data is large, independently accessed or updated, grows without bounds, or involves complex relationships.

That's enough for a theoretical answer.

Then example.

**Don't write:**

> MongoDB embedding is always faster and referencing is always slower.

❌ Absolute claims are dangerous.

## 🧠 THE 10-LINE UNIT III REVISION

If you're revising this unit 5 minutes before the exam, remember this:

```
1. MongoDB is schema-flexible, not structure-free.

2. Design around application workload and access patterns.

3. Related data can be embedded or referenced.

4. Embed when data is commonly accessed together and reasonably bounded.

5. Reference when data is independent, high-cardinality, unbounded,
   frequently changing, or involved in complex relationships.

6. 1:1, 1:M and M:M describe cardinality, not automatically storage strategy.

7. M:M may use references or a relationship collection,
   especially when the relationship has its own attributes.

8. Avoid unbounded arrays and remember the 16 MiB document limit.

9. Duplication can be intentional when it improves reads or preserves
   historical information.

10. Use schema validation for data quality and indexes for query
    performance/uniqueness.
```
