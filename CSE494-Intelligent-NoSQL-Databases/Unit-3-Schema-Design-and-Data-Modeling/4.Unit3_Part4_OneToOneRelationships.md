# 🧠 UNIT III — PART 4: ONE-TO-ONE RELATIONSHIPS

Before jumping into MongoDB, let's understand what one-to-one actually means.

---

## 1. First: What is a relationship?

Suppose we have two types of data:

```
STUDENT
   |
   |
   ?
   |
   ↓
PASSPORT
```

We are asking:

> How many passport records can belong to one student?

And:

> How many students can one passport belong to?

If the answer is:

```
1 Student → 1 Passport
1 Passport → 1 Student
```

then we have a:

```
One-to-One Relationship
```

We commonly write:

```
Student 1 ───────── 1 Passport
```

or:

```
A 1 ↔ 1 B
```

---

## 2. Real-world examples

Think of relationships around you.

### Example 1 — Student ↔ Passport

Normally:

```
One student → one passport
One passport → one student
```

So:

```
Student 1 ↔ 1 Passport
```

### Example 2 — User ↔ Profile

Suppose an application has:

```
User
 └── Profile
```

One user has one profile.

```
User 1 ↔ 1 Profile
```

### Example 3 — Employee ↔ Locker

Imagine a company gives every employee one locker.

```
Employee 1 ↔ 1 Locker
```

### Example 4 — Building ↔ Address

Suppose each building has one address record.

```
Building 1 ↔ 1 Address
```

> MongoDB's own documentation uses examples such as user account ↔ email address and building ↔ address for one-to-one modeling.

---

## 3. Now the important MongoDB question

Suppose we have:

```
Student
Passport
```

MongoDB gives us two major ways to represent their relationship:

### Option A

Put Passport inside Student.

```
Student
 └── Passport
```

This is:

```
EMBEDDING
```

### Option B

Keep Student and Passport separately and connect them using an ID.

```
Student ─────→ Passport
```

This is:

```
REFERENCING
```

And this is exactly the same embedding-vs-referencing decision we learned in Part 3. MongoDB's data-modeling guidance says relationship design should be based on how the application queries and uses the related data.

---

## 4. One-to-One using EMBEDDING

Let's start with the simplest approach.

Suppose our student is:

```
Rahul
```

and his passport information is:

```
Passport Number: P1234567
Country: India
```

Instead of creating two documents, we can put the passport inside the student document.

### MongoDB document

```json
{
    "_id": 101,
    "name": "Rahul",
    "branch": "CSE",

    "passport": {
        "number": "P1234567",
        "country": "India",
        "issueYear": 2025
    }
}
```

Look carefully.

The entire thing is one document.

Inside that document:

```
student
│
├── _id
├── name
├── branch
│
└── passport
     ├── number
     ├── country
     └── issueYear
```

The passport is an embedded document.

---

## 5. Why is this useful?

Imagine the application displays:

```
Student Profile

Name: Rahul
Branch: CSE

Passport Number: P1234567
Country: India
Issue Year: 2025
```

The application always wants:

```
Student + Passport
```

together.

So why separate them?

Instead:

```
ONE DOCUMENT
       ↓
Student
   +
Passport
```

MongoDB can retrieve all of it in a single read.

This is one of the major advantages of embedding: related data can be retrieved together in one database operation.

---

## 6. Think about it like a physical folder 📁

Imagine Rahul has a physical student file:

```
RAHUL'S FILE
│
├── Student Information
│
└── Passport Information
```

Everything related to Rahul is in one folder.

That's essentially what embedding does.

```
Student Document
       │
       ├── Student Data
       │
       └── Passport Data
```

---

## 7. Querying an embedded one-to-one relationship

Now suppose we want to find Rahul using his passport number.

We can use dot notation:

```js
db.students.findOne({
    "passport.number": "P1234567"
})
```

MongoDB looks inside:

```
passport
   ↓
number
   ↓
P1234567
```

and returns Rahul's document.

> MongoDB supports dot notation for querying fields inside embedded documents.

---

## 8. Projection with embedded data

Suppose we only want:

```
name
passport number
```

We can do:

```js
db.students.findOne(
    { "passport.number": "P1234567" },
    {
        name: 1,
        "passport.number": 1,
        _id: 0
    }
)
```

Result:

```json
{
    "name": "Rahul",
    "passport": {
        "number": "P1234567"
    }
}
```

Notice:

```
"passport.number"
```

is again using dot notation.

---

## 9. When does EMBEDDING make sense for 1:1?

Here's where the actual data modeling intelligence begins.

Don't think:

> "It's 1:1, therefore embed."

❌ Wrong.

Instead ask:

> Do these two pieces of data usually belong together?

For example:

```
Student + Passport
```

If the application frequently retrieves:

```
student information
+
passport information
```

together, embedding is attractive.

> MongoDB recommends considering embedding when related data is commonly queried together and remains reasonably bounded.

---

## 10. Another example — User + Settings

Imagine:

```
User
```

has:

```
theme
language
notifications
timezone
```

We could store:

```json
{
    "_id": 1001,
    "username": "patty",

    "settings": {
        "theme": "dark",
        "language": "English",
        "notifications": true,
        "timezone": "IST"
    }
}
```

This is a beautiful candidate for embedding.

Why?

Because:

```
User
+
Settings
```

are closely related.

And settings are:

```
relatively small
bounded
naturally associated with the user
often retrieved in the context of the user
```

---

## 11. Single-document atomicity

Here's another important benefit.

Suppose:

```
Student
 └── Passport
```

is one document.

We can update the passport information within that document.

For example:

```js
db.students.updateOne(
    { _id: 101 },
    {
        $set: {
            "passport.country": "India"
        }
    }
)
```

The update occurs on the single document.

> MongoDB writes are atomic at the single-document level.

So embedding can be very convenient when related information needs to be maintained together.

---

## 12. But now let's flip the situation

Suppose passport information is a separate entity.

Maybe our application has:

```
Students
Passports
Passport verification system
Government verification
Passport renewal system
```

And passport information is frequently accessed independently.

Then maybe we don't want:

```
Student
 └── Passport
```

Instead:

```
Students collection
        │
        │ passportId
        ↓
Passports collection
```

This is:

```
REFERENCING
```

---

## 13. One-to-One using REFERENCING

Let's create two collections.

**`students`**

```json
{
    "_id": 101,
    "name": "Rahul",
    "branch": "CSE",
    "passportId": 501
}
```

**`passports`**

```json
{
    "_id": 501,
    "number": "P1234567",
    "country": "India",
    "issueYear": 2025
}
```

Now look at the relationship:

```
students
┌──────────────────────┐
│ _id: 101             │
│ name: Rahul          │
│ passportId: 501 ─────────────┐
└──────────────────────┘       │
                               ↓
                       ┌──────────────────┐
                       │ passports        │
                       │ _id: 501         │
                       │ number:P1234567  │
                       │ country:India    │
                       └──────────────────┘
```

The:

```
passportId: 501
```

is a reference to the passport document.

> MongoDB's manual-reference approach commonly stores the referenced document's `_id` in another document.

---

## 14. Important: MongoDB does NOT automatically join this

This is a very important beginner concept.

We have:

```
Student
passportId: 501
```

and:

```
Passport
_id: 501
```

MongoDB doesn't magically say:

> "Oh, these IDs match, I'll automatically combine them."

No.

Your application can perform another query, or MongoDB's aggregation framework can use `$lookup` for suitable same-database joins.

Conceptually:

```
Query Student
      ↓
get passportId = 501
      ↓
Query Passport
      ↓
get passport 501
```

---

## 15. Practical reference example

### Insert student

```js
db.students.insertOne({
    _id: 101,
    name: "Rahul",
    branch: "CSE",
    passportId: 501
})
```

### Insert passport

```js
db.passports.insertOne({
    _id: 501,
    number: "P1234567",
    country: "India",
    issueYear: 2025
})
```

Now:

```
Student
   |
   | passportId = 501
   ↓
Passport
   |
   |_id = 501
```

---

## 16. Retrieving the passport

First:

```js
db.students.findOne({ _id: 101 })
```

We get:

```json
{
    "_id": 101,
    "name": "Rahul",
    "branch": "CSE",
    "passportId": 501
}
```

Then:

```js
db.passports.findOne({ _id: 501 })
```

Result:

```json
{
    "_id": 501,
    "number": "P1234567",
    "country": "India",
    "issueYear": 2025
}
```

That's the basic idea of referencing.

---

## 17. So why would we reference a 1:1 relationship?

This is the important question.

Suppose:

```
User
```

has:

```
Account
```

But account information:

```
is queried independently
is updated independently
has its own lifecycle
isn't always needed when retrieving the user
```

Then keeping them separately may make sense.

> MongoDB specifically recommends considering references when the related entity is frequently queried independently or changes independently.

---

## 18. Another example — User + Authentication Data

Imagine:

```
User
```

contains:

```
name
email
age
```

while a separate authentication document contains:

```
passwordHash
lastLogin
failedAttempts
MFA settings
```

Conceptually:

```
users
             authentication
┌─────────┐       ┌──────────────────┐
│ _id     │       │ _id              │
│ name    │       │ userId           │
│ email   │──────→│ passwordHash     │
│ age     │       │ lastLogin        │
└─────────┘       │ MFA              │
                  └──────────────────┘
```

The two pieces may have very different:

```
access patterns
update patterns
security requirements
lifecycle
```

So a reference can be more appropriate.

**Important:** this is an architectural example, not a universal rule that authentication data must be referenced.

---

## 19. EMBED vs REFERENCE — the real comparison

Let's put everything together.

| Factor                                 | Embedding                        | Referencing                                   |
|-------------------------------------------|--------------------------------------|---------------------------------------------------|
| Storage                                     | Same document                        | Separate documents                                 |
| Relationship                                  | Nested                               | ID/reference                                       |
| Reads                                           | Usually fewer                        | May require additional lookup                       |
| Related data queried together                     | Excellent                            | Less convenient                                      |
| Independent access                                  | Less ideal                           | Excellent                                            |
| Independent updates                                   | Can be less convenient               | Good                                                  |
| Data duplication                                        | Possible                             | Usually reduced                                       |
| Atomic single-document update                             | Excellent                            | Requires multiple documents if both change             |
| Document growth                                             | Must remain bounded                  | Easier to avoid parent growth                          |
| Complexity                                                    | Simpler                              | More application/query logic                            |

> MongoDB's guidance emphasizes that this isn't a universal winner: schema design should follow the application's workload and query patterns.

---

## 20. 🔥 THE BIGGEST TRAP

This is something I really want you to remember.

Suppose the examiner asks:

> "How do you model a one-to-one relationship in MongoDB?"

Don't immediately answer:

> "Using embedding."

❌ Too simplistic.

**Correct answer:**

> A one-to-one relationship can be modeled using either embedding or referencing. The choice depends on access patterns, whether the related data is commonly queried together, whether it changes independently, document growth, and other workload requirements.

That is the real MongoDB answer.

---

## 21. 1:1 does NOT mean embedding

Think carefully:

**Cardinality**

answers:

> How many?

```
1 : 1
1 : M
M : M
```

Whereas:

**Embedding vs Referencing**

answers:

> How should I store the relationship?

These are two different decisions.

**Cardinality:**

```
Student ── 1:1 ── Passport
```

**Storage strategy:**

Option 1:

```
Student
 └── Passport
```

OR

Option 2:

```
Student ──passportId──→ Passport
```

🔥 This distinction is extremely important.

---

## 22. SQL vs MongoDB — 1:1 relationship

Since you're studying NoSQL, let's connect it to SQL.

In a relational database, we might have:

```
STUDENT
----------------
student_id PK
name
passport_id FK
```

and:

```
PASSPORT
----------------
passport_id PK
number
country
```

A FOREIGN KEY establishes the relationship.

To truly enforce 1:1, relational design typically also needs a uniqueness constraint on the foreign-key side.

MongoDB doesn't force us into this table/foreign-key structure.

We can simply embed:

```json
{
    "_id": 101,
    "name": "Rahul",
    "passport": {
        "number": "P1234567",
        "country": "India"
    }
}
```

or reference:

```json
{
    "_id": 101,
    "name": "Rahul",
    "passportId": 501
}
```

This is one of the major differences in modeling philosophy.

We have:

```
Student

One student has exactly one profile.

The profile contains:

dateOfBirth

If the application almost always displays:

```
Student

we can embed.

    "profile": {

## 24. What if Profile becomes huge?

Suppose profile eventually contains:

```
personal information
documents
medical records
certificates
activity history
preferences
audit information
...
```

Now:

```
Student
   ↓
Huge Profile
```

The document might become unnecessarily large.

Remember:

> MongoDB documents have a 16 MiB size limit.

So blindly embedding everything can become a bad design.

We might instead separate some information:

```
students
profiles
documents
activities
```

and reference them appropriately.

---

## 25. Another critical factor — independent lifecycle

Suppose:

```
Student
```

is deleted.

Does the related information necessarily disappear?

If:

```
Student + Profile
```

always have the same lifecycle, embedding may make sense.

But if:

```
Student
```

and:

```
Profile
```

are managed independently, referencing may make more sense.

So ask:

> Do these pieces of data live and change together?

If yes → embedding becomes attractive.

If no → reference becomes more attractive.

---

## 26. Our 1:1 decision tree 🧠

Whenever you see:

```
A 1 : 1 B
```

don't panic.

Run this mental checklist:

```
             1:1 Relationship
                    │
                    ↓
       Are A and B commonly read together?
              /              \
            YES               NO
             ↓                 ↓
        Consider Embed    Consider Reference
             │                 │
             ↓                 ↓
     Is B small/bounded?   Is B independent?
          /     \             /      \
        YES      NO         YES       NO
         ↓        ↓          ↓         ↓
      EMBED    RECONSIDER  REFERENCE  Analyze
```

This isn't a rigid algorithm.

It's a thinking framework.

---

## 27. The golden 1:1 rule 🔥

Remember this:

> If related data is small, bounded, tightly coupled, and commonly accessed together → embedding is attractive.

And:

> If related data is independently accessed, independently updated, or has a separate lifecycle → referencing is attractive.

> MongoDB's own modeling guidance uses essentially these workload-oriented considerations.

## 28. One-to-One — exam-ready definition

If the question is:

> "What is a one-to-one relationship?"

Write:

> A one-to-one relationship is a relationship in which each document/entity in one collection is associated with at most one document/entity in another collection, and vice versa. In MongoDB, a one-to-one relationship can be modeled using embedded documents or references depending on application access patterns and data characteristics.

That's a strong answer.

## 29. One-to-One — viva questions

### Q1. What is a 1:1 relationship?

> One entity is associated with one corresponding entity.

```
A 1 ↔ 1 B
```

### Q2. Can MongoDB model 1:1 relationships?

> Absolutely.

Using:

```
Embedding
```

or:

```
Referencing
```

### Q3. Is embedding mandatory for 1:1?

> No.

🔥 Important.

### Q4. When would you embed?

When related data:

```
is commonly accessed together
is reasonably small/bounded
belongs naturally to the parent
often changes with the parent
```

### Q5. When would you reference?

When related data:

```
is independently accessed
changes independently
has its own lifecycle
would make the parent too large
is better maintained separately
```

### Q6. What is the main advantage of embedding?

> You can retrieve related data together in a single document read.

### Q7. What is the main disadvantage?

> The parent document can grow, and independent updates/access patterns may make embedding less suitable.

### Q8. What is a manual reference?

> Storing the `_id` of one document inside another document.

Example:

```json
{
    "studentId": 101,
    "passportId": 501
}
```

> MongoDB describes manual references as the simple, common way to connect separate documents.
