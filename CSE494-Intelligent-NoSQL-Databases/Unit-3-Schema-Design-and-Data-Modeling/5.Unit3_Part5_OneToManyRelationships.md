## 1. First, forget MongoDB for a moment

Let's understand the relationship itself.

Suppose we have a:

```
DEPARTMENT
```

and students:

```
Student 1
Student 2
Student 3
Student 4
...
```

A department can have many students.

So:

```
Department 1 ─────────── MANY Students
```

We call this:

```
One-to-Many Relationship
```

Or simply:

```
1 : M
```

where:

```
1 = one
M = many
```

---

## 2. The most basic picture

Imagine:

```
                ┌── Student A
                │
Department ─────┼── Student B
                │
                ├── Student C
                │
                └── Student D
```

One department:

```
Department
```

has many:

```
Students
```

So:

```
Department 1 → N Students
```

## 4. Now the MongoDB problem

Suppose:

```
Customer
   ↓
Orders
```

Customer has:

```
Order 1
Order 2
Order 3
...
```

Where should we store those orders?

We have two major choices:

### Choice A — Embed

```
Customer
 └── orders[]
       ├── Order 1
       ├── Order 2
       └── Order 3
```

### Choice B — Reference

```
Customer
     ↑
     │ customerId
     │
Orders collection
 ├── Order 1
 ├── Order 2
 └── Order 3
```

Again:

> The relationship being 1:M does **NOT** automatically tell us whether to embed or reference.

That decision depends on workload and growth.

---

## 5. ONE-TO-MANY USING EMBEDDING

Let's start with embedding.

Suppose:

```
Customer: Rahul
```

has three orders:

```
Order 101
Order 102
Order 103
```

We can put all three inside the customer document.

```json
{
    "_id": 101,
    "name": "Rahul",

    "orders": [
        {
            "orderId": 1001,
            "product": "Laptop",
            "amount": 70000
        },
        {
            "orderId": 1002,
            "product": "Mouse",
            "amount": 1200
        },
        {
            "orderId": 1003,
            "product": "Keyboard",
            "amount": 2500
        }
    ]
}
```

Look at the structure:

```
Customer
│
├── _id
├── name
│
└── orders[]
      │
      ├── Order 1
      │     ├── orderId
      │     ├── product
      │     └── amount
      │
      ├── Order 2
      │
      └── Order 3
```

This is a **one-to-many embedded model**.

---

## 6. Why is this powerful?

Imagine the application opens:

```
Rahul's Order History
```

and wants:

```
Rahul
+
all his orders
```

With embedding:

```
Customer document
        ↓
   orders array
        ↓
 all orders available
```

One document read can provide everything needed.

That's one of the main reasons MongoDB recommends embedded one-to-many models when the application views the child documents in the context of the parent.

---

## 7. Think of a physical folder again 📁

Imagine Rahul has:

```
RAHUL CUSTOMER FILE
│
├── Customer information
│
├── Order 1
├── Order 2
└── Order 3
```

That's embedding.

Everything belongs to the same logical document.

---

## 8. Practical MongoDB example

Let's insert it.

```js
db.customers.insertOne({
    _id: 101,
    name: "Rahul",

    orders: [
        {
            orderId: 1001,
            product: "Laptop",
            amount: 70000
        },
        {
            orderId: 1002,
            product: "Mouse",
            amount: 1200
        },
        {
            orderId: 1003,
            product: "Keyboard",
            amount: 2500
        }
    ]
})
```

Now:

```js
db.customers.findOne({ _id: 101 })
```

returns the customer and his orders together.

---

## 9. Querying embedded orders

Suppose we want customers who bought a:

```
Laptop
```

We can use dot notation:

```js
db.customers.find({
    "orders.product": "Laptop"
})
```

MongoDB searches inside the array of embedded documents.

Conceptually:

```
orders
   ↓
product
   ↓
Laptop
```

---

## 10. Querying an order amount

Suppose we want customers who have an order above ₹50,000:

```js
db.customers.find({
    "orders.amount": { $gt: 50000 }
})
```

Again:

```
orders[]
   ↓
amount
   ↓
$gt 50000
```

---

## 11. Updating an embedded child

Suppose Order 1002 changes from:

```
Mouse → Wireless Mouse
```

We can update the matching array element using the positional operator.

```js
db.customers.updateOne(
    { _id: 101, "orders.orderId": 1002 },
    {
        $set: {
            "orders.$.product": "Wireless Mouse"
        }
    }
)
```

The important part:

```
orders.$.product
```

Here `$` refers to the matching array element.

So:

```
orders
  ↓
find orderId = 1002
  ↓
$
  ↓
product
```

---

## 12. Adding another child

Suppose Rahul places another order.

We can use `$push`:

```js
db.customers.updateOne(
    { _id: 101 },
    {
        $push: {
            orders: {
                orderId: 1004,
                product: "Monitor",
                amount: 15000
            }
        }
    }
)
```

Now:

```
orders[]
 ├── 1001
 ├── 1002
 ├── 1003
 └── 1004
```

---

## 13. So embedding sounds amazing, right?

It can be.

But now we reach one of the most important ideas in MongoDB schema design:

```
BOUNDED vs UNBOUNDED DATA
```

🔥🔥🔥

This is something you need to understand deeply.

---

## 14. What does BOUNDED mean?

Bounded means:

> We can reasonably expect the number of child documents to stay within a manageable limit.

For example:

```
User
 └── addresses[]
```

Maybe a user has:

```
1
2
3
4
```

addresses.

That's bounded enough for many applications.

---

## 15. What does UNBOUNDED mean?

Unbounded means:

> The number of child documents can continue growing without a practical upper limit.

Example:

```
Customer
 └── orders[]
```

Imagine Rahul uses Amazon for 20 years.

His orders might become:

```
10
100
1000
5000
10000
...
```

Now imagine storing all of them inside:

```
ONE customer document
```

🚨 That's dangerous.

---

## 16. Why is an unbounded array dangerous?

Remember MongoDB has a:

```
16 MiB maximum BSON document size.
```

So imagine:

```
Customer document
│
├── name
├── email
├── address
│
└── orders[]
      ├── order 1
      ├── order 2
      ├── ...
      ├── order 10,000
      ├── order 20,000
      └── ...
```

The document can become enormous.

Eventually:

```
💥 Document too large
```

So:

> Never blindly embed an unbounded one-to-many relationship.

This is one of the biggest schema-design lessons.

---

## 17. This gives us an important rule

### Bounded "many"

Embedding can be attractive.

```
Course
 └── lessons[]
```

if the course has a reasonably bounded number of lessons.

### Unbounded "many"

Referencing often becomes more appropriate.

```
Customer
 └── orders → separate collection
```

when orders can grow indefinitely.

> MongoDB's guidance specifically recommends references when the child side has high cardinality or embedded data can grow without bounds.

---

## 18. ONE-TO-MANY USING REFERENCING

Now let's model the customer example differently.

Instead of:

```
Customer
 └── orders[]
```

we create:

```
customers
orders
```

### Customer document

```json
{
    "_id": 101,
    "name": "Rahul"
}
```

### Order document

```json
{
    "_id": 1001,
    "customerId": 101,
    "product": "Laptop",
    "amount": 70000
}
```

Another:

```json
{
    "_id": 1002,
    "customerId": 101,
    "product": "Mouse",
    "amount": 1200
}
```

Another:

```json
{
    "_id": 1003,
    "customerId": 101,
    "product": "Keyboard",
    "amount": 2500
}
```

Now our relationship is:

```
customers
   │
   │ _id = 101
   │
   ↓
orders
   ├── customerId = 101
   ├── customerId = 101
   └── customerId = 101
```

The many side stores the reference to the one side.

This is an extremely common MongoDB one-to-many reference pattern. MongoDB's documentation demonstrates referenced one-to-many relationships using a parent identifier on child documents.

---

## 19. Why put `customerId` inside Order?

Think about the question:

> "Which customer does this order belong to?"

Look at:

```json
{
    "_id": 1001,
    "customerId": 101
}
```

Immediately we know:

```
Order 1001
     ↓
customerId = 101
     ↓
Customer 101
```

And if we create:

```
Order 1004
Order 1005
Order 1006
```

they can all point to:

```
customerId: 101
```

So:

```
Customer 101
     ↑
     │
 ┌───┼────┬────┐
 │   │    │    │
1001 1002 1003 1004
```

That's one-to-many.

---

## 20. Finding all orders for Rahul

Now we query the orders collection:

```js
db.orders.find({
    customerId: 101
})
```

Result:

```
Order 1001
Order 1002
Order 1003
Order 1004
...
```

This is one of the biggest advantages of referencing for a large child set:

> The orders can be queried independently as their own documents.

---

## 21. Indexing the reference

If we frequently run:

```js
db.orders.find({
    customerId: 101
})
```

we should think about an index:

```js
db.orders.createIndex({
    customerId: 1
})
```

Now MongoDB has an index specifically supporting queries by customer.

And this is a beautiful connection with our Unit II indexing knowledge.

Schema design and indexing aren't separate worlds.

You design:

```
Relationship
     ↓
Reference field
     ↓
Access pattern
     ↓
Index
```

## 22. Embed vs Reference — One-to-Many

Now let's compare.

| Question                          | Embed                 | Reference                              |
|--------------------------------------|--------------------------|--------------------------------------------|
| Where are children?                    | Inside parent            | Separate collection                         |
| Typical structure                        | `children: []`            | `parentId` in child                         |
| Reads together                             | Excellent                | May require additional query                 |
| Child count                                 | Prefer bounded            | Good for large/high-cardinality               |
| Independent child query                       | Less natural              | Excellent                                      |
| Child independent lifecycle                     | Less ideal                | Excellent                                       |
| Parent document growth                            | Risk                      | Much safer                                       |
| Single-document atomicity                            | Strong                    | Multiple docs may require multiple operations     |
| Complexity                                             | Simpler                   | More application/query logic                       |

> MongoDB recommends embedding when related data is commonly queried together and bounded; references become attractive for high-cardinality, independently queried, independently changing, or unbounded child data.

## 23. 🔥 Let's compare two real examples

### Example A — Course → Lessons

Suppose:

```
MongoDB Course
```

has:

```
10 lessons
```

and the application normally loads:

```
Course + all lessons
```

We could use:

```json
{

            "title": "CRUD"

```

> MongoDB itself gives course-like bounded child sets as a scenario where embedding can work well when the child data is accessed with its parent.

## 24. Example B — Customer → Orders

Now:

```
Customer
 └── 5000 orders
```

Would you do:

```js
{
    name: "Rahul",
    orders: [
        // thousands of orders
    ]
}
```

Probably not.

Instead:

```

```

with:

```json
{

```

Why?

Because orders:

```

are independently queryable
have their own lifecycle
```

## 25. Another classic example — Author → Books

Suppose:

```
Author
```

has:

```
Books
```

You might think:

```
Author
 └── books[]
```

But let's say the same book information is useful independently.

For example:

```
Book
 ├── title
 ├── ISBN
 ├── price
 ├── publisher
 ├── reviews
 └── ...
```

and the book belongs to an author.

Then:

```
authors
books
```

with:

```json
{
    "_id": 501,
    "name": "Author A"
}
```

and:

```json
{
    "_id": 9001,
    "title": "MongoDB Guide",
    "authorId": 501
}
```

can be a better design.

> MongoDB's official one-to-many reference example uses a publisher → books relationship and shows how referencing can avoid repeating publisher information in every book document.

## 26. Here's a subtle but VERY important point

Suppose we have:

```
Author → Books
```

One author has:

```
100 books
```

If we embed the author inside every book:

```json
{
    "title": "Book 1",
    "author": {
        "name": "Author A",
        "location": "..."
    }
}
```

then:

```
Book 1 → author data
Book 2 → author data
Book 3 → author data
...
```

The author information is duplicated.

If the author's location changes:

```
California → Texas
```

you might need to update many book documents.

That's update overhead.

Referencing avoids this duplication:

```json
{
    "title": "Book 1",
    "authorId": 501
}
```

Now author information exists in one place.

> MongoDB explicitly identifies duplication, independent querying, and high-cardinality child sets as reasons to consider references.

---

## 27. But wait — duplication isn't ALWAYS bad

This is an important advanced idea.

MongoDB is comfortable with controlled denormalization.

Suppose an order contains:

```json
{
    "productId": 501,
    "productName": "Laptop",
    "priceAtPurchase": 70000
}
```

The current product price might later become:

```
₹75000
```

But the old order should still say:

```
priceAtPurchase: ₹70000
```

So keeping a copy of relevant information inside the order is intentional.

This is why we shouldn't blindly say:

> "Duplication is bad."

Instead:

> Duplication is a trade-off.

> MongoDB's modeling guidance explicitly discusses duplication as a deliberate choice when the read-performance benefit outweighs update overhead.

---

## 28. Another important concept — "viewed in context"

Suppose we have:

```
Country
 └── Cities
```

and our application always displays:

```
India
Major Cities:
Chennai
Mumbai
Delhi
Bengaluru
```

The cities are being viewed in the context of the country.

Embedding can make sense:

```json
{
    "name": "India",

    "cities": [
        "Chennai",
        "Mumbai",
        "Delhi",
        "Bengaluru"
    ]
}
```

> MongoDB's official one-to-many embedding example specifically uses country → major cities as an example of children viewed in the context of the parent.

---

## 29. The opposite case

Suppose we have:

```
University
 └── Students
```

but the university has:

```
100,000 students
```

And the application frequently asks:

```
Find students with CGPA > 9
Find students from CSE
Find students admitted in 2025
Find student by roll number
```

Then storing all students inside one university document would be a poor design.

Instead:

```
universities
students
```

and:

```json
{
    "_id": 10001,
    "universityId": 1,
    "name": "Rahul",
    "branch": "CSE",
    "cgpa": 9.2
}
```

Now we can independently index:

```
universityId
branch
cgpa
```

and query students efficiently.

This is exactly the type of high-cardinality child relationship for which references are generally more suitable.

## 30. 🔥 The "How many?" test

Whenever you see a one-to-many relationship, ask:

> How many children could there realistically be?

For example:

**User → Settings**

```
1 user → 1 settings
```

That's actually 1:1.

**User → Addresses**

```
1 user → 2–5 addresses
```

Potentially bounded.

Embedding could be reasonable.

**Customer → Orders**

```
1 customer → hundreds/thousands of orders
```

Potentially unbounded.

Reference becomes attractive.

**University → Students**

```
1 university → 100,000+ students
```

Definitely high cardinality.

Reference.

---

## 31. 🔥 The "Do I need them together?" test

Ask:

> When I retrieve the parent, do I usually need all children immediately?

If:

```
YES
```

embedding becomes attractive.

If:

```
NO
```

reference becomes more attractive.

For example:

```
Course → Lessons
```

If the course page always loads its lessons:

> Embed 👍

But:

```
Customer → Orders
```

If the customer profile page doesn't need 500 orders:

> Reference 👍

---

## 32. 🔥 The "Does the child exist independently?" test

Suppose:

```
Order
```

has meaning independently.

You can ask:

```
Find Order #1001
```

You can update it:

```
Order status → Shipped
```

You can track it:

```
Order → Delivery
```

So Order is a fairly independent entity.

Reference is often attractive.

But something like:

```
Customer
 └── Address
```

where the address is simply part of that customer's profile may naturally fit embedding.

---

## 33. 🔥 The "growth" test

This one is critical:

> Will the child array grow forever?

If **NO**:

> Embedding can be considered.

If **YES**:

> Be extremely careful.

Usually consider references or another pattern.

> MongoDB's documentation specifically warns that unbounded embedded arrays can create performance problems and can eventually approach the document-size limit.

---

## 34. A beautiful mental decision tree

Memorize the thinking, not the exact diagram:

```
             ONE → MANY
                 │
                 ↓
       How many children?
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
    Bounded             Unbounded
       │                   │
       ↓                   ↓
Can read together?      Reference
    /       \
  YES        NO
   ↓          ↓
Embed       Reference
```

But there is one more question:

> Does child live independently?

If yes:

> **REFERENCE** becomes stronger.

## 35. One-to-Many — complete practical comparison

### Embedded model

```json
{
    "_id": 101,
    "name": "Rahul",

    "orders": [
        {
            "orderId": 1001,
            "amount": 70000
        },
        {
            "orderId": 1002,
            "amount": 1200
        }
    ]
}
```

### Referenced model

**Customer:**

```json
{
    "_id": 101,
    "name": "Rahul"
}
```

**Orders:**

```json
{
    "_id": 1001,
    "customerId": 101,
    "amount": 70000
}
```

```json
{
    "_id": 1002,
    "customerId": 101,
    "amount": 1200
}
```

Same relationship:

```
Customer 1 → MANY Orders
```

Different storage strategy.

🔥 That's the central idea.

## 36. Exam-ready definition

If asked:

> "What is a one-to-many relationship?"

Write:

> A one-to-many relationship is a relationship in which one parent entity is associated with multiple child entities. In MongoDB, it can be modeled using embedded arrays when the child data is bounded and commonly accessed with the parent, or using references when the child data is large, independently accessed, independently updated, or unbounded.

That's a strong answer.

## 37. Viva questions

### Q1. What is 1:M?

> One parent → many children

Example:

```
Customer → Orders
```

### Q2. How can MongoDB model 1:M?

Two major ways:

```
Embedding
Referencing
```

### Q3. What does an embedded 1:M relationship look like?

```json
{
    "customer": "Rahul",
    "orders": [
        "...",
        "...",
        "..."
    ]
}
```

### Q4. What does a referenced 1:M relationship look like?

**Parent:**

```json
{
    "_id": 101,
    "name": "Rahul"
}
```

**Child:**

```json
{
    "_id": 1001,
    "customerId": 101
}
```

### Q5. What is an unbounded array?

> An array whose number of elements can continue growing without a practical upper bound.

Example:

```
Customer → all historical orders
```

### Q6. Why can unbounded arrays be dangerous?

> Because the parent document can become very large and MongoDB has a 16 MiB document size limit.

### Q7. When is embedding good for 1:M?

When:

```
children are bounded
commonly queried with parent
viewed in parent context
related data doesn't grow indefinitely
```

### Q8. When is referencing good?

When:

```
child count is large
relationship is high-cardinality
children are independently queried
children change independently
data grows without bounds
```

### Q9. Where is the reference usually stored?

A common pattern is:

```
child.parentId
```

So the many side points to the one side.

### Q10. Is duplication always bad?

> No.

MongoDB can intentionally duplicate data when the read-performance benefit outweighs update overhead.
