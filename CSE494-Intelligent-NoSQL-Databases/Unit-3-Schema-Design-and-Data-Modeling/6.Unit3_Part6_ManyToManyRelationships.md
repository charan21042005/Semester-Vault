## 1. First, forget MongoDB again

Let's understand what many-to-many actually means.

Imagine a college.

We have:

```
STUDENTS
```

and:

```
COURSES
```

A student can take many courses.

For example:

```
Rahul
 ├── MongoDB
 ├── Operating Systems
 └── Computer Networks
```

But now look from the other direction.

The MongoDB course has many students:

```
MongoDB
 ├── Rahul
 ├── Priya
 ├── Arjun
 └── Neha
```

So:

```
Student → MANY Courses

Course → MANY Students
```

Therefore:

```
MANY ↔ MANY
```

or:

```
M : M
```

---

## 2. The easiest way to visualize it

Imagine:

```
             COURSES
        ┌───────────────┐
        │ MongoDB       │
        │ OS            │
        │ Networks      │
        └───────────────┘
          ↑   ↑   ↑
          │   │   │
          │   │   │
        ┌─┴───┴───┴─┐
        │ STUDENTS  │
        ├───────────┤
        │ Rahul     │
        │ Priya     │
        │ Arjun     │
        └───────────┘
```

But the actual connections are many:

```
Rahul ─────→ MongoDB
Rahul ─────→ OS
Rahul ─────→ Networks

Priya ─────→ MongoDB
Priya ─────→ Networks

Arjun ─────→ MongoDB
Arjun ─────→ OS
```

That's M:M.

> MongoDB explicitly describes many-to-many as a relationship where each document can be associated with multiple documents on the other side—for example, students and courses.

## 4. Why is M:M harder?

Let's compare.

**One-to-one**

```
A ───── B
```

Simple.

**One-to-many**

```
A ───── B
      ├── C
      └── D
```

Still manageable.

**Many-to-many**

```
A ───── B
│ ╲   ╱ │
│  ╲ ╱  │
│  ╱ ╲  │
│ ╱   ╲ │
C       D
```

Now both sides have multiple connections.

So if we store everything naively, duplication and synchronization can become complicated.

---

## 5. The first MongoDB question

Suppose:

```
Student ↔ Course
```

How do we represent this?

Again, our major choices are:

### Option 1 — Embed related data

```
Student
 └── courses[]
```

or perhaps course documents inside that array.

### Option 2 — Reference related documents

```
Student
 └── courseIds[]
```

and separately:

```
Course
```

### Option 3 — Use a separate relationship collection

```
Student
Course
Enrollment
```

We'll understand all three.

---

## 6. OPTION 1 — EMBEDDING IN MANY-TO-MANY

Let's start with a simple example.

Suppose:

```
Book
```

has multiple authors.

We could embed author information inside the book.

```json
{
    "_id": 101,
    "title": "MongoDB in Practice",

    "authors": [
        {
            "authorId": 1,
            "name": "Rahul Sharma"
        },
        {
            "authorId": 2,
            "name": "Priya Singh"
        }
    ]
}
```

Mental picture:

```
Book
│
├── title
│
└── authors[]
      │
      ├── Author 1
      └── Author 2
```

So far, it looks easy.

---

## 7. But now look from the author's side

Suppose Rahul wrote:

```
Book A
Book B
Book C
```

If we're embedding authors into books, Rahul's information appears in:

```
Book A → Rahul
Book B → Rahul
Book C → Rahul
```

That's duplication.

> MongoDB's own many-to-many lesson points out exactly this issue: embedding the same author document into multiple books creates duplication.

---

## 8. Is duplication automatically bad?

🚨 NO.

This is a concept I want you to carry from the previous part.

In traditional relational design, you were heavily trained to think:

```
DUPLICATION = BAD
```

MongoDB gives us a more nuanced view.

Sometimes:

```
Duplication
+
Faster/easier reads
```

can be a good trade-off.

> MongoDB explicitly notes that some duplication can be acceptable when it provides better query performance.

---

## 9. Let's see when duplication becomes painful

Suppose Rahul changes his name:

```
Rahul Sharma
       ↓
Rahul Kumar
```

If we have embedded:

```
Book A → Rahul Sharma
Book B → Rahul Sharma
Book C → Rahul Sharma
Book D → Rahul Sharma
```

we may need to update all those documents.

That's update overhead.

So we ask:

> Does this data change frequently?

If yes, duplication becomes less attractive.

> MongoDB recommends considering references when duplication creates significant update overhead or the related data changes frequently.

---

## 10. M:M USING AN ARRAY OF REFERENCES

Now let's avoid duplicating the entire author document.

Instead of:

```js
authors: [
    {
        authorId: 1,
        name: "Rahul"
    },
    {
        authorId: 2,
        name: "Priya"
    }
]
```

we can store only IDs:

```json
{
    "_id": 101,
    "title": "MongoDB in Practice",

    "authorIds": [1, 2]
}
```

Now:

```
Book
│
├── title
│
└── authorIds
      ├── 1
      └── 2
```

These are references.

---

## 11. Separate Authors collection

Now:

```json
{
    "_id": 1,
    "name": "Rahul Sharma"
}
```

and:

```json
{
    "_id": 2,
    "name": "Priya Singh"
}
```

Book:

```json
{
    "_id": 101,
    "title": "MongoDB in Practice",
    "authorIds": [1, 2]
}
```

So:

```
             AUTHORS
          ┌────────────┐
          │ 1 Rahul    │
          │ 2 Priya    │
          └────────────┘
             ↑      ↑
             │      │
             1      2
             │      │
          ┌───────────────┐
          │ BOOK 101      │
          │ authorIds     │
          │ [1,2]         │
          └───────────────┘
```

Much less duplicated author information.

---

## 12. But there's a subtle problem

Suppose:

```
Book 101 → [1,2]
Book 102 → [1,3]
Book 103 → [1,4]
```

Now author 1 appears in:

```
Book 101
Book 102
Book 103
```

But that's okay.

We're duplicating the reference ID, not the entire author data.

This is much cheaper than duplicating:

```
name
bio
email
country
...
```

> MongoDB's many-to-many guidance describes this array-of-references approach.

---

## 13. Querying books for an author

Suppose:

```
authorId = 1
```

We can find all books containing that ID:

```js
db.books.find({
    authorIds: 1
})
```

MongoDB can match a scalar against an array containing that value.

Conceptually:

```
Book 101 → [1,2] ✓
Book 102 → [1,3] ✓
Book 103 → [1,4] ✓
Book 104 → [2,3] ✗
```

Result:

```
Book 101
Book 102
Book 103
```

---

## 14. Important: Don't automatically maintain both sides

You might think:

> "Okay, let's store `authorIds` inside books AND `bookIds` inside authors."

So:

```
Book
 └── authorIds[]

Author
 └── bookIds[]
```

That is called a **bidirectional reference**.

It can be done.

But now you have a synchronization problem.

Suppose:

```
Book 101
```

gets a new author.

You must update:

```
Book 101.authorIds
```

AND:

```
Author.bookIds
```

If one update succeeds and the other fails, the relationship can become inconsistent.

> MongoDB's many-to-many course specifically says bidirectional references can be more expensive to manage and does not recommend them by default.

---

## 15. So what should we do?

Usually ask:

> Which direction is queried more often?

Suppose our application is primarily:

```
Book page
   ↓
Show all authors
```

Then:

```json
{
    "title": "...",
    "authorIds": [1,2]
}
```

is useful.

If the primary access pattern is:

```
Author page
   ↓
Show all books
```

then we may choose a model optimized for that direction.

🔥 Again:

> **ACCESS PATTERN FIRST.**

Not:

> "I like this structure better."

---

## 16. The BIGGER problem with M:M

Now let's introduce something more realistic.

Suppose we have:

```
Student ↔ Course
```

A student doesn't just have a relationship with a course.

The relationship itself contains data.

For example:

```
Student: Rahul
Course: MongoDB

Enrollment:
    semester: 5
    enrolledOn: 2026-08-10
    grade: A
    attendance: 92
```

Whoa.

Now the relationship itself has properties.

That's where a separate relationship collection becomes extremely useful.

---

## 17. Introducing the INTERMEDIATE COLLECTION

We can create:

```
students
courses
enrollments
```

Instead of:

```
Student ↔ Course
```

directly, we have:

```
Student
   ↓
Enrollment
   ↓
Course
```

Like this:

```
Student 101
     │
     ↓
Enrollment
     │
     ↓
Course 501
```

---

## 18. What does Enrollment contain?

```json
{
    "_id": 10001,
    "studentId": 101,
    "courseId": 501,
    "semester": 5,
    "grade": "A",
    "attendance": 92
}
```

This is extremely powerful.

We have:

```
studentId
courseId
```

to define the relationship.

And:

```
semester
grade
attendance
```

to describe the relationship.

---

## 19. Let's create the three collections

### Students

```json
{
    "_id": 101,
    "name": "Rahul"
}
```

### Courses

```json
{
    "_id": 501,
    "name": "MongoDB"
}
```

### Enrollments

```json
{
    "_id": 10001,
    "studentId": 101,
    "courseId": 501,
    "semester": 5,
    "grade": "A"
}
```

Mental model:

```
          STUDENT
             │
             │ studentId
             ↓
       ┌─────────────┐
       │ ENROLLMENT  │
       │             │
       │ studentId   │
       │ courseId    │
       │ semester    │
       │ grade       │
       └──────┬──────┘
              │
              │ courseId
              ↓
           COURSE
```

---

## 20. Why is this model so good?

Because now we can easily represent:

```
Rahul → MongoDB
Rahul → OS
Rahul → Networks
```

and:

```
MongoDB → Rahul
MongoDB → Priya
MongoDB → Arjun
```

And every relationship can have its own data.

For example:

```
Rahul → MongoDB → Grade A
Rahul → OS      → Grade B+
Priya → MongoDB → Grade A+
```

---

## 21. This is conceptually similar to SQL junction tables

This should immediately connect with your SQL knowledge.

In SQL, M:M relationships are commonly represented using an intermediate/junction table:

```
STUDENT
   ↓
ENROLLMENT
   ↓
COURSE
```

MongoDB can use a similar conceptual approach with:

```
students
enrollments
courses
```

But remember:

> MongoDB does not require you to reproduce every relational design pattern exactly.

We're choosing this structure because the relationship itself contains meaningful data and/or the relationship is complex.

## 22. Example: Product ↔ Category

Suppose:

```
Product:
Laptop
```

belongs to:

```
Electronics
Computers
Office Equipment
```

We could store:

```json
{
    "_id": 1001,
    "name": "Laptop",

}
```

That's perfectly reasonable if categories are relatively stable and the application primarily needs:

```
Product → Categories
```

## 23. But what if the relationship has data?

Suppose each product-category relationship has:

```
displayOrder
featured
assignedAt
```

Then:

```
Laptop → Electronics
```

might have:

```
displayOrder: 2
featured: true
```

while:

```
Laptop → Computers
```

has:

```
displayOrder: 1
featured: false
```

Now a relationship document becomes attractive:

```json
{
    "productId": 1001,
    "categoryId": 2,
    "displayOrder": 1,
    "featured": false
}
```

🔥 This is an important modeling clue:

> If the relationship itself has important attributes, consider modeling the relationship as its own document.

## 24. M:M has three major modeling patterns

Now let's organize everything.

### Pattern 1 — Embedded documents

```js
Book
 └── authors: [
       { ... },
       { ... }
     ]
```

Useful when:

```
related data is small
commonly read together
duplication is acceptable
data doesn't change frequently
```

### Pattern 2 — Array of references

```
Book
 └── authorIds: [1,2,3]
```

Useful when:

```
related entities are independent
you don't want full duplication
relationship size is manageable
one direction is frequently queried
```

### Pattern 3 — Separate relationship collection

```
students
courses
enrollments
```

Useful when:

```
relationship is complex
relationship has its own attributes
cardinality is high
independent querying of relationships matters
you need more flexible relationship management
```

> MongoDB's reference guidance specifically identifies complex many-to-many relationships as a reason to consider references.

## 26. Finding students enrolled in MongoDB

We can query:

```js
db.students.find({
    courseIds: 501
})
```

This finds:

```
Rahul
Priya
Arjun
```

And if this query is frequent, we can create:

```js

```

You already learned multikey indexes in Unit II—and now you can see why schema design and indexing connect.

## 27. But here's the catch

Suppose a student can enroll in:

```
1000 courses
```

Then:

```js
courseIds: [
    501,
    502,
    503,
    ...
]
```

could become large.

Again:

> **ARRAY GROWTH MATTERS.**

> MongoDB warns that arrays that grow without bounds can hurt read/index performance and potentially approach the BSON document size limit.

## 28. Separate Enrollment collection solves that

Instead:

```
enrollments
```

contains:

```json
{
    "studentId": 101,
    "courseId": 501
}
```

```json
{
    "studentId": 101,
    "courseId": 502
}
```

```json
{
    "studentId": 102,

}
```

etc.

Now the relationship is distributed across separate documents.

No giant array inside one student.

For:

> Find all courses for student 101

> Find all students in course 501

## 30. 🔥 A subtle advanced point: M:M doesn't always require a junction collection

This is very important.

If someone says:

> "Many-to-many means you MUST create an intermediate collection."

❌ Not necessarily in MongoDB.

MongoDB supports multiple ways to model M:M relationships.

You could use:

```
embedded documents
```

or:

```
arrays of references
```

or:

```
separate relationship documents
```

depending on the workload.

> MongoDB's documentation explicitly provides multiple relationship modeling approaches, rather than imposing one relational-style structure.

## 31. 🔥 Another subtle point: bidirectional references

Let's say:

**Student**

```json
{
    "_id": 101,
    "name": "Rahul",
    "courseIds": [501, 502]
}
```

And Course:

```json
{
    "_id": 501,
    "name": "MongoDB",
    "studentIds": [101, 102, 103]
}
```

Looks convenient, right?

We can navigate either direction.

But now:

> Student 101 enrolls in Course 503

We need to update:

```
Student 101
+
Course 503
```

And potentially maintain consistency across both.

That's more writes and more opportunities for synchronization problems.

> MongoDB's many-to-many modeling course therefore cautions against bidirectional references unless the workload truly justifies the additional management cost.

## 32. Think like a database designer

Suppose your application mostly does:

```
Student page
    ↓
Show student's courses
```

Then optimize around:

```
Student → Courses
```

Maybe:

```json
{
    "_id": 101,
    "name": "Rahul",
    "courseIds": [501, 502]
}
```

But if your application mostly does:

```
Course page
    ↓
Show all enrolled students
```

then perhaps a model centered around the course or a relationship collection may be better.

🔥 There is no universal M:M schema.

The application workload determines the design.

> MongoDB's data-modeling guidance explicitly says the way the application uses and displays data should influence the schema structure.

---

## 33. Let's create a practical decision framework

Whenever you see:

```
A ↔ B
```

and both sides have MANY:

Ask these questions.

### Question 1

> Are the related documents small and commonly read together?

```
YES → Consider embedding
```

### Question 2

> Would embedding create significant duplication?

```
YES → Consider references
```

### Question 3

> Does the relationship have its own fields?

For example:

```
grade
date
role
quantity
status
```

```
YES → Strong candidate for relationship documents
```

### Question 4

> Can either side's relationship list grow enormously?

```
YES → Be careful with arrays
     → Consider separate documents/references
```

### Question 5

> Are both sides queried independently?

```
YES → References often become attractive
```

## 34. The ultimate M:M decision tree

```
                  MANY ↔ MANY
                       │
                       ↓
          Is related data commonly
              read together?
                 /          \
               YES           NO
                │             │
                ↓             ↓
           Can duplication   REFERENCE
             be tolerated?
             /       \
           YES        NO
            │          │
            ↓          ↓
         EMBED       REFERENCE
                         │
                         ↓
              Does relationship itself
                 contain attributes?
                    /       \
                  YES        NO
                   │          │
                   ↓          ↓
          RELATIONSHIP      ARRAY OF
           DOCUMENTS       REFERENCES
```

Again, it's not a strict algorithm.

It's your mental checklist.

## 37. M:M exam-ready definition

If the exam asks:

> "What is a many-to-many relationship?"

Write:

> A many-to-many relationship is a relationship in which each entity can be associated with multiple entities on the other side, and vice versa. For example, a student can enroll in multiple courses and a course can have multiple students. In MongoDB, such relationships can be modeled using embedded documents, arrays of references, or separate relationship documents depending on access patterns, cardinality, duplication, and whether the relationship has its own attributes.

That's a very strong answer.

## 38. Viva questions 🔥

### Q1. What is M:M?

```
Many A ↔ Many B
```

Example:

```
Student ↔ Course
```

### Q2. Why is M:M more complex?

> Because both sides can have multiple relationships, which creates more complicated storage, querying, duplication, and synchronization decisions.

### Q3. Can MongoDB embed M:M relationships?

> Yes.

For example:

```
authors: [...]
```

inside a book.

### Q4. Can MongoDB use references for M:M?

> Yes.

For example:

```
authorIds: [1,2,3]
```

### Q5. What is a relationship collection?

> A separate collection that stores the relationship itself.

Example:

```
enrollments
```

containing:

```
studentId
courseId
grade
semester
```

### Q6. When is a relationship collection particularly useful?

> When the relationship itself has important attributes or the relationship is complex/high-cardinality.

### Q7. What is bidirectional referencing?

> Keeping references on both sides.

Example:

```
Student → courseIds[]
Course → studentIds[]
```

### Q8. Why can bidirectional references be problematic?

> Both sides must remain synchronized, increasing write and maintenance complexity. MongoDB's own modeling course advises against this unless justified by the workload.

### Q9. Is duplication always bad in MongoDB?

> No.

Controlled duplication can improve read performance, provided the update cost is acceptable.

### Q10. What should determine M:M schema design?

🔥

```
Access patterns
Cardinality
Data growth
Duplication
Update frequency
Whether relationship has attributes
```
