# 🧠 UNIT III — PART 7: DATA MODELING BEST PRACTICES

---

## 1. First: What does "best practice" actually mean?

A beginner might think:

> "MongoDB is NoSQL, so I can design documents however I want."

We already killed this misconception in Part 1.

MongoDB gives you:

```
FLEXIBILITY
```

It does not give you:

```
NO DESIGN
```

In fact:

> A flexible schema makes good design MORE important, not less important.

> MongoDB's documentation explicitly recommends planning the schema early and iterating as the application evolves.

---

## 2. The master philosophy

If you remember only one thing from this entire part, remember this:

> 🔥 **DESIGN FOR HOW THE APPLICATION USES THE DATA.**

Not merely:

> "What entities exist?"

but:

> "What does my application actually do with them?"

For example, suppose our application has:

```
Customer
Order
Product
```

That's not enough information to decide the schema.

We need to know:

```
How often are customers viewed?
How often are orders viewed?
Does customer page show orders?
How many orders can a customer have?
Are orders updated frequently?
Does an order need product information immediately?
```

Those questions determine the design.

---

## 3. Best Practice #1 — START WITH WORKLOAD

This is the first official step in MongoDB's schema-design process.

Suppose we're designing:

> 🍔 Food Delivery App

We have:

```
Customer
Restaurant
Order
Food Item
Delivery
```

Don't immediately create:

```
customers
restaurants
orders
foodItems
deliveries
```

Instead ask:

> What does the application actually do?

For example:

```
1. Customer opens restaurant page
2. Customer sees menu
3. Customer adds items
4. Customer places order
5. Customer tracks order
6. Restaurant updates order status
7. Customer views order history
```

Now we're thinking like a schema designer.

---

## 4. Build a workload table

> MongoDB recommends creating a workload table containing things such as: action, read/write type, information needed, frequency, and priority.

For our food app:

| Action              | Type   | Data needed         | Frequency  |
|-------------------------|---------|-------------------------|---------------|
| View restaurant           | Read    | restaurant + menu        | Very high      |
| Place order                 | Write   | customer + items          | High            |
| Track order                   | Read    | order status               | Very high        |
| Update order                    | Write   | order status                 | High               |
| View history                      | Read    | customer's orders             | Medium              |

Now something interesting appears.

```
Restaurant + Menu
```

are frequently read together.

Maybe embedding menu items inside a restaurant document is attractive.

But:

```
Customer + ALL Orders
```

could become huge.

So orders may be better represented separately.

🔥 Workload directly influences schema design.

---

## 5. Best Practice #2 — EMBED WHEN DATA BELONGS TOGETHER

From everything we've learned:

Embedding is attractive when related data:

```
is commonly queried together
naturally belongs together
is reasonably bounded
is updated together
shares a lifecycle.
```

> MongoDB's best-practice guidance gives these as major cases for embedding.

Example:

```json
{
    "_id": 501,
    "name": "MongoDB Course",

    "instructor": {
        "name": "Rahul",
        "experience": 8
    }
}
```

If the course page always needs the instructor information:

```
Course
  +
Instructor
```

embedding may be convenient.

---

## 6. Best Practice #3 — REFERENCE WHEN DATA NEEDS INDEPENDENCE

Now consider:

```
Customer
Orders
```

Suppose a customer has:

```
5000 orders
```

and each order has:

```
status
payment
items
delivery
timestamps
```

Putting all of this inside one customer document would create a giant document.

Instead:

```
customers
orders
```

and:

```json
{
    "_id": 1001,
    "customerId": 501,
    "total": 2500,
    "status": "Delivered"
}
```

Reference.

> MongoDB recommends references when the child side has high cardinality, grows without bounds, is independently accessed, or can exist without the parent.

---

## 7. Best Practice #4 — AVOID UNBOUNDED ARRAYS 🚨

This deserves its own section because it is one of MongoDB's major schema anti-patterns.

Suppose we create:

```json
{
    "_id": 101,
    "name": "Rahul",

    "orders": [
        "...",
        "...",
        "..."
    ]
}
```

At first:

```
orders = 5
```

No problem.

Then:

```
orders = 100
```

Still maybe okay.

Then:

```
orders = 10,000
```

Now we have a problem.

> MongoDB warns that unbounded arrays can:
> - make documents excessively large
> - hurt index performance
> - strain application resources
> - approach/exceed the 16 MiB BSON document limit.

---

## 8. Visualize the problem

Bad design:

```
CUSTOMER
│
├── name
├── email
│
└── orders[]
      │
      ├── order 1
      ├── order 2
      ├── order 3
      ├── ...
      ├── order 9999
      ├── order 10000
      └── ...
```

The parent document becomes:

```
      ↓
████████████████████
████████████████████
████████████████████
████████████████████
████████████████████
```

And eventually:

```
💥 TOO LARGE
```

---

## 9. How do we fix an unbounded array?

We have several strategies.

### Strategy 1 — Reference

Move the children to another collection.

```
customers
orders
```

### Strategy 2 — Subset Pattern

This one is really interesting.

Suppose a book has:

```
100,000 reviews
```

But the application only displays:

```
latest 3 reviews
```

Why store all 100,000 reviews inside the book?

Instead:

```
Book
 └── latestReviews: [3 reviews]
```

and:

```
reviews collection
 └── all reviews
```

Now:

```
Book
 └── latest 3 reviews

Reviews collection
 └── remaining reviews
```

> MongoDB's official unbounded-array guidance specifically gives this subset pattern as a way to keep frequently needed data in the parent while storing the rest separately.

---

## 10. Why is the subset pattern clever?

Suppose the application says:

> "When I open a book, show me the three most recent reviews."

We don't need:

```
100,000 reviews
```

We only need:

```
3 reviews
```

So:

```
BOOK
├── title
├── author
└── latestReviews[3]
```

Then:

```
REVIEWS
├── review 4
├── review 5
├── ...
└── review 100000
```

Now the common read is fast and the document remains bounded.

🔥 This is MongoDB thinking:

> Store together what is commonly needed together—not necessarily everything that belongs conceptually to the entity.

---

## 11. Best Practice #5 — DON'T MAKE DOCUMENTS BLOATED

Another MongoDB anti-pattern is the **bloated document**.

A document becomes bloated when you put lots of data together even though the application doesn't normally access that data together.

> MongoDB identifies excessively large documents as a schema anti-pattern because they can degrade performance of common queries.

---

## 12. Example of a bloated document

Suppose:

```js
{
    _id: 101,
    name: "Rahul",

    profile: {...},

    preferences: {...},

    transactionHistory: [...],

    auditLogs: [...],

    loginHistory: [...],

    oldNotifications: [...],

    documents: [...]
}
```

Imagine the application's most common query is simply:

```js
db.users.findOne({ _id: 101 })
```

and the UI only needs:

```
name
profile
```

But MongoDB is storing and potentially reading a massive document.

That's wasteful.

---

## 13. Think of a physical analogy

Imagine you ask someone:

> "Give me Rahul's name."

And they hand you:

> Rahul's entire 500-page life file.

😂

Technically, the answer is inside.

But it's terrible organization.

Same idea with bloated MongoDB documents.

---

## 14. Better design

Separate rarely needed or independently accessed data:

```
users
profiles
auditLogs
transactions
```

Or use a subset/extended-reference style where appropriate.

> MongoDB provides patterns such as subset, extended reference, and outlier specifically to deal with large or uneven document shapes.

---

## 15. Best Practice #6 — DON'T DUPLICATE BLINDLY

MongoDB allows duplication.

But:

```
duplication ≠ automatically good
duplication ≠ automatically bad
```

It's a trade-off.

Suppose:

```
Product
```

contains:

```
name
price
description
```

And an order contains:

```json
{
    "productId": 501,
    "productName": "Laptop",
    "priceAtPurchase": 70000
}
```

Here:

```
productName
priceAtPurchase
```

are duplicated intentionally.

Why?

Because when the order is viewed, we immediately have the information needed.

And:

```
priceAtPurchase
```

should actually represent the historical purchase price, not necessarily the current product price.

That's useful denormalization.

---

## 16. But consider another duplication

Suppose every book stores:

```js
author: {
    name: "Rahul",
    email: "...",
    address: "...",
    phone: "...",
    biography: "..."
}
```

And Rahul has:

```
10,000 books
```

Now changing:

```
Rahul's phone number
```

means potentially updating huge amounts of duplicated data.

That's probably not a good trade-off.

> MongoDB recommends referencing when duplication becomes too complicated to manage or when data changes independently.

---

## 17. The duplication question

Whenever you consider duplication, ask:

```
How often is this data read?
How often does it change?
How expensive is updating duplicates?
How much faster does duplication make reads?
```

If:

```
READS >>> WRITES
```

controlled duplication may be attractive.

If:

```
WRITES >>> READS
```

duplication can become expensive.

This is not an absolute formula, but it's a very useful mental model.

---

## 18. Best Practice #7 — THINK ABOUT ATOMICITY

This connects directly to Unit II.

> MongoDB writes are atomic at the single-document level.

Suppose:

```
Order
├── items
├── total
└── status
```

All inside one document.

If we update that document:

```
items
total
status
```

the single-document write provides atomicity across that document.

---

## 19. Why embedding can help atomicity

Suppose:

```
Bank Account
 └── balance
```

If all information that must change together is within one document, a single-document update can modify it atomically.

But if related information is split across:

```
accounts
transactions
balances
```

then maintaining consistency across multiple documents may require multiple operations or a transaction.

> MongoDB supports distributed/multi-document transactions, but its own documentation cautions that transactions generally carry more performance cost than single-document writes and shouldn't substitute for good schema design.

---

## 20. 🔥 This gives us a powerful design question

Ask:

> What data must change together atomically?

If the answer is:

```
A + B + C
```

and they naturally belong together:

> Embedding

may be attractive.

If:

```
A
```

and:

```
B
```

have independent lifecycles:

> Referencing

may make more sense.

---

## 21. Best Practice #8 — DESIGN AROUND ACCESS PATTERNS

Let's make this extremely clear.

Suppose you have:

```
Employee
Department
```

Don't say:

> "Department has employees, so I'll embed employees."

Instead ask:

**Query A**

> Show department with all employees.

**Query B**

> Find employee by employee ID.

**Query C**

> Find all employees with salary > ₹10 lakh.

**Query D**

> Move employee from Department A to Department B.

Now you have real workload information.

If there are:

```
100,000 employees
```

embedding them all into departments might be terrible.

If there are only:

```
5 employees
```

and the department page always displays them, embedding may be reasonable.

---

## 22. Best Practice #9 — INDEX BASED ON REAL QUERIES

Schema design and indexes must work together.

Suppose our orders collection is:

```json
{
    "_id": 1001,
    "customerId": 501,
    "status": "Delivered",
    "total": 2500
}
```

And our frequent query is:

```js
db.orders.find({
    customerId: 501
})
```

Then:

```js
db.orders.createIndex({
    customerId: 1
})
```

makes sense.

> MongoDB recommends considering indexes for fields that are frequently queried, filtered, sorted, or used in joins/aggregation.

---

## 23. But don't index everything

This is another common beginner mistake.

Suppose:

```
users
```

has:

```
name
email
age
city
country
phone
gender
college
hobby
...
```

And we create:

```
index(name)
index(email)
index(age)
index(city)
index(country)
index(phone)
index(gender)
index(college)
...
```

Looks powerful.

But indexes aren't free.

They:

```
consume storage
consume memory
add maintenance work during writes
can hurt write performance if excessive.
```

> MongoDB explicitly recommends removing unnecessary indexes because they consume resources and can degrade write performance.

---

## 24. Best Practice #10 — AVOID TOO MANY `$lookup`s

Remember referencing?

```
Customer
   ↓
Order
   ↓
Product
   ↓
Restaurant
```

We might eventually create queries that repeatedly do:

```
$lookup
$lookup
$lookup
$lookup
```

Now the query becomes complicated.

> MongoDB lists excessive `$lookup` operations as a schema-design anti-pattern because they increase query complexity and can reduce query performance.

This does not mean:

> "`$lookup` is bad."

It means:

> Don't normalize everything and then force every common read to reconstruct the data through joins.

---

## 25. This is one of the biggest MongoDB mindset shifts

**Traditional relational mindset:**

```
Normalize aggressively
      ↓
JOIN when needed
```

MongoDB often encourages:

```
Understand access patterns
      ↓
Embed/denormalize where useful
      ↓
Keep common reads simple
```

Not:

> Never normalize.

Not:

> Never use `$lookup`.

Instead:

> Choose the model that makes your important application operations efficient and manageable.

> MongoDB itself describes schema design as a balance involving performance, adaptability, consistency, and complexity.

---

## 26. Best Practice #11 — PLAN FOR DOCUMENT GROWTH

This is something beginners often forget.

A schema can work perfectly today:

```
Customer
 └── orders[5]
```

But what happens after:

```
1 year?
5 years?
10 years?
```

Maybe:

```
orders[5000]
```

So don't only ask:

> "Does this schema work now?"

Ask:

> "What will this document look like after the application has been running for years?"

🔥 That's production-level thinking.

---

## 27. Example — Social Media User

**Bad design:**

```js
{
    _id: 1,
    username: "rahul",

    posts: [
        {...},
        {...},
        {...},
        ...
    ],

    comments: [
        {...},
        {...},
        ...
    ],

    notifications: [
        {...},
        {...},
        ...
    ]

```

Everything keeps growing.

This is a recipe for giant documents.

**Better:**

```
users
posts
comments
notifications
```

with appropriate references and perhaps bounded subsets for frequently needed recent information.

> MongoDB identifies unbounded arrays and bloated documents as important schema anti-patterns.

## 28. Best Practice #12 — DATA LIFECYCLE MATTERS

Ask:

> Does this data live forever?

Maybe not.

Consider:

```
login sessions
temporary tokens
old events
logs
historical data
```

Some data should eventually expire or move elsewhere.

> MongoDB's best-practice documentation specifically calls out lifecycle management, including TTL for data that should automatically expire.

For example:

```
Session
createdAt
expiresAt
```

can potentially use a TTL index depending on the application's requirements.

---

## 29. Best Practice #13 — CONSIDER MEMORY / DOCUMENT SIZE

Here's another subtle performance issue.

Suppose:

```
Document A = 2 KB
Document B = 500 KB
Document C = 2 MB
```

If your common query only needs:

```
name
status
```

but the application repeatedly loads the giant document, you're moving unnecessary data.

> MongoDB notes that larger documents can use more RAM and may increase disk I/O when the working set doesn't fit in memory.

So ask:

> Am I storing too much information together just because I can?

---

## 30. Best Practice #14 — DON'T CREATE ONE COLLECTION PER TINY THING

Here's another anti-pattern.

Suppose someone designs:

```
students
student_addresses
student_phones
student_emails
student_preferences
student_hobbies
student_languages
student_skills
student_certificates
...
```

Just because every small concept gets its own collection.

> MongoDB lists creating an excessively large number of collections as a schema anti-pattern because it can hurt storage-engine performance.

Again, this doesn't mean:

> "Use one collection for everything."

It means:

> Collections should have meaningful modeling reasons.

---

## 31. Best Practice #15 — USE DESIGN PATTERNS INTENTIONALLY

MongoDB has several schema design patterns.

You don't need to memorize all of them right now, but you should understand the philosophy.

Examples include:

```
Subset Pattern
Computed Pattern
Extended Reference Pattern
Bucket Pattern
Outlier Pattern
Archive Pattern
Schema Versioning
```

> MongoDB describes schema patterns as reusable approaches for optimizing data models around application access patterns.

The key word:

> **INTENTIONALLY.**

Don't use:

> "Pattern because MongoDB says pattern."

Use:

```
Problem
 ↓
Understand workload
 ↓
Choose pattern
 ↓
Evaluate trade-offs
```

## 32. Let's understand one pattern properly: EXTENDED REFERENCE

Suppose we have:

```
Product
```

with a huge document:

```json
{
    "_id": 501,
    "name": "Laptop",
    "price": 70000,
    "description": "...huge...",
    "specifications": {"...": "..."},
    "reviews": ["..."]
}
```

And orders frequently need only:

```
productId
productName
price
```

Instead of constantly retrieving the giant product document, an order could store a small frequently-used subset:

```json
{
    "orderId": 1001,

    "product": {
        "id": 501,
        "name": "Laptop",
        "price": 70000
    }
}
```

This is controlled duplication.

The full product remains elsewhere.

The order gets the information it commonly needs.

> MongoDB documents the Extended Reference Pattern as a way to duplicate frequently accessed portions of larger documents into related documents.

Here's the opposite mistake.

Then:

```

And every page requires:

```

## 37. 🔥 The complete best-practice checklist

When designing a MongoDB schema, ask these questions in order.

**1️⃣ What does my application do?**

```
User actions
```

**2️⃣ What are the most frequent queries?**

```
Reads
Writes
```

**3️⃣ What data is accessed together?**

> Those pieces may belong together.

**4️⃣ What are the relationships?**

```
1:1
1:M
M:M
```

**5️⃣ Embed or reference?**

Consider:

```
access
size
growth
independence
duplication
update frequency
```

**6️⃣ Can arrays grow without bounds?**

If yes:

```
🚨 redesign
```

**7️⃣ Will the document become bloated?**

Think about:

```
RAM
network transfer
query performance
```

**8️⃣ Is duplication intentional?**

Ask:

```
Why am I duplicating this?
How often does it change?
```

**9️⃣ What needs atomic updates?**

> Keep naturally atomic data together where appropriate.

**🔟 Which fields need indexes?**

> Based on actual query patterns.

**1️⃣1️⃣ Am I creating too many lookups?**

> If common reads require many joins, reconsider the model.

**1️⃣2️⃣ What happens as data grows?**

> This one separates beginner design from production thinking.

## 38. 🔥 Let's turn this into a schema-design workflow

Suppose tomorrow your interviewer/examiner says:

> "Design MongoDB schema for an e-commerce application."

Don't immediately write collections.

Do this:

```
             REQUIREMENT
                  ↓
          Identify users/actions
                  ↓
          Identify workload
                  ↓
       Identify frequent queries
                  ↓
       Identify data relationships
                  ↓
             1:1 / 1:M / M:M
                  ↓
        Embed vs Reference
                  ↓
      Check growth / cardinality
                  ↓
       Check duplication/update cost
                  ↓
         Check atomic operations
                  ↓
           Design indexes
                  ↓
        Test common query patterns
                  ↓
             FINAL SCHEMA
```

🔥 This is the complete mindset.

## 42. 🔥 The five golden rules

If you need a tiny cheat sheet from this entire part:

**Rule 1**

> Design around application access patterns.

**Rule 2**

> Embed data that belongs together and is commonly accessed together.

**Rule 3**

> Reference data that is large, independent, high-cardinality, or unbounded.

**Rule 4**

> Avoid unbounded arrays and bloated documents.

**Rule 5**

> Indexes and schema design must be designed together.

These principles align closely with MongoDB's current schema-design guidance.
