# CASE STUDY 1 🎓 UNIVERSITY MANAGEMENT SYSTEM

Let's start with something familiar.

Suppose we're building a university system containing:

```
Students
Courses
Departments
Enrollments
```

## 1. Understand the application

The application needs to do things like:

```
1. View student profile
2. View student's department
3. View courses taken by student
4. View students enrolled in a course
5. Record enrollment
6. Record grade
7. Find students by department
8. Find courses by department
```

Now we have actual workload.

## 2. Identify relationships

Let's draw them:

```
STUDENT ──────── DEPARTMENT
   │
   │
   ↓
ENROLLMENT
   ↑
   │
 COURSE
```

Now determine cardinality.

**Student → Department**

```
Many students → One department
```

Therefore:

```
Department 1 → Students M
```

**Student → Course**

A student can take many courses.

A course can have many students.

Therefore:

```
Student M ↔ M Course
```

And:

```
Enrollment
```

represents the relationship.

## 3. Department modeling

Suppose:

```
CSE
```

has:

```
5000 students
```

Would we embed:

```js
{
    _id: 1,
    name: "CSE",

    students: [
        {...},
        {...},
        ...
    ]
}
```

❌ Not a good choice for this workload.

Why?

```
students = potentially huge
```

This is a high-cardinality relationship.

> MongoDB recommends references for high-cardinality child relationships and relationships where embedded data can grow without bounds.

## 4. Better Department model

**`departments`**

```json
{
    "_id": 1,
    "name": "Computer Science and Engineering",
    "code": "CSE"
}
```

**`students`**

```json
{
    "_id": 101,
    "name": "Rahul",
    "departmentId": 1,
    "cgpa": 9.1
}
```

Now:

```
Department 1
     ↑
     │
     │ departmentId
     │
 ┌───┼────┬────┐
 ↓   ↓    ↓    ↓
S1   S2   S3   S4
```

Excellent.

## 5. Student ↔ Course

Now:

```
Student M ↔ M Course
```

We could store:

```json
{
    "_id": 101,
    "name": "Rahul",
    "courseIds": [501, 502, 503]
}
```

For a simple application, this might work.

But suppose enrollment has:

```
semester
grade
attendance
enrolledAt
```

Now the relationship itself has important information.

So we use:

**Enrollment collection**

```json
{
    "_id": 10001,
    "studentId": 101,
    "courseId": 501,
    "semester": 5,
    "grade": "A",
    "attendance": 92
}
```

Now:

```
Student
   ↓
Enrollment
   ↓
Course
```

This is much more expressive.

## 6. Final university schema

**`departments`**

```json
{
    "_id": 1,
    "name": "Computer Science and Engineering",
    "code": "CSE"
}
```

**`students`**

```json
{
    "_id": 101,
    "name": "Rahul",
    "departmentId": 1,
    "cgpa": 9.1
}
```

**`courses`**

```json
{
    "_id": 501,
    "name": "MongoDB",
    "credits": 4
}
```

**`enrollments`**

```json
{
    "_id": 10001,
    "studentId": 101,
    "courseId": 501,
    "semester": 5,
    "grade": "A",
    "attendance": 92
}
```

## 7. Indexes

Suppose frequent queries are:

> Find all students in CSE

Then:

```js
db.students.createIndex({
    departmentId: 1
})
```

For:

> Find all courses taken by student 101

we might use:

```js
db.enrollments.createIndex({
    studentId: 1
})
```

For:

> Find all students taking course 501

we might use:

```js
db.enrollments.createIndex({
    courseId: 1
})
```

🔥 Notice how schema and indexes emerge from the workload.

# CASE STUDY 2 🛒 E-COMMERCE APPLICATION

Now let's make things more interesting.

Entities:

```
Customer
Product
Category
Order
```

## 1. Customer

A customer has:

```
name
email
phone
address
```

Address is potentially a good embedding candidate.

Why?

Suppose the customer profile frequently displays:

```
name
email
address
```

together.

So:

```json
{
    "_id": 101,
    "name": "Rahul",
    "email": "rahul@example.com",

    "address": {
        "street": "123 Main Road",
        "city": "Chennai",
        "state": "Tamil Nadu",
        "pincode": "600001"
    }
}
```

This is a classic embedded subdocument.

## 2. But what about Orders?

Customer → Orders is:

```
1 : Many
```

Could be:

```
hundreds
thousands
```

Therefore:

```
Customer
 └── orders[]
```

could become unbounded.

So:

> ❌ Don't blindly embed all orders.

Instead:

```
customers
orders
```

## 3. Order document

```json
{
    "_id": 5001,
    "customerId": 101,

    "status": "Delivered",

    "items": [
        {
            "productId": 701,
            "name": "Laptop",
            "quantity": 1,
            "priceAtPurchase": 70000
        },
        {
            "productId": 702,
            "name": "Mouse",
            "quantity": 2,
            "priceAtPurchase": 1200
        }
    ],

    "total": 72400
}
```

Now notice something beautiful.

We are **referencing** the customer:

```
customerId
```

but **embedding** order items.

Why?

Because the order and its line items are naturally viewed together.

## 4. This is a HYBRID MODEL 🔥

Our design is:

```
Customer
   │
   │ customerId
   ↓
Order
   │
   └── items[]
```

So:

```
Customer → Order
        = reference
```

But:

```
Order → Order Items
        = embedding
```

This is extremely common in real MongoDB design.

You do not have to choose one strategy for the entire database.

Different relationships can use different strategies.

> MongoDB's guidance explicitly frames embedding vs referencing as a decision made relationship-by-relationship according to workload and data characteristics.

## 5. Why embed order items?

Suppose order 5001 contains:

```
Laptop
Mouse
Keyboard
```

When displaying the order, we almost always want:

```
Order
+
its items
```

together.

Also, the purchased price should represent:

```
price at purchase
```

not today's product price.

So:

```json
{
    "productId": 701,
    "name": "Laptop",
    "priceAtPurchase": 70000
}
```

is intentional denormalization.

## 6. Why not just reference Product?

We could have:

```json
{
    "productId": 701
}
```

and then fetch the product.

But suppose today's product price is:

```
₹75,000
```

while Rahul bought it for:

```
₹70,000
```

The order needs historical information.

So the order stores:

```
priceAtPurchase = ₹70,000
```

This is a perfect example of controlled duplication.

> MongoDB recommends considering the read benefit and update frequency when deciding whether duplication is appropriate.

## 7. Product ↔ Category

Suppose:

```
Laptop
```

belongs to:

```
Electronics
Computers
```

That's:

```
M : M
```

For a simple category system, we might store:

```json
{
    "_id": 701,
    "name": "Laptop",
    "categoryIds": [1, 2]
}
```

Then:

```
Product
 └── categoryIds[]
```

## 8. What if categories are heavily queried independently?

Then keeping:

```
categories
```

as separate documents makes sense.

So our e-commerce design becomes:

```
customers
products
categories
orders
```

with:

```
Customer → Orders       reference
Product → Categories    references
Order → Items           embedding
Customer → Address      embedding
```

🔥 One application. Multiple modeling strategies.

That's real schema design.

# CASE STUDY 3 🍔 FOOD DELIVERY APPLICATION

Now let's build something closer to a production workload.

Entities:

```
User
Restaurant
Menu Item
Order
Delivery
```

## 1. Restaurant → Menu Items

A restaurant has:

```
Pizza
Burger
Biryani
Drinks
...
```

Potentially:

```
20
50
100
```

items.

This may be reasonably bounded for many applications.

And restaurant pages commonly show:

```
Restaurant
+
Menu
```

So embedding can be attractive.

```json
{
    "_id": 201,
    "name": "Food Palace",

    "menu": [
        {
            "itemId": 1,
            "name": "Burger",
            "price": 180
        },
        {
            "itemId": 2,
            "name": "Pizza",
            "price": 350
        }
    ]
}
```

## 2. But suppose menu becomes complicated

Now every menu item needs:

```
nutrition
variants
customizations
ingredients
allergens
availability
images
reviews
```

and the menu items evolve independently.

At that point:

```
restaurant
menuItems
```

may become more appropriate.

This illustrates an important MongoDB principle:

> A schema doesn't have to remain frozen forever.

> MongoDB's flexible model allows schemas to evolve, and its official documentation recommends iterating the design as application requirements change.

## 3. Restaurant → Orders

This is:

```
Restaurant 1 → MANY Orders
```

Could be thousands.

So don't put:

```
orders[]
```

inside the restaurant document.

Instead:

```json
{
    "_id": 5001,
    "restaurantId": 201,
    "customerId": 101,
    "status": "Preparing",
    "total": 620
}
```

Now orders can grow independently.

## 4. Order → Items

Again:

```
Order 1 → MANY Items
```

But usually:

```
5 items
10 items
15 items
```

rather than millions.

And order page almost always needs all its items.

So:

```json
{
    "_id": 5001,

    "restaurantId": 201,
    "customerId": 101,

    "items": [
        {
            "itemId": 1,
            "name": "Burger",
            "priceAtOrder": 180,
            "quantity": 2
        },
        {
            "itemId": 2,
            "name": "Pizza",
            "priceAtOrder": 350,
            "quantity": 1
        }
    ],

    "total": 710,
    "status": "Preparing"
}
```

Again:

```
Restaurant → Order = reference
Customer → Order = reference
Order → Items = embed
```

## 5. Why `priceAtOrder`?

Suppose restaurant changes:

```
Burger ₹180 → ₹220
```

Tomorrow.

But today's order must still say:

```
Burger × 2 = ₹360
```

So:

```
priceAtOrder
```

is historical data.

This is intentional denormalization.

## 6. Delivery

Suppose every order has one delivery record:

```
Order 1 ↔ Delivery 1
```

This is:

```
1 : 1
```

Would we embed?

Possibly:

```json
{
    "_id": 5001,
    "status": "Out for delivery",

    "delivery": {
        "riderName": "Arjun",
        "estimatedTime": "20 minutes"
    }
}
```

if delivery information is:

```
small
commonly accessed with the order
tightly coupled.
```

But if delivery has a separate operational system:

```
rider tracking
GPS
delivery events
status history
```

then a separate collection may make more sense.

Again:

> 1:1 does not automatically mean embed.

# CASE STUDY 4 📱 SOCIAL MEDIA APPLICATION

This one is excellent for understanding unbounded arrays.

Suppose a user has:

```
Profile
Posts
Followers
Following
Notifications
Messages
```

## 1. Profile

Basic profile:

```json
{
    "_id": 101,
    "username": "rahul",
    "bio": "Developer",
    "profilePhoto": "..."
}
```

Simple.

## 2. Posts

Could we do:

```js
{
    _id: 101,
    username: "rahul",

    posts: [
        {...},
        {...},
        {...},
        ...
    ]
}
```

🚨 Potentially terrible.

Why?

Posts are unbounded.

A highly active user could have thousands of posts.

**Better:**

```
users
posts
```

Post:

```json
{
    "_id": 9001,
    "userId": 101,
    "text": "Hello world!",
    "createdAt": "ISODate(...)"
}
```

## 3. Followers

This is another interesting case.

Suppose:

```
Rahul → 500,000 followers
```

Don't create:

```js
{
    followers: [
        // 500,000 IDs
    ]
}
```

as a giant array.

Instead, depending on workload, a separate relationship representation is more appropriate.

For example:

**`follows`**

```json
{
    "followerId": 201,
    "followingId": 101
}
```

This represents:

```
User 201 → follows → User 101
```

Now:

```
followerId
followingId
```

can be indexed according to common queries.

## 4. Why this is better?

We can query:

**Who does Rahul follow?**

```js
db.follows.find({
    followerId: 101
})
```

**Who follows Rahul?**

```js
db.follows.find({
    followingId: 101
})
```

Now the relationship can grow independently.

# CASE STUDY 5 📚 ONLINE LEARNING PLATFORM

This one is especially useful because MongoDB's own current documentation uses an online learning platform as an example of a schema evolving over time.

Suppose initially we have:

```
Course
Lesson
```

## 1. Version 1 — Simple system

Initially:

```
Course
 └── lessons[]
```

For example:

```json
{
    "_id": 501,
    "title": "MongoDB Basics",

    "lessons": [
        {
            "title": "Introduction",
            "description": "..."
        },
        {
            "title": "CRUD",
            "description": "..."
        }
    ]
}
```

This is perfectly reasonable if lessons are simple and bounded.

## 2. Version 2 — Requirements evolve

Now the application introduces:

```
Video
Quiz
Assignment
External Resources
```

Suddenly a lesson might contain:

```
title
description
video
quiz
assignments
resources
slides
...
```

The embedded course document starts becoming complicated.

> MongoDB's official best-practices example describes essentially this evolution and suggests moving lessons into a separate collection when the content types and requirements become more complex.

## 3. Version 2 schema

Now:

```
courses
lessons
```

**Course:**

```json
{
    "_id": 501,
    "title": "MongoDB Basics",
    "instructorId": 100
}
```

**Lesson:**

```json
{
    "_id": 1001,
    "courseId": 501,
    "title": "Introduction",
    "type": "video",
    "videoUrl": "...",
    "duration": 20
}
```

Another lesson:

```json
{
    "_id": 1002,
    "courseId": 501,
    "title": "Quiz",
    "type": "quiz",
    "questions": ["..."]
}
```

Now different lesson types can evolve independently.

## 4. What did we learn?

This is extremely important:

> Schema design is **not**:

```
Design once
       ↓
Never change
```

It is:

```
Requirements
     ↓
Initial schema
     ↓
Application evolves
     ↓
Workload changes
     ↓
Schema evolves
```

> MongoDB's flexible schema supports this iterative approach, although large production schemas can become harder to modify, so planning early still matters.

## 🔥 THE BIG LESSON FROM PART 8

MongoDB schema design is **not** about memorizing:

```
1:1 → embed
1:M → reference
M:M → junction table
```

❌ That would be the wrong lesson.

The real lesson is:

```
              APPLICATION
                   ↓
                WORKLOAD
                   ↓
             ACCESS PATTERNS
                   ↓
              RELATIONSHIPS
                   ↓
        ┌──────────┴──────────┐
        ↓                     ↓
      EMBED                REFERENCE
        │                     │
        └──────────┬──────────┘
                   ↓
           GROWTH / CARDINALITY
                   ↓
             DUPLICATION
                   ↓
              ATOMICITY
                   ↓
                INDEXES
                   ↓
             FINAL SCHEMA
```

> MongoDB's official schema-design process follows this same overall progression: identify workload, map relationships, apply patterns, and then create indexes.

## 🧠 PART 8 — MASTER TAKEAWAYS

Remember these six:

> 1. Design around application workload, not just entities.
>
> 2. Related data commonly retrieved together → consider embedding.
>
> 3. High-cardinality, independently changing, or unbounded data → consider references.
>
> 4. A relationship can itself have data → model the relationship explicitly.
>
> 5. One application can use both embedding and referencing.
>
> 6. Schema design is iterative; as requirements and access patterns change, the schema may need to evolve.
