## 1. First: Why do we even need validation?

Remember what we learned in Part 1.

> MongoDB is schema-flexible.

So technically, this collection can contain:

**`students`**

```json
{
    "name": "Rahul",
    "age": 21,
    "branch": "CSE"
}
```

and:

```json
{
    "name": "Priya",
    "age": 20,
    "branch": "ECE",
    "cgpa": 8.7
}
```

and even:

```json
{
    "studentName": "Arjun",
    "favouriteColor": "Blue"
}
```

MongoDB doesn't automatically say:

> "HEY! This document doesn't look like the others."

That's the flexibility we discussed.

But imagine a real college application.

We don't want:

```json
{
    "name": 12345,
    "age": "twenty",
    "cgpa": "excellent"
}
```

😂

Our application expects:

```
name  → string
age   → integer
cgpa  → number
branch → one of allowed branches
```

So we need:

```
Schema Validation
```

---

## 2. Schema-less ≠ Validation-less

This distinction is VERY important for exams and viva.

**Wrong understanding:**

> MongoDB doesn't have schema.

❌ Too simplistic.

**Better:**

> MongoDB does not enforce a rigid, predefined schema by default and supports flexible document structures.

And we can still add:

> schema validation rules to enforce desired structure and data constraints.

So:

```
MongoDB
   ↓
Flexible schema
   ↓
We decide the structure
   ↓
Validation rules can enforce that structure
```

Think of it like:

**Flexibility**

> "You are free to design your documents."

**Validation**

> "But once I define these rules, incoming documents must respect them."

> MongoDB's JSON Schema validation uses `$jsonSchema` and supports BSON-specific validation through `bsonType`.


## 4. MongoDB Schema Validation

MongoDB allows us to specify a:

```
validator
```

when creating a collection.

Basic structure:

```js
db.createCollection("students", {
    validator: {
        $jsonSchema: {
            // ...
        }
    }
})
```

Mental model:

```
createCollection()
       ↓
validator
       ↓
$jsonSchema
       ↓
rules
       ↓
MongoDB checks inserted/updated documents
```

---

## 5. `$jsonSchema`

This is one of the most important things in this part.

```
$jsonSchema
```

means:

> "The document must satisfy this JSON Schema."

> MongoDB supports JSON Schema draft 4 with MongoDB-specific differences/extensions.

---

## 6. Let's build a REAL validation schema

Let's say our student collection should follow:

```
name
    ↓
string

age
    ↓
integer
17–30

cgpa
    ↓
number
0–10

branch
    ↓
CSE / ECE / EEE / MECH
```

We can define:

```js
db.createCollection("students", {
    validator: {
        $jsonSchema: {
            bsonType: "object",

            required: [
                "name",
                "age",
                "cgpa",
                "branch"
            ],

            properties: {

                name: {
                    bsonType: "string"
                },

                age: {
                    bsonType: "int",
                    minimum: 17,
                    maximum: 30
                },

                cgpa: {
                    bsonType: ["double", "int"],
                    minimum: 0,
                    maximum: 10
                },

                branch: {
                    enum: ["CSE", "ECE", "EEE", "MECH"]
                }
            }
        }
    }
})
```

🔥 Don't memorize this blindly.

Let's understand every single piece.

---

## 7. `bsonType: "object"`

```
bsonType: "object"
```

means:

> The entire document should be a BSON object/document.

Basically:

```
{
    ...
}
```

is expected.

---

## 8. `required`

Now:

```js
required: [
    "name",
    "age",
    "cgpa",
    "branch"
]
```

means these fields **must exist**.

So this is valid:

```json
{
    "name": "Rahul",
    "age": 21,
    "cgpa": 8.7,
    "branch": "CSE"
}
```

But:

```json
{
    "name": "Rahul",
    "age": 21
}
```

❌ invalid

because:

```
cgpa
branch
```

are missing.

---

## 9. `properties`

Now:

```js
properties: {
    name: {...},
    age: {...},
    cgpa: {...},
    branch: {...}
}
```

means:

> Define rules for individual fields.

Think:

```
properties
    |
    +---- name → rules
    |
    +---- age → rules
    |
    +---- cgpa → rules
    |
    +---- branch → rules
```

---

## 10. `name` validation

```js
name: {
    bsonType: "string"
}
```

means:

> `name` must be a string

Valid:

```
name: "Rahul"
```

Invalid:

```
name: 123
```

because:

```
123 → integer
```

not:

```
string
```

---

## 11. `age` validation

```js
age: {
    bsonType: "int",
    minimum: 17,
    maximum: 30
}
```

This combines multiple rules.

**Rule 1**

```
bsonType: "int"
```

> Age must be an integer.

**Rule 2**

```
minimum: 17
```

> Age cannot be below 17.

**Rule 3**

```
maximum: 30
```

> Age cannot be above 30.

Therefore:

```
16 ❌
17 ✅
21 ✅
30 ✅
31 ❌
"21" ❌
```

---

## 12. `cgpa`

```js
cgpa: {
    bsonType: ["double", "int"],
    minimum: 0,
    maximum: 10
}
```

Here we're allowing:

```
double
OR
int
```

because:

```
8.7
```

is naturally a floating-point number, while:

```
8
```

can be an integer depending on how it is inserted.

And:

```
0 ≤ CGPA ≤ 10
```

So:

```
8.7 ✅
9.5 ✅
10 ✅
0 ✅
10.5 ❌
-1 ❌
"8.7" ❌
```

Notice something important:

> BSON type matters.

This:

```
cgpa: 8.7
```

is numeric.

But:

```
cgpa: "8.7"
```

is a string.

Even though humans look at both and think:

> "That's 8.7."

MongoDB sees:

```
8.7
↓
number

"8.7"
↓
string
```

🔥 This connects directly to our BSON topic from Unit II.

## 13. `enum`

Now this:

```js
branch: {
    enum: [
        "CSE",
        "ECE",
        "EEE",
        "MECH"
    ]
}
```

means:

> `branch` can only have one of these values.

Valid:

```
branch: "CSE"
branch: "ECE"
```

Invalid:

```
branch: "Civil"
```

> MongoDB's JSON Schema validation supports `enum` to restrict a field to a defined set of values.

## 14. So what exactly happens during insertion?

Suppose our validator exists.

We execute:

```js
db.students.insertOne({
    name: "Rahul",
    age: 21,
    cgpa: 8.7,
    branch: "CSE"
})
```

MongoDB checks:

```
Document
   ↓
Does name exist?       ✅
Is name string?        ✅
Does age exist?        ✅
Is age integer?        ✅
17 ≤ age ≤ 30?         ✅
Does cgpa exist?       ✅
Is cgpa numeric?       ✅
0 ≤ cgpa ≤ 10?         ✅
Does branch exist?     ✅
Is branch allowed?     ✅
   ↓
INSERT
```

🔥 Success.

```js
db.students.insertOne({
```

Check:


## 20. Nested document validation

Suppose:

```json
{
    "name": "Rahul",

    "address": {
        "city": "Amritsar",
        "pincode": 143001
    }
}
```

We can validate the nested object too.

Conceptually:

```js
properties: {
    address: {
        bsonType: "object",

        required: ["city", "pincode"],

        properties: {
            city: {
                bsonType: "string"
            },

            pincode: {
                bsonType: "int"
            }
        }
    }
}
```

So validation can go inside the document tree.

Think:

```
student
│
├── name
│
├── age
│
└── address
     │
     ├── city
     └── pincode
```

And each level can have rules.

## 21. Array validation

Suppose a student has:

```json
{
    "skills": [
        "C++",
        "Python",
        "MongoDB"
    ]
}
```

We could say:

```js
skills: {
    bsonType: "array",
    items: {
        bsonType: "string"
    }
}
```

Meaning:

```
skills must be an array
        ↓
every item must be a string
```

Therefore:

```
skills: ["C++", "Python"]
```

✅

But:

```
skills: ["C++", 123]
```

❌

because:

```
"C++" → string ✅
123    → integer ❌
```

## 22. Now a VERY important option: `validationAction`

So far we've assumed:

```
Invalid document
      ↓
REJECT
```

But MongoDB gives us control over what happens when validation fails.

Two major actions you'll encounter:

```
error
warn
```

> MongoDB's current documentation also lists `errorAndLog` in newer MongoDB versions, but for your core syllabus, understand `error` and `warn` first.

---

## 23. `validationAction: "error"`

```
validationAction: "error"
```

means:

> Reject invalid documents.

Example:

```js
db.createCollection("students", {
    validator: {
        $jsonSchema: {
            // ...
        }
    },
    validationAction: "error"
})
```

Invalid insert:

```
INSERT
 ↓
Validation
 ↓
❌
 ↓
REJECT
```

This is the default behavior.

---

## 24. `validationAction: "warn"`

Now:

```
validationAction: "warn"
```

means:

> Allow the invalid operation, but record the validation violation in the MongoDB log.

So:

```
INSERT
 ↓
Validation
 ↓
❌
 ↓
WARN
 ↓
INSERT STILL HAPPENS
```

Why would we ever want this?

Imagine you already have a huge old database and you're introducing validation.

You might not want to suddenly block all old/inconsistent data during a migration.

So:

```
warn
```

can be useful during transition.

> MongoDB documents this as a way to allow invalid documents while recording the violation.

---

## 25. `validationLevel`

Now comes another important concept.

```
validationLevel
```

This controls:

> How strictly MongoDB applies validation rules, particularly with existing documents.

The main levels are:

```
strict
moderate
```

and MongoDB also supports:

```
off
```

for disabling validation.

---

## 26. `strict`

```
validationLevel: "strict"
```

This is the default.

Think:

> "Everyone follows the new rules."

MongoDB applies validation to inserts and updates.

Suppose old collection contains:

```json
{
    "_id": 1,
    "name": "Rahul"
}
```

Then we introduce a new rule:

```
name required
phone required
```

With strict validation, updates to documents are checked against the rules.

---

## 27. `moderate`

This one is more interesting.

```
validationLevel: "moderate"
```

Think:

> "New documents and already-valid documents must follow the rules, but existing invalid documents can be left alone during updates."

Example:

Before validation:

**Student A**

```json
{
    "name": "Rahul",
    "phone": "12345"
}
```

valid.

**Student B:**

```json
{
    "name": "Priya"
}
```

invalid according to the new rule because `phone` is missing.

With:

```
moderate
```

MongoDB applies the new validation rules to:

```
Student A → yes
Student B → not required to pass the new rules
```

This is useful during schema migration.

> MongoDB explicitly documents this distinction between strict and moderate.

---

## 28. SUPER IMPORTANT: `validationLevel` vs `validationAction`

Students often mix these.

Don't.

**`validationLevel`**

asks:

> WHO/WHICH documents are subject to validation?

```
strict
moderate
off
```

**`validationAction`**

asks:

> WHAT should happen when validation fails?

```
error
warn
```

Mental shortcut:

```
LEVEL  → HOW STRICTLY?
ACTION → WHAT TO DO?
```

🔥 Remember this.

## 29. Updating validation rules

Suppose collection already exists.

We don't need to delete and recreate it.

MongoDB provides:

```
collMod
```

to modify collection validation rules.

Example:

```js
db.runCommand({
    collMod: "students",

    validator: {
        $jsonSchema: {
            bsonType: "object",

            required: [
                "name",
                "age",
                "cgpa"
            ],

            properties: {
                name: {
                    bsonType: "string"
                },

                age: {
                    bsonType: "int",
                    minimum: 17
                },

                cgpa: {
                    bsonType: ["double", "int"],
                    minimum: 0,
                    maximum: 10
                }
            }
        }
    },

    validationLevel: "strict",

    validationAction: "error"
})
```

The important idea is:

```
Existing collection
       ↓
collMod
       ↓
Change validator
       ↓
Change validation level/action if needed
```

> MongoDB allows the validation schema, level, and action to be modified.

## 30. What happens to OLD documents?

This is subtle and viva-worthy.

Suppose yesterday you had:

```json
{
    "name": "Rahul",
    "age": 21
}
```

No validation existed.

Today you add:

```
required:
    name
    age
    cgpa
```

Rahul doesn't have `cgpa`.

Does MongoDB automatically delete Rahul?

**NO.**

Existing documents remain.

> Changing validation rules can make existing documents invalid according to the new schema; MongoDB doesn't magically rewrite them. How future updates are treated depends on `validationLevel`.

This is an important schema-evolution concept.

## 31. Validation vs Unique Constraint

🔥 Another common trap.

Suppose we want:

> email must be unique

Don't think:

```
$jsonSchema
```

automatically provides uniqueness.

Schema validation and indexes solve different problems.

**Validation**

checks things like:

```
type
required fields
range
allowed values
structure
```

**Unique index**

handles uniqueness:

```js
db.students.createIndex(
    { email: 1 },
    { unique: true }
)
```

So:

```
Validation
     +
Indexes
     ↓
Data quality + uniqueness
```

This connects directly to our Unit II indexing topic.

## 33. `additionalProperties: false` — advanced but important

JSON Schema also allows:

```
additionalProperties: false
```

Meaning:

> Don't allow fields that aren't defined in the schema's `properties`.

For example:

```js
properties: {
    name: {
        bsonType: "string"
    },

    age: {
        bsonType: "int"
    }
},

additionalProperties: false
```

Now:

```json
{
    "name": "Rahul",
    "age": 21
}
```

✅

But:

```json
{
    "name": "Rahul",
    "age": 21,
    "favouriteColor": "Blue"
}
```

❌

because `favouriteColor` isn't defined.

**BUT THERE IS A TRAP 🚨**

MongoDB automatically adds:

```
_id
```

to documents.

> Therefore, if you use `additionalProperties: false`, you need to account for `_id` in the schema's properties, otherwise documents can be rejected because of the automatically generated `_id`. MongoDB explicitly calls this out in its schema-validation guidance.

For now, just remember:

> `additionalProperties: false` = strict field whitelist.

## 34. One complete practical example

Let's create a proper student collection.

```js
db.createCollection("students", {
    validator: {
        $jsonSchema: {
            bsonType: "object",

            required: [
                "name",
                "age",
                "cgpa",
                "branch"
            ],

            properties: {

                name: {
                    bsonType: "string",
                    description: "Name must be a string"
                },

                age: {
                    bsonType: "int",
                    minimum: 17,
                    maximum: 30,
                    description: "Age must be between 17 and 30"
                },

                cgpa: {
                    bsonType: ["double", "int"],
                    minimum: 0,
                    maximum: 10,
                    description: "CGPA must be between 0 and 10"
                },

                branch: {
                    enum: [
                        "CSE",
                        "ECE",
                        "EEE",
                        "MECH"
                    ],
                    description: "Invalid branch"
                }
            }
        }
    },

    validationLevel: "strict",

    validationAction: "error"
})
```

Now:

### Valid

```js
db.students.insertOne({
    name: "Rahul",
    age: 21,
    cgpa: 8.7,
    branch: "CSE"
})
```

✅

### Invalid age

```js
db.students.insertOne({
    name: "Rahul",
    age: 15,
    cgpa: 8.7,
    branch: "CSE"
})
```

❌

### Invalid CGPA

```js
db.students.insertOne({
    name: "Rahul",
    age: 21,
    cgpa: 12,
    branch: "CSE"
})
```

❌

### Invalid branch

```js
db.students.insertOne({
    name: "Rahul",
    age: 21,
    cgpa: 8.7,
    branch: "Civil"
})
```

❌

### Missing branch

```js
db.students.insertOne({
    name: "Rahul",
    age: 21,
    cgpa: 8.7
})
```

❌

### Wrong type

```js
db.students.insertOne({
    name: "Rahul",
    age: "21",
    cgpa: 8.7,
    branch: "CSE"
})
```

❌

## 37. Exam-ready definitions

**Schema Validation**

> Schema validation is the mechanism in MongoDB used to enforce rules on the structure and content of documents stored in a collection.

**`$jsonSchema`**

> `$jsonSchema` is a MongoDB validation operator used to specify JSON Schema-based rules for validating documents.

**`required`**

> Specifies fields that must be present in a document.

**`properties`**

> Defines validation rules for individual document fields.

**`bsonType`**

> Specifies the BSON data type a field or document must have.

**`enum`**

> Restricts a field to a predefined set of allowed values.

**`validationAction`**

> Determines what MongoDB does when a document violates validation rules, such as rejecting it with `error` or allowing it with `warn`.

**`validationLevel`**

> Determines how strictly MongoDB applies validation rules, particularly to existing documents during updates.

## 38. 🔥 Most important viva questions

### Q1. Is MongoDB schema-less?

**Best answer:**

> MongoDB is schema-flexible and does not enforce a rigid schema by default, but schema validation can be configured to enforce desired document structures and constraints.

### Q2. What is `$jsonSchema`?

> It is a MongoDB validation operator used to define JSON Schema-based validation rules.

### Q3. Difference between `required` and `properties`?

```
required
→ field must exist

properties
→ rules for field
```

### Q4. What does `bsonType` do?

> Specifies the required BSON data type of a field.

### Q5. What does `enum` do?

> Restricts a field to a predefined set of values.

### Q6. Difference between `validationLevel` and `validationAction`?

🔥

```
validationLevel
→ how strictly rules apply

validationAction
→ what happens when rule fails
```

### Q7. What is strict validation?

> Validation rules are applied to all inserts and updates.

### Q8. What is moderate validation?

> Validation applies to new documents and updates to existing documents that already satisfy the validation rules; existing invalid documents are treated more leniently during updates.

### Q9. Does adding validation automatically fix existing invalid documents?

> **NO.**

They remain as they are unless you explicitly clean/update them.

### Q10. Does schema validation guarantee uniqueness?

> **NO.**

Use a unique index for uniqueness.

## 39. 🚨 Common traps

### Trap 1

> MongoDB has no schema.

❌

Say:

> MongoDB has a flexible schema by default and supports schema validation.

### Trap 2

> `required` means the field has the correct type.

❌

`required` only says:

```
field must exist
```

Type is controlled separately.

### Trap 3

> `validationAction: warn` rejects invalid data.

❌

It allows the operation and records the violation.

### Trap 4

> `validationLevel: moderate` means weak validation everywhere.

❌

It has a specific meaning around existing invalid documents.

### Trap 5

> Schema validation creates indexes.

❌

Indexes are a separate mechanism.

### Trap 6

> Adding validation automatically cleans old documents.

❌

It doesn't.
