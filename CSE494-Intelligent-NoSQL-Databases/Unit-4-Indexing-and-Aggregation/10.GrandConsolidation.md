## 2. INDEXING — ABSOLUTE MASTER CONCEPT

Remember our library analogy.

Suppose you have:

```
1,000,000 books
```

and someone asks:

> Find all books by author "Robert".

Without an index:

```
Book 1
 ↓
Book 2
 ↓
Book 3
 ↓
...
 ↓
Book 1,000,000
```

That's conceptually like:

```
COLLSCAN
```

With an index:

```
Author Index
     ↓
"Robert"
     ↓
Relevant documents
```

Conceptually:

```
IXSCAN
```

## 3. What is an index?

**Exam-ready definition:**

> An index is a data structure that MongoDB uses to efficiently locate documents matching query conditions without scanning every document in the collection.

But remember the trade-off:

```
INDEX
 ↓
Faster reads
 +
Extra storage
 +
Extra write/update maintenance
```

> MongoDB recommends designing indexes around actual/common query patterns rather than simply indexing everything.

---

## 4. SINGLE-FIELD INDEX

Suppose frequent query:

```js
db.students.find({
    studentId: 101
})
```

Create:

```js
db.students.createIndex({
    studentId: 1
})
```

Meaning:

```
studentId
    ↓
INDEX
```

Use when the query primarily relies on one field.

---

## 5. COMPOUND INDEX

Suppose frequent query:

```js
db.students.find({
    branch: "CSE",
    year: 4
})
```

We can create:

```js
db.students.createIndex({
    branch: 1,
    year: 1
})
```

Now:

```
branch
   ↓
year
```

is represented in the index order.

> And field order matters for compound indexes. MongoDB supports queries using index prefixes; `{branch:1, year:1}` supports the `branch` prefix, while `year` alone isn't an index prefix.

---

## 6. PREFIX — THE THING YOU MUST REMEMBER

Index:

```js
{
    branch: 1,
    year: 1,
    cgpa: -1
}
```

Prefixes are:

```
branch
branch + year
branch + year + cgpa
```

Think:

```
[A, B, C]

A
A+B
A+B+C
```

Not:

```
B
C
B+C
```

as equivalent prefixes.

This is one of the most common compound-index questions.

---

## 7. ESR

For compound indexes, remember:

```
E → Equality
S → Sort
R → Range
```

Example:

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8 }
}).sort({
    year: -1
})
```

Conceptually:

```
Equality → branch
Sort     → year
Range    → cgpa
```

So an index might be designed around:

```
branch
year
cgpa
```

The exact optimal design depends on workload and selectivity, but ESR is the important design guideline you learned. MongoDB's current compound-index documentation explicitly discusses ESR and the importance of field order.

---

## 8. TEXT INDEX

Normal index:

```js
db.books.createIndex({
    title: 1
})
```

is good for queries such as:

```js
db.books.find({
    title: "MongoDB Basics"
})
```

But what if we ask:

> Find documents where the description contains "cloud computing".

That's a text-search problem.

Text index:

```js
db.books.createIndex({
    description: "text"
})
```

Then:

```js
db.books.find({
    $text: {
        $search: "cloud computing"
    }
})
```

> A self-managed MongoDB collection can have at most one text index, though that index can include multiple text fields. MongoDB currently recommends MongoDB Search for improved full-text search capabilities.

For your course:

```
TEXT INDEX
 ↓
$text
 ↓
search words in text
```

## 9. INDEX TYPE DECISION MATRIX

This is your Unit IV decision table.

| Situation                                    | Think                     |
|--------------------------------------------------|-------------------------------|
| Query frequently filters one field                 | Single-field index               |
| Query frequently uses multiple fields                 | Compound index                     |
| Query needs word-based text search                       | Text index                           |
| Field contains arrays                                       | Multikey behavior                      |
| Need efficient query + sort                                    | Compound index                           |
| Need to investigate performance                                   | `explain()`                                |
| Query can return entirely from index                                 | Covered query                                |

> MongoDB also automatically creates the `_id` index for normal collections, and arrays can cause indexes to become multikey.

## 11. COLLSCAN VS IXSCAN

### COLLSCAN

```
COLLECTION
   ↓
Document 1
Document 2
Document 3
...
```

MongoDB scans the collection.

### IXSCAN

```
INDEX
 ↓
matching index keys
 ↓
relevant documents
```

MongoDB scans the index.

So when reading an `explain()` result:

```
COLLSCAN
```

should immediately make you think:

> Collection scan.

And:

```
IXSCAN
```

should make you think:

> Index scan.

> MongoDB's explain documentation identifies these execution stages and explains that covered queries can use an `IXSCAN` without a `FETCH`.

Suppose:

```js

```

You're basically asking:

> "MongoDB, show me how you executed this query."

This is incredibly important.

You're not just asking:

> Did I get the correct result?

You're asking:

> HOW did MongoDB get the result?

## 13. What do we inspect?

The major things:

```
winningPlan
executionStages
nReturned
totalKeysExamined
totalDocsExamined
executionTimeMillis
```

Suppose:

```
nReturned = 10
totalDocsExamined = 100000
```

You should think:

> Hmm. MongoDB examined 100,000 documents to return only 10.

That's potentially inefficient.

Now:

```
nReturned = 10
totalDocsExamined = 10
```

Much less unnecessary document examination.

Don't judge performance from one number alone; use the execution plan and representative workload/data.

## 14. COVERED QUERY

This is one of the coolest concepts in Unit IV.

Suppose:

```js
db.students.createIndex({
    studentId: 1,
    name: 1
})
```

Query:

```js
db.students.find(
    {
        studentId: 101
    },
    {
        name: 1,
        _id: 0
    }
)
```

What does the query need?

```
studentId → index contains it
name      → index contains it
_id       → explicitly excluded
```

Therefore MongoDB can potentially answer the query entirely using the index.

That's a:

```
COVERED QUERY
```

> MongoDB describes a covered query as one where the index contains all fields needed by the query, allowing MongoDB to satisfy it using index keys without examining the collection documents.

---

## 15. Covered-query mental picture

Normal query:

```
QUERY
 ↓
INDEX
 ↓
FETCH DOCUMENT
 ↓
RESULT
```

Covered:

```
QUERY
 ↓
INDEX
 ↓
RESULT
```

No document fetch required.

In `explain()`, a covered query can show an `IXSCAN` that is not beneath a `FETCH`.

## 16. WHY `_id: 0`?

Suppose index contains:

```
studentId
name
```

But projection automatically includes `_id` unless excluded.

If we write:

```js
{
    name: 1
}
```

MongoDB may also need `_id`.

So:

```js
{
    name: 1,
    _id: 0
}
```

is important when constructing a classic covered-query example.

## 17. NOW WE ENTER AGGREGATION

**Indexing asks:**

> Find efficiently.

**Aggregation asks:**

> Process intelligently.

Basic syntax:

```js
db.students.aggregate([
    {
        $match: {
            branch: "CSE"
        }
    }
])
```

Pipeline:

```
COLLECTION
    ↓
$match
    ↓
next stage
    ↓
next stage
    ↓
RESULT
```

> MongoDB defines an aggregation pipeline as one or more stages that process documents sequentially, passing each stage's output to the next.

---

## 18. `$match`

Think:

```
$match = FILTER
```

Example:

```js
{
    $match: {
        branch: "CSE",
        cgpa: {
            $gte: 8
        }
    }
}
```

Meaning:

```
branch = CSE
AND
CGPA >= 8
```

---

## 19. `$project`

Think:

```
$project = SHAPE THE OUTPUT
```

Example:

```js
{
    $project: {
        name: 1,
        cgpa: 1,
        _id: 0
    }
}
```

---

## 20. `$set`

Think:

```
$set = ADD/CALCULATE FIELD
```

Example:

```js
{
    $set: {
        total: {
            $multiply: [
                "$price",
                "$quantity"
            ]
        }
    }
}
```

> `$set` is an alias for `$addFields`; it adds fields while retaining existing fields.

---

## 21. `$group`

Think:

```
$group = GROUP + CALCULATE
```

Example:

```js
{
    $group: {
        _id: "$branch",

        count: {
            $sum: 1
        },

        averageCgpa: {
            $avg: "$cgpa"
        }
    }
}
```

---

## 22. `$sort`

Think:

```
$sort = ORDER
```

```js
{
    $sort: {
        averageCgpa: -1
    }
}
```

---

## 23. `$limit`

Think:

```
$limit = TOP N / ONLY N
```

```js
{
    $limit: 5
}
```

---

## 24. `$unwind`

Think:

```
$unwind = ARRAY → INDIVIDUAL PIPELINE DOCUMENTS
```

Before:

```json
{
    "name": "Rahul",
    "skills": [
        "Python",
        "MongoDB",
        "C++"
    ]
}
```

After:

```
Rahul → Python
Rahul → MongoDB
Rahul → C++
```

This is one of the most important patterns in practical aggregation.

---

## 25. `$lookup`

Think:

```
$lookup = JOIN-LIKE OPERATION
```

Example:

```js
{
    $lookup: {
        from: "departments",
        localField: "departmentId",
        foreignField: "_id",
        as: "department"
    }
}
```

Output:

```
student
   +
department[]
```

Then often:

```
$unwind
```

to flatten that one-element array.

## 26. ACCUMULATORS MASTER TABLE

| Operator      | Think                                     |
|-------------------|------------------------------------------------|
| `$sum`               | Add / count                                       |
| `$avg`                 | Average                                             |
| `$min`                   | Lowest                                                |
| `$max`                     | Highest                                                 |
| `$push`                      | Collect values, duplicates allowed                        |
| `$addToSet`                     | Collect unique values                                       |
| `$first`                           | First value in current order                                  |
| `$last`                               | Last value in current order                                      |

The critical thing:

```
$group
   ↓
accumulator
```

The accumulator works across documents belonging to each group.

## 27. THE MOST IMPORTANT AGGREGATION PATTERNS

### Pattern A — Count per category

```js
[
    {
        $group: {
            _id: "$category",
            count: {
                $sum: 1
            }
        }
    }
]
```

### Pattern B — Average per category

```js
[
    {
        $group: {
            _id: "$category",
            average: {
                $avg: "$value"
            }
        }
    }
]
```

### Pattern C — Total

```js
[
    {
        $group: {
            _id: null,
            total: {
                $sum: "$amount"
            }
        }
    }
]
```

### Pattern D — Top N

```
$sort
 ↓
$limit
```

### Pattern E — Array analysis

```
$unwind
 ↓
$group
```

### Pattern F — Calculate then summarize

```
$set
 ↓
$group
```

### Pattern G — Reference another collection

```
$lookup
 ↓
$unwind
 ↓
$project / $group
```

## 28. NOW — THE MOST IMPORTANT THING: QUESTION TRANSLATION

This is where I want your DSA-style logic building to kick in.

Suppose the question says:

> Find the top 5 products by revenue from completed orders.

Don't start coding.

Translate English:

```
"completed"
$match

"products are inside items array"
$unwind

"revenue"
price × quantity

Therefore:
$set

"by product"
$group
_id: "$items.product"

"revenue total"
$sum

"top"
$sort descending

"5"
$limit 5
```

Now code almost writes itself:

```js
db.orders.aggregate([
    {
        $match: {
            status: "completed"
        }
    },

    {
        $unwind: "$items"
    },

    {
        $set: {
            revenue: {
                $multiply: [
                    "$items.price",
                    "$items.quantity"
                ]
            }
        }
    },

    {
        $group: {
            _id: "$items.product",

            totalRevenue: {
                $sum: "$revenue"
            }
        }
    },

    {
        $sort: {
            totalRevenue: -1
        }
    },

    {
        $limit: 5
    }
])
```

**THAT is the skill.**

Not memorizing 50 pipelines.

## 33. A VERY IMPORTANT NUANCE

Don't memorize:

> "Every aggregation needs an index."

❌ No.

Aggregation is a processing framework.

Indexes can help specific stages and access patterns, especially filtering and sorting situations where the optimizer can use them.

> MongoDB's query optimization guidance emphasizes designing indexes around common queries and workload characteristics.

So think:

```
Need index?
     ↓
What query/stage?
     ↓
What fields?
     ↓
How selective?
     ↓
What does explain() say?
```

## 34. COMPLETE PERFORMANCE LOOP

This is the production mindset:

```
1. Identify frequent query
          ↓
2. Understand filter/sort fields
          ↓
3. Design index
          ↓
4. Run query
          ↓
5. explain("executionStats")
          ↓
6. Inspect plan
          ↓
7. Check documents examined
          ↓
8. Check keys examined
          ↓
9. Check execution time
          ↓
10. Adjust index/query if needed
          ↓
11. Test again
```

> MongoDB recommends profiling index configurations against representative workloads and removing indexes that are no longer useful.

## 35. COMPLETE AGGREGATION PERFORMANCE LOOP

Similarly:

```
1. Understand requirement
          ↓
2. Filter unnecessary documents
          ↓
3. Unwind only when required
          ↓
4. Calculate required fields
          ↓
5. Group
          ↓
6. Lookup only when necessary
          ↓
7. Sort
          ↓
8. Limit
          ↓
9. Inspect performance
```

And remember:

> Correctness first, optimization second.

Don't destroy a correct pipeline just because you want fewer stages.

## 36. SINGLE vs COMPOUND vs TEXT — FINAL COMPARISON

| Feature               | Single             | Compound                       | Text                                |
|--------------------------|-----------------------|-------------------------------------|-------------------------------------------|
| Fields                     | One                     | Multiple                              | One or multiple text fields                 |
| Main purpose                 | Field lookup              | Multi-field queries                     | Word/text search                              |
| Example                         | `{age:1}`                   | `{branch:1,year:1}`                       | `{description:"text"}`                          |
| Order important?                   | Usually less relevant          | Yes                                          | Different semantics                                |
| `$text`                                | ❌                                | Can include text key                            | ✅                                                   |
| Prefix concept                            | N/A                                 | Important                                          | Special restrictions                                   |
| Typical use                                  | Simple filter                          | Filter + sort/range                                    | Full-text search                                          |

> MongoDB's current documentation distinguishes these index types and notes that text indexes are the legacy self-managed full-text mechanism, with MongoDB Search recommended for newer full-text workloads.

## 41. 30 BEST UNIT IV VIVA QUESTIONS 🔥

Let's do these quickly but with answers that are actually viva-friendly.

**1. What is an index?**

> A data structure that helps MongoDB locate documents efficiently for supported queries.

**2. Why use indexes?**

> To improve query performance by reducing unnecessary data scanning.

**3. What is COLLSCAN?**

> Scanning documents in the collection to find matching documents.

**4. What is IXSCAN?**

> Scanning an index to locate relevant records.

**5. What is a single-field index?**

> An index built on one field.

**6. What is a compound index?**

> An index containing multiple fields.

**7. Why does compound-index field order matter?**

> Because the index is organized according to field order and supports index prefixes.

**8. What is an index prefix?**

> The beginning subset of fields in a compound index.

**9. What is ESR?**

> Equality, Sort, Range — a guideline for arranging compound-index fields.

**10. What is a text index?**

> An index that supports `$text` queries on string content in self-managed MongoDB deployments.

**11. How many text indexes can a collection have?**

> At most one text index.

**12. What is `explain()`?**

> A mechanism for examining how MongoDB executes a query or operation.

**13. What is a covered query?**

> A query whose required query/projection fields can be satisfied entirely from the index without fetching collection documents.

**14. What does `totalDocsExamined` mean?**

> Number of collection documents examined during execution.

**15. What does `totalKeysExamined` mean?**

> Number of index keys examined.

**16. What is aggregation?**

> Processing documents through a sequence of pipeline stages to produce transformed or summarized results.

**17. What is an aggregation pipeline?**

> A sequence of stages where each stage processes the output of the previous stage.

**18. What does `$match` do?**

> Filters documents.

**19. What does `$project` do?**

> Controls/reshapes fields in output documents.

**20. What does `$group` do?**

> Groups documents by a key and can calculate aggregate values.

**21. What does `$sum: 1` commonly do?**

> Counts documents within each group.

**22. What does `$avg` do?**

> Calculates an average.

**23. What does `$unwind` do?**

> Deconstructs an array so each element becomes a separate pipeline document.

**24. What does `$lookup` do?**

> Performs a left outer join-like operation with another collection.

**25. Why is `$unwind` often used after `$lookup`?**

> Because `$lookup` adds matching documents as an array.

**26. What does `$sort` do?**

> Orders documents.

**27. What does `$limit` do?**

> Restricts the number of documents passed onward.

**28. Does aggregation normally modify source documents?**

> No, not with ordinary `aggregate()` pipelines; `$merge` or `$out` can write results.

**29. Why use `$match` early when possible?**

> To reduce unnecessary documents flowing through later stages and potentially improve performance.

**30. What is the difference between indexing and aggregation?**

> Indexing helps find data efficiently; aggregation processes and analyzes data.

🔥 That's your Unit IV viva core.

## 42. COMMON UNIT IV TRAPS 🚨

### Trap 1

> Compound index `{a,b}`

doesn't mean:

```
b alone
```

is automatically an equivalent prefix.

### Trap 2

> `$group` does not automatically sort output.

Use:

```
$sort
```

when order matters.

### Trap 3

> `$unwind` doesn't multiply according to quantity.

It expands array elements.

### Trap 4

> `$lookup` produces matching results as an array.

### Trap 5

> `$first` doesn't automatically mean "highest."

Sort first if highest/lowest matters.

### Trap 6

> `$project` and `$set` aren't identical.

```
$project
→ reshape/select

$set
→ add/change while retaining existing fields
```

### Trap 7

> More indexes ≠ always better.

Indexes have storage and write-maintenance costs.

### Trap 8

> COLLSCAN isn't automatically "wrong."

For some queries, scanning may be reasonable depending on selectivity and workload.

The correct question is:

> Is this execution plan efficient for this workload?

## 43. WHAT TO WRITE IN AN EXAM

If asked:

> Explain indexing in MongoDB.

Write:

> An index is a data structure that improves query performance by allowing MongoDB to locate matching documents more efficiently. MongoDB supports several index types including single-field, compound, multikey, text, geospatial and others. Indexes improve read performance but require additional storage and maintenance during writes. Indexes should therefore be designed according to application query patterns.

Then example:

```js
db.students.createIndex({
    branch: 1,
    year: 1
})
```

## 44. WHAT TO WRITE FOR AGGREGATION

If asked:

> Explain aggregation framework.

Write:

> MongoDB's aggregation framework processes documents through a sequence of pipeline stages. Each stage performs an operation such as filtering, grouping, sorting, transforming or joining data, and passes its output to the next stage. The pipeline can produce summarized and analytical results.

Example:

```js
db.students.aggregate([
    {
        $match: {
            branch: "CSE"
        }
    },

    {
        $group: {
            _id: "$year",
            averageCgpa: {
                $avg: "$cgpa"
            }
        }
    },

    {
        $sort: {
            averageCgpa: -1
        }
    }
])
```

## 45. WHAT NOT TO WRITE

Avoid vague statements like:

> "Index makes MongoDB faster."

Too incomplete.

Better:

> "Indexes can improve query performance by reducing the amount of data MongoDB must scan, at the cost of additional storage and write/update maintenance."

Don't write:

> "`$group` sorts documents."

❌ Wrong.

Write:

> "`$group` groups documents by a specified key and can calculate aggregate values."

Don't write:

> "`$lookup` is exactly the same as SQL JOIN."

Better:

> "`$lookup` provides a left outer join-like operation between collections."
