## 1. First: Why do we need compound indexes?

Let's return to our student collection.

```json
{
    "name": "Rahul",
    "branch": "CSE",
    "cgpa": 8.7,
    "year": 4
}
```

Suppose our application frequently asks:

```js
db.students.find({
    branch: "CSE",
    year: 4
})
```

We could create two separate indexes:

```js
db.students.createIndex({ branch: 1 })
```

and:

```js
db.students.createIndex({ year: 1 })
```

But the query is fundamentally about the combination:

```
branch + year
```

So MongoDB allows us to create:

```js
db.students.createIndex({
    branch: 1,
    year: 1
})
```

That's a:

```
Compound index
```

> MongoDB defines a compound index as an index containing references to multiple fields. A compound index can support queries on the indexed fields and their index prefixes.

---

## 2. Single vs Compound

Let's make the difference crystal clear.

### Single-field index

```js
db.students.createIndex({
    branch: 1
})
```

One field:

```
branch
```

### Compound index

```js
db.students.createIndex({
    branch: 1,
    year: 1
})
```

Two fields:

```
branch
year
```

### Three-field compound index

You can have:

```js
db.students.createIndex({
    branch: 1,
    year: 1,
    cgpa: -1
})
```

Now the index involves:

```
branch
   ↓
year
   ↓
cgpa
```

> MongoDB currently permits up to 32 fields in a single compound index.

But obviously, that doesn't mean:

> "Let's put 32 fields into every index." 😂

We'll see why later.

---

## 3. Basic syntax

The syntax is:

```js
db.collection.createIndex({
    field1: 1,
    field2: 1,
    field3: -1
})
```

Example:

```js
db.students.createIndex({
    branch: 1,
    cgpa: -1
})
```

Meaning:

```
First organize by branch
        ↓
Within each branch,
organize by cgpa descending
```

That sentence is **VERY IMPORTANT.**

Read it again:

> First field controls the major ordering; subsequent fields organize values within the preceding field's groups.

> MongoDB's documentation describes compound indexes as sorting data in the order specified by the index fields.

---

## 4. Let's visualize a compound index

Suppose our students are:

```
Rahul   CSE   8.7
Arjun   CSE   7.8
Sneha   EEE   8.9
Priya   ECE   9.1
Karan   CSE   9.2
Meera   EEE   8.1
```

Create:

```js
db.students.createIndex({
    branch: 1,
    cgpa: -1
})
```

Conceptually, the index is ordered something like:

```
CSE
 ├── 9.2 → Karan
 ├── 8.7 → Rahul
 └── 7.8 → Arjun

ECE
 └── 9.1 → Priya

EEE
 ├── 8.9 → Sneha
 └── 8.1 → Meera
```

Notice what's happening.

First:

```
branch
```

is organized.

Then:

```
cgpa
```

is organized within each branch.

So the index isn't simply:

```
branch
cgpa
```

as two independent things.

It is an **ordered combination:**

```
(branch, cgpa)
```

That's the core idea.

---

## 5. Why field order matters

Now we reach the most important concept of this part.

Compare:

**Index A**

```js
{
    branch: 1,
    cgpa: -1
}
```

with:

**Index B**

```js
{
    cgpa: -1,
    branch: 1
}
```

They are **not** the same index.

They organize the data differently.

> MongoDB explicitly states that field order in a compound index is very important because the index is structured according to that order.

---

## 6. Think of a dictionary

Imagine a giant dictionary.

It's primarily arranged by:

```
A
B
C
D
...
```

Now imagine within each letter, words are alphabetically ordered.

So:

```
A
 ├── apple
 ├── ant
 └── aquarium
```

The first ordering determines how you enter the structure.

Similarly:

```js
{
    branch: 1,
    cgpa: -1
}
```

means conceptually:

```
branch first
     ↓
cgpa second
```

Whereas:

```js
{
    cgpa: -1,
    branch: 1
}
```

means:

```
cgpa first
     ↓
branch second
```

Different structure.

Different query usefulness.

---

## 7. The magical concept: INDEX PREFIX

This is probably the most important term you'll learn today.

Suppose we create:

```js
db.students.createIndex({
    branch: 1,
    year: 1,
    cgpa: -1
})
```

The index is:

```
branch
year
cgpa
```

Its prefixes are:

```
branch

branch + year

branch + year + cgpa
```

> MongoDB can use a compound index for queries involving the index's prefix fields.

---

## 8. Visualize the prefix

Think of:

```
[A] → [B] → [C]
```

where:

```
A = branch
B = year
C = cgpa
```

Valid prefixes are:

```
[A]

[A, B]

[A, B, C]
```

But:

```
[B]
```

is **NOT** a prefix.

And:

```
[B, C]
```

is **NOT** a prefix.

And:

```
[A, C]
```

isn't the complete leading prefix either.

This is the reason field order matters so much.

---

## 9. Example with actual queries

Suppose:

```js
db.students.createIndex({
    branch: 1,
    year: 1
})
```

### Query 1

```js
db.students.find({
    branch: "CSE"
})
```

✅ Supported by the index.

Why?

Because:

```
branch
```

is the first field.

### Query 2

```js
db.students.find({
    branch: "CSE",
    year: 4
})
```

✅ Supported.

Because it uses:

```
branch + year
```

which is the complete index.

### Query 3

```js
db.students.find({
    year: 4
})
```

This does not get the same benefit from this compound index as a query on the prefix `branch`.

Why?

Because:

```
year
```

is not the beginning of:

```
branch → year
```

> MongoDB's documentation gives the same principle: an index `{name: 1, gpa: -1}` supports queries on `name` or `name + gpa`, but not a query on `gpa` alone because `gpa` is not an index prefix.

---

## 10. This is the FIRST huge rule

Memorize this conceptually:

> 🔥 A compound index is most directly useful from its **leftmost** fields — its index prefixes.

For:

```js
{
    A: 1,
    B: 1,
    C: 1
}
```

think:

```
A
A+B
A+B+C
```

Not:

```
B
C
B+C
```

This is why we don't randomly arrange fields.

---

## 11. Let's connect this to a real university

Suppose we have:

```json
{
    "studentId": 101,
    "branch": "CSE",
    "year": 4,
    "cgpa": 8.7
}
```

Our university portal frequently asks:

**Query A**

> Show all CSE students.

```js
db.students.find({
    branch: "CSE"
})
```

**Query B**

> Show all CSE 4th-year students.

```js
db.students.find({
    branch: "CSE",
    year: 4
})
```

**Query C**

> Show all students with CGPA above 8.5.

```js
db.students.find({
    cgpa: { $gt: 8.5 }
})
```

If our index is:

```js
{
    branch: 1,
    year: 1
}
```

then it naturally helps A and B.

It isn't designed around C.

That's why:

> Index design should come from actual query patterns.

> MongoDB recommends mapping application queries and the fields they access before designing indexes.

---

## 12. Why not just make three indexes?

You could technically have:

```
{ branch: 1 }
{ year: 1 }
{ cgpa: 1 }
```

But now MongoDB has to maintain multiple structures.

And our application might benefit more from a compound index designed around a frequent multi-field query.

So the question isn't:

> "Which fields exist?"

It's:

> "Which combinations of fields does the application frequently query, filter, sort, or project?"

That's the database engineer mindset.

---

## 13. Compound index with equality conditions

Let's take:

```js
db.students.find({
    branch: "CSE",
    year: 4
})
```

Both are exact matches.

These are called:

```
Equality predicates
```

And an index like:

```js
{
    branch: 1,
    year: 1
}
```

fits naturally.

> MongoDB's ESR guideline says equality fields should come first in a compound index.

---

## 14. Wait — what's ESR?

🔥 Now we're reaching the famous MongoDB indexing guideline.

**E — Equality**

Exact match:

```
{ branch: "CSE" }
```

**S — Sort**

Ordering:

```js
.sort({
    cgpa: -1
})
```

**R — Range**

Range condition:

```
{ cgpa: { $gte: 8.5 } }
```

So:

```
E → Equality
S → Sort
R → Range
```

MongoDB calls this the:

```
ESR (Equality, Sort, Range) guideline
```

> In most cases, MongoDB recommends arranging compound index keys using ESR because it produces efficient indexes for common query patterns.

---

## 15. Let's understand Equality first

Equality means:

> "I know exactly what value I'm looking for."

Examples:

```
{ branch: "CSE" }
{ year: 4 }
{ department: "Engineering" }
{ country: "India" }
```

Conceptually:

```
branch = CSE
        ↓
exact group

year = 4
        ↓
exact group
```

> MongoDB says equality fields should come first in the index because they narrow the search space before subsequent fields are processed.

---

## 16. Sort

Suppose:

```js
db.students.find({
    branch: "CSE"
}).sort({
    cgpa: -1
})
```

We're doing:

```
Equality:
branch = CSE

Sort:
cgpa descending
```

An appropriate index could be:

```js
{
    branch: 1,
    cgpa: -1
}
```

Conceptually:

```
CSE
 ├── 9.5
 ├── 9.2
 ├── 8.9
 ├── 8.7
 └── 7.8
```

The index can provide the results in the desired ordering rather than requiring an additional in-memory sort in suitable cases. MongoDB documents this pattern explicitly.

---

## 17. Range

Now:

```
{
    cgpa: { $gte: 8.5 }
}
```

means:

```
CGPA >= 8.5
```

That's a range.

Other examples:

```
{ age: { $gt: 20 } }
{ salary: { $lte: 100000 } }
{ price: { $gte: 500, $lte: 2000 } }
```

> MongoDB treats inequality operators such as `$ne`, `$nin`, and `$regex` as range-like predicates for ESR purposes.

---

## 18. Putting ESR together

Suppose our query is:

```js
db.products.find({
    category: "Laptop",
    price: { $gte: 50000 }
}).sort({
    rating: -1
})
```

Let's identify the components.

**Equality**

```
category = Laptop
```

**Range**

```
price >= 50000
```

**Sort**

```
rating descending
```

ESR tells us to generally think:

```
Equality
    ↓
Sort
    ↓
Range
```

So a candidate index would be:

```js
{
    category: 1,
    rating: -1,
    price: 1
}
```

> MongoDB's current ESR documentation gives this exact conceptual pattern: equality first, then sort vs range depending on the workload.

---

## 19. But wait — isn't it always ESR?

Here's an important advanced nuance.

The guideline is ESR, but MongoDB's documentation says there are cases where **ERS** can be better.

That's:

```
Equality
Range
Sort
```

When?

> If the range predicate is highly selective.

For example:

```
1 billion documents
       ↓
range filter reduces to 500 documents
       ↓
then sorting 500 documents may be cheap
```

In such a case:

```
E → R → S
```

can sometimes be preferable.

> MongoDB explicitly says that if avoiding an in-memory sort is critical, place sort before range (ESR); if the range predicate is highly selective, placing range before sort (ERS) may be better.

Don't worry about memorizing ERS yet.

For now:

> ESR is your starting guideline.

Later, `explain()` will teach us how to verify the actual performance.

Let's create:

```js

})
```

Now query:

```js
db.students.find({
    branch: "CSE"

```

Our index is conceptually:

```
branch ASC
      ↓
cgpa DESC
```

So:

```

 ├── 9.8
 ├── 9.4
 ├── 9.1
 ├── 8.9
 └── 8.2

ECE
 ├── 9.6
 ├── 9.0

 ...
```

The CSE section is already ordered by descending CGPA.

That's why this index matches the query beautifully.

## 21. Why `{ branch: 1, cgpa: -1 }` and `{ cgpa: -1, branch: 1 }` differ

Let's put them side-by-side.

### Index A

```js
{
    branch: 1,
    cgpa: -1
}
```

Conceptually:

```
branch
  ↓
cgpa
```

Useful for:

```
branch
branch + cgpa
branch + sort by cgpa
```

### Index B

```js
{
    cgpa: -1,
    branch: 1
}
```

Conceptually:

```
cgpa
  ↓
branch
```

Useful patterns are different.

It is naturally organized first by CGPA, then branch.

So:

```
Index A ≠ Index B
```

even though they contain the same two fields.

This is one of the most important facts in MongoDB indexing.

Imagine your phone contacts are sorted:

**Version A**

```
Country
   ↓
City
      ↓
Name
```

You can quickly navigate:

```
India
India + Amritsar
India + Amritsar + Rahul
```

But if you ask:

```

```

without first narrowing by country, that isn't the natural prefix.

Now reverse the structure:

```
City
   ↓
Country
      ↓
Name
```

Suddenly:

```
Amritsar
Amritsar + India
```

become the natural prefixes.

That's exactly how field ordering in compound indexes works.

## 23. Compound index and sorting

This deserves special attention.

Suppose:

```js
db.students.createIndex({
    branch: 1,
    cgpa: -1
})
```

This index has:

```
branch ASC
cgpa DESC
```

It can support the corresponding sort direction:

```js
.sort({
    branch: 1,
    cgpa: -1
})
```

It can also support the complete reverse:

```js
.sort({
    branch: -1,
    cgpa: 1
})
```

> MongoDB documents that a compound index can support its own sort pattern or the complete reverse of that pattern.

But not arbitrary mixtures.

For example, an index:

```js
{
    score: -1,
    username: 1
}
```

doesn't support every possible combination of directions.

---

## 24. Prefix + sorting

There's another subtle rule.

Suppose:

```js
db.data.createIndex({
    a: 1,
    b: 1,
    c: 1,
    d: 1
})
```

Prefixes:

```
a
a+b
a+b+c
a+b+c+d
```

Now if you're sorting on:

```
b
```

you can't simply say:

> "b is in the index, so MongoDB will use it for sorting."

The preceding prefix fields matter.

> MongoDB's documentation explains that an index can support sorting on a subset of its keys when the query has equality conditions on the prefix keys that come before the sort keys.

So:

```
index:
A → B → C

query:
A = something

sort:
B
```

is a natural situation.

But:

```
query:
nothing about A

sort:
B
```

doesn't give you the same benefit.

---

## 25. Compound indexes and equality fields

Here's a subtle but useful point.

Suppose:

```js
{
    branch: 1,
    year: 1,
    cgpa: -1
}
```

and query:

```js
{
    branch: "CSE",
    year: 4
}
```

Both are equality fields.

The equality fields can be placed in either order relative to each other from the ESR guideline perspective:

```
branch + year
```

or:

```
year + branch
```

can both satisfy the "equality fields first" principle.

But which one is better overall depends on the broader query workload and prefix requirements.

For example:

**If you frequently query `branch` alone**

then:

```
{ branch: 1, year: 1 }
```

may be preferable because `branch` becomes a useful prefix.

**If you frequently query `year` alone:**

```
{ year: 1, branch: 1 }
```

may be more useful for that workload.

> MongoDB's ESR guidance says multiple equality fields can appear in either order relative to each other, but all equality fields should precede sort/range fields.

---

## 26. This is why query workload comes first

Imagine these application queries:

```
Q1:
branch = CSE

Q2:
branch = CSE AND year = 4

Q3:
year = 4

Q4:
branch = CSE
sort by cgpa
```

You shouldn't simply say:

> "ESR says something, so I'll randomly arrange fields."

Instead:

```
APPLICATION
     ↓
QUERY PATTERNS
     ↓
FREQUENCY
     ↓
FILTERS
     ↓
SORTS
     ↓
RANGES
     ↓
INDEX ORDER
```

That's real index design.

```

Imagine a train.

```
🚂 → A → B → C
```

You can enter at:

```

## 32. What if we have multiple compound indexes?

Suppose:

```js
db.students.createIndex({
    branch: 1,
    year: 1
})
```

and:

```js
db.students.createIndex({
    cgpa: -1,
    name: 1
})
```

Now we have:

```
Index 1:
branch → year

Index 2:
cgpa → name
```

Different indexes support different workload patterns.

This is why index design is essentially:

> Matching data-access patterns to data structures.

---

## 33. Don't create redundant indexes blindly

Suppose we already have:

```js
{
    branch: 1,
    year: 1
}
```

Do we automatically need:

```js
{
    branch: 1
}
```

Not necessarily.

The compound index already has:

```
branch
```

as its prefix, so it can support many queries involving `branch` alone. MongoDB explicitly documents this prefix behavior.

So blindly creating:

```
branch index
+
branch/year index
```

may be unnecessary depending on your workload.

Again:

> Don't index blindly.

---

## 34. But compound index isn't always a replacement for every single index

Suppose you have:

```js
{
    branch: 1,
    year: 1
}
```

This doesn't mean you've automatically solved:

```js
find({ cgpa: 8.9 })
```

because `cgpa` isn't present.

And:

```js
find({ year: 4 })
```

doesn't get the same prefix benefit as:

```js
find({ branch: "CSE" })
```

So compound indexes are powerful, but their field order and prefix structure matter.

## 35. One subtle point about `{a:1,b:1}` vs `{a:1,b:-1}`

Suppose:

```js
{
    branch: 1,
    cgpa: 1
}
```

and:

```js
{
    branch: 1,
    cgpa: -1
}
```

Are they completely different?

They have the same field order, but different sort direction for `cgpa`.

This matters particularly when supporting multi-field sorts.

For example, an index:

```js
{
    score: -1,
    username: 1
}
```

naturally supports:

```js
{
    score: -1,
    username: 1
}
```

and its complete reverse:

```js
{
    score: 1,
    username: -1
}
```

but not arbitrary direction combinations.

We'll revisit this in our performance section.

## 36. Compound Index + Range

Let's do a practical example.

Query:

```js
db.students.find({
    branch: "CSE",
    cgpa: { $gte: 8.5 }
})
```

We have:

```
Equality:
branch = CSE

Range:
cgpa >= 8.5
```

A natural compound index is:

```js
{
    branch: 1,
    cgpa: 1
}
```

Why?

```
Equality
   ↓
branch

Range
   ↓
cgpa
```

That's:

```
E → R
```

For a query with only equality and range, this is a natural ESR-style arrangement.

## 37. Compound Index + Equality + Sort + Range

Now:

```js
db.products.find({
    category: "Laptop",
    price: { $gte: 50000 }
}).sort({
    rating: -1
})
```

Identify:

```
category → Equality
rating   → Sort
price    → Range
```

Starting from ESR:

```
E → S → R
```

Therefore:

```js
{
    category: 1,
    rating: -1,
    price: 1
}
```

is a candidate design.

> MongoDB's query optimization documentation demonstrates the same conceptual ordering: equality first, sort second, range third.

---

## 38. But what if the range is extremely selective?

Suppose:

```
1,000,000,000 products
```

and:

```
price >= 9,999,999
```

returns:

```
only 10 products
```

Then perhaps:

```
E → R → S
```

could be more efficient.

Why?

```
category equality
       ↓
very selective price range
       ↓
only 10 documents
       ↓
sort 10 documents
```

This is the ERS case we mentioned earlier.

> MongoDB explicitly recommends considering ERS when the range predicate is highly selective.

This is why:

> ESR is a guideline, not a magical law.

## 41. The golden rules of compound indexes

Mate, these are the things I want looping in your brain after this part.

### 🔥 Rule 1

> Compound index = index on multiple fields.

```js
{
    branch: 1,
    year: 1
}
```

### 🔥 Rule 2

> Field order matters.

```
{ branch: 1, year: 1 }
```

is **not** equivalent to:

```
{ year: 1, branch: 1 }
```

### 🔥 Rule 3

> Prefix matters.

For:

```
A → B → C
```

think:

```
A
A+B
A+B+C
```

### 🔥 Rule 4

> Don't design indexes from fields alone. Design them from queries.

```
WORKLOAD
   ↓
QUERY PATTERNS
   ↓
INDEX DESIGN
```

> MongoDB's indexing guidance explicitly recommends mapping application queries before creating indexes.

### 🔥 Rule 5

> ESR is the starting guideline.

```
E = Equality
S = Sort
R = Range
```

Generally:

```
Equality → Sort → Range
```

But highly selective ranges can sometimes motivate:

```
Equality → Range → Sort
```

### 🔥 Rule 6

> A compound index isn't automatically useful for every field inside it.

For:

```
A → B → C
```

a query on:

```
A
```

can naturally use the prefix.

A query only on:

```
B
```

doesn't get the same prefix advantage.

## 🧠 ONE FINAL DRY RUN

Suppose you have:

```js
db.orders.createIndex({
    customerId: 1,
    status: 1,
    orderDate: -1
})
```

Application query:

```js
db.orders.find({
    customerId: 101,
    status: "Delivered"
}).sort({
    orderDate: -1
})
```

Let's decode it.

**Step 1**

Fields:

```
customerId
status
orderDate
```

**Step 2**

Query:

```
customerId = 101
```

Equality.

**Step 3**

```
status = Delivered
```

Equality.

**Step 4**

```
orderDate DESC
```

Sort.

So conceptually:

```
E
E
S
```

Index:

```
customerId
    ↓
status
    ↓
orderDate
```

Beautiful match.

Now imagine someone creates:

```js
{
    orderDate: -1,
    customerId: 1,
    status: 1
}
```

Have they used the same three fields?

Yes.

Have they created an equivalent index?

**NO.**

Because now the index starts with:

```
orderDate
```

rather than:

```
customerId
```

The index's structure and useful query prefixes have changed.

That's why field order is king in compound indexes. 🔥
