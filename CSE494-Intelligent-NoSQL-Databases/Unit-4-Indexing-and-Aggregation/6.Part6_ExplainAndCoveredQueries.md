## 1. First: What is `explain()`?

Imagine you run:

```js
db.students.find({
    branch: "CSE"
})
```

MongoDB gives you the results.

But you're asking:

> "Okay, MongoDB... HOW did you find them?"

Normally, the database doesn't show you all its internal execution details.

`explain()` lets us ask:

> "Show me the query plan and/or execution statistics for this operation."

> MongoDB provides `explain()` for operations such as `find()`, `aggregate()`, `count()`, `distinct()`, and others.

So:

```
Normal query
     ↓
"Give me the answer."

explain()
     ↓
"Show me HOW you got the answer."
```

That's the fundamental idea.

---

## 2. Why do we need `explain()`?

Suppose you created:

```js
db.students.createIndex({
    branch: 1
})
```

You run:

```js
db.students.find({
    branch: "CSE"
})
```

You might think:

> "Great, the index exists. Therefore MongoDB used it."

❌ Not necessarily.

MongoDB's query optimizer chooses a plan based on the query and available indexes.

So we need:

```js
db.students.find({
    branch: "CSE"
}).explain("executionStats")
```

to inspect what actually happened.

> MongoDB's docs explicitly recommend `explain()` for analyzing query plans, index effectiveness, and performance issues.

---

## 3. The basic syntax

You can write:

```js
db.students.find({
    branch: "CSE"
}).explain()
```

Or:

```js
db.students.find({
    branch: "CSE"
}).explain("executionStats")
```

Or:

```js
db.students.find({
    branch: "CSE"
}).explain("allPlansExecution")
```

MongoDB supports three main verbosity modes:

```
queryPlanner
executionStats
allPlansExecution
```

> For `cursor.explain()`, `queryPlanner` is the default verbosity.

---

## 4. The three explain modes

Let's understand them from easiest to deepest.

### 🟢 Mode 1 — `queryPlanner`

```js
db.students.find({
    branch: "CSE"
}).explain("queryPlanner")
```

This mainly tells us:

> What plan did MongoDB choose?

You can inspect:

```
queryPlanner
    ↓
winningPlan
    ↓
COLLSCAN / IXSCAN / etc.
```

It doesn't fully execute the winning plan to give you the complete execution statistics.

---

## 5. `winningPlan`

This is a very important term.

Suppose MongoDB has:

```
Index A
Index B
Index C
No index
```

The query optimizer may consider different possibilities.

Conceptually:

```
Query
  │
  ├── Plan A → Index A
  ├── Plan B → Index B
  ├── Plan C → Index C
  └── Plan D → Collection scan
              ↓
       Query optimizer
              ↓
        WINNING PLAN
```

The selected plan appears under:

```
winningPlan
```

> MongoDB's explain output contains `queryPlanner`, which includes the selected winning plan and rejected candidate plans.

---

## 6. 🟡 Mode 2 — `executionStats`

This is the one we'll use a lot.

```js
db.students.find({
    branch: "CSE"
}).explain("executionStats")
```

Now MongoDB actually executes the winning plan and gives us execution statistics.

This lets us inspect things such as:

```
nReturned
totalKeysExamined
totalDocsExamined
executionTimeMillis
executionStages
```

> MongoDB documents `executionStats` as the verbosity mode that executes the winning plan to completion and reports its execution statistics.

This is generally our main practical performance-analysis mode.

---

## 7. 🔴 Mode 3 — `allPlansExecution`

This goes deeper.

```js
db.students.find({
    branch: "CSE"
}).explain("allPlansExecution")
```

This can provide information about the winning plan and execution information captured for other candidate plans during plan selection.

Think:

```
queryPlanner
     ↓
Which plan wins?

executionStats
     ↓
How did winning plan perform?

allPlansExecution
     ↓
How did candidate plans compare during selection?
```

For your normal practical work:

> `executionStats` is the one you should become very comfortable with.

       ↓

       ↓

## 10. Now create the index

```js
db.students.createIndex({
    branch: 1
})
```

Now run:

```js
db.students.find({
    branch: "CSE"
}).explain("executionStats")
```

Conceptually, we may now see:

```
winningPlan:
    IXSCAN
```

possibly with:

```
FETCH
  ↓
IXSCAN
```

Why FETCH?

Because the index tells MongoDB:

> "These documents match."

But MongoDB still needs to retrieve the actual full documents to return:

```json
{
    "name": "...",
    "branch": "...",
    "cgpa": "...",
    "year": "..."
}
```

We'll unpack that shortly.

---

## 11. Understanding execution stages

This is where explain starts looking intimidating.

You may see something conceptually like:

```json
{
    "stage": "FETCH",
    "inputStage": {
        "stage": "IXSCAN"
    }
}
```

Don't panic.

Read it from the inside outward.

```
IXSCAN
  ↓
find matching index entries
  ↓
FETCH
  ↓
retrieve actual documents
  ↓
return results
```

> MongoDB explains that execution stages form a hierarchy where child stages feed results to parent stages; `IXSCAN` scans index keys and `FETCH` retrieves documents.

---

## 12. IXSCAN

We've already seen it.

```
IXSCAN
```

means:

> MongoDB is scanning index keys.

Suppose:

```
{ branch: 1 }
```

Then the index contains information associated with `branch`.

The query:

```
{ branch: "CSE" }
```

can scan the relevant portion of that index.

---

## 13. FETCH

Now imagine the index gives us:

```
Document references:
    ↓
Doc 1
Doc 3
Doc 4
```

But our application asks for:

```
{
    name: 1,
    branch: 1,
    cgpa: 1
}
```

The index only has:

```
branch
```

It doesn't have:

```
name
cgpa
```

So MongoDB has to go back to the collection:

```
IXSCAN
   ↓
matching index entries
   ↓
FETCH
   ↓
actual documents
```

That is what `FETCH` represents.

---

## 14. This gives us an important distinction

### Indexed query

```
IXSCAN
  ↓
FETCH
  ↓
RESULT
```

versus:

### Covered query

```
IXSCAN
  ↓
RESULT
```

🔥 No FETCH.

Why?

Because the index itself contains everything MongoDB needs.

That's our next major concept.

---

## 15. COVERED QUERY

> A covered query is a query that MongoDB can satisfy entirely from an index without examining the actual collection documents.

> MongoDB's current documentation defines it essentially this way: the index contains the fields required for both the query conditions and returned results, so MongoDB can match and return the results using only index keys.

This is powerful.

---

## 16. Let's build one from scratch

Suppose our documents are:

```json
{
    "studentId": 101,
    "name": "Rahul",
    "branch": "CSE",
    "year": 4
}
```

We frequently run:

```js
db.students.find(
    {
        studentId: 101
    },
    {
        studentId: 1,
        name: 1,
        _id: 0
    }
)
```

What fields do we need?

```
Query:
studentId

Output:
studentId
name
```

So let's create:

```js
db.students.createIndex({
    studentId: 1,
    name: 1
})
```

Now the index contains:

```
studentId
name
```

Everything our query needs.

Therefore MongoDB may be able to answer the query without fetching the actual document.

---

## 17. Visualize it

**Without covering:**

```
QUERY
 ↓
INDEX
 ↓
studentId = 101
 ↓
FETCH DOCUMENT
 ↓
read name
 ↓
RESULT
```

**With covering:**

```
QUERY
 ↓
INDEX
 ↓
studentId = 101
 ↓
name already in index
 ↓
RESULT
```

🔥 The second one avoids the document fetch.

## 18. The `totalDocsExamined = 0` clue

This is one of the most beautiful practical clues.

For a covered query, MongoDB's explain output can show:

```
totalDocsExamined: 0
```

because no collection documents needed to be examined.

> MongoDB's current explain documentation explicitly identifies a covered query as one where the `IXSCAN` isn't under a `FETCH`, and `executionStats.totalDocsExamined` is 0.

So:

```
IXSCAN
+
totalDocsExamined = 0
```

is a very strong signal of a covered query.

---

Collection:

```

```

## 20. Why did we exclude `_id`?

🔥 Important.

Remember:

> MongoDB automatically includes `_id` in normal projections unless you explicitly exclude it.

Suppose our index contains:

```
studentId
name
```

but MongoDB's result also wants:

```
_id
```

Our index doesn't contain `_id` as part of the compound index we're discussing.

So to make the query covered, we explicitly say:

```
_id: 0
```

Thus:

```js
{
    studentId: 1,
    name: 1,
    _id: 0
}
```

> MongoDB's covered-query requirements include having all fields needed for the query and returned result in the index; excluding `_id` is a common part of creating a covered query when `_id` isn't in the index.

---

## 21. This gives us a very important formula

For a simple covered query:

```
QUERY FIELDS
      +
RETURNED FIELDS
      ↓
must be available in INDEX
      ↓
NO DOCUMENT FETCH
      ↓
COVERED QUERY
```

That's the core.

Suppose index:

```js
{

Query:

We need:

```

```

  ↓

```

Not covered.

## 23. Another NOT-covered example

Suppose:

```js
db.students.createIndex({
    studentId: 1
})
```

Query:

```js
db.students.find({
    studentId: 101
})
```

At first glance you might say:

> "The query field is indexed, so it's covered."

❌ Not necessarily.

Why?

Because the result normally includes the entire document.

The index only contains:

```
studentId
```

but the document has:

```
studentId
name
branch
cgpa
year
...
```

MongoDB needs the document.

So:

```
IXSCAN
 ↓
FETCH
```

not covered.

## 24. Projection is the key to covered queries

This is why covered queries are usually built with a projection.

For example:

```js
db.students.find(
    { studentId: 101 },
    {
        name: 1,
        _id: 0
    }
)
```

with:

```js
{
    studentId: 1,
    name: 1
}
```

index.

Now:

```
Filter:
studentId

Output:
name

Index:
studentId + name
```

Everything is there.

🔥 Covered.

## 26. Why is a covered query potentially faster?

Because MongoDB doesn't need to retrieve full documents.

Imagine:

```
Document size = 5 KB
```

but index entry relevant to our query is much smaller.

Instead of:

```
INDEX
 ↓
FETCH 5 KB document
 ↓
extract 2 fields
```

MongoDB can potentially do:

```
INDEX
 ↓
extract required fields
 ↓
RESULT
```

> MongoDB's documentation notes that querying only the index can be significantly faster because index keys are generally smaller than the documents they catalog.

---

## 27. But don't create indexes just for covering everything

This is another trap.

Imagine your document has:

```
50 fields
```

and you create:

```
50-field index
```

just to cover one query.

😭

That's usually terrible index design.

Remember:

```
COVERED QUERY
       ↓
potential read benefit
       +
larger index
       +
more storage
       +
more write maintenance
```

So covered queries are powerful, but should still be designed according to workload.

---

## 28. Covered query + write trade-off

Suppose an index is:

```js
{
    customerId: 1,
    orderId: 1,
    total: 1,
    status: 1,
    date: 1
}
```

Every time one of these fields changes:

```
customerId
orderId
total
status
date
```

the index may need maintenance.

So don't think:

> "Let's include every field the application might ever return."

Instead:

> Cover important, frequent, performance-sensitive query patterns where the benefit justifies the index cost.

---

## 29. FETCH isn't necessarily bad

This is important.

You might see:

```
IXSCAN
 ↓
FETCH
```

and think:

> "BAD!"

No.

A normal efficient indexed query often needs a FETCH.

For example, MongoDB's own explain example shows an efficient query using `IXSCAN` followed by `FETCH`, with only a small number of keys/documents examined.

So:

```
IXSCAN + FETCH
```

can still be excellent.

Covered query:

```
IXSCAN without FETCH
```

is simply an additional optimization opportunity.

## 33. One caveat: `_id`

Remember this.

Suppose:

```js
db.students.createIndex({
    studentId: 1,
    name: 1
})
```

and:

```js
db.students.find(
    { studentId: 101 },
    {
        studentId: 1,
        name: 1
    }
)
```

The projection implicitly includes:

```
_id
```

unless excluded.

If `_id` isn't available in the index, the query may need to fetch the document.

So use:

```
_id: 0
```

when appropriate.

---

## 34. Another caveat: null

> MongoDB's current query-optimization documentation notes that covered-query behavior has a limitation around queries where fields are compared to `null`.

For your core mental model:

```
Covered query
   ↓
all required fields in index
   ↓
plus certain query/projection conditions must be satisfied
```

So don't memorize:

> "If all visible fields are in the index, it is ALWAYS covered."

There are additional conditions.

## 35. Multikey indexes and covered queries

Here's another interesting connection to Part 2.

Suppose:

```json
{
    "skills": ["Python", "MongoDB"]
}
```

and:

```js
db.students.createIndex({
    skills: 1
})
```

Because `skills` is an array, this is a multikey index.

Can we always get a covered query over that array?

**No.**

> MongoDB documents that multikey indexes cannot cover queries over array fields in the general case, although certain covered cases involving non-array fields exist.

So:

```
ARRAY FIELD
    ↓
MULTIKEY INDEX
    ↓
covering behavior has restrictions
```

This is an advanced connection worth remembering.

## 37. Why `explain()` is better than guessing

Imagine two indexes:

```
{ quantity: 1, type: 1 }
```

and:

```
{ type: 1, quantity: 1 }
```

Both contain the same fields.

Which is better for:

```js
{
    quantity: { $gte: 100, $lte: 300 },
    type: "food"
}
```

We shouldn't just guess.

We can test them with `hint()` and `explain("executionStats")`.

> MongoDB's official example demonstrates exactly this style of comparison and shows that the index `{ type: 1, quantity: 1 }` can examine fewer index keys for that query than `{ quantity: 1, type: 1 }`.

That is real query optimization.

---

## 38. `explain()` does not modify your data

Very important.

If you're worried:

> "Will `explain()` actually update/delete anything?"

> MongoDB's documentation states that for write operations, explain reports what would happen but does not apply the modification.

So:

```
explain()
```

is an analysis tool.

## 39. One important warning about `executionTimeMillis`

Don't make this mistake:

```
Query A:
executionTimeMillis = 5

Query B:
executionTimeMillis = 7

Therefore A is definitely better forever.
```

Not necessarily.

`explain()` itself changes how the query is executed/planned, and timing can vary with system conditions.

> MongoDB's docs say `executionTimeMillis` represents the time spent in the explain execution, including planning/selection and execution, so use it alongside the plan and examined counts rather than treating it as the only metric.

So your analysis should be:

```
winningPlan
+
nReturned
+
totalKeysExamined
+
totalDocsExamined
+
executionTimeMillis
```
