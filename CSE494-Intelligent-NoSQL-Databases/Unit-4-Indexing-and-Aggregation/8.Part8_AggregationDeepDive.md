## 1. First — let's go DEEP into `$group`

We already saw:

```js
db.students.aggregate([
    {
        $group: {
            _id: "$branch",
            count: { $sum: 1 }
        }
    }
])
```

Let's understand what is really happening.

Suppose:

```js
[
    { name: "Rahul", branch: "CSE", cgpa: 8.7 },
    { name: "Priya", branch: "ECE", cgpa: 9.1 },
    { name: "Arjun", branch: "CSE", cgpa: 7.8 },
    { name: "Sneha", branch: "CSE", cgpa: 8.9 }
]
```

We say:

```
_id: "$branch"
```

MongoDB effectively creates:

```
CSE group
 ├── Rahul
 ├── Arjun
 └── Sneha

ECE group
 └── Priya
```

Then the accumulator operates inside each group.

That's the key.

---

## 2. `$sum`

### Case 1 — Count documents

```js
{
    $group: {
        _id: "$branch",
        count: { $sum: 1 }
    }
}
```

For CSE:

```
1 + 1 + 1 = 3
```

ECE:

```
1 = 1
```

Output:

```
{ _id: "CSE", count: 3 }
{ _id: "ECE", count: 1 }
```

### Case 2 — Add a field

Suppose:

```js
[
    { branch: "CSE", fees: 50000 },
    { branch: "CSE", fees: 55000 },
    { branch: "ECE", fees: 48000 }
]
```

We can do:

```js
db.students.aggregate([
    {
        $group: {
            _id: "$branch",
            totalFees: { $sum: "$fees" }
        }
    }
])
```

CSE:

```
50000 + 55000 = 105000
```

ECE:

```
48000
```

So `$sum` doesn't only mean "count."

It can mean:

> Add numerical values across documents in each group.

> MongoDB's `$sum` returns the sum of numerical values and ignores non-numeric values.

---

## 3. `$avg`

Suppose:

```
CSE:
8.7
7.8
8.9
```

Then:

```
{
    $avg: "$cgpa"
}
```

calculates:

```
(8.7 + 7.8 + 8.9) / 3
```

So:

```js
db.students.aggregate([
    {
        $group: {
            _id: "$branch",
            averageCgpa: { $avg: "$cgpa" }
        }
    }
])
```

Output:

```json
{
    "_id": "CSE",
    "averageCgpa": 8.466666
}
```

> `$avg` calculates the average of numerical values and ignores non-numeric values.

---

## 4. `$min`

Want the lowest CGPA per branch?

```js
db.students.aggregate([
    {
        $group: {
            _id: "$branch",
            lowestCgpa: {
                $min: "$cgpa"
            }
        }
    }
])
```

For CSE:

```
8.7
7.8
8.9
 ↓
7.8
```

So:

```json
{
    "_id": "CSE",
    "lowestCgpa": 7.8
}
```

---

## 5. `$max`

Exactly the opposite:

```js
db.students.aggregate([
    {
        $group: {
            _id: "$branch",
            highestCgpa: {
                $max: "$cgpa"
            }
        }
    }
])
```

CSE:

```
8.7
7.8
8.9
 ↓
8.9
```

> `$min` and `$max` return the lowest and highest expression values for each group.

## 6. Combining ALL of them

This is where practical questions start getting interesting.

```js
db.students.aggregate([
    {
        $group: {
            _id: "$branch",

            count: {
                $sum: 1
            },

            totalCgpa: {
                $sum: "$cgpa"
            },

            averageCgpa: {
                $avg: "$cgpa"
            },

            minimumCgpa: {
                $min: "$cgpa"
            },

            maximumCgpa: {
                $max: "$cgpa"
            }
        }
    }
])
```

Conceptually:

```
               CSE
                │
      ┌─────────┼──────────┐
      ↓         ↓          ↓
    COUNT      AVG        MAX
      ↓         ↓          ↓
      3       8.46        8.9
                │
               MIN
                ↓
               7.8
```

That's a complete branch-level statistical summary.

## 7. `$push` — collect values into an ARRAY

Now something different.

Suppose:

```
Rahul → CSE
Arjun → CSE
Sneha → CSE
Priya → ECE
```

We want:

```
CSE → ["Rahul", "Arjun", "Sneha"]
ECE → ["Priya"]
```

Use:

```js
db.students.aggregate([
    {
        $group: {
            _id: "$branch",
            students: {
                $push: "$name"
            }
        }
    }
])
```

Output:

```json
{
    "_id": "CSE",
    "students": [
        "Rahul",
        "Arjun",
        "Sneha"
    ]
}
```

> `$push` creates an array containing expression values from the documents in each group.

---

## 8. `$push` is VERY useful

Imagine orders:

```js
[
    {
        customer: "A",
        product: "Laptop"
    },
    {
        customer: "A",
        product: "Mouse"
    },
    {
        customer: "A",
        product: "Keyboard"
    },
    {
        customer: "B",
        product: "Phone"
    }
]
```

We can do:

```js
db.orders.aggregate([
    {
        $group: {
            _id: "$customer",
            products: {
                $push: "$product"
            }
        }
    }
])
```

Result:

```json
{
    "_id": "A",
    "products": [
        "Laptop",
        "Mouse",
        "Keyboard"
    ]
}
```

So `$push` is basically:

> "Collect these values together into an array for each group."

## 9. `$addToSet` — unique values

Suppose:

```js
[
    { student: "A", subject: "MongoDB" },
    { student: "A", subject: "Python" },
    { student: "A", subject: "MongoDB" }
]
```

Using:

```
$push
```

could give:

```
["MongoDB", "Python", "MongoDB"]
```

But maybe we want:

```
["MongoDB", "Python"]
```

Use:

```js
db.enrollments.aggregate([
    {
        $group: {
            _id: "$student",
            subjects: {
                $addToSet: "$subject"
            }
        }
    }
])
```

> `$addToSet` produces an array of unique values for each group; its output order is not guaranteed.

So:

```
$push
→ duplicates allowed

$addToSet
→ unique values
```

🔥 Remember this difference.

## 10. `$first` and `$last`

These are slightly more dangerous conceptually.

```js
{
    $first: "$name"
}
```

means:

> Give me the value from the first document encountered in the group.

And:

```js
{
    $last: "$name"
}
```

means:

> Give me the value from the last document encountered.

But here's the important catch:

> What does "first" mean?

It depends on the order of documents.

Therefore, if you care about which document is first/last, establish the desired order with `$sort` first.

Example:

```js
db.students.aggregate([
    {
        $sort: {
            cgpa: -1
        }
    },
    {
        $group: {
            _id: "$branch",
            topper: {
                $first: "$name"
            }
        }
    }
])
```

Now:

```
sort highest CGPA first
        ↓
group by branch
        ↓
first student in each branch
        ↓
topper
```

That's a very useful pattern.

> MongoDB notes that `$first` and `$last` are meaningful according to the order of documents, and its documentation describes an optimization when a matching sort/group index is available.

## 12. NOW — `$unwind` 🔥

This is one of the most important aggregation stages in MongoDB.

Especially because MongoDB documents commonly contain arrays.

Suppose:

```json
{
    "name": "Rahul",
    "skills": [
        "Python",
        "MongoDB",
        "C++"
    ]
}
```

One document contains three array elements.

What if we want to process each skill separately?

That's what `$unwind` does.

---

## 13. What does `$unwind` mean?

> Officially, `$unwind` deconstructs an array field and outputs a separate document for each element.

**Before:**

```json
{
    "name": "Rahul",
    "skills": [
        "Python",
        "MongoDB",
        "C++"
    ]
}
```

**After:**

```json
{
    "name": "Rahul",
    "skills": "Python"
}
```

```json
{
    "name": "Rahul",
    "skills": "MongoDB"
}
```

```json
{
    "name": "Rahul",
    "skills": "C++"
}
```

ONE document became THREE documents.

---

## 14. Visualize `$unwind`

This:

```
Rahul
 ├── Python
 ├── MongoDB
 └── C++
```

becomes:

```
Rahul → Python
Rahul → MongoDB
Rahul → C++
```

So:

> `$unwind` = explode an array into separate pipeline documents.

That one sentence is gold.

---

## 15. Why would we ever need this?

Suppose we want:

> How many students have each skill?

Original:

```js
[
    {
        name: "Rahul",
        skills: ["Python", "MongoDB"]
    },
    {
        name: "Priya",
        skills: ["Python", "Java"]
    },
    {
        name: "Arjun",
        skills: ["MongoDB", "C++"]
    }
]
```

We cannot simply group directly as though every skill were a separate document.

First:

```js
{
    $unwind: "$skills"
}
```

Now pipeline becomes:

```
Rahul → Python
Rahul → MongoDB

Priya → Python
Priya → Java

Arjun → MongoDB
Arjun → C++
```

Then:

```js
{
    $group: {
        _id: "$skills",
        count: { $sum: 1 }
    }
}
```

Result:

```
Python   → 2
MongoDB  → 2
Java     → 1
C++      → 1
```

Mate, this is extremely important.

This pattern should be burned into memory:

```

 ↓

 ↓
INDIVIDUAL ELEMENTS
 ↓
$group
 ↓
ANALYSIS
```

For example:

```js
db.students.aggregate([
    {
        $unwind: "$skills"

        $group: {

```

This is a classic aggregation pattern.

## 18. `$set` / `$addFields`

Now suppose we want to create a new field without removing existing fields.

Use:

```js
{
    $set: {
        passed: true
    }
}
```

> MongoDB's `$set` aggregation stage adds fields while retaining existing fields; `$set` is an alias for `$addFields`.

For example:

```js
db.students.aggregate([
    {
        $set: {
            passed: {
                $gte: ["$cgpa", 5]
            }
        }
    }
])
```

If:

```
cgpa = 8.7
```

then:

```
passed: true
```

---

## 19. `$project` vs `$set`

This is a VERY important distinction.

### `$project`

Think:

> What fields should the output document contain?

Example:

```js
{
    $project: {
        name: 1,
        cgpa: 1,
        _id: 0
    }
}
```

It reshapes what passes through.

### `$set`

Think:

> Keep the existing document and add/change these fields.

Example:

```js
{
    $set: {
        passed: true
    }
}
```

So:

```
$project
→ reshape/select

$set
→ add/change fields while retaining the existing fields
```

---

## 20. `$set` can calculate fields

Suppose an order has:

```json
{
    "product": "Laptop",
    "price": 50000,
    "quantity": 2
}
```

We want:

```
total = price × quantity
```

Use:

```js
db.orders.aggregate([
    {
        $set: {
            total: {
                $multiply: [
                    "$price",
                    "$quantity"
                ]
            }
        }
    }
])
```

Output:

```json
{
    "product": "Laptop",
    "price": 50000,
    "quantity": 2,
    "total": 100000
}
```

This introduces an important concept:

### Expressions

> Aggregation stages can use expressions to calculate values from fields. MongoDB describes expressions as the mechanism used by pipeline stages to determine what to include, reshape documents, or compute values.

## 21. Common arithmetic expressions

You'll encounter things like:

```
$add
$subtract
$multiply
$divide
$mod
```

For example:

```js
{
    $multiply: [
        "$price",
        "$quantity"
    ]
}
```

means:

```
price × quantity
```

And:

```js
{
    $add: [
        "$marks1",

    ]
}
```

means:

```
marks1 + marks2 + marks3
```

## 22. Conditional expressions

We already saw `$cond`.

Example:

```js
{
    $set: {
        result: {
            $cond: [
                { $gte: ["$cgpa", 5] },
                "PASS",
                "FAIL"
            ]
        }
    }
}
```

Meaning:

```
IF cgpa >= 5
    ↓
PASS
ELSE
    ↓
FAIL
```

So aggregation can actually perform logic, not just filtering.

## 23. `$lookup` — MongoDB's join-like operation

Now we reach another BIG concept.

MongoDB encourages embedding in many cases, but sometimes data is stored separately.

Suppose we have:

**`students`**

```json
{
    "_id": 101,
    "name": "Rahul",
    "departmentId": 10
}
```

**`departments`**

```json
{
    "_id": 10,
    "name": "Computer Science"
}
```

The student document only has:

```
departmentId = 10
```

How can we bring department information into the pipeline?

Enter:

```
$lookup
```

> MongoDB describes `$lookup` as performing a left outer join with another collection in the same database, adding an array containing matching foreign documents to each input document.

---

## 24. Basic `$lookup`

```js
db.students.aggregate([
    {
        $lookup: {
            from: "departments",
            localField: "departmentId",
            foreignField: "_id",
            as: "department"
        }
    }
])
```

Understand each part:

**`from`**

```
from: "departments"
```

> Which collection should MongoDB look into?

**`localField`**

```
localField: "departmentId"
```

> Field from the current collection.

**`foreignField`**

```
foreignField: "_id"
```

> Field from the other collection.

**`as`**

```
as: "department"
```

> Name of the new field containing matching documents.

---

## 25. What does the result look like?

Before:

```json
{
    "_id": 101,
    "name": "Rahul",
    "departmentId": 10
}
```

After `$lookup`:

```json
{
    "_id": 101,
    "name": "Rahul",
    "departmentId": 10,

    "department": [
        {
            "_id": 10,
            "name": "Computer Science"
        }
    ]
}
```

Notice something.

`$lookup` produces an **ARRAY**.

Even if there is one match.

That's why we may subsequently use:

```
$unwind
```

if we want the department object itself rather than a one-element array.

---

## 26. `$lookup` + `$unwind`

This combination is extremely common.

```js
db.students.aggregate([
    {
        $lookup: {
            from: "departments",
            localField: "departmentId",
            foreignField: "_id",
            as: "department"
        }
    },
    {
        $unwind: "$department"
    }
])
```

Now:

```json
{
    "_id": 101,
    "name": "Rahul",
    "departmentId": 10,

    "department": {
        "_id": 10,
        "name": "Computer Science"
    }
}
```

So the mental sequence is:

```
students
   ↓
$lookup
   ↓
department ARRAY
   ↓
$unwind
   ↓
department OBJECT
```

🔥 Very practical.

## 27. `$lookup` vs embedding

This takes us directly back to Unit III Data Modeling.

Remember:

```
EMBED
vs
REFERENCE
```

If we embed:

```json
{
    "name": "Rahul",
    "department": {
        "id": 10,
        "name": "Computer Science"
    }
}
```

we don't need `$lookup`.

But if we reference:

```json
{
    "name": "Rahul",
    "departmentId": 10
}
```

then `$lookup` can combine the information when needed.

This is why Unit III and Unit IV connect beautifully:

```
DATA MODELING
      ↓
Embed / Reference
      ↓
Reference chosen
      ↓
Need related data?
      ↓
$lookup
```

> MongoDB itself cautions that excessive `$lookup` use can hurt performance and suggests considering embedding when related data is naturally stored together.

## 28. A COMPLETE `$lookup` example

Suppose:

**`students`**

```js
[
    {
        name: "Rahul",
        departmentId: 10
    },
    {
        name: "Priya",
        departmentId: 20
    }
]
```

**`departments`**

```js
[
    {
        _id: 10,
        name: "Computer Science"
    },
    {
        _id: 20,
        name: "Electronics"
    }
]
```

Pipeline:

```js
db.students.aggregate([
    {
        $lookup: {
            from: "departments",
            localField: "departmentId",
            foreignField: "_id",
            as: "department"
        }
    },
    {
        $unwind: "$department"
    },
    {
        $project: {
            _id: 0,
            name: 1,
            department: "$department.name"
        }
    }
])
```

Result:

```json
{
    "name": "Rahul",
    "department": "Computer Science"
}
```

```json
{
    "name": "Priya",
    "department": "Electronics"
}
```

Look at the entire flow:

```
STUDENT
  ↓
$lookup
  ↓
DEPARTMENT ARRAY
  ↓
$unwind
  ↓
DEPARTMENT OBJECT
  ↓
$project
  ↓
CLEAN RESULT
```

**Question:**

> Find total revenue by product.

This requires multiple steps.

---

## 30. Stage 1 — `$unwind`

```js
{
    $unwind: "$items"
}
```

Now:

```
Order 101 → Laptop
Order 101 → Mouse
Order 101 → Mouse
Order 102 → Keyboard
```

Actually, careful: `$unwind` does not create one document per quantity. It creates one document per array element.

So:

```
Order 101 → Laptop quantity 1
Order 101 → Mouse quantity 2
Order 102 → Keyboard quantity 1
```

This distinction is important.

---

## 31. Stage 2 — Calculate item revenue

```js
{
    $set: {
        itemRevenue: {
            $multiply: [
                "$items.price",
                "$items.quantity"
            ]
        }
    }
}
```

Now:

```
Laptop  → 80000 × 1 = 80000
Mouse   → 1000 × 2 = 2000
Keyboard → 2000 × 1 = 2000
```

---

## 32. Stage 3 — Group by product

```js
{
    $group: {
        _id: "$items.product",

        totalRevenue: {
            $sum: "$itemRevenue"
        }
    }
}
```

Output:

```
Laptop    → 80000
Mouse     → 2000
Keyboard  → 2000
```

```js

    $sort: {
        totalRevenue: -1
    }
}
```

Final:

## 36. Grouping by MULTIPLE fields

Suppose we want:

> Average CGPA by branch AND year.

We can't simply:

```

```

because we need two dimensions.

We can make `_id` an object:

```js
{
    $group: {
        _id: {

```


```json

    "_id": {
        "branch": "CSE",
        "year": 3

```

This is essentially:


## 39. `$sortByCount`

MongoDB also provides a convenient stage:

```js

    $sortByCount: "$branch"
}
```

Conceptually:

```

+
COUNT
+
SORT COUNT DESC
```

So:

```js
db.students.aggregate([
    {
        $sortByCount: "$branch"
    }

```

could produce:

```json

    "count": 3
}
```

```json
{
    "_id": "ECE",
    "count": 1
}
```

This is a shortcut for a common pattern. MongoDB lists `$sortByCount` as a stage that groups incoming documents by an expression and computes the count for each distinct group.

## 44. Performance — where should `$match` go?

Suppose:

```js
[
    { $match: { status: "completed" } },
    { $unwind: "$items" },
    { $group: {"...": "..."} }
]
```

versus:

```js
[
    { $unwind: "$items" },
    { $group: {"...": "..."} },
    { $match: {"...": "..."} }
]
```

If you can eliminate irrelevant documents before expensive processing, that's often beneficial.

So a common principle is:

> Filter as early as practical.

And MongoDB's aggregation optimization framework can also optimize certain pipeline sequences internally; don't assume the server executes every written stage in a completely naive way.

---

## 45. But don't blindly say "match always first"

Important nuance.

Suppose your `$match` depends on a field created by:

```
$set
```

Then obviously:

```
$set
 ↓
$match
```

may be necessary.

Example:

```js
{
    $set: {
        total: {
            $multiply: ["$price", "$quantity"]
        }
    }
}
```

then:

```js
{
    $match: {
        total: { $gt: 50000 }
    }
}
```

You couldn't filter on `total` before it exists.

So the better rule is:

> Put filtering early when possible, but pipeline correctness comes first.

---

## 46. `$group` is a blocking stage

This is a deeper performance point.

Imagine:

```
1 million documents
        ↓
     $group
```

MongoDB may need to process the incoming documents to form the groups before the stage can fully produce its results.

That's why `$group` is described as a **blocking stage**, and large groups can have significant memory implications.

You don't need to fear it.

Just understand:

```
$match
→ reduces data

$group
→ summarizes data

$group can be expensive
→ especially with large inputs
```

## 51. The biggest traps from Part 8 🚨

### Trap 1 — `$unwind` doesn't multiply based on quantity

If:

```js
items: [
    { product: "Mouse", quantity: 5 }
]
```

`$unwind` creates **one** document for that array element.

It does **NOT** create five documents.

### Trap 2 — `$lookup` gives an array

Even one matching department usually appears inside:

```js
department: [
    {"...": "..."}
]
```

Hence:

```
$lookup
↓
$unwind
```

is a common combination.

### Trap 3 — `$push` vs `$addToSet`

```
$push
→ duplicates allowed

$addToSet
→ unique values
```

### Trap 4 — `$first` depends on ordering

If you want highest CGPA:

```
$sort CGPA descending
↓
$group
↓
$first
```

Don't randomly use `$first` and assume it means "highest."

### Trap 5 — `$group` does not automatically sort output

> MongoDB explicitly states that `$group` does not order its output documents. If you want a specific order, use `$sort`.

### Trap 6 — `$lookup` isn't a reason to abandon good data modeling

If related data is naturally bounded and accessed together, embedding may be better than repeatedly joining it.
