## 1. What is Mongoose?

> Mongoose is an Object Data Modeling (ODM) library for MongoDB and Node.js.

Break the term:

```
O  → Object
D  → Data
M  → Modeling
```

An ODM lets you work with database documents as **JavaScript objects with rules**.

Compare with SQL world: an ORM (Object-Relational Mapper) maps objects to tables. An ODM maps objects to **documents**.

```
Native driver   →  collection of anything
Mongoose        →  collection with a defined shape and rules
```

Important truth:

> Mongoose sits on top of the MongoDB driver. It does not replace MongoDB; it adds a layer in your application.

```
Your code
   ↓
Mongoose (schema, validation, helpers)
   ↓
MongoDB driver
   ↓
MongoDB
```

## 2. Why use Mongoose?

| Need | Mongoose feature |
|--------|----------------------|
| Define document shape | Schema |
| Reject bad data before saving | Validation |
| Fill missing values | Defaults |
| Track created/updated times | `timestamps` |
| Reuse logic | Methods, statics, virtuals |
| Relate collections | `ref` + `populate()` |
| Cleaner query code | Model methods |

---

## 3. The BIG THREE — memorize this chain

```
SCHEMA  →  MODEL  →  DOCUMENT
```

### Schema

> The blueprint describing fields, types and rules.

### Model

> A class built from a schema. It represents a collection and gives you methods like `find`, `create`, `updateOne`.

### Document

> One instance of a model, i.e., one record in the collection.

Analogy:

```
Schema    = architectural blueprint of a house
Model     = the construction company that builds houses from it
Document  = one actual house
```

In MongoDB terms:

```
Schema    → rules
Model     → students collection (interface to it)
Document  → { name: "Rahul", ... }
```

## 4. Install and connect

In your project folder:

```
npm install mongoose dotenv
```

Create `db.js`:

```js
require("dotenv").config();
const mongoose = require("mongoose");

async function connectDB() {
    try {
        await mongoose.connect(process.env.MONGODB_URI, {
            dbName: "collegeDB"
        });
        console.log("✅ Mongoose connected");
    } catch (err) {
        console.error("❌ Connection error:", err.message);
        process.exit(1);
    }
}

module.exports = connectDB;
```

Notes:

```
mongoose.connect()  → opens the connection (manages pooling for you)
dbName              → which database to use
process.exit(1)     → stop the app if the DB is unreachable at startup
```

You call `connectDB()` **once** when the app starts. (Same one-connection rule as Part 1.)

## 5. Your first schema

Create `models/Student.js`:

```js
const mongoose = require("mongoose");

const studentSchema = new mongoose.Schema({
    name: String,
    branch: String,
    cgpa: Number,
    year: Number
});

const Student = mongoose.model("Student", studentSchema);

module.exports = Student;
```

Read it:

```
new mongoose.Schema({...})   → define fields and types
mongoose.model("Student", s) → create the Model
```

Collection name rule:

```
Model name: "Student"
        ↓ Mongoose lowercases + pluralizes
Collection: students
```

So the `Student` model talks to the `students` collection.

## 7. Fields with options (the real power)

Instead of just a type, give an object of rules:

```js
const studentSchema = new mongoose.Schema({
    name: {
        type: String,
        required: true,
        trim: true
    },
    branch: {
        type: String,
        enum: ["CSE", "ECE", "EEE", "ME", "CE"]
    },
    cgpa: {
        type: Number,
        min: 0,
        max: 10
    },
    year: {
        type: Number,
        default: 1
    }
});
```

Now Mongoose enforces:

```
name   → must exist, whitespace trimmed
branch → must be one of the listed values
cgpa   → between 0 and 10
year   → defaults to 1 if not provided
```

## 8. Built-in validators

| Option | Applies to | Meaning |
|-----------|---------------|------------|
| `required` | all | field must be present |
| `default` | all | value used if missing |
| `enum` | String/Number | allowed list |
| `min`, `max` | Number/Date | range |
| `minlength`, `maxlength` | String | length limits |
| `match` | String | regex must match |
| `trim` | String | remove surrounding spaces |
| `lowercase`, `uppercase` | String | transform |

Custom error messages:

```js
cgpa: {
    type: Number,
    min: [0, "CGPA cannot be negative"],
    max: [10, "CGPA cannot exceed 10"]
}
```

Email pattern example:

```js
email: {
    type: String,
    required: [true, "Email is required"],
    lowercase: true,
    match: [/^\S+@\S+\.\S+$/, "Please enter a valid email"]
}
```

---

## 9. Custom validators

When built-ins are not enough:

```js
phone: {
    type: String,
    validate: {
        validator: function (v) {
            return /^[6-9]\d{9}$/.test(v);
        },
        message: props => `${props.value} is not a valid phone number`
    }
}
```

The validator returns `true` (valid) or `false` (invalid).

## 10. Using the model — a taste (full CRUD in Part 3)

```js
const connectDB = require("./db");
const Student = require("./models/Student");

async function main() {
    await connectDB();

    const s = new Student({ name: "Rahul", branch: "CSE", cgpa: 8.7 });
    await s.save();
    console.log("Saved:", s);

    process.exit(0);
}

main();
```

Output shows the document with `_id`, plus `year: 1` from the default and `__v: 0`.

### What is `__v`?

> `__v` is the version key Mongoose adds to track document revisions (mainly used for array-modification safety). You can ignore it for now.

## 11. What happens with bad data?

```js
const bad = new Student({ name: "Arjun", branch: "XYZ", cgpa: 15 });

try {
    await bad.save();
} catch (err) {
    console.log(err.message);
}
```

Error (shape):

```
Student validation failed:
branch: `XYZ` is not a valid enum value for path `branch`.,
cgpa: Path `cgpa` (15) is more than maximum allowed value (10).
```

🔥 The bad document **never reaches the database.**

```
App data
   ↓
Mongoose validation
   ↓ fails
ERROR — nothing saved
```

## 12. Type casting

Mongoose tries to convert values to the schema type.

```js
new Student({ name: "Meera", cgpa: "8.5" });   // "8.5" → 8.5
```

But impossible conversions fail:

```js
new Student({ name: "Meera", cgpa: "eight" });  // CastError
```

Mongoose says:

```
Cast to Number failed for value "eight"
```

---

## 13. Strict mode — extra fields get dropped

By default Mongoose is **strict**.

```js
const s = new Student({ name: "Karan", hobby: "chess" });
await s.save();
```

`hobby` is not in the schema → Mongoose **ignores it** and does not save it.

```
Schema fields   → saved
Unknown fields  → silently discarded (strict mode)
```

That's a very common "why isn't my field saving?" trap. 🚨

## 14. Defaults and `timestamps`

```js
const studentSchema = new mongoose.Schema({
    name: { type: String, required: true },
    active: { type: Boolean, default: true },
    joinedOn: { type: Date, default: Date.now }
}, {
    timestamps: true
});
```

The second argument is **schema options**.

`timestamps: true` automatically adds:

```
createdAt → set when first saved
updatedAt → updated on each change
```

Notice `default: Date.now` (no parentheses) so it runs at document-creation time, not when the file loads.

## 15. Nested objects

Same as embedding in Unit III:

```js
const studentSchema = new mongoose.Schema({
    name: String,
    address: {
        city: String,
        state: String,
        pincode: Number
    }

```

Stored document:

```json
{
    "name": "Rahul",

}
```

Access: `student.address.city`

Querying later uses dot notation: `"address.city"`.

## 16. Arrays

```js
skills: [String]
```

Array of subdocuments:

```js
const itemSchema = new mongoose.Schema({
    product: String,
    price: Number,
    quantity: { type: Number, min: 1 }
}, { _id: false });

const orderSchema = new mongoose.Schema({
    customer: String,
    status: { type: String, default: "pending" },
    items: [itemSchema]
});
```

`_id: false` stops Mongoose from adding an `_id` to each item (optional).

Remember the Unit IV e-commerce pipeline with `$unwind: "$items"`? This is the schema that produces those documents. 🔥

## 17. References and `ref` (Unit III: referencing)

Two collections:

```js
// models/Department.js
const departmentSchema = new mongoose.Schema({
    name: { type: String, required: true }
});
module.exports = mongoose.model("Department", departmentSchema);
```

```js
// models/Student.js
const studentSchema = new mongoose.Schema({
    name: String,
    department: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "Department"
    }
});
```

```
students.department  →  stores Department's _id
ref: "Department"    →  tells Mongoose which model it points to
```

Later `populate("department")` replaces that ID with the full department document (Part 3). It's Mongoose's friendly cousin of `$lookup` from Unit IV.

```
Unit III → reference chosen
Unit IV  → $lookup (inside MongoDB)
Unit V   → populate (Mongoose convenience)
```

## 18. Indexes in a schema (Unit IV connection)

You can declare indexes where you define the model.

Field-level:

```js
email: { type: String, index: true }
```

Unique index:

```js
email: { type: String, unique: true }
```

Schema-level compound index:

```js
studentSchema.index({ branch: 1, cgpa: -1 });
```

Text index:

```js
bookSchema.index({ title: "text", description: "text" });
```

Same indexes you studied in Unit IV, now declared in code. When the model is initialized, Mongoose can build them (autoIndex behavior; many teams disable auto index creation in production and manage indexes deliberately).

### ⚠️ The `unique` misunderstanding

`unique: true` is **not a validator**. It creates a unique **index** in MongoDB.

```
required, min, max...  → Mongoose validators (checked in the app)
unique                 → MongoDB index (enforced by the database)
```

Duplicates produce a MongoDB error with code `11000` (duplicate key), not a normal validation error. Handle it separately in your error handling:

```js
catch (err) {
    if (err.code === 11000) {
        console.log("Duplicate value:", err.keyValue);
    }
}
```

## 19. Virtuals

A **virtual** is a computed property that is **not stored** in the database.

```js
studentSchema.virtual("grade").get(function () {
    if (this.cgpa >= 9) return "A";
    if (this.cgpa >= 8) return "B";
    return "C";
});
```

Usage: `student.grade`

To include virtuals when converting to JSON:

```js
const studentSchema = new mongoose.Schema({ /* ... */ }, {
    toJSON: { virtuals: true }
});
```

```
Stored   → cgpa
Computed → grade (not in DB)
```

## 20. Instance methods and statics

### Instance method (on one document)

```js
studentSchema.methods.isTopper = function () {
    return this.cgpa >= 9;
};

// use
const s = await Student.findOne({ name: "Priya" });
console.log(s.isTopper());
```

### Static method (on the model)

```js
studentSchema.statics.findByBranch = function (branch) {
    return this.find({ branch });
};

// use
const cse = await Student.findByBranch("CSE");
```

```
methods  → this = one document
statics  → this = the model
```

Define these **before** calling `mongoose.model()`.

## 21. Mongoose validation vs MongoDB schema validation

You learned MongoDB-side validation in Unit III (`$jsonSchema`, validation rules). Now compare.

| Feature | Mongoose validation | MongoDB `$jsonSchema` validation |
|-------------|--------------------------|------------------------------------|
| Where it runs | In your Node app | Inside the database server |
| Protects against | Bad data from this app | Bad data from **any** client |
| Language | JavaScript rules | JSON Schema rules |
| Bypassed by | Other apps, shell, some bulk operations | Not bypassed by clients (unless bypass option used) |
| Best use | Friendly app-level errors | Last line of defense |

Mature view:

> Use Mongoose validation for developer-friendly checks and error messages. Use database-level validation when multiple applications or direct access can write to the same data.

```
Mongoose validation = front door guard
Database validation = vault door
```

Some Mongoose update operations do not run validators unless you enable them (for example, `runValidators: true` on update queries). We'll show this in Part 3.

## 22. A complete model file

`models/Student.js`:

```js
const mongoose = require("mongoose");

const studentSchema = new mongoose.Schema({
    name: {
        type: String,
        required: [true, "Name is required"],
        trim: true,
        minlength: 2
    },
    email: {
        type: String,
        required: true,
        unique: true,
        lowercase: true,
        match: [/^\S+@\S+\.\S+$/, "Invalid email"]
    },
    branch: {
        type: String,
        enum: ["CSE", "ECE", "EEE", "ME", "CE"],
        required: true
    },
    year: { type: Number, min: 1, max: 4, default: 1 },
    cgpa: { type: Number, min: 0, max: 10 },
    skills: [String],
    address: {
        city: String,
        state: String
    },
    department: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "Department"
    }
}, { timestamps: true });

// compound index (Unit IV)
studentSchema.index({ branch: 1, cgpa: -1 });

// virtual
studentSchema.virtual("grade").get(function () {
    return this.cgpa >= 9 ? "A" : this.cgpa >= 8 ? "B" : "C";
});

// static
studentSchema.statics.findByBranch = function (branch) {
    return this.find({ branch });
};

module.exports = mongoose.model("Student", studentSchema);
```

This one file already shows: types, validation, defaults, nested object, array, reference, index, virtual, static, timestamps. 🔥

## 23. Dry run: what happens on `save()`?

```js
const s = new Student({ name: " Rahul ", email: "RAHUL@Gmail.com", branch: "CSE", cgpa: 8.7 });
await s.save();
```

Step by step:

```
1. new Student(...)         → document created in memory
2. Defaults applied         → year: 1
3. Setters/transforms       → name trimmed → "Rahul", email lowercased
4. Casting                  → types converted if possible
5. Validation               → required/enum/match/min/max checked
6. If invalid               → throw ValidationError, STOP
7. Insert into MongoDB      → via driver
8. Unique index check       → MongoDB may reject duplicate email (code 11000)
9. Document returned        → with _id, createdAt, updatedAt, __v
```

## 25. Native driver vs Mongoose

| Point | Native driver | Mongoose |
|---------|--------------------|-------------|
| Schema | None in code | Defined |
| Validation | Manual or DB-side | Built in |
| Learning curve | Closer to shell | Extra concepts |
| Flexibility | Maximum | Structured |
| Relationships | Manual `$lookup` | `ref` + `populate()` |
| Typical use | Scripts, tools, maximum control | Typical web apps |

Neither is "better". They serve different needs. Mongoose is very popular in Express applications.

## 27. 🔥 PART 2 — WHAT YOU MUST REMEMBER

**What is Mongoose?**

> An ODM library for MongoDB and Node.js that adds schemas, validation and helper methods.

**Big three?**

> Schema (blueprint) → Model (collection interface) → Document (one record).

**How does the model map to a collection?**

> Model `Student` → collection `students` (lowercased, pluralized).

**What is strict mode?**

> Fields not in the schema are not saved.

**Is `unique` a validator?**

> No. It creates a unique index; violations give error code 11000.

**Where do Mongoose validators run?**

> In the application, before data is sent to MongoDB.

**What is a virtual?**

> A computed property that is not stored in the database.

**What is `ref`?**

> It links an ObjectId field to another model so it can be populated.

---

## 🚨 Common traps

1. Expecting unknown fields to save (strict mode drops them).
2. Treating `unique: true` as validation.
3. Defining `methods`/`statics` after calling `mongoose.model()`.
4. Using `Date.now()` instead of `Date.now` in `default`.
5. Assuming Mongoose validation protects data written by other tools.
6. Calling `mongoose.connect()` repeatedly instead of once.
7. Forgetting `await` on `save()`.
