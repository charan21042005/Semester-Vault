## 2. Why manual tuning stops scaling

Imagine a real product:

```
200 different query shapes
 12 microservices
 millions of requests per hour
 new features shipped weekly
 data volume doubling every year
```

Problems:

```
1. Nobody can read explain() output for 200 queries every week.
2. Workloads CHANGE: yesterday's perfect index is today's dead weight.
3. Slow queries appear suddenly after a deployment or data growth.
4. Too many indexes (write cost!) and too few indexes (slow reads) both hurt.
5. Experts are expensive and busy.
```

So we want **tools that watch the workload, spot problems and suggest fixes** — that's what "AI-driven / AI-assisted optimization" is about.

---

## 3. What does "AI-driven query optimization" actually mean?

Be precise here — this is where weak answers go wrong.

> AI-driven query optimization means using **data analysis, statistics, machine learning, or AI models** to observe a database workload and **recommend or automate** tuning decisions — such as indexes, query rewrites, and capacity changes.

It can operate at several levels:

```
LEVEL 1  Rule-based advisors      "Query scans 90% of collection → suggest index"
LEVEL 2  Statistical analytics     "Latency of this query is 5× its normal baseline"
LEVEL 3  Machine-learning models   "Predict cost/latency, forecast workload, cluster query patterns"
LEVEL 4  LLM-assisted tools        "Write/explain/rewrite queries from natural language"
LEVEL 5  Autonomous tuning         "System creates/drops indexes on its own" (cloud/research systems)
```

### What it does NOT mean

```
✘ It does not mean MongoDB's core query planner is a neural network.
✘ It does not mean you can skip understanding indexes and explain().
✘ It does not mean the AI is always right.
```

MongoDB's built-in planner (next section) is a **classic engine** (trial-based plan selection with caching). "AI-driven" optimization, in practice, is mostly **tooling around** the database that analyses workload data and suggests changes — plus research directions that may reach products over time.

## 4. How MongoDB's own query planner works (the baseline)

When a query arrives:

```
QUERY
  ↓
Planner finds all indexes that could help  → candidate plans
  ↓
Candidate plans are run briefly in a TRIAL ("plan race")
  ↓
The plan that returns results most efficiently in the trial wins
  ↓
Winning plan is CACHED for that query SHAPE
  ↓
Future queries of the same shape reuse the cached plan
```

Key vocabulary:

```
Query shape      = the structure of a query (which fields, which operators, sort) WITHOUT the specific values
                   {branch:"CSE", cgpa:{$gt:8}}  and  {branch:"ECE", cgpa:{$gt:9}}  → same shape
Plan cache       = stored winning plans per shape
winningPlan /    = what explain() shows (Unit IV Part 6)
rejectedPlans
```

> MongoDB's documentation describes the query optimizer as processing queries, choosing the most efficient plan from candidate plans using available indexes, and caching plan choices for query shapes. Cache entries can be invalidated (for example when indexes change or the collection changes significantly) so plans can be re-evaluated.

See what's cached (aggregation stage, Unit IV style):

```js
db.students.aggregate([ { $planCacheStats: {} } ])
```

The planner **cannot invent an index**. If no good index exists, even the best planner can only pick the least-bad plan (often `COLLSCAN`). Index design remains the human/tool decision. That gap is exactly where advisors come in.

## 5. Step 1 of any optimization: MEASURE — the database profiler

You can't improve what you don't measure. MongoDB can record slow operations.

### 5.1 The profiler

```js
// level 0 = off, level 1 = log only SLOW operations, level 2 = log ALL operations
db.setProfilingLevel(1, { slowms: 100 })
```

Meaning:

```
level 1 + slowms:100  → record every operation slower than 100 ms
```

Recorded documents go into the capped collection **`system.profile`** of that database:

```js
db.system.profile.find().sort({ ts: -1 }).limit(3).pretty()
```

A typical entry (simplified):

```json
{
    "op": "query",
    "ns": "collegeDB.students",
    "command": { "find": "students", "filter": { "branch": "CSE", "cgpa": { "$gte": 8 } }, "sort": { "year": -1 } },
    "keysExamined": 0,
    "docsExamined": 50000,
    "nreturned": 12000,
    "planSummary": "COLLSCAN",
    "millis": 210,
    "ts": "2026-11-20T05:10:00Z"
}
```

Look at it with Unit IV eyes:

```
planSummary: COLLSCAN       → no useful index
docsExamined: 50000         → scanned everything
nreturned:   12000
millis:       210           → slow
```

### 5.2 Other places slow queries show up

```
mongod log file      → "Slow query" entries for ops slower than slowms
Atlas Query Profiler → visual chart of slow operations (Atlas)
Atlas Performance Advisor → suggestions (next section)
mongostat / mongotop → server-level activity (command-line tools)
```

🚨 Profiling at level 2 on a busy production server adds overhead. Use level 1 with a sensible `slowms`, and note that the profiler may be restricted on free/shared Atlas tiers (use Atlas's own tools there).

### 5.3 The efficiency ratio — your core AI feature

Remember Unit IV Part 5:

```
efficiency = nreturned / docsExamined       (closer to 1.0 is better)
waste      = docsExamined / nreturned       (closer to 1.0 is better; huge = problem)
```

A tool (or an ML model!) can compute this for **thousands of operations** — which no human can do by eye.

### 5.4 `$indexStats` — which indexes are actually used? (Unit IV Part 5)

```js
db.students.aggregate([ { $indexStats: {} } ])
```

Each index reports how many times it was used (`accesses.ops`) since the last server restart. An index with `ops: 0` over a long period is a **drop candidate** (after careful checking).

## 6. Atlas Performance Advisor & Query Profiler (awareness)

MongoDB Atlas (the managed cloud service) provides tooling that does exactly this analysis automatically:

```
Atlas Query Profiler        → timeline/graph of slow operations, filterable by namespace, duration, etc.
Atlas Performance Advisor   → watches slow queries and RECOMMENDS INDEXES
                              (shows which queries would benefit, and may also flag redundant/unused indexes)
Atlas Real-time Performance Panel → live operations, hot collections
Schema suggestions           → hints about anti-patterns (e.g. unbounded arrays, too many indexes)
```

How such an advisor works conceptually:

```
Collect slow-query logs
       ↓
Group by QUERY SHAPE
       ↓
Rank shapes by impact (frequency × time × docs examined)
       ↓
For top shapes: derive an index (equality → sort → range, i.e. ESR)
       ↓
Estimate benefit
       ↓
Show recommendation → HUMAN decides → create index
```

> MongoDB's documentation describes Performance Advisor as monitoring queries that MongoDB considers slow and suggesting new indexes to improve query performance. Availability and exact features depend on the Atlas cluster tier — check the current Atlas documentation for your tier.

That is **AI-assisted optimization in production today**: workload analytics + rules/heuristics (and, increasingly, ML) → recommendation → **human approval**.

## 7. Build your own mini index advisor in Python 🔥

The best way to understand an advisor is to build a tiny one. This reuses everything from Unit IV (ESR!) and Part 5 (PyMongo).

### 7.1 The idea

```
system.profile entries
        ↓
extract (filter fields, sort fields) per operation
        ↓
classify fields: EQUALITY / RANGE / SORT
        ↓
group operations by query SHAPE
        ↓
compute stats per shape: count, avg ms, avg waste
        ↓
if shape is slow or wasteful AND uses COLLSCAN / bad ratio
        ↓
SUGGEST index using ESR
```

### 7.2 The code

`index_advisor.py`:

```python
from collections import defaultdict
from statistics import mean

RANGE_OPS = {"$gt", "$gte", "$lt", "$lte", "$ne", "$nin", "$regex"}
LOGICAL_OPS = {"$and", "$or", "$nor"}


def classify_filter(filt: dict):
    """Return (equality_fields, range_fields) from a find() filter (top level only)."""
    equality, ranges = [], []
    for field, cond in filt.items():
        if field in LOGICAL_OPS or field.startswith("$"):
            continue                                   # skip complex logic in this simple advisor
        if isinstance(cond, dict) and any(k in RANGE_OPS for k in cond):
            ranges.append(field)
        elif isinstance(cond, dict) and "$in" in cond:
            equality.append(field)                     # $in behaves like multiple equalities
        else:
            equality.append(field)
    return equality, ranges


def sort_fields(sort_spec) -> list:
    if not sort_spec:
        return []
    return list(sort_spec.keys())


def query_shape(ns, filt, sort_spec):
    equality, ranges = classify_filter(filt)
    return (ns, tuple(sorted(equality)), tuple(sorted(ranges)), tuple(sort_fields(sort_spec)))


def esr_index(equality, sort_f, ranges):
    """Equality fields first, then sort fields, then range fields (Unit IV Part 3)."""
    ordered = []
    for f in list(equality) + list(sort_f) + list(ranges):
        if f not in ordered:
            ordered.append(f)
    return ordered


def analyse(profile_docs, min_waste=10, min_ms=50):
    shapes = defaultdict(list)

    for p in profile_docs:
        cmd = p.get("command", {})
        if "find" not in cmd:                           # this simple advisor handles find() only
            continue
        shape = query_shape(p["ns"], cmd.get("filter", {}), cmd.get("sort"))
        shapes[shape].append(p)

    recommendations = []
    for (ns, equality, ranges, sort_f), ops in shapes.items():
        avg_ms = mean(o.get("millis", 0) for o in ops)
        waste_values = [
            o.get("docsExamined", 0) / max(o.get("nreturned", 0), 1) for o in ops
        ]
        avg_waste = mean(waste_values)
        uses_collscan = any("COLLSCAN" in o.get("planSummary", "") for o in ops)

        if (uses_collscan or avg_waste >= min_waste) and avg_ms >= min_ms:
            keys = esr_index(equality, sort_f, ranges)
            if not keys:
                continue
            recommendations.append({
                "collection": ns,
                "calls": len(ops),
                "avg_ms": round(avg_ms, 1),
                "avg_waste": round(avg_waste, 1),
                "collscan": uses_collscan,
                "suggested_index": {k: 1 for k in keys},
                "impact": round(len(ops) * avg_ms, 1),     # simple impact score
            })

    return sorted(recommendations, key=lambda r: r["impact"], reverse=True)


if __name__ == "__main__":
    from db import db

    profile = list(db["system.profile"].find({"op": "query"}))
    for rec in analyse(profile):
        print(rec)
```

### 7.4 Dry run of the logic

```
Op 1 filter {branch:"CSE", cgpa:{$gte:8}}  sort {year:-1}
  classify → equality = [branch], range = [cgpa], sort = [year]
  shape    = (students, (branch,), (cgpa,), (year,))
Op 2 same fields, different VALUES (ECE, 9) → SAME SHAPE  ✔  (grouped together)
Op 3 {_id:123} → different shape; uses IXSCAN, fast → no recommendation

Shape A stats: calls=2, avg 200 ms, waste ≈ 1056, COLLSCAN → flagged
ESR: equality(branch) → sort(year) → range(cgpa)
Suggested index: { branch: 1, year: 1, cgpa: 1 }   ← exactly Unit IV Part 3's ESR rule
```

This is the **same reasoning** a commercial advisor performs — with far more sophistication (handling `$or`, aggregations, cardinality estimates, existing indexes, write cost). Understanding the toy version explains the real thing.

### 7.5 What our toy advisor ignores (and real tools consider)

```
- Existing indexes (don't suggest what already exists or is a prefix)
- Selectivity / cardinality of fields (which equality field first?)
- Sort DIRECTION (compound indexes need matching directions, Unit IV Part 3)
- $or queries, array fields, text/geo queries
- Aggregation pipelines ($match + $sort at the beginning)
- Write cost of the new index (read/write trade-off, Unit IV Part 5)
- Index size vs available RAM
- Covered-query opportunities
```

Which is exactly why the final decision stays with a human. 👇

## 8. Test a recommendation safely — hidden indexes

Never just create-and-forget. MongoDB lets you **hide** an index from the query planner **without dropping it**.

```js
// Make the planner ignore this index (but keep maintaining it)
db.students.hideIndex("branch_1_year_1_cgpa_1")

// Measure the queries now...

// Bring it back instantly
db.students.unhideIndex("branch_1_year_1_cgpa_1")
```

Use cases:

```
Considering DROPPING an index?  Hide it first, watch performance for a week.
                                If nothing gets slower → safe to drop.
                                If something breaks     → unhide in one second (no rebuild!).
```

> MongoDB documents hidden indexes (available from version 4.4) as a way to evaluate the impact of removing an index without actually dropping it.

Test a **new** index with `explain` on a staging copy first:

```python
plan = db.command({
    "explain": {"find": "students",
                "filter": {"branch": "CSE", "cgpa": {"$gte": 8}},
                "sort": {"year": -1}},
    "verbosity": "executionStats",
})
s = plan["executionStats"]
print(s["nReturned"], s["totalKeysExamined"], s["totalDocsExamined"], s["executionTimeMillis"])
```

## 9. ML idea #1 — Anomaly detection on query latency (with code)

> **Anomaly detection** = automatically spotting values that are unusual compared with normal behaviour.

Scenario: a query normally takes ~8 ms. After yesterday's deployment some calls take 250 ms. A dashboard might not scream — but an anomaly detector will.

Simple, effective statistical approach — **z-score** per query shape:

```
z = (value − mean) / standard_deviation        → "how many standard deviations from normal"
|z| > 3  → flag as anomaly
```

```python
import numpy as np
import pandas as pd

# imagine this came from system.profile: one row per slow-query log entry
df = pd.DataFrame({
    "shape": ["students:branch+cgpa"] * 12,
    "millis": [8, 9, 7, 8, 10, 9, 8, 7, 9, 8, 250, 9],
})

def flag_anomalies(frame: pd.DataFrame, z_limit: float = 3.0) -> pd.DataFrame:
    out = frame.copy()
    grp = out.groupby("shape")["millis"]
    out["z"] = (out["millis"] - grp.transform("mean")) / grp.transform("std")
    out["anomaly"] = out["z"].abs() > z_limit
    return out

result = flag_anomalies(df)
print(result[result["anomaly"]])
```

Output (conceptually):

```
                  shape  millis         z  anomaly
10  students:branch+cgpa     250  3.15...     True
```

A more robust variant uses the **median** and **MAD** (median absolute deviation), because a few huge outliers inflate the mean/standard deviation and can hide themselves.

More ML-flavoured versions: Isolation Forest (`sklearn.ensemble.IsolationForest`), seasonal baselines (the 9 AM spike is normal on weekdays), forecasting-residual methods.

```
Statistics/ML watches the numbers → alerts a human → human investigates with explain()
```

## 11. ML idea #3 — Learning from query history (clustering & prediction)

```
CLUSTERING (unsupervised): group thousands of query shapes into a few "families"
   → you design 3 indexes for 3 families instead of 200 for 200 shapes.

PREDICTING COST (supervised): features = filter fields, operators, collection size,
   index available?, selectivity estimate     label = measured milliseconds
   → model estimates "how slow would this query be?" BEFORE running it.
```

Research systems use **learned cost models** and **learned cardinality estimation** to help query optimizers estimate how many rows operators will produce — an area of active database research, mostly studied in relational systems, with ideas that carry over to document databases.

## 12. ML idea #4 — Learned indexes (research awareness)

Classic index: **B-tree** (Unit IV Part 1). Traditional idea.

> A **learned index** replaces or augments a structure like a B-tree with a **model that learns the data distribution** to predict where a key is located.

```
B-tree:   navigate levels of a tree → find position
Learned:  model(key) ≈ position → small local search to fix the error
```

Why people research it: potentially smaller memory footprint and faster lookups for certain data distributions. This idea was popularised by research ("The Case for Learned Index Structures", Kraska et al., 2018).

Reality check for your viva:

```
✔ Interesting research direction
✘ MongoDB's standard indexes are still B-tree-based (as taught in Unit IV)
✘ Don't claim MongoDB uses learned indexes in production
```

## 14. LLM-assisted querying (text-to-MQL) 🤖

Large language models (like ChatGPT/Claude-type assistants) can turn English into MongoDB queries:

```
"Top 5 products by revenue from completed orders"
        ↓  (LLM, given your schema)
db.orders.aggregate([ {$match:{status:"completed"}}, {$unwind:"$items"}, ... ])
```

Where they genuinely help:

```
✔ Drafting pipelines quickly (they know Unit IV patterns!)
✔ Explaining an unfamiliar query line by line
✔ Suggesting an index for a given query (then you verify with explain())
✔ Converting SQL → MQL, shell → PyMongo/Node
✔ Spotting anti-patterns ($match late, $lookup overuse...)
```

### The dangers 🚨

```
1. HALLUCINATION  → invents fields/collections/operators that don't exist
2. WRONG LOGIC    → looks right, returns wrong numbers (e.g. $limit before $sort)
3. NO WORKLOAD CONTEXT → doesn't know your data size, existing indexes, write load
4. DESTRUCTIVE    → a "cleanup" suggestion may be deleteMany({}) or $out over a real collection
5. INJECTION      → user text inside a prompt can manipulate the model (prompt injection)
6. DATA LEAKAGE   → sending sensitive documents/schemas to an external AI service
7. FALSE CONFIDENCE → fluent explanations that are subtly wrong
```

### Safe usage pattern

```
GIVE the model:  schema + sample documents (non-sensitive) + existing indexes + the goal
THEN:            review the query yourself
                 run explain() first
                 run on staging / with a READ-ONLY database user
                 set limits (limit, maxTimeMS)
                 only then promote to production
```

### Code: a safety gate for AI-generated pipelines

```python
ALLOWED_STAGES = {
    "$match", "$project", "$set", "$addFields", "$unwind", "$group",
    "$sort", "$limit", "$skip", "$count", "$lookup", "$sortByCount",
}
FORBIDDEN_STAGES = {"$out", "$merge"}           # these WRITE data


def validate_pipeline(pipeline, max_stages=12):
    """Raise ValueError if an (AI-generated) pipeline looks unsafe."""
    if not isinstance(pipeline, list) or not pipeline:
        raise ValueError("Pipeline must be a non-empty list")
    if len(pipeline) > max_stages:
        raise ValueError("Pipeline too long")

    for stage in pipeline:
        if not isinstance(stage, dict) or len(stage) != 1:
            raise ValueError("Each stage must be a dict with exactly one key")
        name = next(iter(stage))
        if name in FORBIDDEN_STAGES:
            raise ValueError(f"Stage {name} writes data and is not allowed")
        if name not in ALLOWED_STAGES:
            raise ValueError(f"Stage {name} is not on the allow-list")

    return True


def safe_run(collection, pipeline, limit=100, max_time_ms=5000):
    validate_pipeline(pipeline)
    guarded = pipeline + [{"$limit": limit}]       # never return unbounded results
    return list(collection.aggregate(guarded, maxTimeMS=max_time_ms))
```

Test it (no database needed):

```python
good = [{"$match": {"status": "completed"}}, {"$group": {"_id": "$customer", "n": {"$sum": 1}}}]
bad  = [{"$match": {}}, {"$out": "orders"}]

print(validate_pipeline(good))        # True

try:
    validate_pipeline(bad)
except ValueError as e:
    print("Blocked:", e)              # Blocked: Stage $out writes data and is not allowed
```

What this gate demonstrates:

```
ALLOW-LIST (not block-list)   → only known-safe stages pass
NO write stages               → $out / $merge forbidden
LIMIT appended                → can't return millions of docs
maxTimeMS                     → server aborts runaway queries
```

(A production system adds more: read-only DB user, collection allow-list, field checks against the real schema, rate limits, logging, and explain-based cost checks.)

## 15. Using explain() automatically — a "guard rail" check

Combine Unit IV and AI: before running any generated query, **ask MongoDB how it would run it** and refuse if it's a huge collection scan.

```python
def explain_find(collection_name, db, filt, sort=None):
    cmd = {"find": collection_name, "filter": filt}
    if sort:
        cmd["sort"] = sort
    return db.command({"explain": cmd, "verbosity": "queryPlanner"})


def has_collscan(plan_node: dict) -> bool:
    """Walk the plan tree looking for COLLSCAN."""
    if plan_node.get("stage") == "COLLSCAN":
        return True
    children = []
    if "inputStage" in plan_node:
        children.append(plan_node["inputStage"])
    children += plan_node.get("inputStages", [])
    return any(has_collscan(c) for c in children)


plan = explain_find("students", db, {"branch": "CSE"})
winning = plan["queryPlanner"]["winningPlan"]
if has_collscan(winning):
    print("⚠ This query would scan the whole collection — add an index or refuse")
```

`queryPlanner` verbosity doesn't execute the query — it's cheap, so safe as a gate.

## 16. Query-level optimizations an assistant (or you) should check

```
1. Does a suitable index exist?             (ESR, prefix rule)             Unit IV Part 3
2. Is the query selective?                  (docsExamined vs nReturned)    Unit IV Part 5
3. Can it be COVERED?                       (projection + index)           Unit IV Part 6
4. Is projection used?                      (return only needed fields)
5. Is there a LIMIT?                        (don't fetch 1M docs)
6. In aggregation: $match/$sort first?      (so indexes can help)          Unit IV Part 7/8
7. Is $lookup's foreignField indexed?       (join performance)             Unit IV Part 9
8. Is skip() huge?                          (switch to keyset pagination)  Unit V Part 3
9. Is $regex unanchored (/abc/)?            (can't use index efficiently; consider anchored /^abc/ or text/search)
10. Are there redundant/unused indexes?     ($indexStats + hidden index test)
11. Is the data model the real problem?     (embed vs reference)           Unit III
12. Are results cached where sensible?      (application-level cache)
```

Notice: #11 — sometimes **no index fixes a bad data model**. AI tools can't fully replace design thinking from Unit III.

## 17. The complete AI-assisted optimization workflow

```
┌──────────────────────────────────────────────────────────────┐
│ 1. COLLECT   profiler / slow logs / metrics / $indexStats    │
├──────────────────────────────────────────────────────────────┤
│ 2. ANALYSE   group by query shape, rank by impact,           │
│              detect anomalies, forecast load                  │
├──────────────────────────────────────────────────────────────┤
│ 3. RECOMMEND advisor / ML model / LLM proposes:              │
│              new index, drop index, query rewrite, schema fix │
```

## 18. Human-in-the-loop — the golden rule

```
AI/ML  =  excellent at scanning huge logs, spotting patterns, drafting options
HUMAN  =  responsible for business context, risk, cost and final approval
```

Why humans stay in the loop:

```
- The tool doesn't know a table is about to be archived
- The tool may ignore write-heavy periods
- A "faster" index can consume RAM that other queries needed
- Models can be wrong, stale or biased by unusual workload periods
- Accountability: someone must own the production change
```

## 21. Common traps 🚨

### Trap 1 — "AI will fix my queries automatically"

AI tools suggest; understanding Unit IV is still required.

### Trap 2 — Claiming MongoDB uses a neural-network optimizer

Its built-in planner uses classic plan selection with caching. AI-driven optimization here means tooling/analytics around it.

### Trap 3 — Blindly applying advisor suggestions

Check write cost, existing indexes, size and real workload first.

### Trap 4 — Profiling everything in production

Level 2 profiling has overhead; use level 1 with a sensible `slowms`.

### Trap 5 — Judging by one run

Latency varies (cache warm-up, load). Compare plans **and** examined counts, over a representative workload.

### Trap 6 — Trusting AI-written queries without testing

Hallucinated fields and wrong stage order are common. Validate, explain, test on staging.

### Trap 7 — Letting AI run write stages

Block `$out`, `$merge`, `deleteMany`, `updateMany` for generated queries; use read-only users.

### Trap 8 — Ignoring query shape

Optimising one literal query instead of the **shape** that repeats thousands of times.

### Trap 9 — Dropping an index immediately because it looks unused

`$indexStats` resets on restart and may miss monthly/yearly jobs. Hide first.

### Trap 10 — Sending sensitive logs to an external AI

Redact personal data in filters and documents.

### Trap 11 — Forgetting the data model

Some performance problems are modelling problems (Unit III).

## 23. 🔥 PART 7 — WHAT YOU MUST REMEMBER

**What is AI-driven query optimization?**

> Using analytics, ML or AI to observe workloads and recommend or automate database tuning (indexes, query rewrites, capacity), with humans validating the changes.

**How does MongoDB's own planner choose a plan?**

> It evaluates candidate plans from available indexes, picks the most efficient winner, and caches it per query shape.

**How do you find slow queries?**

> The database profiler (`setProfilingLevel`, `system.profile`), slow-query logs, and Atlas Query Profiler / Performance Advisor.

**What is a query shape?**

> A query's structure (fields, operators, sort) ignoring literal values.

**What key ratio shows waste?**

> `totalDocsExamined / nReturned` (or `keysExamined / nReturned`).

**What does Atlas Performance Advisor do?**

> Analyses slow queries and recommends indexes.

**How do you safely test dropping an index?**

> Hide it (`hideIndex`), monitor, then drop — or unhide instantly if things slow down.

**Dangers of LLM-generated queries?**

> Hallucinated fields, wrong logic, destructive writes, no workload awareness, prompt injection, data leakage.

**What is a learned index?**

> A research idea using ML models to predict key positions, in place of or alongside tree-based indexes; MongoDB's standard indexes remain B-tree-based.

**What is the golden rule?**

> Human-in-the-loop: AI recommends, humans validate and approve.
