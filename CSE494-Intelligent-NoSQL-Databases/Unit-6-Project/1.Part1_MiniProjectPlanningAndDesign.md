# 🟢 PART 1 — MINI PROJECT: PLANNING & DESIGN

## 1. What does a mini project actually test?

Most students think a mini project tests: *"Can you write code that runs?"*

That is only **20%** of it. A good mini project tests whether you can run the **full life-cycle**:

```
   IDEA
     ↓
 REQUIREMENTS      "what must the system do?"
     ↓
 DATA MODEL        "what are the collections?"  (Unit III)
     ↓
 INDEXES           "what must be fast?"          (Unit IV)
     ↓
 APPLICATION CODE  "how does the app talk to DB?"(Unit V)
     ↓
 REPORTS           "what insights can I show?"   (Unit IV aggregation)
     ↓
 TESTING           "does it really work?"
     ↓
 DOCUMENTATION     "can someone else run it?"
     ↓
 DEMO + VIVA       "can I explain every decision?"
```

> **Examiners rarely care how fancy your UI is. They care whether you can justify your design.**
> "Why is this embedded?" "Why is this index here?" "What happens if two students book the last seat together?" — those are the questions that separate a 9/10 from a 6/10.

So this Part is **design before code**. A builder who starts typing before planning rebuilds the project three times. 🏗️

## 2. Choosing the project

### What makes a good mini-project topic for a MongoDB course?

It should naturally need:

| Need | Why |
|---|---|
| **At least 3 collections** | shows relationships |
| **A one-to-many AND a many-to-many** | forces embed-vs-reference thinking |
| **Some nested/array data** | shows MongoDB's document strength |
| **Filters + sorting + pagination** | shows queries and indexes |
| **At least 2–3 reports** | shows aggregation |
| **A "rule" that can go wrong** | shows atomicity / validation / error handling |

### Our project: 🎓 **CourseHub**

> **CourseHub** is a backend system for a college department to manage **students, courses, enrollments and results**, and to answer questions like *"which courses have the best average?"* and *"which students are at risk?"*.

Why this one?

- You already understand the domain (you ARE the user). No time wasted learning the problem.
- It has a perfect many-to-many: **a student takes many courses, a course has many students.**
- The relationship carries its own data (marks, attendance) — a classic modelling question.
- Reports come naturally.
- It reuses your `students` mental model from Units II–V.

> You are free to swap the topic (library system, hospital, e-commerce, hostel, event booking). **The steps below stay identical.** Only the nouns change.

## 3. Step 1 — Requirements

A **requirement** is a sentence that says what the system must do or be. We split them in two kinds.

### 3.1 Functional requirements (what it DOES)

```
FR1  Add, view, update, delete students
FR2  Add, view, update, delete courses
FR3  Enroll a student in a course
FR4  Stop enrollment when the course is full or inactive
FR5  Stop the same student enrolling twice in the same course
FR6  Record marks (internal + final) and attendance for an enrollment
FR7  Auto-calculate total and grade from marks
FR8  List students/courses with search, filter, sort, pagination
FR9  Report: average marks per course
FR10 Report: top students by average marks
FR11 Report: at-risk students (low attendance or low marks)
```

### 3.2 Non-functional requirements (how WELL it does it)

```
NFR1 Fast: listing and reports must use indexes, not full scans
NFR2 Correct: no duplicate enrollments, no overbooked seats, even under simultaneous requests
NFR3 Safe: invalid data rejected; secrets not in code; no injection
NFR4 Clear errors: right HTTP status codes and readable messages
NFR5 Runnable by anyone: README + seed script
```

> **Mate, the non-functional list is what makes your project look professional.** Students who list only functional requirements look like beginners.

### 3.3 User stories (optional but impressive)

A user story is one line: *"As a ___, I want ___, so that ___."*

```
As an ADMIN,   I want to add courses with a seat limit,
               so that classes don't overflow.
As a STUDENT,  I want to enroll in a course,
               so that I can attend it.
As a FACULTY,  I want to enter marks and attendance,
               so that results are recorded.
As an HOD,     I want to see at-risk students,
               so that I can intervene early.
```

> We will not build login/roles in the mini project (that is its own big topic — Part 4 explains how production does it). The stories just clarify who benefits.

## 4. Step 2 — Find the entities (nouns) and actions (verbs)

A trick that works every time:

> **Read the requirements. Circle the NOUNS → candidate collections. Circle the VERBS → candidate operations/endpoints.**

From our requirements:

```
NOUNS : student, course, enrollment, marks, attendance, grade, seat, report
VERBS : add, view, update, delete, enroll, record, calculate, list, search, report
```

Now decide which nouns are **real entities** (own collection) and which are just **fields**:

| Noun | Entity or field? | Reason |
|---|---|---|
| student | **Entity** → `students` | exists on its own |
| course | **Entity** → `courses` | exists on its own |
| enrollment | **Entity** → `enrollments` | relationship that has its own data |
| marks | field of enrollment | meaningless without an enrollment |
| attendance | field of enrollment | same |
| grade | field (derived) | computed from marks |
| seat | field of course (`maxSeats`, `enrolledCount`) | a number |
| report | not stored | computed on demand by aggregation |

Result: **three collections** — `students`, `courses`, `enrollments`.

## 5. Step 3 — Relationships and the embed/reference decision

Time to use **Unit III**. Recall the decision questions:

```
1. Is it ONE-TO-FEW and read together?                → EMBED
2. Can it grow without a limit?                       → REFERENCE
3. Is it needed independently of the parent?          → REFERENCE
4. Is it shared by many parents (many-to-many)?       → REFERENCE
5. Does it change often while the parent doesn't?     → REFERENCE
```

### 5.1 Relationship map

```
         ┌───────────┐                  ┌───────────┐
         │ STUDENT   │                  │  COURSE   │
         └─────┬─────┘                  └─────┬─────┘
               │ 1                          1 │
               │                              │
               │ many                    many │
               ▼                              ▼
            ┌──────────────────────────────────┐
            │          ENROLLMENT              │
            │ student → _id of student         │
            │ course  → _id of course          │
            │ marks, attendance, status        │
            └──────────────────────────────────┘

 Student ↔ Course is MANY-TO-MANY.
 Enrollment is the "bridge" (junction) that also carries data.
```

### 5.2 Decisions, one by one

| Question | Decision | Why |
|---|---|---|
| Student's **address**? | **Embed** `{city, state}` | one-to-one, always read with student |
| Student's **skills**? | **Embed array** `["python","sql"]` | small, bounded, read together |
| Course's **topics**? | **Embed array** | small list, read with course |
| Student ↔ Course? | **Separate `enrollments` collection with references** | many-to-many, unbounded, carries own data |
| Why not embed enrollments inside student? | A student has few courses, but **a course could have hundreds of students** and we query both directions; also marks update often | |
| Why not embed enrollments inside course? | Course doc would grow large; students' marks get updated constantly → rewriting a big doc | |

> **The golden sentence for your viva:** *"I used a separate `enrollments` collection because Student–Course is many-to-many and the relationship itself holds data (marks, attendance), so it must be its own document. Small, bounded, always-together data like address and skills is embedded."*

### 5.3 What about duplicating a field? (Unit III "extended reference" idea)

Reports like "top students" need the student's **name**. We could `$lookup` it (join) every time, or **copy** the name into enrollment. 

We will use **`$lookup`** (single source of truth, name changes stay correct). If your report were extremely hot and read-heavy, you could copy `studentName` into enrollments and accept the update cost. Knowing **both options** and choosing one with a reason is what scores marks.

## 6. Step 4 — Final schema with sample documents

### 6.1 `students`

```js
{
  _id: ObjectId("..."),
  rollNo: "CSE2301",
  name: "Aarav Mehta",
  email: "aarav@college.edu",
  branch: "CSE",
  year: 2,
  skills: ["python", "sql"],
  address: { city: "Bengaluru", state: "Karnataka" },
  createdAt: ISODate("..."),
  updatedAt: ISODate("...")
}
```

### 6.2 `courses`

```js
{
  _id: ObjectId("..."),
  code: "CSE494",
  title: "MongoDB and NoSQL Systems",
  credits: 3,
  department: "CSE",
  semester: 5,
  topics: ["CRUD", "Indexing", "Aggregation"],
  maxSeats: 60,
  enrolledCount: 0,          // kept in sync atomically
  isActive: true,
  createdAt: ISODate("..."),
  updatedAt: ISODate("...")
}
```

### 6.3 `enrollments`

```js
{
  _id: ObjectId("..."),
  student: ObjectId("..."),   // → students._id
  course:  ObjectId("..."),   // → courses._id
  status: "enrolled",         // "enrolled" | "completed" | "dropped"
  attendance: 82,             // percent 0–100
  marks: { internal: 34, final: 51 },
  total: 85,                  // internal + final (derived)
  grade: "A",                 // derived from total
  createdAt: ISODate("..."),
  updatedAt: ISODate("...")
}
```

### 6.4 Field-by-field "why" table (viva favourite)

| Field | Why it exists |
|---|---|
| `rollNo`, `email` | natural identifiers → **unique indexes** |
| `courses.code` | human-friendly unique key |
| `enrolledCount` | cheap "is it full?" check without counting enrollments each time |
| `enrollments.student/course` | the two references forming the many-to-many |
| `status` | lets us keep history (dropped/completed) instead of deleting |
| `total`, `grade` | **derived** fields stored for fast reports; recalculated whenever marks change |
| `createdAt/updatedAt` | Mongoose `timestamps: true` |

> Derived fields are a **trade-off**: faster reads, but you must keep them correct. We update them in one place (the marks route), so they stay in sync.

## 7. Step 5 — Turn QUERIES into an INDEX PLAN (Unit IV applied)

> **Indexes are chosen from the queries you will actually run — never from guesswork.**

### 7.1 Write the query list first

| # | Query | Where used |
|---|---|---|
| Q1 | find student by `rollNo` | profile lookup |
| Q2 | find students by `branch`, sorted by `name` | list page |
| Q3 | find course by `code` | course lookup |
| Q4 | list active courses by `department` + `semester` | catalogue |
| Q5 | all enrollments of one student | "my courses" |
| Q6 | all enrollments of one course (by `status`) | class list |
| Q7 | does enrollment (student, course) already exist? | duplicate guard |
| Q8 | reports on completed enrollments | analytics |

### 7.2 Map each query to an index

| Index | Serves | Notes |
|---|---|---|
| `students: { rollNo: 1 }` **unique** | Q1 + prevents duplicates | |
| `students: { email: 1 }` **unique** | login-like lookups, duplicate guard | |
| `students: { branch: 1, name: 1 }` | Q2 | equality (`branch`) then sort (`name`) — **ESR rule** |
| `courses: { code: 1 }` **unique** | Q3 | |
| `courses: { department: 1, semester: 1, isActive: 1 }` | Q4 | all equality filters |
| `enrollments: { student: 1, course: 1 }` **unique** | Q5 (prefix `student`) + Q7 + **hard guarantee of no duplicates** | one index, three jobs 🔥 |
| `enrollments: { course: 1, status: 1 }` | Q6 | |
| `enrollments: { status: 1, total: -1 }` | Q8 report sorting | add only if reports are hot |

> **The compound unique index `{student:1, course:1}` is the star.** It (a) speeds "all of a student's enrollments" via its prefix, (b) answers the duplicate check, and (c) makes duplicates *impossible* at the database level — even if two requests arrive at the same millisecond.

### 7.3 Prove it later

In Part 3 we will run `explain("executionStats")` on each important query and confirm `IXSCAN`, not `COLLSCAN`. **Plan → build → measure.**

## 8. Step 6 — Plan the REPORTS as pipelines (Unit IV applied)

Before coding, sketch each report as pipeline stages in plain English.

### Report A — average marks per course

```
enrollments
  → $match   { status: "completed" }
  → $group   by course: avg(total), count, max(total)
  → $lookup  courses (get title/code)
  → $project clean output
  → $sort    avgTotal descending
```

### Report B — top students

```
enrollments
  → $match   { status: "completed" }
  → $group   by student: avg(total), courses count
  → $sort    avgTotal descending
  → $limit   N
  → $lookup  students (get name/rollNo)
  → $project
```

### Report C — at-risk students

```
enrollments
  → $match   { status: "enrolled" or "completed",
               $or: [ attendance < 75, total < 50 ] }
  → $lookup  students
  → $lookup  courses
  → $project (student name, course code, attendance, total, reason)
```

> **Pipeline-order reminder (Unit IV):** `$match` and `$limit` early → fewer documents flow through later stages → faster.

## 9. Step 7 — Business rules (the "what can go wrong" list)

This is where a normal project becomes a **good** project. Write every rule down.

```
RULE 1  Enrolling in an INACTIVE course        → refuse (409)
RULE 2  Enrolling when course is FULL          → refuse (409)
RULE 3  Enrolling twice in same course         → refuse (409)
RULE 4  Marks must be inside range:
        internal 0–40, final 0–60              → refuse (400)
RULE 5  Attendance must be 0–100               → refuse (400)
RULE 6  total = internal + final, grade from total
RULE 7  Deleting a student with enrollments    → refuse OR cascade (we choose: refuse, 409)
RULE 8  A student/course/enrollment id that doesn't exist → 404
RULE 9  Malformed id                           → 400
```

### The hard one — Rule 2 under concurrency 😈

Imagine **1 seat left**, two students click *Enroll* at the same moment:

```
 Student A request                 Student B request
 ─────────────────                 ─────────────────
 read course: enrolledCount=59
                                   read course: enrolledCount=59
 59 < 60 ✅ allowed
                                   59 < 60 ✅ allowed
 insert enrollment
                                   insert enrollment
 set enrolledCount = 60
                                   set enrolledCount = 60

 RESULT: 61 students in a 60-seat course 💥
```

This is a **race condition**: *read → decide → write* in three separate steps lets two requests sneak in between.

The fix (built in Part 2) is to make "check AND increment" **one atomic database operation**:

```js
Course.findOneAndUpdate(
  { _id, isActive: true, $expr: { $lt: ["$enrolledCount", "$maxSeats"] } },
  { $inc: { enrolledCount: 1 } }
)
```

> MongoDB guarantees a **single-document** update is atomic (Unit IV/V ideas). Only ONE of the two simultaneous requests can match the filter and increment; the other gets `null` → "course full". **No transaction needed.** This is a gem for your viva. 💎

## 10. Step 8 — REST API design

An API design table is the **contract** between frontend and backend. Make it before coding.

| Method | URL | Purpose | Success | Common errors |
|---|---|---|---|---|
| POST | `/api/students` | create student | 201 | 400, 409 |
| GET | `/api/students` | list (filter/sort/page) | 200 | – |
| GET | `/api/students/:id` | one student | 200 | 400, 404 |
| PATCH | `/api/students/:id` | update fields | 200 | 400, 404, 409 |
| DELETE | `/api/students/:id` | delete (if no enrollments) | 204 | 400, 404, 409 |
| POST | `/api/courses` | create course | 201 | 400, 409 |
| GET | `/api/courses` | list courses | 200 | – |
| GET | `/api/courses/:id` | one course | 200 | 400, 404 |
| PATCH | `/api/courses/:id` | update | 200 | 400, 404, 409 |
| POST | `/api/enrollments` | enroll `{studentId, courseId}` | 201 | 400, 404, 409 |
| GET | `/api/enrollments?student=..` | list enrollments | 200 | 400 |
| PATCH | `/api/enrollments/:id/result` | set marks + attendance | 200 | 400, 404 |
| PATCH | `/api/enrollments/:id/drop` | drop enrollment | 200 | 404, 409 |
| GET | `/api/reports/course-averages` | Report A | 200 | – |
| GET | `/api/reports/top-students?limit=5` | Report B | 200 | – |
| GET | `/api/reports/at-risk` | Report C | 200 | – |

> Notice: **nouns in URLs, verbs in HTTP methods** (Part 3 of Unit V). `PATCH …/drop` is an *action* on an enrollment, kept as a sub-resource so we don't hard-delete history.

## 12. Step 10 — Tech-stack decision (and its justification)

| Choice | Picked | Why | Alternative |
|---|---|---|---|
| Database | MongoDB | nested data, flexible schema, aggregation | – |
| Runtime | Node.js | same language as JSON documents; async I/O | Python (FastAPI/Flask) |
| Web framework | Express | minimal, universal | Fastify, Koa |
| DB layer | **Mongoose** | schema, validation, hooks | native driver |
| Analytics | Python + PyMongo | pandas/scikit-learn ecosystem | Node-only |
| Config | `dotenv` | secrets out of code | environment variables directly |

> If your faculty wants **only Python**, swap Express+Mongoose for Flask/FastAPI+PyMongo. The **design (Steps 1–7) does not change at all.** That is the point of designing first.

## 15. Common traps 🚨

### Trap 1: Starting to code first
Result: wrong schema discovered on day 5. **Design first.**

### Trap 2: Making every relationship a reference (SQL habit)
MongoDB's strength is embedding bounded, always-together data. Address and skills should be **embedded**.

### Trap 3: Embedding unbounded data
Enrollments inside a course would grow forever.

### Trap 4: Indexes added "because it feels fast"
Every index slows writes and uses RAM. Index only what your **query list** demands.

### Trap 5: Check-then-write seat logic
The race condition in §9. Use one atomic update.

### Trap 6: Forgetting unique indexes
Application-level "check if exists" alone is not safe under concurrency. The **database** must enforce uniqueness.

### Trap 7: Committing `.env`
Secrets leak. Commit `.env.example`, ignore `.env`.

### Trap 8: Only a happy-path demo
Show failures too: duplicate enrollment → 409, full course → 409. That impresses examiners more than ten successful calls.

### Trap 9: Over-scoping
Login, roles, UI, payments... Don't. **Three collections done well beat eight done badly.**

### Trap 10: No numbers
"It's fast" proves nothing. Show `explain()` output: `IXSCAN`, `totalDocsExamined`.

## 17. 🔥 PART 1 — WHAT YOU MUST REMEMBER

**What does a mini project test?**

> The full life-cycle: requirements → design → indexes → code → reports → testing → documentation → viva.

**How do you find collections?**

> Circle the nouns in requirements; real entities become collections, the rest become fields.

**Why a separate `enrollments` collection?**

> Student–Course is many-to-many and the relationship carries its own data (marks, attendance).

**What do you embed?**

> Small, bounded, always-read-together data (address, skills, topics).

**How do you choose indexes?**

> From the list of queries you will actually run (equality → sort → range, ESR).

**Which index guarantees no duplicate enrollments?**

> Unique compound index on `{ student: 1, course: 1 }`.

**How do you stop two students taking the last seat?**

> One atomic `findOneAndUpdate` that checks and increments together.

**What is a non-functional requirement?**

> How well the system works — speed, correctness, safety, clarity, runnability.

**What is the right build order?**

> Bottom-up: connect → model → routes → rules → reports → verify → document, testing after each step.
