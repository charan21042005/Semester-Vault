## 2. `analytics/risk_report.py`

The idea in one line:

> **Flatten enrollments with one aggregation → group per student in Python → apply simple, explainable rules → print a table.**

```python
"""CourseHub analytics: per-student risk report (PyMongo)."""
import os
from collections import defaultdict

from pymongo import MongoClient

LOW_ATTENDANCE = 75
LOW_MARKS = 50


def fetch_rows(db):
    """One flat row per enrollment, with student and course info joined in."""
    pipeline = [
        {"$match": {"status": {"$in": ["enrolled", "completed"]}}},
        {"$lookup": {"from": "students", "localField": "student",
                     "foreignField": "_id", "as": "s"}},
        {"$lookup": {"from": "courses", "localField": "course",
                     "foreignField": "_id", "as": "c"}},
        {"$unwind": "$s"},
        {"$unwind": "$c"},
        {"$project": {"_id": 0, "rollNo": "$s.rollNo", "name": "$s.name",
                      "branch": "$s.branch", "course": "$c.code",
                      "attendance": 1, "total": 1}},
    ]
    return list(db.enrollments.aggregate(pipeline))


def average(values):
    """Average of the non-None values, or None if there are none."""
    nums = [v for v in values if v is not None]
    return sum(nums) / len(nums) if nums else None


def summarize_students(rows):
    """Group enrollment rows by student and compute averages."""
    per = defaultdict(lambda: {"name": "", "branch": "", "att": [], "tot": [], "courses": 0})
    for r in rows:
        s = per[r["rollNo"]]
        s["name"], s["branch"] = r["name"], r["branch"]
        s["att"].append(r.get("attendance"))
        s["tot"].append(r.get("total"))
        s["courses"] += 1

    out = []
    for roll, s in per.items():
        avg_att = average(s["att"])
        avg_tot = average(s["tot"])
        level, reasons = risk_level(avg_att, avg_tot)
        out.append({"rollNo": roll, "name": s["name"], "branch": s["branch"],
                    "courses": s["courses"], "avg_attendance": avg_att,
                    "avg_total": avg_tot, "risk": level, "reasons": reasons})
    return sorted(out, key=lambda x: x["rollNo"])


def risk_level(avg_att, avg_tot):
    """Simple, explainable rule-based risk score (points -> level)."""
    if avg_att is None and avg_tot is None:
        return "NO DATA", []

    points, reasons = 0, []
    if avg_att is not None:
        if avg_att < LOW_ATTENDANCE:
            points += 2
            reasons.append(f"attendance {avg_att:.0f}% < {LOW_ATTENDANCE}%")
        elif avg_att < 85:
            points += 1
            reasons.append(f"attendance {avg_att:.0f}% is borderline")
    if avg_tot is not None:
        if avg_tot < LOW_MARKS:
            points += 2
            reasons.append(f"marks {avg_tot:.0f} < {LOW_MARKS}")
        elif avg_tot < 60:
            points += 1
            reasons.append(f"marks {avg_tot:.0f} is borderline")

    level = "HIGH" if points >= 3 else "MEDIUM" if points == 2 else "LOW" if points == 1 else "OK"
    return level, reasons


def fmt(x):
    return "-" if x is None else f"{x:.1f}"


def print_report(students):
    print(f"{'ROLL':<9}{'NAME':<14}{'BR':<5}{'#C':<4}{'ATT%':<7}{'AVG':<7}{'RISK':<9}WHY")
    print("-" * 78)
    for s in students:
        print(f"{s['rollNo']:<9}{s['name'][:13]:<14}{s['branch']:<5}{s['courses']:<4}"
              f"{fmt(s['avg_attendance']):<7}{fmt(s['avg_total']):<7}{s['risk']:<9}"
              f"{'; '.join(s['reasons'])}")


def main():
    uri = os.environ.get("MONGODB_URI", "mongodb://127.0.0.1:27017")
    db_name = os.environ.get("DB_NAME", "coursehub")
    client = MongoClient(uri, serverSelectionTimeoutMS=5000)
    client.admin.command("ping")                  # fail fast if DB is unreachable
    rows = fetch_rows(client[db_name])
    print(f"Loaded {len(rows)} enrollment rows from '{db_name}'\n")
    print_report(summarize_students(rows))
    client.close()


if __name__ == "__main__":
    main()
```

### How it works, piece by piece

| Piece | What & why |
|---|---|
| `fetch_rows` | one aggregation with two `$lookup`s → every row already has student + course info. The *database* does the joining; Python just receives rows |
| `average()` | ignores `None`, returns `None` if nothing to average — because marks/attendance may be "not recorded yet" |
| `summarize_students` | groups rows by `rollNo` using `defaultdict` |
| `risk_level` | **rule-based points** → `HIGH / MEDIUM / LOW / OK / NO DATA`, and it also returns **reasons** |
| `client.admin.command("ping")` | PyMongo connects **lazily** (Unit V Part 4) — this forces a real check so errors show up at the start |
| `serverSelectionTimeoutMS=5000` | fail in 5 s, not 30 s, if MongoDB is down |

### Why rules before ML?

Because **a rule you can explain beats a model you can't** when a human must act on the result. A mentor can say *"you're flagged because attendance is 62% and marks average 44"* — that is actionable and fair. (Part 4 and Part 7 return to explainability.)

## 3. Optional: a tiny ML model — `analytics/predict_final.py`

**Question:** *"Given a student's internal marks and attendance, can we predict their final-exam marks?"*

This is **regression** (predicting a number) — Unit V Part 6 recap:

```
FEATURES (X)  : internal marks, attendance
LABEL    (y)  : final marks
MODEL         : LinearRegression  →  final ≈ a·internal + b·attendance + c
METRICS       : MAE (average error in marks), R² (how much variation explained)
```

```python
"""Optional ML: predict FINAL marks from internal marks + attendance."""
import os

import numpy as np
from pymongo import MongoClient
from sklearn.linear_model import LinearRegression
from sklearn.metrics import mean_absolute_error, r2_score
from sklearn.model_selection import train_test_split

MIN_ROWS = 30     # below this, a model would just be noise


def build_xy(docs):
    """docs -> (X, y). Skips any row with a missing value."""
    X, y = [], []
    for d in docs:
        internal = d.get("marks", {}).get("internal")
        final = d.get("marks", {}).get("final")
        att = d.get("attendance")
        if None in (internal, final, att):
            continue
        X.append([internal, att])
        y.append(final)
    return np.array(X, dtype=float), np.array(y, dtype=float)


def train_and_report(X, y):
    if len(y) < MIN_ROWS:
        print(f"Only {len(y)} usable rows (need {MIN_ROWS}+). Add more data first.")
        return None
    X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, random_state=42)
    model = LinearRegression().fit(X_tr, y_tr)
    pred = model.predict(X_te)
    print(f"Train rows: {len(y_tr)}   Test rows: {len(y_te)}")
    print(f"MAE : {mean_absolute_error(y_te, pred):.2f} marks")
    print(f"R^2 : {r2_score(y_te, pred):.3f}   (1.0 perfect, 0 = no better than the mean)")
    print(f"final ≈ {model.coef_[0]:.2f}*internal + {model.coef_[1]:.2f}*attendance + {model.intercept_:.2f}")
    return model


def main():
    uri = os.environ.get("MONGODB_URI", "mongodb://127.0.0.1:27017")
    client = MongoClient(uri, serverSelectionTimeoutMS=5000)
    db = client[os.environ.get("DB_NAME", "coursehub")]
    docs = list(db.enrollments.find({"status": "completed"},
                                    {"_id": 0, "attendance": 1, "marks": 1}))
    X, y = build_xy(docs)
    train_and_report(X, y)
    client.close()


if __name__ == "__main__":
    main()
```

### The honest part 🔥

With the **seeded** data, there are only ~15 completed enrollments **and their marks are random numbers** — so a model would be pure noise. That is why the script **refuses to train below 30 rows** and says so.

When I tested the pipeline offline on **synthetic data that really does depend on internal marks and attendance** (80 rows), it printed:

```
Train rows: 60   Test rows: 20
MAE : 2.26 marks
R^2 : 0.840
final ≈ 0.86*internal + 0.19*attendance + -13.43
```

That output is from my synthetic test data, **not** from your seed — it only shows what a healthy result *looks like*. With random seed data, expect an R² near 0 (or negative) — and that is the **correct** answer: "no relationship to learn".

> **What to say in the viva:** *"I included a regression model to demonstrate the PyMongo → pandas/NumPy → scikit-learn path from Unit V. I set a minimum-rows guard because a model trained on 15 random rows would be misleading. With real historical data the same code would give meaningful metrics."* — That sentence shows maturity.

### Remember the Unit V ML cautions

- **Split before judging** — we use `train_test_split`, never score on training data.
- **Data leakage** — `final` is the label, so it must **not** also be a feature. (Notice `X` only has `internal` and `attendance`.)
- **Privacy/fairness** — predictions about students affect people. Treat them as *support for a human decision*, not a verdict.

## 4. Index proof with `explain` — `analytics/check_indexes.py`

In Part 1 you promised "each key query uses an index". **Prove it.**

```python
"""Run explain('executionStats') on CourseHub's key queries."""
import os

from pymongo import MongoClient

QUERIES = [
    ("Q1 student by rollNo", "students",
     {"find": "students", "filter": {"rollNo": "CSE2301"}}),
    ("Q2 branch + sort name", "students",
     {"find": "students", "filter": {"branch": "CSE"}, "sort": {"name": 1}}),
    ("Q3 course by code", "courses",
     {"find": "courses", "filter": {"code": "CSE494"}}),
    ("Q4 catalogue filter", "courses",
     {"find": "courses",
      "filter": {"department": "CSE", "semester": 5, "isActive": True}}),
    ("Q6 class list", "enrollments",
     {"find": "enrollments", "filter": {"status": "enrolled"}}),
    ("Q8 completed report", "enrollments",
     {"aggregate": "enrollments", "cursor": {},
      "pipeline": [{"$match": {"status": "completed"}},
                   {"$group": {"_id": "$course", "avg": {"$avg": "$total"}}}]}),
]


def planner_and_stats(explain):
    """Find queryPlanner/executionStats for find AND aggregate explain output."""
    if "queryPlanner" in explain:
        return explain["queryPlanner"], explain.get("executionStats", {})
    for stage in explain.get("stages", []):          # aggregate: first stage is $cursor
        if "$cursor" in stage:
            c = stage["$cursor"]
            return c.get("queryPlanner", {}), c.get("executionStats", {})
    return {}, {}


def collect_stages(plan, found=None):
    """Walk a plan tree and collect stage names (and index names)."""
    found = [] if found is None else found
    if not isinstance(plan, dict):
        return found
    if "queryPlan" in plan:                          # newer engines wrap the plan
        return collect_stages(plan["queryPlan"], found)
    if "stage" in plan:
        found.append(plan["stage"] + (f"({plan['indexName']})" if "indexName" in plan else ""))
    for key in ("inputStage", "thenStage", "elseStage"):
        collect_stages(plan.get(key), found)
    for child in plan.get("inputStages", []):
        collect_stages(child, found)
    return found


def verdict(stages):
    text = " ".join(stages)
    if "COLLSCAN" in text:
        return "❌ COLLSCAN"
    if "IXSCAN" in text:
        return "✅ IXSCAN"
    return "❔ check manually"


def main():
    uri = os.environ.get("MONGODB_URI", "mongodb://127.0.0.1:27017")
    client = MongoClient(uri, serverSelectionTimeoutMS=5000)
    db = client[os.environ.get("DB_NAME", "coursehub")]

    for label, _coll, cmd in QUERIES:
        explain = db.command({"explain": cmd, "verbosity": "executionStats"})
        planner, stats = planner_and_stats(explain)
        stages = collect_stages(planner.get("winningPlan", {}))
        print(f"{label:<26} {verdict(stages):<14}"
              f" returned={stats.get('nReturned')}"
              f" docsExamined={stats.get('totalDocsExamined')}"
              f" keysExamined={stats.get('totalKeysExamined')}")
        print(f"{'':<26} stages: {' > '.join(stages)}")
    client.close()


if __name__ == "__main__":
    main()
```

What it does:

- `db.command({"explain": <command>, "verbosity": "executionStats"})` — explain from PyMongo (Unit V Part 5).
- `planner_and_stats` — handles both `find` explain and **aggregate** explain (where the plan hides inside the first `$cursor` stage).
- `collect_stages` — walks the plan tree and lists stage names (`FETCH > IXSCAN(index)`). It also looks inside a `queryPlan` wrapper, because newer server versions wrap the plan.
- `verdict` — `✅ IXSCAN` or `❌ COLLSCAN`.

Run:

```bash

```

Shape of the output:

```
Q1 student by rollNo       ✅ IXSCAN      returned=1 docsExamined=1 keysExamined=1
                           stages: FETCH > IXSCAN(rollNo_1)
Q2 branch + sort name      ✅ IXSCAN      returned=3 docsExamined=3 keysExamined=3
                           stages: FETCH > IXSCAN(branch_1_name_1)
...
```

> I tested the **parsing functions** offline against hand-written explain dictionaries (one `IXSCAN`, one `COLLSCAN`, and the wrapped-plan form) and they classified them correctly. Real `explain` output differs a little between MongoDB versions, so if a line shows `❔ check manually`, open the raw explain in `mongosh` and read it like in Unit IV.

### ⚠️ Honest caveat about tiny data

With only a handful of documents the planner's choice can look surprising (for instance, a filter that matches most of the collection can legitimately pick a collection scan). **Indexes prove their worth at scale.** For your report, you can generate a larger dataset (see Exercise 3 at the end) and show `docsExamined` staying small while the collection grows.

## 5. Seat reconciliation — `analytics/reconcile_seats.py`

In Part 2 we admitted: *if the server dies between "take a seat" and "create the enrollment", the counter can drift.* Production systems answer this with a **reconciliation job** — recompute the truth from the source data and fix the cache.

```python
"""Recompute courses.enrolledCount from the enrollments (dry-run by default)."""
import os
import sys

from pymongo import MongoClient, UpdateOne


def expected_counts(db):
    """courseId -> number of enrollments that hold a seat."""
    pipeline = [
        {"$match": {"status": {"$in": ["enrolled", "completed"]}}},
        {"$group": {"_id": "$course", "n": {"$sum": 1}}},
    ]
    return {d["_id"]: d["n"] for d in db.enrollments.aggregate(pipeline)}


def plan_fixes(courses, expected):
    """Pure function: list the courses whose stored count is wrong."""
    fixes = []
    for c in courses:
        correct = expected.get(c["_id"], 0)
        if c.get("enrolledCount", 0) != correct:
            fixes.append({"_id": c["_id"], "code": c["code"],
                          "stored": c.get("enrolledCount", 0), "correct": correct})
    return fixes


def main():
    apply_changes = "--apply" in sys.argv
    uri = os.environ.get("MONGODB_URI", "mongodb://127.0.0.1:27017")
    client = MongoClient(uri, serverSelectionTimeoutMS=5000)
    db = client[os.environ.get("DB_NAME", "coursehub")]

    fixes = plan_fixes(list(db.courses.find({}, {"code": 1, "enrolledCount": 1})),
                       expected_counts(db))

    if not fixes:
        print("✅ All seat counters are correct.")
    for f in fixes:
        print(f"{f['code']}: stored={f['stored']} correct={f['correct']}")

    if fixes and apply_changes:
        result = db.courses.bulk_write(
            [UpdateOne({"_id": f["_id"]}, {"$set": {"enrolledCount": f["correct"]}}) for f in fixes])
        print(f"🔧 Fixed {result.modified_count} course(s).")
    elif fixes:
        print("(dry run — run again with --apply to fix)")
    client.close()


if __name__ == "__main__":
    main()
```

Usage:

```bash
python reconcile_seats.py            # dry run: only reports differences
python reconcile_seats.py --apply    # actually fixes them
```

Try it yourself (great demo!):

```js
// mongosh: deliberately corrupt a counter
db.courses.updateOne({ code: "ECE210" }, { $set: { enrolledCount: 5 } })
```
```bash
python reconcile_seats.py
# ECE210: stored=5 correct=1
# (dry run — run again with --apply to fix)
python reconcile_seats.py --apply
# 🔧 Fixed 1 course(s).
```

> **Dry-run-by-default** is a life-saving habit for any script that changes data. The tested pure function `plan_fixes` returned only the wrong course when I fed it three sample courses.

> **Concept link:** `enrolledCount` is a *derived / denormalized* value (Unit III trade-off). Derived values make reads fast, but you need a way to **verify and repair** them. That sentence is gold for a viva.

## 10. 25 examiner questions — with model answers

**1. Why MongoDB for this project?**
Nested/array data (address, skills, topics), flexible schema, and strong aggregation for reports.

**2. Why is `enrollments` a separate collection?**
Student–Course is many-to-many and the relationship has its own data (marks, attendance); embedding would create unbounded or heavily-rewritten documents.

**3. What did you embed and why?**
Address, skills, topics — small, bounded, always read with the parent.

**4. How do you prevent duplicate enrollments?**
Unique compound index on `{student, course}`; the database enforces it, and error 11000 becomes HTTP 409.

**5. What if two students take the last seat at once?**
Seat reservation is one atomic `findOneAndUpdate` whose filter checks `enrolledCount < maxSeats`; only one request can match.

**6. Why not a transaction?**
A single-document atomic update is enough for the seat; transactions need a replica set and cost more. I use a compensating `$inc: -1` if the next step fails, plus a reconciliation script.

**7. What is `$expr` doing there?**
It lets the filter compare two fields of the same document (`enrolledCount` vs `maxSeats`).

**8. Which indexes did you create and why?**
Each one maps to a listed query (table in the report). The `{student, course}` index serves duplicate check, "my courses" lookup and uniqueness.

**9. How do you know the indexes are used?**
`explain("executionStats")` shows `IXSCAN` and small `docsExamined`; I included before/after screenshots.

**10. What's a covered query / ESR rule?**
(Unit IV) ESR: index fields ordered Equality, Sort, Range. `{branch, name}` is Equality then Sort.

**11. Why store `total` and `grade` instead of computing them?**
Faster reports; it's derived data I recompute whenever marks change, in one place.

**12. What is the downside of derived fields?**
They can go out of sync — hence the single update path and the reconciliation script.

**13. How does `$lookup` differ from Mongoose `populate`?**
`$lookup` joins inside the database in one aggregation; `populate` runs extra queries from the app. I used `$lookup` for reports and `populate` for simple listing.

**14. Why `$group` before `$lookup` in reports?**
So only the few grouped rows are joined, not every enrollment.

**15. How do you protect against NoSQL injection?**
Whitelist fields, check `typeof` of query parameters, validate ids with a strict regex, escape user text before using it in `$regex`.

**16. Why does the API default marks to `null`?**
`null` = not recorded; `0` would be a real score and corrupt reports.

**17. What status codes do you return?**
200, 201, 204, 400 (validation / bad id), 404 (missing), 409 (conflict: duplicate/full/inactive), 500 (unexpected).

**18. What does `runValidators: true` do?**
Runs schema validators on update queries, which skip them by default.

**19. Where are secrets kept?**
In `.env`, ignored by Git; `.env.example` documents the variables.

**20. Why wait for `Model.init()`?**
So unique indexes exist before the server takes requests.

**21. How is the Python part connected?**
Same database via PyMongo; it reads with an aggregation and applies rules, plus an optional regression model.

**22. Is the ML model reliable?**
Only if there's enough real data; the script refuses to train under 30 rows, and I explain metrics and leakage risks.

**23. What would you change for production?**
Authentication/roles, TLS, replica set + backups, monitoring, rate limiting, automated tests, disabling auto-index creation (Part 4).

**24. How would this scale?**
Indexes first, then read replicas, then sharding with a good shard key (e.g. a hashed or compound key) if one server is no longer enough.

**25. What are the limitations?**
No login, no UI, no automated test suite, small data volume, regex name search not index-friendly.

## 12. Common traps 🚨

### Trap 1: ML on seed data and claiming results
Random numbers can't be predicted. Say so.

### Trap 2: Labelling a rule-based script "AI"
It is a **rule-based** system; that is fine and often better. Don't overclaim.

### Trap 3: Forgetting to activate the Python venv
`ModuleNotFoundError: No module named 'pymongo'` — activate first, then `pip install`.

### Trap 4: `explain()` on an empty/tiny collection and drawing big conclusions
Prove scale effects with bigger data.

### Trap 5: Running `--apply` blindly
Always dry-run first and read the differences.

### Trap 6: README without setup steps
No marker will guess your commands.

### Trap 7: Demo only the happy path
Failures show your rules actually work.

### Trap 8: Hard-coded connection strings in scripts
Use environment variables (as the scripts do).

### Trap 9: No plan B for the live demo
Keep screenshots and a cloud database ready.

### Trap 10: Not being able to explain your own code
If you can't explain a line, rewrite it simpler.

## 14. 🔥 PART 3 — WHAT YOU MUST REMEMBER

**Why a Python script on the same DB?**

> Demonstrates both drivers on one database and the real-world split between live service and analytics.

**Why rules before ML?**

> Rules are explainable and need no training data; ML needs enough real data and careful evaluation.

**Why a minimum-rows guard on the model?**

> A model on a few random rows only fits noise.

**How do you prove an index is used?**

> `explain("executionStats")` → `IXSCAN`, low `docsExamined`.

**What is reconciliation?**

> Recomputing a derived value from source data and repairing mismatches.

**Why dry-run by default?**

> Data-changing scripts must show what they would do before doing it.

**What goes in a good demo?**

> Pitch → data model → happy path → failures → race proof → reports → index proof → limitations.
