# 🟢 SECTION 1 — WHAT IS "PRODUCTION"?

## 1. Laptop vs production

| Question | On your laptop (development) | In production |
|---|---|---|
| Who uses it? | You | Real users, maybe thousands |
| If it crashes? | Restart it | Money / trust / data is lost |
| Data | Fake, disposable | Real, irreplaceable |
| Network | Only `localhost` | Internet, other servers, attackers |
| Failure of one machine | Doesn't matter | Must be survived automatically |
| Secrets | `.env` on your disk | Managed secret store |
| Changes | Edit and rerun | Reviewed, tested, reversible |
| Monitoring | Your eyes | Dashboards + alerts at 3 a.m. |

> **The mindset shift:** in development you ask *"does it work?"*. In production you ask *"what happens when it breaks, when it's attacked, when it grows, and when the person who built it is asleep?"*

## 2. The seven pillars (our map for this Part)

```
        ┌────────────────────────────────────────────┐
        │             PRODUCTION-READY               │
        └────────────────────────────────────────────┘
   1 DATA MODEL      →  stays correct and fast as data grows
   2 PERFORMANCE     →  indexes, query habits
   3 SECURITY        →  only the right people/apps can do the right things
   4 CORRECTNESS     →  write/read guarantees, transactions where needed
   5 AVAILABILITY    →  survives machine failures (replica sets)
   6 RECOVERY        →  backups you have actually tested
   7 OPERABILITY     →  monitoring, alerts, safe changes, documentation
```

# 🟢 SECTION 2 — DATA MODEL PRACTICES

## 3. Ten schema rules that save you later

```
1. Model for your QUERIES, not for "how things look" (Unit III)
2. Embed small, bounded, read-together data; reference the rest
3. NEVER let an array grow without limit (16 MB document cap, slow updates)
4. Keep documents reasonably small — don't drag huge blobs through every read
5. Use consistent field names and types across documents
6. Store money/precise numbers carefully (integers in smallest unit, or Decimal128)
7. Store dates as real Date values (UTC), not strings
8. Avoid very deep nesting
9. Add a schemaVersion field so documents can evolve safely
10. Validate on the way IN (app validation AND database validation)
```

### Why "unbounded arrays" is the #1 beginner killer

```js
// ❌ every comment pushed into the post forever
{ _id: 1, title: "Hello", comments: [ /* 1 … 50,000 … */ ] }
```

Problems: document nears the **16 MB** limit, every read drags all comments, every update rewrites a huge document. Fix: **reference** (a `comments` collection with `postId`) or the **bucket** pattern (a few hundred per document). You saw exactly this logic with `enrollments`.

### Money

```
price: 19.99      ← floating point, tiny rounding errors
price: 1999       ← integer paise/cents  ✅ simple and exact
price: NumberDecimal("19.99")   ← Decimal128 ✅ exact decimals
```

## 4. Database-level validation: `$jsonSchema`

Mongoose validates in **your Node app only**. A different script (or a person in `mongosh`) bypasses it. **Database-side validation** protects the data no matter who writes.

```js
// mongosh
db.createCollection("courses", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["code", "title", "credits", "maxSeats"],
      properties: {
        code:     { bsonType: "string", description: "course code" },
        title:    { bsonType: "string", minLength: 3 },
        credits:  { bsonType: "int", minimum: 1, maximum: 6 },
        maxSeats: { bsonType: "int", minimum: 1 },
        isActive: { bsonType: "bool" }
      }
    }
  },
  validationLevel: "strict",     // check all inserts AND updates
  validationAction: "error"      // reject (the alternative "warn" only logs)
})
```

Test it:

```js
db.courses.insertOne({ code: "X1", title: "ab", credits: 3, maxSeats: 10 })
// ❌ fails: title shorter than minLength 3  → "Document failed validation"
```

| Setting | Meaning |
|---|---|
| `validationLevel: "strict"` | validate every insert and update (default) |
| `validationLevel: "moderate"` | validate inserts and updates only to documents that were *already valid* — useful when old bad data exists |
| `validationAction: "error"` | reject invalid writes (default) |
| `validationAction: "warn"` | allow but log a warning — good for rolling out new rules |

> **Two layers = defence in depth:** Mongoose gives friendly errors fast; `$jsonSchema` is the last line of defence. A numeric field written as `int` vs `double` can matter to `bsonType` checks — check how your driver stores numbers (JavaScript numbers are doubles by default unless the driver converts them), and use `"number"` in the schema if you accept both.

## 5. Schema versioning (safe evolution)

Your schema **will** change. Old and new documents coexist.

```js
{ schemaVersion: 1, name: "Aarav Mehta" }                          // old
{ schemaVersion: 2, firstName: "Aarav", lastName: "Mehta" }        // new
```

Application code reads `schemaVersion` and handles both, while a background job migrates old documents in small batches. This lets you deploy new code **without downtime** and without one giant risky update.

# 🟢 SECTION 3 — INDEXING PRACTICES

## 6. Index rules

```
1. Index from your QUERY LIST, never "just in case"
2. Every index costs: disk, RAM, and slower writes — so fewer, better indexes
3. Order compound index fields: Equality → Sort → Range (ESR)
4. A compound index also serves its PREFIXES ({a,b} serves a, and a+b)
5. Delete indexes nobody uses (check $indexStats)
6. Keep the "working set" (hot data + indexes) within RAM if possible
7. Test every important query with explain("executionStats")
8. Build indexes on big live collections deliberately, off-peak
9. Don't let the ORM silently create indexes in production
```

### Find unused indexes

```js
db.enrollments.aggregate([ { $indexStats: {} } ])
// look at accesses.ops — an index with ops: 0 for a long time is a candidate to remove
```

(Counters reset when the server restarts, so judge over a meaningful period — Unit V Part 7.)

### Hide before you drop (Unit V Part 7)

```js
db.enrollments.hideIndex("status_1_total_-1")   // planner ignores it, but it still exists
// watch for slowness; if all is well:
db.enrollments.dropIndex("status_1_total_-1")
// if slow:
db.enrollments.unhideIndex("status_1_total_-1")
```

## 7. Mongoose: turn off automatic index building in production

In development, Mongoose builds the indexes declared in your schema when the app starts — convenient. In production, a large index build triggered by *every app instance starting up* is dangerous.

```js
// production-friendly: do not auto-build
mongoose.set("autoIndex", process.env.NODE_ENV !== "production");
```

Instead, create indexes with a **deliberate script/migration**:

```js
// scripts/sync-indexes.js  (run once per deployment, intentionally)
import "dotenv/config";
import { connectDB, disconnectDB } from "../src/db.js";
import { Student } from "../src/models/Student.js";
import { Course } from "../src/models/Course.js";
import { Enrollment } from "../src/models/Enrollment.js";

await connectDB(process.env.MONGODB_URI);
for (const Model of [Student, Course, Enrollment]) {
  await Model.createIndexes();            // creates missing indexes declared in the schema
  console.log("indexes ok:", Model.collection.name);
}
await disconnectDB();
```

> `syncIndexes()` also **drops** indexes that aren't in the schema — powerful but dangerous; read its docs before using it on production data. `createIndexes()` only adds.

> **Important for our unique index:** if the app runs with `autoIndex` off, the unique `{student, course}` index **must** already exist — otherwise duplicates are possible. That's why the sync script is part of the deployment checklist.

# 🟢 SECTION 4 — QUERY PRACTICES

## 8. Query habits

| Habit | Why |
|---|---|
| **Always `limit`** lists | no endpoint should be able to return 10 million rows |
| **Project** only needed fields | less network, less memory; can enable covered queries |
| **Avoid deep `skip`** | `skip(100000)` still walks 100 000 entries — use keyset pagination (Unit V Part 3) |
| **Filter early in pipelines** | `$match`/`$limit` first |
| **Set `maxTimeMS`** | a runaway query gets cancelled instead of eating the server |
| **Avoid unanchored regex** on big data | `/aar/i` can't use an index well |
| **Don't `find()` everything then filter in code** | let the database filter |
| **Prefer atomic update operators** (`$inc`, `$push`, `$set`) | no read-modify-write races |
| **Use `$lookup` sparingly on huge collections** | consider embedding or copying a field if a join runs on every request |
| **Measure with `explain`** | never guess |

```js
// a safe default query shape
Student.find(filter)
  .select("rollNo name branch")      // projection
  .sort({ name: 1 })
  .limit(50)                         // cap
  .maxTimeMS(2000)                   // kill if slower than 2 s
  .lean();
```

# 🟢 SECTION 5 — APPLICATION & DRIVER PRACTICES

## 9. Connection management

```
ONE client/connection per process, created at startup, reused everywhere
(never connect inside a request handler)
```

Useful options (names are standard driver options; check your driver docs for defaults):

```js
await mongoose.connect(uri, {
  maxPoolSize: 20,                    // max simultaneous connections from THIS process
  serverSelectionTimeoutMS: 5000,     // fail fast if no server reachable
  socketTimeoutMS: 45000,             // abandon a stuck socket
  appName: "coursehub-api"            // shows up in server logs/profiler → easy to identify
});
```

### Pool sizing — the hidden trap

```
Total possible connections = instances × maxPoolSize
   10 app instances × 100 pool size = 1,000 connections to the database!
```

Each connection uses server resources. Size pools **per instance** so the total is sensible.

### Serverless / short-lived functions

Functions that start and stop constantly can open a new connection every invocation. Reuse the client across invocations (module-level variable) — otherwise connection counts explode.

## 10. Retries and timeouts

- **Retryable writes**: modern drivers can automatically retry certain writes once after a transient failure (e.g., a primary election). Atlas connection strings usually include `retryWrites=true`.
- **Idempotency matters**: retrying `$inc: 1` blindly could double-count if the first attempt actually succeeded. Know which of your operations are safe to repeat — that's one reason our seat logic uses conditional filters and unique indexes.
- **Always use timeouts** — an operation without a timeout can hang a request forever.

## 11. Health checks and graceful shutdown

```js
// readiness: "can I actually serve traffic?"
app.get("/health", async (req, res) => {
  try {
    await mongoose.connection.db.admin().command({ ping: 1 });
    res.json({ status: "ok" });
  } catch {
    res.status(503).json({ status: "db-unreachable" });
  }
});
```

- A load balancer or orchestrator (Kubernetes, etc.) calls `/health`; `503` means "don't send me traffic".
- On `SIGTERM` (deployment restart): stop accepting new requests, finish current ones, close DB — as in our `server.js`.

## 12. Error handling and logging

- **Never** send stack traces or raw DB errors to clients (our handler returns a generic 500).
- **Log** enough to debug: timestamp, request id, route, status, duration. Use a structured logger (JSON logs) in real systems.
- **Never log** passwords, tokens, or full personal data.
- Distinguish **expected** errors (400/404/409) from **unexpected** ones (500) — alert on the second kind.

# 🟢 SECTION 6 — SECURITY, IN LAYERS 🔒

## 13. Security is layers, not one lock

```
 INTERNET
    │
 ┌──▼────────────────────────────────────────┐
 │ 1 NETWORK    firewall / private network / IP allow-list │
 ├──────────────────────────────────────────┤
 │ 2 TRANSPORT  TLS encryption in transit               │
 ├──────────────────────────────────────────┤
 │ 3 AUTHENTICATION  who are you?                        │
 ├──────────────────────────────────────────┤
 │ 4 AUTHORIZATION   what may you do? (roles)           │
 ├──────────────────────────────────────────┤
 │ 5 APPLICATION   validation, injection defence, rate limits │
 ├──────────────────────────────────────────┤
 │ 6 DATA          encryption at rest / field-level          │
 ├──────────────────────────────────────────┤
 │ 7 AUDIT         who did what, when                        │
 └──────────────────────────────────────────┘
```

> If one layer fails, the others still protect you. That's **defence in depth**.

## 14. Layer 1 — Network

```
✅ Never expose mongod to the open internet
✅ Bind to private interfaces only (default is localhost-only in modern versions)
✅ Allow only your app servers' IPs (firewall / security groups / Atlas IP access list)
✅ Prefer private connectivity (VPC peering / private endpoints) over public IPs
❌ "0.0.0.0/0 allow all" on a database — this is how real breaches happened
```

Config sketch (self-managed `mongod.conf`):

```yaml
net:
  port: 27017
  bindIp: 127.0.0.1,10.0.1.15      # localhost + this server's PRIVATE address
```

## 15. Layer 2 — TLS (encryption in transit)

Without TLS, anyone on the network path can read credentials and data.

```yaml
net:
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/ssl/mongodb.pem
    CAFile: /etc/ssl/ca.pem
```

Atlas connections use TLS by default (`mongodb+srv://` implies TLS).

## 16. Layers 3 & 4 — Authentication and role-based access control (RBAC)

### Authentication — who are you?

Self-managed MongoDB does **not** require login unless you turn it on — an out-of-the-box local install is open to whoever can reach it.

```yaml
security:
  authorization: enabled
```

Create the first admin (using the localhost exception) and then an **application user**:

```js
// mongosh — step 1: admin user
use admin
db.createUser({
  user: "admin",
  pwd: passwordPrompt(),         // prompts, so the password isn't in history
  roles: [ { role: "userAdminAnyDatabase", db: "admin" } ]
})

// restart mongod with authorization enabled, then log in as admin
// step 2: a LEAST-PRIVILEGE user for the application
use coursehub
db.createUser({
  user: "coursehub_app",
  pwd: passwordPrompt(),
  roles: [ { role: "readWrite", db: "coursehub" } ]
})
```

Connection string for the app:

```
mongodb://coursehub_app:<password>@db1.internal:27017/coursehub?authSource=coursehub
```

(`authSource` = the database where the user was created.)

### Authorization — what may you do?

MongoDB uses **role-based access control**: users get roles; roles are sets of privileges.

| Built-in role | Gives |
|---|---|
| `read` | read all non-system collections in one DB |
| `readWrite` | read + write in one DB |
| `dbAdmin` | admin tasks (indexes, stats) in one DB — no data access by itself |
| `userAdmin` | manage users/roles in one DB |
| `readAnyDatabase`, `readWriteAnyDatabase` | across all databases (powerful!) |
| `clusterAdmin`, `root` | very high privilege |

### Principle of least privilege 🔥

> **Give every user and every app only the permissions it needs — nothing more.**

| Who | Role |
|---|---|
| CourseHub API | `readWrite` on `coursehub` only |
| Analytics script (only reads) | `read` on `coursehub` |
| Reconcile script (updates counters) | a **custom role** limited to `find`/`update` on `courses` & `enrollments` |
| Human DBA | `dbAdmin` / `userAdmin`, with audit |

A custom role example:

```js
use coursehub
db.createRole({
  role: "seatReconciler",
  privileges: [
    { resource: { db: "coursehub", collection: "courses" },     actions: ["find", "update"] },
    { resource: { db: "coursehub", collection: "enrollments" }, actions: ["find"] }
  ],
  roles: []
})
```

> **Why it matters:** if the analytics script's credentials leak, an attacker with a `read`-only user can't delete your data. Blast radius = smaller.

## 17. Layer 5 — Application security

### 17.1 Injection defence (recap of Unit V Part 3)

```
✅ whitelist the fields you accept
✅ check typeof of query params/body values (string vs object)
✅ validate ids with a strict pattern
✅ escape user text used inside $regex
❌ never pass req.body straight into a query
❌ never run $where / eval-style JavaScript with user input
```

### 17.2 Passwords

```
✅ hash with a slow, salted algorithm (bcrypt / argon2) — never store plain text, never fast hashes like MD5/SHA1
✅ never log or return password hashes
```

### 17.3 HTTP hardening for the CourseHub API

```bash
npm install helmet express-rate-limit
```

```js
import helmet from "helmet";
import rateLimit from "express-rate-limit";

app.disable("x-powered-by");      // don't advertise the framework
app.use(helmet());                // sets several security-related HTTP headers

app.use("/api", rateLimit({
  windowMs: 60 * 1000,            // 1 minute
  max: 100,                       // 100 requests per IP per minute
  standardHeaders: true,
  legacyHeaders: false,
}));
```

- `helmet` sets common protective headers.
- `express-rate-limit` slows brute-force and abuse. (Option names can change between major versions — check the package docs.)
- Add CORS only for origins you trust; add authentication (e.g., JWT/session) before exposing write routes.

## 18. Layer 6 — Data protection

| Mechanism | What it protects | Notes |
|---|---|---|
| **Encryption in transit** (TLS) | data on the wire | always |
| **Encryption at rest** | disks/backups if stolen | Atlas encrypts storage by default; self-managed can use encrypted disks or Enterprise encrypted storage engine |
| **Client-side field-level encryption (CSFLE)** / **Queryable Encryption** | sensitive fields encrypted *before* they leave the app, so even DBAs/the server can't read them | newer, specialised; check current docs for supported query types |
| **Data minimisation** | store less personal data | the safest data is data you never collected |
| **Backups are data too** | encrypt and restrict access to them | |

## 19. Layer 7 — Auditing

*Who deleted that collection?* Without an audit trail you can't answer. Auditing features exist in Atlas and MongoDB Enterprise; at minimum, log admin actions and keep **per-person** accounts (no shared "admin" login).

## 20. Secrets management

```
❌ credentials hard-coded in source code
❌ committed .env files
✅ environment variables injected at deploy time
✅ a secrets manager (cloud secret store / vault) for real systems
✅ rotate credentials; separate credentials per environment (dev ≠ staging ≠ prod)
```

> If a secret was ever committed to Git, **assume it's compromised** — rotate it. Deleting the file in a later commit doesn't remove it from history.

## 21. The MongoDB security checklist (memorise this one)

```
☐ Authentication ENABLED
☐ Role-based access, least privilege, one user per app/person
☐ Network: not public; firewall / IP allow-list / private network
☐ TLS for all connections
☐ Encryption at rest (and encrypted, access-controlled backups)
☐ Secrets outside the code; rotated
☐ Input validation + injection defences in the app
☐ Rate limiting, secure headers
☐ Auditing / logging, no sensitive data in logs
☐ Regular updates / patches
```

# 🟢 SECTION 7 — DURABILITY & CONSISTENCY

## 22. Write concern — "how safe must a write be before I get 'OK'?"

```
w: 1          → acknowledged by the primary only
w: "majority" → acknowledged after a MAJORITY of replica-set members have it
j: true       → also written to the on-disk journal
```

```js
db.enrollments.insertOne(
  { student: 1, course: 2 },
  { writeConcern: { w: "majority", j: true } }
)
```

| Choice | Speed | Safety |
|---|---|---|
| `w: 1` | fastest | if the primary dies before replicating, the write may be **rolled back** after failover |
| `w: "majority"` | slower | survives a primary failure — data is on most members |

> Defaults differ by version and deployment (modern versions generally default to majority in common replica-set setups, but there are exceptions such as when an arbiter is involved) — **don't rely on memory; check your version's docs and set it explicitly for important data.** Atlas connection strings typically include `w=majority`.

**Use `w: "majority"` for data you cannot lose** (payments, enrollments, orders). Lower levels can be fine for disposable data like logs.

## 23. Read concern & read preference

### Read concern — "how safe must the data I read be?"

| Level | Meaning |
|---|---|
| `local` | what this member has (may later be rolled back) |
| `majority` | data acknowledged by a majority — won't be rolled back |
| `snapshot` | consistent snapshot (used in transactions) |
| `linearizable` | strongest, slowest — reflects all prior majority-acknowledged writes |
| `available` | lowest latency; mostly relevant to sharded setups |

### Read preference — "which member do I read from?"

| Mode | Reads from |
|---|---|
| `primary` (default) | the primary — always the latest data |
| `primaryPreferred` | primary, else a secondary |
| `secondary` | a secondary — **may be slightly behind** |
| `secondaryPreferred` | a secondary if available |
| `nearest` | lowest-latency member |

```
 Reading from secondaries spreads load, BUT:
 "stale read" risk → a user saves data, refreshes, and doesn't see it yet
 (replication lag). Use primary for read-your-own-writes screens.
```

## 24. Transactions — when to use them

MongoDB operations on a **single document are atomic** (even with nested arrays). Many designs need nothing more. Multi-document ACID transactions exist (they need a replica set or sharded cluster):

```js
const session = await mongoose.startSession();
try {
  await session.withTransaction(async () => {
    await Course.updateOne({ _id: courseId }, { $inc: { enrolledCount: 1 } }, { session });
    await Enrollment.create([{ student: studentId, course: courseId }], { session });
  });
} finally {
  await session.endSession();
}
```

`withTransaction` retries on transient errors and commits when the callback finishes; if the callback throws, it aborts.

### Guidance

```
✅ Prefer a design where one document holds what must change together
✅ Use transactions when several documents MUST change together or not at all
✅ Keep them short (they hold resources; there's a time limit)
❌ Don't use transactions as a reflex to cure a bad schema
```

> This is exactly the trade-off in CourseHub: single-document atomic seat reservation + compensation (cheap, simple) vs a transaction (cleaner guarantee, needs a replica set, more overhead).

# 🟢 SECTION 8 — HIGH AVAILABILITY

## 25. Replica sets (recap + production view)

```
              ┌────────────┐
   writes ──▶ │  PRIMARY   │
              └─────┬──────┘
          replicates│(oplog)
        ┌───────────┴───────────┐
        ▼                       ▼
 ┌────────────┐          ┌────────────┐
 │ SECONDARY  │          │ SECONDARY  │
 └────────────┘          └────────────┘
```

- Writes go to the **primary**; secondaries copy them from the **oplog**.
- If the primary fails, the remaining members hold an **election** and one secondary becomes primary — usually within seconds to tens of seconds.
- **Use an odd number of voting members** (commonly 3) so a majority exists.
- Spread members across **different machines / racks / zones** — three members on one server is not high availability.
- Applications use a connection string listing the members + `replicaSet=name`; the driver finds the current primary and handles failover (with retryable writes smoothing it over).

```
mongodb://db1:27017,db2:27017,db3:27017/coursehub?replicaSet=rs0&w=majority&retryWrites=true
```

### What a replica set is NOT

> **A replica set is not a backup.** If someone runs `db.dropDatabase()`, that deletion is replicated to every member within moments. You still need real backups (next section).

# 🟢 SECTION 9 — BACKUP & DISASTER RECOVERY

## 26. The two numbers every business asks

```
RPO (Recovery Point Objective) = how much DATA LOSS can we tolerate?   "last 5 minutes"
RTO (Recovery Time Objective)  = how much DOWNTIME can we tolerate?    "back in 1 hour"
```

Your backup strategy is chosen to meet RPO/RTO — not the other way round.

## 27. Backup methods

| Method | How | Good for | Caveat |
|---|---|---|---|
| **Logical** — `mongodump` / `mongorestore` | exports BSON | small/medium data, migrations, dev copies | slower on big data; not a point-in-time snapshot of a busy cluster unless used with oplog options |
| **Filesystem / volume snapshots** | snapshot the disk | large datasets, fast restore | must be done consistently (journaling on same volume, or use a safe procedure) |
| **Managed backups** (Atlas Cloud Backup / continuous) | automatic | most teams; supports point-in-time restore on suitable tiers | tier-dependent features — check plan |
| **Oplog-based point-in-time** | replay oplog | recover to "just before the mistake" | needs planning/tooling |

### Commands you should recognise

```bash
# dump one database to a folder
mongodump --uri="mongodb://coursehub_app:<pw>@localhost:27017/coursehub?authSource=coursehub" \
          --out=./backup-2026-11-20

# restore it (into the same or another server)
mongorestore --uri="mongodb://localhost:27017" ./backup-2026-11-20
```

(Use `--drop` with `mongorestore` only when you intend to replace existing collections.)

## 28. The 3-2-1 rule and the golden rule

```
3 copies of your data
2 different storage types/places
1 copy off-site (different region/account)
```

> ## 🔥 An untested backup is not a backup — it's a hope.
> Schedule **restore drills**: restore into a scratch environment, run a few queries, record how long it took (that's your real RTO).

Also: **protect backups** (encrypted, restricted, immutable if possible) — ransomware attacks target backups too.

# 🟢 SECTION 10 — MONITORING & ALERTING

## 29. What to watch

| Area | Signals | Why |
|---|---|---|
| **Availability** | is each member up? who is primary? | detect failover/outage |
| **Replication** | replication lag, oplog window | stale secondaries; risk during failover |
| **Throughput** | opcounters (insert/query/update/delete per sec) | load trends |
| **Latency** | slow queries (profiler / Atlas Query Profiler) | users feel it first |
| **Connections** | current vs available | pool exhaustion |
| **Memory/cache** | WiredTiger cache usage, page faults | working set too big |
| **Disk** | free space, IOPS | **a full disk stops the database** |
| **Locks / queues** | operations waiting | contention |
| **Errors** | auth failures, app 5xx rate | attacks, bugs |

### Handy built-ins

```js
db.serverStatus()                 // big status document (connections, opcounters, memory…)
db.currentOp()                    // what's running RIGHT NOW (find the runaway query)
db.setProfilingLevel(1, { slowms: 100 })   // log slow operations (Unit V Part 7)
```

```bash
mongostat      # live per-second counters
mongotop       # time spent reading/writing per collection
```

Dashboards: Atlas metrics, Ops Manager / Cloud Manager, or exporters feeding Prometheus + Grafana.

## 30. Alerts: few, meaningful, actionable

```
🚨 no primary for > 1 minute
🚨 disk > 80 % full
🚨 replication lag > 10 s sustained
🚨 connections > 80 % of limit
🚨 slow-query count spike
🚨 backup job failed
🚨 app 5xx rate > 2 %
```

> Too many alerts = people ignore them ("alert fatigue"). Alert on things a human must **act** on.

# 🟢 SECTION 11 — SCALING

## 31. The scaling ladder

```
 STEP 1  Fix the queries/indexes/schema        ← cheapest, biggest wins (Unit IV)
    ↓
 STEP 2  Scale UP (vertical): more RAM/CPU/faster disk
    ↓
 STEP 3  Scale reads OUT: secondaries (mind stale reads) + caching layer
    ↓
 STEP 4  Scale OUT (horizontal): SHARDING
```

> **Never start at Step 4.** Most applications never need sharding; they need better indexes.

## 32. Sharding in one page (awareness level)

```
 clients ──▶ mongos (router) ──▶ ┌─────────┐ ┌─────────┐ ┌─────────┐
                  │              │ shard 1 │ │ shard 2 │ │ shard 3 │   (each a replica set)
                  ▼              └─────────┘ └─────────┘ └─────────┘
          config servers (metadata: which chunk lives where)
```

- Data is split by a **shard key** into chunks spread across shards.
- `mongos` routes queries; queries that include the shard key go to **one** shard (**targeted**); queries without it go to **all** shards (**scatter-gather** — slow).

### Choosing a shard key 🔥 (the decision you can't easily undo)

| Property | Want |
|---|---|
| **High cardinality** | many distinct values, so data can split |
| **Low frequency per value** | no single value dominating ("hot" chunk) |
| **Non-monotonic** | not an always-increasing key like a timestamp or default `_id` ObjectId — all inserts hit one shard |
| **Matches your queries** | most queries include it → targeted |

| Strategy | Behaviour |
|---|---|
| **Ranged** key | adjacent values together — good for range queries, risk of hot spots with monotonic keys |
| **Hashed** key | even distribution — great for write spread, poor for range queries |
| **Compound** key | combine, e.g. `{ tenantId: 1, _id: 1 }` for multi-tenant apps |

Changing a shard key later is possible in newer versions but heavy — pick carefully.

# 🟢 SECTION 12 — OPERATIONS

## 33. Environments and change management

```
 DEV  →  TEST/STAGING (production-like, fake data)  →  PRODUCTION
```

- Never test destructive scripts on production. (Remember the seed script that runs `deleteMany({})`!)
- Keep configuration per environment (`NODE_ENV`, separate connection strings and credentials).
- **Version control everything**: code, index definitions, migration scripts.
- Make changes **small, reviewed, reversible**. Deploy a backward-compatible schema change first, new code second, cleanup last.

## 34. Safe migrations

```
1. Add the new field/index (backward compatible)
2. Deploy code that writes both / reads both
3. Backfill old documents in SMALL BATCHES (rate-limited)
4. Switch reads to the new shape
5. Remove the old field later
```

```js
// batch backfill sketch: add schemaVersion to old documents, 1000 at a time
let n;
do {
  const res = await Student.updateMany(
    { schemaVersion: { $exists: false } },     // only unmigrated documents
    { $set: { schemaVersion: 1 } },
    { limit: 0 }                                // see note below
  );
  n = res.modifiedCount;
} while (n > 0);
```

> Note: `updateMany` has no built-in batch-size limit — to truly batch, first fetch a page of `_id`s with `.limit(1000)` and update `{ _id: { $in: ids } }`, pausing between batches. Always rehearse migrations on a copy.

## 35. Upgrades and maintenance

- Keep MongoDB and drivers on **supported versions**; read release notes for breaking changes.
- Upgrade one replica-set member at a time (secondaries first, then step down the primary) — the standard rolling approach.
- Plan **capacity**: watch disk and memory growth; add before you hit limits.
- **Data lifecycle**: use TTL indexes for expiring data (logs, sessions), archive cold data, consider time series collections for metrics.

```js
// TTL: auto-delete audit entries after 30 days
db.audit.createIndex({ createdAt: 1 }, { expireAfterSeconds: 60 * 60 * 24 * 30 })
```

(The TTL monitor runs periodically, so deletion is not instantaneous.)

## 36. Common traps 🚨

### Trap 1: Running with no authentication
Local default installs are open. Enabling auth is step one for anything reachable by others.

### Trap 2: Database open to `0.0.0.0/0`
Anyone on the internet can try to connect. Restrict by IP/private network.

### Trap 3: Using the admin account in the app
One leaked credential = total loss. Use a least-privilege app user.

### Trap 4: Believing "replica set = backup"
Replication copies deletes too. Take real, tested backups.

### Trap 5: Never testing a restore
You find out the backup is broken on the worst day.

### Trap 6: `w: 1` for data you can't lose
A failover can roll the write back.

### Trap 7: Reading from secondaries and expecting the latest data
Replication lag → stale reads.

### Trap 8: Auto-building indexes on every app start in production
Big builds during peak traffic. Build deliberately.

### Trap 9: Pool size × instances ignored
Hundreds of connections the server doesn't need.

### Trap 10: Choosing a monotonic shard key
All inserts hit one shard — a hot spot.

### Trap 11: Sharding before fixing queries
Complexity added for a problem indexes would have solved.

### Trap 12: Committed secrets
Rotate them; Git history remembers.

### Trap 13: Only application-level validation
Other writers bypass it. Add database validation for critical data.

### Trap 14: Alert overload
So many alerts that nobody reads them.

### Trap 15: Treating a free/shared tier as production
Learning environment, not for critical load.

## 38. 🔥 PART 4 — WHAT YOU MUST REMEMBER

**What changes between development and production?**

> Real users, real data, real attackers, real failures — so you need security, durability, availability, backups, monitoring and safe change processes.

**Name the layers of MongoDB security.**

> Network, TLS, authentication, authorization (RBAC), application defences, data encryption, auditing.

**What is least privilege?**

> Each user/app gets only the permissions it needs, limiting damage if credentials leak.

**What is write concern `majority`?**

> The write is acknowledged only after a majority of replica-set members have it, so it survives a primary failure.

**Is a replica set a backup?**

> No — it provides availability; deletes and corruption replicate. Backups are separate.

**What are RPO and RTO?**

> Acceptable data loss and acceptable downtime — they drive the backup design.

**What makes a good shard key?**

> High cardinality, low frequency, non-monotonic, and aligned with query patterns.

**Why disable `autoIndex` in production?**

> Large index builds at every app start can hurt a live system; build indexes deliberately.

**Why add `$jsonSchema` if Mongoose already validates?**

> Other clients bypass Mongoose; the database is the last line of defence.

**When do you need a transaction?**

> When several documents must change together or not at all — and a single-document atomic design can't achieve it.

**The scaling order?**

> Fix queries/indexes → scale up → read replicas/caching → shard.
