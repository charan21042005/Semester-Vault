# 🧮 SECTION B — "WHAT'S THE OUTPUT?" (with full working)

Setup for B1–B5:

```js
// db.nums
{ _id: 1, a: 5 }
{ _id: 2, a: 10 }
{ _id: 3, a: 15 }
```

### B1.
```js
db.nums.aggregate([
  { $match: { a: { $gte: 10 } } },
  { $group: { _id: null, total: { $sum: "$a" }, n: { $sum: 1 } } }
])
```
**Working:** `$match` keeps `a:10` and `a:15`. `$group` with `_id: null` = one group for everything. total = 25, n = 2.

**Output:** `[ { _id: null, total: 25, n: 2 } ]`

### B2.
```js
db.nums.updateMany({ a: { $gt: 5 } }, { $set: { a: 0 } })
```
**Working:** two docs match (10 and 15), both change.

**Output:** `{ acknowledged: true, matchedCount: 2, modifiedCount: 2 }`

Run it **again**: filter `a > 5` now matches nothing (values are 5, 0, 0) → `matchedCount: 0, modifiedCount: 0`.

### B3. (Fresh collection, as above)
```js
db.nums.updateOne({ _id: 9 }, { $set: { a: 1 } }, { upsert: true })
```
**Working:** nothing has `_id: 9` → upsert inserts `{ _id: 9, a: 1 }`.

**Output:** `matchedCount: 0, modifiedCount: 0, upsertedCount: 1, upsertedId: 9`

### B4.
```js
db.nums.find({ a: { $in: [5, 15] } }, { _id: 0, a: 1 }).sort({ a: -1 })
```
**Working:** matches a=5 and a=15; projection keeps only `a`; sort descending.

**Output:** `{ a: 15 }` then `{ a: 5 }`

### B5.
```js
db.nums.insertOne({ _id: 2, a: 99 })
```
**Working:** `_id: 2` already exists, and `_id` has a built-in unique index.

**Output:** an error: `E11000 duplicate key error ... index: _id_ dup key: { _id: 2 }`

---

### B6. (Array + `$unwind`)
```js
// { _id: 1, tags: ["x", "y"] }  and  { _id: 2, tags: [] }
db.t.aggregate([ { $unwind: "$tags" } ])
```
**Working:** doc 1 becomes two docs (`tags:"x"`, `tags:"y"`). Doc 2 has an empty array → it is **dropped** (unless `preserveNullAndEmptyArrays: true`).

**Output:** 2 documents, both with `_id: 1`.

### B7. (Node)
```js
const r = await Student.updateOne({ rollNo: "CSE2301" }, { $set: { year: 3 } });
console.log(r.matchedCount, r.modifiedCount);
```
If that student **already has** `year: 3`:

**Output:** `1 0` — matched but nothing changed. (Classic trap: `modifiedCount 0` does **not** mean "not found".)

### B8. (Python cursor)
```python
cur = db.students.find({"year": 2})
a = list(cur)
b = list(cur)
print(len(a) > 0, len(b))
```
**Output:** `True 0` — the cursor was consumed by the first `list()`.

### B9. (Node, missing await)
```js
const x = collection.findOne({ rollNo: "CSE2301" });
console.log(typeof x.then);
```
**Output:** `function` — `x` is a **Promise**, not the document. Forgetting `await` is bug #1 in Node DB code.

### B10. (Pagination)
```js
// 10 docs sorted by _id ascending: ids 1..10
db.c.find().sort({ _id: 1 }).skip(3).limit(2)
```
**Output:** ids `4` and `5`. (skip 3 → drop 1,2,3; limit 2 → take 4,5.)

# 🐞 SECTION C — CODE READING & BUG SPOTTING

For each snippet: **find the bug, say why, give the fix.**

### C1.
```js
app.get("/students", async (req, res) => {
  const client = new MongoClient(uri);
  await client.connect();
  const list = await client.db("x").collection("students").find().toArray();
  res.json(list);
});
```
**Bug:** a **new client per request** (and it is never closed) → connection storm / leaks.
**Fix:** create **one** shared client at startup and reuse it.

### C2.
```js
const s = await Student.findOneAndUpdate({ rollNo }, { year: 3 });
res.json(s);
```
**Bug:** returns the **old** document (no `new: true`); also validators don't run on updates unless `runValidators: true`.
**Fix:** `{ new: true, runValidators: true }`.

### C3. (native driver)
```js
await col.updateOne({ _id: req.params.id }, { $set: { year: 3 } });
```
**Bug:** `req.params.id` is a **string**; `_id` is an **ObjectId** → matches nothing (`matchedCount: 0`).
**Fix:** `new ObjectId(req.params.id)` (after validating with `ObjectId.isValid`).

### C4.
```js
const c = await Course.findById(id);
if (c.enrolledCount < c.maxSeats) {
  await Enrollment.create({ student, course: id });
  c.enrolledCount++;
  await c.save();
}
```
**Bug:** classic **race condition** (read → decide → write).
**Fix:** one atomic `findOneAndUpdate` with the seat check inside the filter and `$inc` in the update.

### C5.
```js
const studentSchema = new Schema({ email: { type: String, unique: true } });
// "Mongoose will reject duplicates with a ValidationError"
```
**Bug:** wrong belief. `unique` builds an **index**; the failure is a **duplicate key error (11000)**, thrown by MongoDB, and only if the index has finished building.
**Fix:** handle `err.code === 11000` → respond **409**.

### C6.
```js
ids.forEach(async (id) => {
  await Student.deleteOne({ _id: id });
});
console.log("all deleted");
```
**Bug:** `forEach` doesn't wait for async callbacks; "all deleted" prints **before** deletions finish.
**Fix:** `await Promise.all(ids.map(id => Student.deleteOne({ _id: id })))` — or better, one `deleteMany({ _id: { $in: ids } })`.

### C7.
```js
db.students.aggregate([
  { $group: { _id: "$branch", avg: { $avg: "$cgpa" } } },
  { $match: { branch: "CSE" } }
])
```
**Bug:** after `$group`, the field `branch` no longer exists (it became `_id`) → matches nothing. Also filtering late is wasteful.
**Fix:** put `$match: { branch: "CSE" }` **first**.

### C8.
```python
from bson import ObjectId   # fine
# requirements.txt contains:  bson
```
**Bug:** installing the standalone PyPI `bson` package conflicts with PyMongo's built-in `bson`.
**Fix:** `pip uninstall bson` then `pip install pymongo` (bson comes bundled).

### C9.
```js
const uri = "mongodb+srv://admin:MyPass123@cluster0.abcde.mongodb.net/coursehub";
```
**Bug:** **hardcoded credentials** in source (and a powerful `admin` user for an app).
**Fix:** `process.env.MONGODB_URI` from `.env` (git-ignored), and a least-privilege app user. **Rotate the password** if it was ever committed.

### C10.
```js
const filter = { email: req.body.email, password: req.body.password };
const user = await User.findOne(filter);
```
**Bug:** NoSQL **injection**: a client can send `{"email": {"$ne": null}, "password": {"$ne": null}}`. Also plain-text password storage.
**Fix:** force strings (`String(req.body.email)`), validate types, store **hashed** passwords (e.g., bcrypt), compare hashes.

# 🧩 SECTION D — SCENARIO / DESIGN QUESTIONS (with model answers)

### D1. A blog: posts have comments. Embed or reference?
**Model answer:** Depends on volume. If a post has **few, bounded** comments always shown with the post → embed. If comments can grow without limit (viral posts), are queried independently, or need independent updates/moderation → **reference** (a `comments` collection with `postId`, index on `{ postId: 1, createdAt: -1 }`). Hybrid: embed the latest 5 comments + reference the rest (the *subset pattern*).

### D2. Query `{ branch: "CSE", cgpa: { $gt: 8 } }` sorted by `name` is slow. Which index?
**Model answer (ESR):** Equality `branch`, then Sort `name`, then Range `cgpa` → `{ branch: 1, name: 1, cgpa: 1 }`. Verify with `explain("executionStats")`: expect IXSCAN, no in-memory SORT stage, docsExamined close to nReturned.

### D3. Two users book the last seat at the same time. Prevent overbooking?
**Model answer:** Make *check + reserve* **one atomic operation**: `findOneAndUpdate({ _id, $expr: { $lt: ["$enrolledCount","$maxSeats"] } }, { $inc: { enrolledCount: 1 } })`. One request gets the document; the other gets `null` → respond 409 "course full". If the later insert of the enrollment fails (duplicate), **compensate** with `$inc: -1`. Transactions are the alternative for multi-document atomicity (need a replica set).

### D4. A report takes 40 s on 5M documents. What do you do?
**Model answer:** (1) Run `explain` on the first stage; ensure `$match` is first and indexed. (2) Add `$project` to shrink documents early. (3) Check for `$lookup` on an unindexed foreign field → add that index. (4) Consider pre-aggregation (a summary collection updated incrementally, or `$merge`). (5) Add `maxTimeMS` and run on a secondary/analytics node if acceptable. (6) Measure again.

### D5. Management asks: "Can an AI just auto-create indexes for us?"
**Model answer:** AI/advisors can **recommend** indexes by analysing slow queries, but each index costs write speed, RAM and disk. So: use recommendations, test on staging or with a **hidden index**, check with `explain`, then a human approves. Never auto-drop/auto-create blindly in production.

### D6. Your app must survive a server crash. What does MongoDB give you?
**Model answer:** A **replica set** (primary + secondaries) with automatic election on primary failure, drivers with **retryable writes**, and `w: "majority"` write concern so acknowledged writes survive failover. Plus backups for disasters replication can't fix (human error, corruption).

### D7. Students' personal data is stored. What must you think about?
**Model answer:** Collect only what's needed; **authentication + RBAC**; TLS in transit, encryption at rest; restrict network access; never log sensitive fields; hash passwords; retention policy/TTL for old data; access auditing; follow your institution's privacy rules/laws.

### D8. When should you NOT use MongoDB?
**Model answer:** When the workload is heavily **relational with complex multi-table joins and strict multi-row transactions** as the core (e.g., classic double-entry accounting), or when the team needs mature SQL tooling and strong relational constraints everywhere. MongoDB *does* support multi-document transactions and `$lookup`, but a relational DB can be the more natural fit there.

# 🎤 SECTION E — VIVA RAPID-FIRE (60 × 30 seconds)

> **Rule:** answer in **1–2 sentences**. If they want more, they'll ask. Say these out loud.

## Unit I
1. **What is NoSQL?** — Databases that store data in non-tabular models (document, key-value, column, graph), built for flexible schemas and horizontal scaling.
2. **SQL vs NoSQL in one line?** — SQL: fixed schema, tables, joins, strong ACID by default; NoSQL: flexible schema, varied models, scale-out, trade-offs chosen per system.
3. **Explain CAP.** — In a distributed system you can't have all of Consistency, Availability and Partition tolerance together; since partitions happen, you choose C or A during one.
4. **Is MongoDB CP or AP?** — Typically described as CP: with a single primary, on a partition the minority side can't accept writes. (Tunable with read/write concerns.)
5. **Four NoSQL types with an example each?** — Key-value (Redis), column-family (Cassandra), document (MongoDB), graph (Neo4j).
6. **What is BSON?** — Binary JSON: MongoDB's storage/wire format, supporting extra types like Date, ObjectId, Decimal128.
7. **What is `mongod` vs `mongosh`?** — `mongod` is the server process; `mongosh` is the interactive shell client.
8. **What is Compass?** — The official GUI to browse, query, index and analyse data.
9. **What is Atlas?** — MongoDB's managed cloud service (hosting, backups, scaling, monitoring).
10. **Briefly, MongoDB architecture?** — Applications → driver → `mongod`; data in collections, WiredTiger storage engine; replica sets for HA, sharding for scale.

## Unit II
11. **Collection vs document?** — A collection is a group of documents; a document is one BSON record of field–value pairs.
12. **What is `_id`?** — The mandatory unique primary key of a document; auto-generated `ObjectId` if not given.
13. **What's in an ObjectId?** — 12 bytes: a 4-byte timestamp, a 5-byte random value, a 3-byte counter.
14. **`insertOne` vs `insertMany`?** — One document vs an array of documents; `insertMany` is ordered by default (stops at first error).
15. **`updateOne` vs `replaceOne`?** — `updateOne` modifies fields using operators; `replaceOne` swaps the whole document (keeping `_id`).
16. **What does `upsert` do?** — Update if matched, otherwise insert a new document.
17. **`$set` vs `$unset`?** — Set/add a field vs remove a field.
18. **`$push` vs `$addToSet`?** — Always append vs append only if absent.
19. **What does projection do?** — Chooses which fields come back (`{name:1, _id:0}`).
20. **`find().sort().skip().limit()` order?** — Logically sort → skip → limit, whatever order you write them.

## Unit III
21. **Embedding vs referencing?** — Embed: nest related data in one document (fast reads, atomic single-doc updates). Reference: store `_id`s and fetch/join separately (flexible, avoids bloat).
22. **Rule of thumb to choose?** — "Data that is used together lives together"; reference when the many side is large, unbounded or shared.
23. **How do you model many-to-many?** — Either arrays of references on one/both sides, or a junction collection (when the relationship has its own data).
24. **What is the unbounded array anti-pattern?** — Arrays that grow forever, risking 16 MB documents and slow updates.
25. **What's schema validation?** — `$jsonSchema` rules on a collection (required fields, types, ranges) enforced by MongoDB.
26. **`validationLevel` and `validationAction`?** — Level: which docs are checked (strict/moderate). Action: error (reject) or warn (log).
27. **Subset pattern?** — Embed only the most-used subset (e.g., latest 5 reviews) and keep the rest referenced.
28. **Why store derived fields?** — Faster reads/reports; cost: keep them in sync.

## Unit IV
29. **What is an index?** — A sorted structure (B-tree) of selected fields that lets queries avoid scanning every document.
30. **Cost of indexes?** — Extra disk/RAM and slower writes (each write updates every relevant index).
31. **Single vs compound index?** — One field vs several fields in a defined order; order matters.
32. **What is the prefix rule?** — A compound index `{a,b,c}` supports queries on `a`, `a+b`, `a+b+c`, not `b` alone.
33. **State ESR.** — Equality, Sort, Range — the best order of fields in a compound index.
34. **What is a text index?** — Index for word search with `$text`; one per collection.
35. **What does `explain("executionStats")` show?** — The winning plan, stages (IXSCAN/COLLSCAN), keys/docs examined, nReturned, time.
36. **COLLSCAN vs IXSCAN?** — Full scan vs index scan.
37. **What is a covered query?** — Answered from the index alone; docsExamined = 0.
38. **Ideal ratio?** — `docsExamined` ≈ `nReturned`.
39. **What is the aggregation pipeline?** — Documents flow through ordered stages (`$match`, `$group`, `$project`, `$sort`, `$lookup`…), each transforming the stream.
40. **Why `$match` first?** — It shrinks the stream early and can use an index.
41. **`$group` vs `$project`?** — Group aggregates many docs into one per key; project reshapes each doc.
42. **What does `$lookup` do?** — Left outer join to another collection in the same database.
43. **`$unwind` use?** — Flatten an array into one document per element.
44. **Index types beyond these?** — TTL, unique, partial, sparse, geospatial, hashed, wildcard, vector (Atlas).

## Unit V
45. **Why a driver?** — Application code needs a language-native way to speak the MongoDB wire protocol.
46. **Native driver vs Mongoose?** — Driver: thin, flexible, no schema. Mongoose: schemas, validation, middleware, `populate`, models on top of the driver.
47. **Schema → Model → Document?** — Schema defines shape, Model is the collection-bound class, Document is one instance.
48. **Why one MongoClient?** — It owns the connection pool; one per app avoids connection storms.
49. **What does `populate()` do?** — Replaces referenced `_id`s with the actual documents (done as extra queries; `$lookup` does it in one server-side pipeline).
50. **`unique` in Mongoose?** — Creates a unique index; error 11000 on duplicates, not a ValidationError.
51. **PyMongo sync or async?** — PyMongo's classic API is synchronous; an async API exists (`AsyncMongoClient`, in recent versions) and Motor was the long-time async option — check your installed version.
52. **ML pipeline from MongoDB?** — Aggregate → features → DataFrame → train/test split → fit → evaluate → save model → write predictions back.
53. **What's overfitting?** — Model memorises training data and fails on new data; detect with held-out test / cross-validation.
54. **How can AI help query optimisation?** — Analyse profiler/slow logs to spot patterns, recommend indexes, detect anomalies, forecast workload — with human approval.
55. **Danger of LLM-written queries?** — Hallucinated fields, destructive operations, injection; mitigate with allow-lists, read-only users, `explain` guard, human review.

## Unit VI
56. **Why a mini project?** — To integrate modelling, CRUD, indexing, aggregation and application code into one working, defensible system.
57. **Atomic seat booking in one line?** — A single `findOneAndUpdate` with the capacity check in the filter and `$inc` in the update.
58. **Top 3 production practices?** — Security layers (auth, TLS, network, least privilege), replica set + tested backups, monitoring with actionable alerts.
59. **Write concern `majority`?** — The write is acknowledged only after a majority of replica-set members have it, so it survives failover.
60. **What are AI-augmented databases and AutoML?** — Databases with built-in AI help (vector search, tuning advisors, natural-language interfaces); AutoML automates model selection/tuning — both assist, neither replaces fundamentals.
