## 7. Big-picture comparison tables (exam favourites)

### 7.1 SQL vs NoSQL (MongoDB)

| Aspect | SQL (relational) | MongoDB (document) |
|---|---|---|
| Data unit | Row in a table | Document in a collection |
| Schema | Fixed, defined first | Flexible; optional validation |
| Relationships | Foreign keys + joins | Embedding or references (`$lookup`, `populate`) |
| Scaling | Typically vertical first; sharding is more involved | Designed for horizontal scale (sharding) |
| Transactions | Strong ACID, multi-row, mature | Single-document atomic by default; multi-document transactions supported |
| Query language | SQL | MQL / aggregation pipeline |
| Best fit | Strict structure, complex joins, reporting on normalised data | Evolving structure, nested data, high-volume, read-together patterns |

> Careful wording: never say one is "better". Say **"better suited to"**.

### 7.2 Embed vs reference

| | Embed | Reference |
|---|---|---|
| Reads | One query | Two queries / `$lookup` / `populate` |
| Writes | Atomic on one document | Atomic per document; multi-doc needs transactions |
| Size risk | Document growth (16 MB) | Low |
| Duplication | Possible | Minimal |
| Use when | Read together, small, bounded | Large, unbounded, shared, independent |

### 7.3 Native driver vs Mongoose vs PyMongo

| | Node driver | Mongoose | PyMongo |
|---|---|---|---|
| Language | JavaScript | JavaScript | Python |
| Schema | None | Yes (app-level) | None |
| Validation | Manual / `$jsonSchema` | Built in | Manual / `$jsonSchema` |
| Style | `await` | `await` | Synchronous (async API exists in recent versions) |
| IDs | `ObjectId` from `mongodb` | `ObjectId` via Mongoose types | `ObjectId` from `bson` |
| Best for | Thin/fast/flexible | Structured apps | Scripts, data science, ML |

## 8. Ten discussion topics (balanced points)

The syllabus says *Discussion*. These are the debates that come up in class, viva, and interviews. For each, know **two sides** and give a **reasoned conclusion**.

### 8.1 "Is NoSQL replacing SQL?"
- *For:* flexible schema, scale-out, developer speed, modern workloads.
- *Against:* relational databases are mature, ubiquitous, great for structured/transactional data; many systems use **both** (polyglot persistence).
- *Conclusion:* **complementary**, chosen per workload.

### 8.2 "Schema-less: freedom or chaos?"
- *Freedom:* quick iteration, heterogeneous data.
- *Chaos:* inconsistent fields, hard analytics, silent bugs.
- *Conclusion:* flexible **by design, with validation** where it matters.

### 8.3 "Embed everything vs normalise everything"
- Both extremes fail: giant documents vs endless lookups.
- *Conclusion:* model **around access patterns**.

### 8.4 "Are indexes always good?"
- *Good:* read speed.
- *Bad:* write cost, memory, maintenance.
- *Conclusion:* index **what queries need**, verify with `explain`, remove the unused.

### 8.5 "ORM/ODM (Mongoose) vs raw driver"
- *Mongoose:* structure, validation, productivity; extra layer, some overhead.
- *Driver:* control, performance, less magic.
- *Conclusion:* team size and app complexity decide.

### 8.6 "Is eventual consistency acceptable?"
- Depends on domain: a "likes" counter vs a bank balance.
- MongoDB lets you **tune** with read/write concerns.

### 8.7 "Should the database or the application enforce rules?"
- App: richer logic. DB: last line of defence for **every** client (Node, Python, shell).
- *Conclusion:* **both** (we used Mongoose validators and `$jsonSchema`/indexes).

### 8.8 "Atlas vs self-hosting"
- *Atlas:* backups, monitoring, scaling, security defaults; cost, less low-level control.
- *Self-hosted:* control, potentially cheaper at scale; you carry operations burden.

### 8.9 "Can AI be trusted to tune and query databases?"
- *Helpful:* spots patterns humans miss, drafts indexes/queries fast.
- *Risky:* hallucinations, destructive suggestions, bias in training data, cost.
- *Conclusion:* **assist, validate, approve** — human in the loop.

### 8.10 "Privacy and ethics of student data"
- Collect minimum, secure it, define retention, be transparent, avoid biased prediction use (e.g., unfair labelling of "at-risk" students).
- *Conclusion:* technical power requires **responsibility**.

**How to answer a discussion question in 4 lines:**
```
1. State both sides fairly.
2. Give one concrete example (use students/CourseHub).
3. Give your conclusion with the deciding factor ("it depends on ___").
4. Mention one trade-off you accept.
```
