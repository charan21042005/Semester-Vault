## Part 4 — Best practices for production
```
Seven pillars: schema · indexing · queries · app/driver · security · reliability · operations

• Security in LAYERS: network → TLS → authentication → RBAC (least privilege) → app (injection,

• Reliability: replica set (3 members), RPO/RTO, backups 3-2-1, RESTORE DRILLS
• Operations: monitoring + few actionable alerts; scaling ladder (indexes → vertical → replicas → sharding);
```

# 🔥 PART C — MINI-PROJECT CHEAT CARD (CourseHub)

Keep this on one page for your demo and viva.

### C.1 Pitch (20 seconds)
> "CourseHub is a Node.js + Express + Mongoose backend on MongoDB that manages students, courses, enrollments and results. It enforces business rules — no duplicate enrollment, no overbooking even under concurrency — and provides aggregation reports and a Python analytics script that flags at-risk students."

### C.2 Collections and relationships
```
students ──< enrollments >── courses        (N-N through a junction collection)
students: rollNo*, email*, name, branch, year, skills[], address{}
courses:  code*, title, credits, department, semester, topics[], maxSeats, enrolledCount, isActive
enrollments: student→, course→, status, attendance, marks{internal,final}, total, grade
(* = unique index)
```
**Why `enrollments` is separate:** the relationship has its own data (marks, attendance, status) and is queried from both sides. **Why embed `address`, `skills`, `topics`:** read together, small, bounded.

### C.3 Index plan
```
students    { rollNo:1 } unique · { email:1 } unique · { branch:1, name:1 }
courses     { code:1 } unique · { department:1, semester:1, isActive:1 }
enrollments { student:1, course:1 } unique ⭐ · { course:1, status:1 } · { status:1, total:-1 } (if reports are hot)
```

### C.4 Business rules → status codes
```
inactive course / full / duplicate enrollment / delete student with enrollments → 409
marks or attendance out of range, malformed id                                → 400
id not found                                                                  → 404
created                                                                       → 201 · deleted → 204 · ok → 200 · unexpected → 500
```

### C.5 API (16 endpoints)
```
/api/students        POST GET           /api/students/:id       GET PATCH DELETE
/api/courses         POST GET           /api/courses/:id        GET PATCH
/api/enrollments     POST GET           /api/enrollments/:id/result  PATCH     /:id/drop  PATCH
/api/reports/course-averages · /top-students?limit= · /at-risk        (all GET)
```

### C.6 The one trick to show off 💎
```
Seat race fix:  check + increment in ONE atomic operation
  → one request gets the doc, the other gets null → 409 "course full"
Proof: scripts/race.js fires many simultaneous requests; enrolledCount never exceeds maxSeats
```

### C.7 Demo order (5–7 min)
```
1. Architecture sketch (20 s)
2. Seed data, start server (30 s)
3. Create a student → list with filter/pagination (1 min)
4. Enroll → duplicate enroll → 409 (1 min)
5. Fill the last seat → next enroll → 409 full (1 min)
6. Set marks → total/grade computed (30 s)
7. Reports + at-risk Python output (1 min)
8. explain(): IXSCAN on enrollments lookup (1 min)
9. Limitations + next steps (30 s)
```

## E.3 Unit III — modelling in a glance
```
Embed     → read together · small · bounded · atomic single-doc updates
Reference → large · unbounded · shared · changes independently · needs its own queries
1-1: embed (or reference if rarely read together)
1-N: one-to-few → embed · one-to-many → reference (or subset pattern) · one-to-squillions → reference to parent
N-N: arrays of refs OR a junction collection (when relationship carries data)
Anti-patterns: unbounded arrays · giant documents · duplicating data that changes · "one big collection for everything"
Validation: $jsonSchema (required, bsonType, minimum/maximum, enum) · validationLevel · validationAction
```

```js
db.createCollection("students", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["rollNo", "name", "cgpa"],
    properties: {
      rollNo: { bsonType: "string" },
      cgpa:   { bsonType: ["double", "int"], minimum: 0, maximum: 10 }
    }
  }},
  validationAction: "error"
})
```

## E.4 Unit IV — indexes, explain, aggregation
```js
db.students.createIndex({ rollNo: 1 }, { unique: true })
db.students.createIndex({ branch: 1, cgpa: -1 })                 // compound; order matters
db.students.createIndex({ bio: "text" })                          // one text index per collection
db.logs.createIndex({ at: 1 }, { expireAfterSeconds: 3600 })      // TTL
db.students.getIndexes();  db.students.dropIndex("name_1")

db.students.find({ branch: "CSE" }).sort({ cgpa: -1 }).explain("executionStats")
// check: stage (IXSCAN vs COLLSCAN) · totalKeysExamined · totalDocsExamined · nReturned · executionTimeMillis
```
```
Prefix rule: {a,b,c} serves a · a+b · a+b+c  (not b alone)
ESR:         Equality → Sort → Range
Covered:     filter + projection fields ALL in the index (and _id:0) → docsExamined = 0
Healthy:     docsExamined ≈ nReturned
Cost:        every index slows writes and uses RAM
```
```js
db.students.aggregate([
  { $match:   { year: 3 } },                                        // FIRST: filter early, uses index
  { $group:   { _id: "$branch", avgCgpa: { $avg: "$cgpa" }, n: { $sum: 1 } } },
  { $match:   { n: { $gte: 5 } } },                                  // fine here: filtering a computed value
  { $sort:    { avgCgpa: -1 } },
  { $project: { _id: 0, branch: "$_id", avgCgpa: { $round: ["$avgCgpa", 2] }, n: 1 } }
])
```
```
Stages: $match $group $project $addFields/$set $sort $limit $skip $unwind $lookup $count $out/$merge
$group accumulators: $sum $avg $min $max $push $addToSet $first $last
```

# 🔥 PART F — DECISION MATRICES

### F.1 Which data-modelling choice?
| Situation | Choose |
|---|---|
| Address of a student | **Embed** (1-1, read together) |
| 3 phone numbers | **Embed** (one-to-few) |
| Student ↔ courses with marks | **Reference + junction collection** |
| Millions of log events per device | **Reference** to parent (never an array inside the device) |
| Latest 5 comments + all comments | **Subset pattern** (embed 5, reference rest) |

### F.2 Which index?
| Query pattern | Index |
|---|---|
| equality on one field | `{ field: 1 }` |
| equality + sort | `{ eqField: 1, sortField: 1 }` |
| equality + sort + range | `{ eq: 1, sort: 1, range: 1 }` (ESR) |
| must be unique | add `{ unique: true }` |
| word search | text index |
| auto-delete old data | TTL index |
| report reading few fields | consider a **covered** index |

### F.3 Which tool in code?
| Need | Choose |
|---|---|
| Quick script / data science / ML | **PyMongo** |
| Structured web API with validation | **Mongoose** |
| Thin, flexible, performance-critical Node code | **Node driver** |
| One-off exploration | **mongosh / Compass** |

### F.4 Should I use a transaction?
```
Single document change?          → NO (already atomic)
Check + update in one doc?       → NO (atomic findOneAndUpdate, like the seat booking)
Several documents must succeed together (e.g., transfer between accounts)? → YES (replica set required)
```

# 🔥 PART G — ERROR → CAUSE → FIX

| Symptom | Likely cause | Fix |
|---|---|---|
| `MongoServerSelectionError` / timeout | server down, wrong URI, Atlas IP not allow-listed, no network | start `mongod`; check URI; add IP to Atlas allow-list |
| `Authentication failed` | wrong user/password or auth database; special chars not URL-encoded | check credentials; URL-encode password |
| `E11000 duplicate key` | unique index violated | return 409; handle `err.code === 11000` |
| `ValidationError` (Mongoose) | validator failed | return 400 with messages |
| `CastError` | invalid ObjectId/type | validate id first; return 400 |
| `matchedCount: 0` | filter matched nothing (string vs ObjectId?) | convert id; check filter |
| `modifiedCount: 0` but matched 1 | value unchanged | not an error |
| Query slow, `COLLSCAN` | no suitable index | create index per ESR; re-run explain |
| `Document failed validation` | `$jsonSchema` rejected the write | fix the data or the schema |
| Returned old doc after update | missing `{ new: true }` / `ReturnDocument.AFTER` | add it |
| Nothing prints / unexpected Promise | missing `await` | add `await` |
| Python: empty second loop | cursor already consumed | `list()` once, reuse the list |
| `ImportError: bson` conflict | standalone `bson` package installed | `pip uninstall bson` → `pip install pymongo` |
| Overbooked seats | read-then-write race | atomic `findOneAndUpdate` |
| App crash on connection storm | new client per request | one shared client |

# 🔥 PART H — 25 "MUST-NAIL" VIVA QUESTIONS (one-breath answers)

1. **NoSQL?** Non-tabular databases (document, key-value, column, graph) built for flexible schema and scale-out.
2. **CAP?** Consistency, Availability, Partition tolerance — during a partition you choose C or A.
3. **BSON?** MongoDB's binary JSON format with richer types.
4. **Collection/document?** Group of documents / one BSON record.
5. **`_id`?** Mandatory unique key; ObjectId by default.
6. **Embed vs reference?** Nest vs link; choose by access pattern, size, growth, sharing.
7. **Schema-less?** Flexible, not structureless; validation optional but available.
8. **Index?** B-tree structure speeding lookups at the cost of write speed and memory.
9. **ESR?** Equality → Sort → Range.
10. **explain?** Shows the plan and stats: IXSCAN/COLLSCAN, docs examined, nReturned.
11. **Covered query?** Index alone answers it; docsExamined 0.
12. **Aggregation pipeline?** Ordered stages transforming a document stream.
13. **Why `$match` first?** Shrinks data early; can use an index.
14. **`$lookup`?** Left outer join to another collection.
15. **Driver vs Mongoose?** Thin client vs ODM with schemas/validation/hooks.
16. **Why one client?** It manages the connection pool.
17. **Mongoose `unique`?** An index, not a validator; error 11000.
18. **`new: true`?** Return the updated document, not the old one.
19. **PyMongo `ObjectId`?** `from bson import ObjectId` (don't pip install bson).
20. **Data leakage?** Test/future info leaks into training → fake-good scores.
21. **AI-driven optimisation?** AI/ML analyses workload to recommend tuning; humans validate with explain.
22. **Atomic seat booking?** One `findOneAndUpdate` with capacity in the filter and `$inc` in the update.
23. **Production security?** Layers: network, TLS, auth, RBAC, app, data, audit; secrets outside code.
24. **RPO/RTO?** Tolerable data loss / tolerable downtime.
25. **AI-augmented DB / AutoML?** AI help for search/query/tuning on top of fundamentals / automated model and setting search — assist, not replace.
