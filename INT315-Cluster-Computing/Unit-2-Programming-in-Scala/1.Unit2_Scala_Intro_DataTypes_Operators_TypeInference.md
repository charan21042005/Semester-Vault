## 1. First: What Exactly is Scala?

**Viva definition:**

> Scala is a general-purpose programming language that combines object-oriented and functional programming features and runs on the Java Virtual Machine (JVM).

The name **Scala** comes from **Scalable Language**.

```
Scala
  │
  ├── Object-Oriented Programming
  │
  ├── Functional Programming
  │
  └── Runs on JVM
```

> This is important because Spark is heavily associated with Scala.

---

## 2. Why Does Spark Use Scala?

> This is a very likely viva question.

**Best answer:**

> Spark was originally developed in Scala, and Scala provides concise syntax, strong support for functional programming, and seamless integration with the JVM, making it well suited for distributed data-processing operations in Spark.

For example, Spark operations naturally look like:

```scala
rdd.map(x => x * 2)
```

instead of writing lengthy loops. This becomes especially important when we reach:

```
RDD
 ↓
map()
 ↓
filter()
 ↓
reduce()
```

> Scala's functional programming features make this style natural.

## 3. Major Features of Scala

> You should know these for both theory and viva.

### Feature 1 — Object-Oriented

Scala supports:

- classes
- objects
- inheritance
- encapsulation
- polymorphism
- traits

So Scala can be used in traditional OOP style.

### Feature 2 — Functional Programming

Scala supports concepts such as:

- functions
- higher-order functions
- immutability
- `map`
- `filter`
- `reduce`
- anonymous functions

Example:

```scala
val nums = List(1, 2, 3, 4)

nums.map(x => x * 2)
```

```
List(2, 4, 6, 8)
```

> We'll go deeply into functions later.

### Feature 3 — Statically Typed

Scala is **statically typed**. That means the compiler determines/checks the type of variables and expressions.

```scala
val age: Int = 20
```

Here: `age → Int`

But Scala also has **type inference**, which means we often don't need to explicitly write the type:

```scala
val age = 20
```

Scala infers: `age → Int`

> We'll dedicate a complete part to type inference.

### Feature 4 — Concise Syntax

Scala allows us to write less code while expressing the same logic.

```scala
val square = (x: Int) => x * x
```

This represents a function.

```scala
val square = (x: Int) => x * x

square(5)
```

```
25
```

### Feature 5 — JVM Based

Scala programs run on the Java Virtual Machine.

```
Scala Source Code
       ↓
 Scala Compiler
       ↓
 JVM Bytecode
       ↓
      JVM
       ↓
   Execution
```

> Therefore Scala can also interact with the Java ecosystem.

**Viva answer:** "Scala is JVM-based, so Scala applications can use Java libraries and run on JVM infrastructure."

### Feature 6 — Interoperability with Java

Scala can use Java classes and libraries. This is another reason Scala fits naturally into the JVM ecosystem.

## 5. What is REPL?

The Scala environment used by `spark-shell` follows the **REPL** style.

REPL means: **R**ead → **E**valuate → **P**rint → **L**oop

```
       ┌──────────┐
       │   Read   │
       └────┬─────┘
            ↓
       ┌──────────┐
       │ Evaluate │
       └────┬─────┘
            ↓
       ┌──────────┐
       │  Print   │
       └────┬─────┘
            ↓
       ┌──────────┐
       │   Loop   │
       └────┬─────┘
            │
            └──────→ Read again
```

For example, inside `spark-shell`:

```scala
scala> 10 + 20
```

```
res0: Int = 30
```

It immediately:

1. reads `10 + 20`
2. evaluates it
3. prints result
4. waits for your next command

> That's why it's extremely useful for practical exams.

## 9. `val` — Immutable Reference

```scala

```

```
val → cannot reassign

```

---

## 10. `var` — Mutable Variable

```scala
var age = 21
```

```scala
age = 22
```

This is valid.

```scala
age
```

```
22
```

```
val → immutable
var → mutable
```

---

## 11. ⭐ VERY IMPORTANT: `val` vs `var`

| `val` | `var` |
|---|---|
| Immutable binding | Mutable binding |
| Cannot be reassigned | Can be reassigned |
| Preferred when value doesn't need reassignment | Used when reassignment is required |
| `val x = 10` | `var x = 10` |

**Viva answer:** "`val` defines an immutable binding, so it cannot be reassigned after initialization, whereas `var` defines a mutable variable whose value can be reassigned."

---

## 12. But Be Careful With the Word "Immutable"

> This is a very good technical distinction.

```scala
val nums = scala.collection.mutable.ArrayBuffer(1, 2, 3)
```

Can the collection itself change? **Yes:**

```scala
nums += 4
```

So `val` does not necessarily mean the object itself is immutable — it means the **reference/binding** cannot be reassigned.

```
val nums
   │
   └──────→ Object
```

You cannot make `nums` point to another object:

```scala
nums = anotherObject  // ❌ not allowed
```

But if the object itself is mutable, its contents may change.

> 🔥 Excellent viva statement: "`val` prevents reassignment of the reference, but it does not automatically make the referenced object immutable." That's a marks-grabbing distinction.

**Viva:** "Scala uses semicolon inference, so semicolons are generally optional at the end of statements."

## 22. One Subtle Point: Scala is Statically Typed but Dynamically Inferred

Students sometimes say: *"Scala is dynamically typed because I don't specify the type."*

❌ **Wrong.**

✅ **Correct:** "Scala is statically typed, but it supports type inference, so the compiler can determine the type without requiring us to explicitly write it."

```scala
val x = 100
```

You don't write `val x: Int = 100` but Scala still knows `x → Int`.

## 23. Why Type Inference is Useful

Compare:

```scala
val number: Int = 100
val name: String = "Scala"
val price: Double = 99.99
```

with:

```scala

val name = "Scala"
val price = 99.99
```

The second is shorter while still being statically typed.

**Viva answer:** "Type inference reduces unnecessary type annotations while retaining compile-time type checking." 🔥 Good interview wording.

```scala

```

  ↓

## 29. Explicit vs Inferred Types

**Explicit:**

```scala

**Inferred:**

> Both are statically typed. The difference is whether you explicitly provide the type.

## 32. Type Conversion — Basic Practical Knowledge

## 34. Type Conversion vs Type Inference

> Don't confuse these.

**Type inference** — Scala determines the type automatically:

```scala

```

**Type conversion** — you explicitly convert:

```scala

```

```
Inference = determine type
Conversion = change type
```

> 🔥 Very important distinction.

## 25. Now Something VERY Scala-Specific: Operators are Essentially Method Calls

Scala operator style:
object operator argument
```

It returns the remainder of a division.

**Q4. What is the result of `10 / 3` in Scala?**
`3`, because both operands are integers.

**Q5. What is `10.0 / 3`?**
A floating-point result because `10.0` is a `Double`.

**Q6. What does `&&` mean?**
Logical AND; both conditions must be true.

**Q7. What does `||` mean?**
Logical OR; at least one condition must be true.

**Q8. What does `!` do?**
It logically negates a Boolean value.

**Q9. What is a method?**
A named operation associated with a type/class/object that can be invoked to perform a computation.

**Q10. What is `apply()` in Scala?**
`apply()` is a method that Scala allows us to invoke using function-like syntax, such as `array(1)` instead of `array.apply(1)`.

> 🔥 That last answer is particularly worth remembering.

## 1. First — What Does "Type" Actually Mean?

```scala
val x = 10
```

We know `10 → integer`. But Scala doesn't merely store "10." It determines the **type** of the expression.

```
10
 ↓
Int
 ↓
x
```

Therefore: `x: Int = 10`

> The type tells Scala what operations are valid and how the value should be handled.

---

## 2. Scala is Statically Typed

> This is one of your most important viva statements.

**Scala is a statically typed language.** That means types are checked at compile time rather than being completely determined only while the program is running.

```scala
val x: Int = 10
```

Scala knows `x → Int`. If you try something incompatible:

```scala
val x: Int = "Hello"   // ❌
```

Scala rejects it. You cannot put a `String` into something explicitly declared as `Int`.

---

## 3. Then Why Don't We Write Types Everywhere?

Because of **type inference**. Instead of `val age: Int = 21`, Scala allows `val age = 21`. Scala looks at `21` and infers `Int`. Therefore: `age: Int = 21`

---

## 4. What is Type Inference?

**Definition for viva:**

> Type inference is Scala's ability to automatically determine the type of an expression or variable from its value and surrounding context without requiring an explicit type annotation.

```scala
val x = 100        // x → Int
val name = "Spark" // name → String
val price = 99.5   // price → Double
```

---

## 5. Let's Actually See Inference in Spark Shell

```scala
val a = 100
```

```
a: Int = 100
```

```scala
val b = 100L
```

```
b: Long = 100
```

```scala
val c = 10.5
```

```
c: Double = 10.5
```

```scala
val d = 10.5f
```

```
d: Float = 10.5
```

> So the REPL is actually giving you a very nice demonstration of type inference.

---

## 6. Explicit Type Annotation

You can tell Scala exactly what type you want. Syntax:

```scala
val variableName: Type = value
```

```scala
val age: Int = 21
```

```
val
 ↓
immutable binding

age
 ↓
variable name

: Int
 ↓
explicit type annotation

= 21
 ↓
value
```

---

## 7. Inferred vs Explicit

**Explicit:** `val age: Int = 21`
**Inferred:** `val age = 21`

Both result in `age → Int`.

```
Explicit:
Programmer specifies type

Inference:
Compiler determines type
```

---

## 8. Why is Type Inference Useful?

Imagine writing:

```scala
val a: Int = 10
val b: Int = 20
val c: Int = 30
val d: Int = 40
val e: Int = 50
```

You can instead write:

```scala
val a = 10
val b = 20
val c = 30
val d = 40
val e = 50
```

The compiler still knows their types.

**Strong viva answer:** "Type inference reduces unnecessary type annotations while preserving static type checking, making Scala programs more concise without abandoning compile-time type safety." 🔥 That's an excellent interview-style answer.

---

## 9. Type Inference Isn't Guessing Randomly

> This is important.

```scala
val x = 10 + 20
```

Scala doesn't just see the final answer `30`. It understands `10 → Int`, `20 → Int`, `+` operation, → `Int`. So `x → Int`

---

## 10. Inference From Expressions

```scala
val x = 10 * 2
```

```
x: Int = 20
```

```scala
val y = 10.0 * 2
```

`y → Double`. Why? Because `10.0 → Double`, `2 → Int` — the operation results in a floating-point value.

---

## 11. Inference From Method Return Types

```scala
val text = "Spark"
val len = text.length
```

`length` returns an integer, therefore `len → Int`

```scala
val x = 10
val y = x.toDouble
```

`y → Double`

> So type inference can use the type returned by expressions and methods.

---

## 12. Function Return Type Inference

We'll study functions properly later, but here's an early example:

```scala
val square = (x: Int) => x * x
```

Scala knows `x → Int`, `x * x → Int`. So the function returns an `Int`. This is another example of inference.

---

## 13. Context Can Influence the Type

> This is slightly more advanced but useful.

```scala
val x: Double = 10
```

Here the literal `10` is being used where a `Double` is expected. Scala can represent it as `10 → Double`. The declared expected type provides context.

Compare:

```scala
val x = 10
```

Here there is no explicit expected type, so `10 → Int`

> This gives you an important principle: Scala's inferred type can depend on the context in which an expression appears.

---

## 14. Type Compatibility

Now let's see something practical. This works:

```scala
val x: Long = 10
```

because Scala can represent the integer literal `10` as the expected `Long`. But don't generalize that into "Any Int can automatically become any other numeric type." The exact rules depend on context and conversions.

> When you want to explicitly convert a value, use conversion methods.

---

## 15. Explicit Numeric Conversion

Scala provides methods such as: `.toByte`, `.toShort`, `.toInt`, `.toLong`, `.toFloat`, `.toDouble`

```scala
val x = 10
val y = x.toDouble
```

`x → Int`, `y → Double`

---

## 16. Int → Long

```scala
val x = 100
val y = x.toLong
```

```
100
 ↓
Int
 ↓ .toLong
Long
```

```scala
println(y)
```

```
100
```

> The displayed number looks the same, but its type has changed.

---

## 17. Int → Double

```scala
val x = 100
val y = x.toDouble
```

`y → Double`

```scala
println(y)
```

```
100.0
```

---

## 18. Double → Int

Now the opposite direction:

```scala
val x = 10.75
val y = x.toInt
```

```
10
```

The `.75` is discarded.

```
10.75
   ↓ .toInt
10
```

> This is called a narrowing conversion in the broad numeric sense because the target type has a smaller range/representation.

---

## 19. Why Can Information Be Lost?

```scala
val x = 123.987
val y = x.toInt
```

```
123
```

The fractional part is gone.

**Viva:** "Converting from a floating-point type to an integer type can lose fractional information."

---

## 20. Another Important Example: Long → Int

```scala
val x: Long = 3000000000L
val y = x.toInt
```

The target `Int` cannot represent every possible `Long` value. So this can produce a value different from the original because of overflow/wrapping behavior.

> The important exam lesson is: narrowing conversions can lose information if the source value cannot be represented by the target type.

You don't need to memorize the exact overflow mechanics for this syllabus unless your professor specifically asks.

---

## 21. Widening vs Narrowing

### Widening

Moving to a type capable of representing a broader range/precision:

```
Int
 ↓
Long
 ↓
Float / Double
```

Conceptually, you are moving toward a type with greater representational capacity.

```scala
val x = 10
val y = x.toLong
```

### Narrowing

Moving toward a more restricted representation:

```
Double
 ↓
Int
```

```scala
val x = 10.75
val y = x.toInt   // Potential information loss.
```

---

## 22. Don't Confuse Widening With Type Inference

```scala
val x: Double = 10
```

That's not the same concept as:

```scala
val x = 10
```

In the first: Expected type → `Double`. In the second: Literal → `Int`

```
Type inference
      ≠
Type conversion
      ≠
Type widening
```

> These are related but different concepts.

## 23. Now the Scala Type Hierarchy

> This is where things become interesting.

Scala has a unified type hierarchy. A simplified picture:

```
                    Any
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
        AnyVal                AnyRef
          │                     │
    Primitive/value         Reference types
       types                   / objects
```

Let's understand it slowly.

---

## 24. `Any`

`Any` is the root of Scala's type hierarchy.

```
Any
├── AnyVal
└── AnyRef
```

It can represent values of both value types and reference types.

```scala
val a: Any = 10
val b: Any = "Scala"
val c: Any = true
```

These are all allowed because their types fit under `Any`.

---

## 25. `AnyVal`

`AnyVal` is the parent category for Scala's value types. It includes types such as:

```
Byte
Short
Int
Long
Float
Double
Char
Boolean
Unit
```

```
AnyVal
 │
 ├── Byte
 ├── Short
 ├── Int
 ├── Long
 ├── Float
 ├── Double
 ├── Char
 ├── Boolean
 └── Unit
```

---

## 26. `AnyRef`

`AnyRef` is the base type for reference types.

```scala
val name: AnyRef = "Scala"
```

A `String` is a reference type in Scala's type system. Collections and user-defined classes are also reference-type categories.

You don't need to overcomplicate `AnyRef` for tomorrow's practical. Remember:

```
Any
├── AnyVal → value types
└── AnyRef → reference types
```

---

## 27. Why Would We Ever Use `Any`?

Sometimes you need to hold values of different types.

```scala
val values: List[Any] = List(10, "Scala", true, 10.5)
```

Now the list can contain `Int`, `String`, `Boolean`, `Double` because all fit under `Any`. However, this sacrifices some type specificity.

> So don't casually use `Any` everywhere.

---

## 28. `Any` and Practical Type Safety

```scala
val values: List[Any] = List(10, "Scala", true)
```

Now `values` contains different types. If you want to perform an integer-specific operation, Scala cannot simply assume every element is an integer.

> That's one reason strongly typed collections are preferable when possible.

```scala
val nums = List(10, 20, 30)
```

is much easier to work with numerically.

---

## 29. `Nothing`

Now an advanced type. `Nothing` is a subtype of every type.

```
        Any
       /   \
   AnyVal AnyRef
       ...
        ↑
     Nothing
```

You mainly encounter it in expressions that never successfully return a normal value, such as throwing an exception.

```scala
def fail(): Nothing = {
  throw new RuntimeException("Error")
}
```

> Don't worry about memorizing the implementation for your practical.

**Viva definition:** "`Nothing` is the bottom type in Scala's type hierarchy and represents computations that do not return normally."

---

## 30. `Null`

Another special type is `Null`. It is associated with null references and is mainly relevant to reference types.

For your current practical, the important thing is: `null` is not the same thing as `()`, and not the same thing as `Nothing`. These are different concepts.

> For normal Spark coding, you should avoid unnecessary `null` usage where possible.

---

## 31. Important Hierarchy to Memorize

```
                     Any
                      │
             ┌────────┴────────┐
             ↓                 ↓
           AnyVal            AnyRef
             │                 │
       value types        reference types
             │

       Boolean, Char...   classes, etc.

And conceptually, `Nothing` is the bottom type.

## 36. String → Int

## 37. Compile-Time vs Runtime Error

**Example 1 — Compile-time type mismatch**

```scala
val x: Int = "Hello"   // ❌ rejected at compile time
```

Scala rejects this based on type checking.

**Example 2 — Runtime parsing failure**

```scala
val x = "Hello".toInt   // ❌ fails at runtime
```

The expression is syntactically and type-wise valid because `String` has a `toInt` method, but the actual content cannot be parsed as an integer. So the failure occurs when it executes.

> 🔥 This distinction can impress in viva.
