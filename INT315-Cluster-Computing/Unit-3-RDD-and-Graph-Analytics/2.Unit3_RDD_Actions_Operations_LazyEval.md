# PART 4 — ⚡ RDD Actions

> The syllabus asks you to understand RDD functions, operations and methods, so actions are a major part of what you need for both the practical and viva.

## 1. What is an Action?

An **action** is an RDD operation that:

- triggers computation,
- evaluates the required transformation chain,
- and produces a result or performs a side effect.

For example:

```scala
val nums = sc.parallelize(1 to 5)

val doubled = nums.map(_ * 2)
```

At this point:

```
nums
 ↓
map
 ↓
doubled
```

Spark has a logical computation to perform.

Now:

```scala
doubled.collect()
```

is an action.

Conceptually:

```
nums
 ↓
map
 ↓
doubled
 ↓
collect()
 ↓
EXECUTION
 ↓
result
```

---

## 2. Why are Actions important?

This is the heart of Spark's lazy execution model.

Suppose you write:

```scala
val nums = sc.parallelize(1 to 10)

val even = nums.filter(_ % 2 == 0)

val doubled = even.map(_ * 2)
```

Have the numbers necessarily been processed already?

**No.**

Spark can record:

```
nums
 |
 | filter
 ↓
even
 |
 | map
 ↓
doubled
```

Now when you say:

```scala
doubled.collect()
```

Spark knows:

> "The user actually needs the result now."

So computation is triggered.

---

## 3. First and most important action — `collect()`

### What does `collect()` do?

> `collect()` returns all elements of an RDD to the driver.

**Example:**

```scala
val nums = sc.parallelize(List(10,20,30,40,50))

nums.collect()
```

**Output:**

```
Array(10, 20, 30, 40, 50)
```

**Diagram:**

```
                 RDD
          ----------------
          |      |       |
         P1     P2      P3
          |      |       |
          +------+------+ 
                 |
                 ↓
              collect()
                 |
                 ↓
               Driver
                 |
                 ↓
       Array(10,20,30,40,50)
```

---

## 4. Why does `collect()` trigger computation?

Consider:

```scala
val nums = sc.parallelize(1 to 10)

val even = nums.filter(_ % 2 == 0)

val doubled = even.map(_ * 2)
```

Nothing asks Spark for the final result yet.

Then:

```scala
doubled.collect()
```

Now Spark has to execute:

```
filter
   ↓
map
   ↓
collect
```

**Result:**

```
Array(4,8,12,16,20)
```

So:

> An action triggers the execution of the necessary transformation lineage.

---

## 5. ⚠️ Why `collect()` can be dangerous

> This is a VERY important viva question.

Suppose:

```
RDD = 1 billion records
```

and you execute:

```scala
rdd.collect()
```

Spark attempts to bring all those records to the driver.

Conceptually:

```
Workers
 |  |  |
 |  |  |
 +--+--+------→ DRIVER
                  |
              Huge result
                  ↓
          Driver memory pressure
```

This can cause:

- high memory usage
- driver overload
- OutOfMemoryError
- application failure

Therefore:

> Use `collect()` carefully, especially for large RDDs.

For inspection, prefer:

```scala
rdd.take(10)
```

when you only need a sample.

## 7. `count()` with transformation

Consider:

```scala

```

**Output:**

```

```

Why?

```

  ↓

  ↓

  ↓
count
  ↓
5
```

So the filter transformation gets executed because `count()` is an action.

## 9. `take(n)`

> `take(n)` returns up to the first `n` elements.

**Example:**

```scala
val nums = sc.parallelize(1 to 10)

nums.take(3)
```

**Output:**

```
Array(1, 2, 3)
```

Another:

```scala
nums.take(5)
```

**Output:**

```
Array(1,2,3,4,5)
```

---

## 10. `take()` vs `collect()`

This is very important.

| `collect()` | `take(n)` |
|---|---|
| Returns all elements | Returns up to n elements |
| Can produce a huge result | Limits result size |
| Can overload driver memory | Safer for inspection |
| Use when dataset is known to be manageable | Good for sampling/inspection |

For example:

```scala
rdd.take(10)
```

is generally preferable to:

```scala
rdd.collect()
```

if you're just trying to see a few records.

---

## 11. `take()` doesn't mean "take exactly n"

Suppose:

```scala
val nums = sc.parallelize(List(1,2,3))
```

Then:

```scala
nums.take(10)
```

doesn't magically create 10 elements.

It returns:

```
Array(1,2,3)
```

Hence:

> `take(n)` returns up to `n` elements.

## 12. `reduce()` — VERY IMPORTANT

Now we reach one of the most useful actions.

> `reduce()` combines the elements of an RDD using a function.

Suppose:

```
1 2 3 4 5
```

We want the sum.

```scala
val nums = sc.parallelize(List(1,2,3,4,5))

nums.reduce((a,b) => a + b)
```

**Result:**

```
15
```

Because: `1 + 2 + 3 + 4 + 5 = 15`

---

## 13. How does `reduce()` conceptually work?

It doesn't necessarily mean Spark simply does:

```
1 + 2
 ↓
3 + 3
 ↓
6 + 4
 ↓
10 + 5
 ↓
15
```

In distributed computing, Spark can combine values within partitions and then combine partial results.

Conceptually:

```
          RDD
       /       \
     P1         P2
   1 2 3      4 5
     |          |
   local       local
   reduce      reduce
     |          |
     6          9
       \       /
        \     /
         reduce
           |
          15
```

This is why a suitable reduction function should work correctly regardless of how Spark groups the elements.

---

## 14. `reduce()` for multiplication

```scala
val nums = sc.parallelize(List(1,2,3,4,5))

nums.reduce((a,b) => a * b)
```

**Result:**

```
120
```

Because: `1 × 2 × 3 × 4 × 5 = 120`

---

## 15. `reduce()` using `_`

Instead of:

```scala
nums.reduce((a,b) => a + b)
```

you can write:

```scala
nums.reduce(_ + _)
```

Both mean: combine two values using `+`.

Likewise:

```scala
nums.reduce(_ * _)
```

means multiplication.

---

## 16. `reduce()` for maximum

```scala
val nums = sc.parallelize(List(10,50,20,80,30))

nums.reduce((a,b) => if (a > b) a else b)
```

**Result:**

```
80
```

Or, depending on API/version, a simpler aggregation method such as:

```scala
nums.max()
```

can directly return the maximum.

We'll see those inspection/aggregation methods shortly.

---

## 17. Important property of `reduce()`

The function used with distributed `reduce()` should generally be:

### Associative

Grouping should not change the result.

For addition:

```
(1 + 2) + 3
```

and:

```
1 + (2 + 3)
```

both equal `6`.

### Commutative is also useful

For addition: `1 + 2 = 2 + 1`

This allows Spark flexibility in combining values across partitions.

### 🎯 Viva answer

> `reduce()` should use a function that is associative, and ideally commutative for predictable distributed aggregation, because Spark may combine values in different orders/groupings across partitions.

## 22. `foreach()`

> `foreach()` applies a function to each element, generally for side effects.

**Example:**

```scala
val nums = sc.parallelize(List(1,2,3,4))

nums.foreach(x => println(x))
```

Conceptually:

```
1
2
3
4
```

But here's an important practical point:

> In a distributed environment, `println` executes on executor-side tasks, so output may appear in **executor logs** rather than neatly in the driver's console.

Therefore, don't rely on:

```scala
rdd.foreach(println)
```

as your primary way of retrieving results.

Use:

```scala
rdd.collect()
```

or:

```scala
rdd.take(n)
```

for inspection.

---

## 23. `foreach()` vs `map()`

This is a nice viva question.

**`map()`**

```scala
val result = rdd.map(_ * 2)
```

Produces a new RDD.

**`foreach()`**

```scala
rdd.foreach(println)
```

Performs an action/side effect and doesn't produce a new RDD for further transformation.

Think:

```
map
 ↓
new RDD

foreach
 ↓
do something with each element
```

---

## 24. `saveAsTextFile()`

Another important action.

Suppose:

```scala
val nums = sc.parallelize(List(10,20,30,40))
```

We can save the RDD as text:

```scala
nums.saveAsTextFile("C:/sparkoutput/numbers")
```

Spark writes the output as a **directory** containing partition output files rather than simply creating one ordinary text file in the general distributed case.

Conceptually:

```
RDD
 |
 | saveAsTextFile()
 ↓
output directory
 |
 +---- part-00000
 +---- part-00001
 +---- ...
```

The number of part files is related to the number of output partitions.

---

## 25. Important Windows practical warning

If you run:

```scala
nums.saveAsTextFile("C:/sparkoutput/numbers")
```

and then run the same command again, Spark may complain because the output path already exists.

So during practical:

```
First run → works
Second run → output directory already exists
```

You may need to remove the old output directory before rerunning, depending on your local setup.

---

## 26. `saveAsTextFile()` vs `collect()`

| `collect()` | `saveAsTextFile()` |
|---|---|
| Brings data to driver | Writes data to storage |
| Returns result to application | Produces output files |
| Risky for huge data | Better suited to distributed output |
| Mainly for retrieval/inspection | Used for saving results |

**Very important concept:**

> Don't use `collect()` just to save a huge dataset.

Another useful action is:

```scala

```

Then:

```scala
nums.takeOrdered(3)
```

**Result:**

```scala

```

```
nums
 |
 | filter()
 ↓

 |
```

## 30. What happens internally?

At a high level:

**You write:**

```scala

```

**Spark thinks:**

```
nums
  |
filter
  |
map
  |
collect
  |
execute
```

The action tells Spark:

> "I need the result now."

This is the foundation of lazy evaluation.

## 35. `collect()` vs `foreach()` — examiner trap

**Examiner:** "Which is better for displaying a large RDD?"

Don't say `collect()` automatically.

Say:

> `collect()` brings all data to the driver and can cause memory problems for large datasets. For inspecting a limited amount of data, `take()` is safer. `foreach()` executes on the executors and is mainly useful for side effects rather than collecting results.

That's a strong answer.

## 36. `reduce()` vs `collect()`

**`collect()`**

Returns elements:

```
1 2 3 4 5
```

**`reduce()`**

Combines them:

```
1 + 2 + 3 + 4 + 5
          ↓
         15
```

So:

```
collect → retrieve
reduce  → aggregate
```

## 37. A very important concept — Actions can produce different kinds of results

Actions don't all return the same thing.

```
collect()
   ↓
Array[T]

count()
   ↓
Long

first()
   ↓
T

take(n)
   ↓
Array[T]

reduce()
   ↓
T

sum()
   ↓
numeric result

saveAsTextFile()
   ↓
writes output
```

So "action returns an RDD" is **wrong**.

> An action generally does not create another RDD.

## 38. Transformation vs Action — MASTER TABLE 🔥

| Property | Transformation | Action |
|---|---|---|
| Creates new RDD? | Yes | Generally no |
| Lazy? | Yes | Triggers execution |
| Produces final result? | No | Yes / performs side effect |
| Example | `map()` | `collect()` |
| Example | `filter()` | `count()` |
| Example | `flatMap()` | `reduce()` |
| Example | `distinct()` | `saveAsTextFile()` |

### One-line memory trick

> Transformation builds the plan; Action asks Spark to execute it.

That's probably the best mental shortcut for this entire section.

## 44. Common mistakes ⚠️

**Mistake 1 — Calling `map()` an action**

❌ Wrong.

```
map → transformation
```

**Mistake 2 — Calling `collect()` a transformation**

❌ Wrong.

```
collect → action
```

**Mistake 3 — Thinking transformation immediately executes**

❌ Generally wrong.

```scala
val x = rdd.map(...)
```

is lazy.

**Mistake 4 — Using `collect()` on huge data**

❌ Dangerous.

Use `take()` for inspection when appropriate.

**Mistake 5 — Thinking `reduce()` returns an RDD**

❌ No.

It returns the aggregated result.

**Mistake 6 — Thinking `foreach()` is a way to safely retrieve results**

❌ No.

It's primarily for side effects.

# PART 5 — ⚙️ RDD Operations & Methods

We now know:

```
RDD
 |
 +── Transformations
 |      map()
 |      filter()
 |      flatMap()
 |      distinct()
 |      union()
 |      ...
 |
 +── Actions
        collect()
        count()
        reduce()
        ...
```

Now we're going to focus on the important RDD operations/methods used in actual Spark applications, especially **key-value RDDs**.

This directly falls under the syllabus requirement of describing RDD functions, operations and methods.

## 1. What are Key-Value RDDs?

Before `reduceByKey()` and `groupByKey()`, we need to understand one simple concept.

A normal RDD might contain:

```
1
2
3
4
5
```

So: `RDD[Int]`

A **key-value RDD** contains elements in pairs:

```
("Alice", 85)
("Bob", 72)
("Charlie", 91)
```

Conceptually: `RDD[(String, Int)]`

Each element has:

```
KEY       VALUE

Alice  →   85
Bob    →   72
Charlie →  91
```

This is extremely useful when we want to group or aggregate data based on a key.

---

## 2. Creating a Key-Value RDD

Let's create one:

```scala
val students = sc.parallelize(
  List(
    ("Alice", 85),
    ("Bob", 72),
    ("Charlie", 91),
    ("David", 68)
  )
)
```

Check:

```scala
students.collect()
```

**Output:**

```
Array(
  (Alice,85),
  (Bob,72),
  (Charlie,91),
  (David,68)
)
```

Here:

```
(Alice,85)
   ↓
key   = Alice
value = 85
```

---

## 3. Accessing Key and Value

Remember from Unit II:

```scala
pair._1
```

means first element.

```scala
pair._2
```

means second element.

For:

```scala
("Alice", 85)
```

we have:

```
._1 → Alice
._2 → 85
```

So:

```scala
students.filter(_._2 >= 80)
```

means:

> Keep student records whose second field/marks are at least 80.

**Result:**

```
(Alice,85)
(Charlie,91)
```

---

## 4. `mapValues()`

This is a useful key-value RDD operation.

Suppose:

Very important.

Works on the complete pair:

```scala
  case (name, marks) => (name, marks + 5)
```

**`mapValues()`**

Works specifically on the value:

```
 ↓

(key, value) → (same key, transformed value)
```

### Viva answer

> `map()` transforms the complete RDD element, while `mapValues()` is used with pair RDDs to transform only the values while preserving the keys.

## 8. What does `reduceByKey(_ + _)` mean?

Break it down:

```scala
reduceByKey(_ + _)
```

**`ByKey`**

Spark performs the reduction separately for each key.

**`_ + _`**

Values associated with the same key are combined using addition.

So:

```
Apple → 10,15
       ↓
      10+15
       ↓
      25
```

This is important.


Does this immediately return the final values?

**No.**

It creates another RDD:

```

   |
reduceByKey()
   ↓
totals RDD
```

Therefore:

> `reduceByKey()` is a transformation.

Then:

```scala
totals.collect()
```

is the action that requests the result.

```
       ↓
```

## 14. `groupByKey()` does NOT aggregate

This is critical.

Suppose:

```
(A,10)
(A,30)
```

`groupByKey()` gives:

```
A → [10,30]
```

It does **not** give:

```
A → 40
```

If you want `40`:

```scala
data.reduceByKey(_ + _)
```

gives:

```
A → 40
```

So:

```
groupByKey
 ↓
group values

reduceByKey
 ↓
combine/reduce values
```

## 15. `reduceByKey()` vs `groupByKey()` 🔥🔥🔥

> This is almost guaranteed viva material.

| `reduceByKey()` | `groupByKey()` |
|---|---|
| Aggregates values by key | Groups values by key |
| Requires a combining function | Doesn't require a reduction function |
| Produces one value per key after reduction | Produces grouped values per key |
| Can perform local/partial aggregation before shuffle | Typically moves grouped values across partitions |
| Usually preferred for aggregation | Can be less efficient for simple aggregation |
| Example `_ + _` | No reduction function |

---

## 16. Why is `reduceByKey()` generally better for aggregation?

Suppose we have:

```
Partition 1:
(A,10)
(A,20)
(A,30)
```

Instead of sending all three values across the network, Spark can conceptually combine them locally:

```
10 + 20 + 30
      ↓
     60
```

and then shuffle:

```
(A,60)
```

This is called **map-side/local combining** conceptually.

With `groupByKey()`, Spark needs to group the values, which can result in more data being transferred.

So:

> When the goal is aggregation, `reduceByKey()` is generally preferred because it can perform local combining before shuffle, reducing data movement.

This is an excellent evaluator-impressing answer.

---

## 17. Important caveat

Don't say:

> ❌ "`groupByKey()` is always bad."

Too strong.

**Better:**

> `groupByKey()` is useful when we genuinely need all values associated with each key. However, when the goal is aggregation, `reduceByKey()` is generally more efficient because it can combine values before shuffle.

That's technically much stronger.

## 42. One subtle point about `mapValues()`

`mapValues()` is specifically designed for pair RDDs.

If: `RDD[(K,V)]`

then: `rdd.mapValues(f)`

conceptually gives: `RDD[(K,V2)]` where the key stays the same.

Example:

```
(K,V)
 ↓
(K,f(V))
```

Whereas `map()` can completely change the structure:

```
(K,V)
 ↓
anything
```

## 43. One subtle point about `reduceByKey()`

`reduceByKey()` expects a function that combines two values of the same type.

For `RDD[(String,Int)]`, you can do:

```scala
reduceByKey(_ + _)
```

because `Int + Int → Int`.

You can also do:

```scala
reduceByKey((a,b) => if (a > b) a else b)
```

to find maximum value per key.

**Example:**

```
("Alice",80)
("Alice",95)
("Bob",70)
("Bob",90)
```

```scala
val highest = students.reduceByKey((a,b) => if (a > b) a else b)
```

**Result:**

```
(Alice,95)
(Bob,90)
```

**Minimum:**

## 47. 🔥 Viva questions from Part 5

**Q1. What is a pair RDD?**
An RDD whose elements are key-value pairs, such as `(key, value)`.

**Q2. What is `reduceByKey()`?**
A transformation that combines values having the same key using a specified reduction function.

**Q3. Is `reduceByKey()` an action?**
No. It is a transformation.

**Q4. What does `groupByKey()` do?**
Groups all values associated with the same key.

**Q5. Does `groupByKey()` perform aggregation?**
No. It groups values but does not combine them into a single aggregate.

**Q6. Difference between `reduceByKey()` and `groupByKey()`?**
`reduceByKey()` combines values by key using a reduction function, while `groupByKey()` groups all values by key without reducing them. For aggregation, `reduceByKey()` is generally preferred because it can perform local combining before shuffle.

🔥 Memorize this one.

**Q7. What is `mapValues()`?**
It transforms only the values of a pair RDD while keeping the keys unchanged.

**Q8. What does `sortByKey()` do?**
Sorts a pair RDD according to its keys.

**Q9. What does `keys` return?**
An RDD containing only the keys.

**Q10. What does `values` return?**
An RDD containing only the values.

**Q11. What does `lookup(key)` do?**
Returns the values associated with a specified key in a pair RDD.

**Q12. What is `distinct()`?**
A transformation that returns unique elements.

**Q13. Does `union()` remove duplicates?**
No.

**Q14. What does `intersection()` do?**
Returns elements common to both RDDs.

**Q15. What is `glom()` useful for?**
It groups the elements of each partition into an array, making partition contents easier to inspect.

## 49. ⚠️ Common practical mistakes

**Mistake 1**

Writing:

```scala

```

on `RDD[Int]`.

❌ `reduceByKey()` is for pair/key-value RDDs.

You need `RDD[(K,V)]`, e.g.:

```scala
sc.parallelize(List(("A",1),("B",2)))
```

**Mistake 2**

Thinking `groupByKey()` automatically sums values.

❌ No. It groups them.

**Mistake 3**

Thinking `union()` removes duplicates.

❌ No.

Use:

```scala
rdd1.union(rdd2).distinct()
```

if you need unique values.

**Mistake 4**

Thinking `mapValues()` changes keys.

❌ No. It transforms values.

**Mistake 5**

Thinking `sortByKey()` sorts values.

❌ It sorts according to keys.

# PART 6 — 🧠 Lazy Evaluation, Lineage & Fault Tolerance

> The syllabus includes RDD creation, functions, operations and methods; understanding lazy execution and lineage gives you the internal reasoning behind those operations.

## 1. First: What does "Lazy Evaluation" mean?

The simplest definition:

> Lazy evaluation means Spark does not immediately execute transformations when they are called. It records the transformations and executes them when an action requires a result.

This is one of the most important Spark concepts.

Remember:

```
Transformation
      ↓
No immediate execution
      ↓
Build computation plan
      ↓
Action
      ↓
Execution
```

---

## 2. Let's prove it practically

Start with:

```scala
val nums = sc.parallelize(1 to 10)
```

Now:

```scala
val even = nums.filter(_ % 2 == 0)
```

Then:

```scala
val doubled = even.map(_ * 2)
```

At this point:

```
nums
 |
 | filter
 ↓
even
 |
 | map
 ↓
doubled
```

You haven't asked Spark for the actual result.

Now:

```scala
doubled.collect()
```

This is the action.

Spark now has to execute the necessary computation.

---

## 3. Why does Spark use lazy evaluation?

This is the important question.

If Spark executed every transformation immediately, imagine:

```scala
val a = rdd.filter(...)
val b = a.map(...)
val c = b.filter(...)
val d = c.map(...)
```

Spark could potentially perform separate computations at every stage.

That can create unnecessary work.

Instead, Spark can look at the overall computation:

```
RDD
 |
filter
 |
map
 |
filter
 |
map
 |
ACTION
```

and optimize execution around the complete computation.

So lazy evaluation helps Spark:

- avoid unnecessary computation,
- build an execution plan,
- optimize the computation,
- pipeline suitable transformations,
- execute only when a result is required.

### 🎯 Viva answer

> Lazy evaluation allows Spark to defer transformation execution until an action is called, enabling Spark to optimize the computation and avoid unnecessary work.

---

## 4. Transformation chain

Let's create a simple chain:

```scala
val nums = sc.parallelize(1 to 10)

val even = nums.filter(_ % 2 == 0)

val doubled = even.map(_ * 2)

val large = doubled.filter(_ > 10)
```

The logical chain is:

```
nums
 |
filter
 ↓
even
 |
map
 ↓
doubled
 |
filter
 ↓
large
```

Now:

```scala
large.collect()
```

causes Spark to execute the necessary chain.

---

## 5. What if we never call an action?

Suppose:

```scala
val nums = sc.parallelize(1 to 100)

val even = nums.filter(_ % 2 == 0)

val doubled = even.map(_ * 2)
```

And then we stop.

No `collect()`, `count()`, `reduce()`, `saveAsTextFile()`.

Then Spark doesn't need to produce the final result.

Conceptually:

```
Transformation chain exists
          |
          ↓
No action
          |
          ↓
No need to execute the result-producing computation
```

This is the essence of laziness.

---

## 6. A common misconception

Some students say:

> ❌ "Transformations don't do anything."

That's not the best way to say it.

**Better:**

> Transformations define a computation and create a new RDD logically, but their actual data processing is deferred until an action requires the result.

This is much more accurate.

---

## 7. Lazy evaluation doesn't mean "nothing happens"

When you write:

```scala
val doubled = nums.map(_ * 2)
```

Spark does establish the relationship:

```
nums → map → doubled
```

It knows how `doubled` depends on `nums`.

What's deferred is the actual **execution** of the data processing.

---

## 8. Lineage — the second major concept

Now we come to lineage.

> Lineage means: The history/dependency information describing how an RDD was derived from previous RDDs.

Example:

```
Original RDD
     |
   filter
     ↓
   RDD 2
     |
    map
     ↓
   RDD 3
     |
   filter
     ↓
   RDD 4
```

Spark can maintain this dependency information. That is the lineage.

---

## 9. Why is lineage important?

Because RDDs are **fault tolerant**.

Imagine:

```
RDD
 |
 +---- Partition 1
 |
 +---- Partition 2  ← LOST
 |
 +---- Partition 3
```

Spark doesn't necessarily need a traditional full copy of the entire RDD.

Instead, it can look at the lineage:

```
Source
  |
filter
  |
map
  |
lost partition
```

and recompute the missing partition.

---

## 10. The key idea of RDD fault tolerance

Remember this sentence:

> RDD fault tolerance is primarily achieved through lineage and recomputation of lost partitions.

This is an excellent viva answer.

---

## 11. Example of lineage

Suppose:

```scala
val rdd1 = sc.parallelize(1 to 10)
```

Then:

```scala
val rdd2 = rdd1.filter(_ % 2 == 0)
```

Then:

```scala
val rdd3 = rdd2.map(_ * 10)
```

**Lineage:**

```
rdd1
 |
 | filter
 ↓
rdd2
 |
 | map
 ↓
rdd3
```

If a partition of `rdd3` needs to be recomputed, Spark knows that it came from:

```
    ↓
 filter
    ↓
rdd2
    ↓
 map
    ↓
rdd3
```

So it can reproduce the missing computation.

---

## 12. Lineage is NOT the same as storing every result

This distinction is important.

Lineage means Spark remembers the **dependency/computation relationships**.

It does **not** mean:

> ❌ Spark permanently stores every intermediate RDD

No.

RDDs are immutable and can be recomputed from their dependencies.

If you explicitly `cache`/`persist` an RDD, then Spark may retain its partitions according to the chosen storage level.

---

## 13. `cache()`

Now we connect this to something we briefly saw earlier.

Suppose:

```scala
val nums = sc.parallelize(1 to 1000000)

val even = nums.filter(_ % 2 == 0)
```

Suppose we use `even` repeatedly.

We can write:

```scala
even.cache()
```

This tells Spark:

> Persist this RDD using the default caching storage level so it can potentially be reused without recomputing it from its lineage each time.

---

## 14. Very important: `cache()` is also lazy

Suppose:

```scala
even.cache()
```

Does Spark immediately process and store every partition?

**Not necessarily.**

Caching is generally materialized when an action causes the RDD to be computed.

For example:

```scala
even.cache()

even.count()
```

The action `count()` causes computation, and the resulting partitions can be cached according to the storage level.

---

## 15. Why cache an RDD?

Suppose we have:

```
Original data
     |
 expensive transformations
     ↓
  processed RDD
```

And we use that processed RDD multiple times:

```
processed RDD
   |       |
   |       +---- count()
   |
   +------------ collect()
```

Without caching, Spark may need to recompute the upstream lineage when required.

With caching:

```
processed RDD
     |
   cache
     |
 +---+------+
 |          |
count()   collect()
```

The cached data can be reused if available.

---

## 16. When should you use `cache()`?

**Good situation:**

```
Expensive transformation
        ↓
RDD used multiple times
```

For example:

```scala
val processed = rdd
  .filter(...)
  .map(...)
  .flatMap(...)
```

If you repeatedly perform:

```scala
processed.count()
processed.collect()
processed.take(10)
```

caching may help.

---

## 17. When is caching unnecessary?

If you use an RDD only once:

```scala
val result = rdd.map(...).filter(...)

result.collect()
```

then caching the intermediate RDD may provide little or no benefit and can consume resources.

So:

> Cache reused, expensive-to-compute RDDs when the cost-benefit makes sense.

---

## 18. `cache()` vs `persist()`

You may see both.

**`cache()`**

Simple convenience method using the default storage level.

```scala
rdd.cache()
```

**`persist()`**

Allows you to specify a storage level.

Conceptually:

```scala
rdd.persist(storageLevel)
```

The important exam-level distinction:

```
cache()
 ↓
default storage level

persist()
 ↓
choose storage level
```

> You don't need to memorize every storage-level constant for tomorrow's RDD-focused practical unless your instructor specifically asks.

---

## 19. Cache is not permanent storage

This is another common mistake.

Don't say:

> ❌ "`cache()` permanently saves the RDD in RAM."

Wrong.

**Better:**

> `cache()` requests that Spark persist the RDD using its default storage level so that it can be reused efficiently; cached data is managed by Spark and may be evicted when resources are constrained.

That's a much stronger viva answer.

---

## 20. Lineage and cache work together

Imagine:

```
Source RDD
    |
 expensive transformation
    ↓
Processed RDD
    |
   cache()
    |
    ↓
Action
```

If cached partitions are available:

```
Future action
     |
     ↓
Use cached partitions
```

If cached data is lost/evicted:

```
Cached partition unavailable
          |
          ↓
Use lineage
          |
          ↓
Recompute
```

This is a beautiful point to mention in viva.

---

## 21. Lineage vs Cache

| Lineage | Cache |
|---|---|
| Records dependency/history | Stores computed partitions for reuse |
| Helps fault recovery | Helps avoid repeated computation |
| Fundamental to RDD fault tolerance | Optional performance optimization |
| Doesn't mean all intermediate data is stored | Uses storage resources |
| Recompute missing data | Reuse available cached data |

---

## 22. Fault scenario — understand this properly

Suppose:

```
RDD
 |
 +---- P1
 +---- P2
 +---- P3
```

`P2` is lost.

Spark can conceptually do:

```
Original source
      |
   transformation 1
      |
   transformation 2
      |
    P2 again
```

Instead of:

```
Recompute entire RDD from scratch
```

The exact recovery strategy depends on dependencies and what data remains available, but the key RDD concept is:

> Recompute the lost partition from lineage.

---

## 23. Why is RDD fault tolerance powerful?

Traditional distributed systems often rely heavily on replication.

RDDs can exploit:

```
Immutable data
      +
Lineage
      +
Recomputation
```

to recover lost partitions.

This makes RDDs particularly useful for distributed data processing.

---

## 24. RDD lineage and immutability

These three concepts are strongly connected:

```
              RDD
               |
       -------------------
       |        |        |
 Immutable   Lineage   Partitioned
       |        |        |
       ↓        ↓        ↓
 predictable  recovery parallelism
```

Because RDDs aren't modified in place, Spark can maintain clear dependency relationships.

---

## 25. Narrow dependency

We briefly introduced this in Part 3.

Consider:

```scala
val even = nums.filter(_ % 2 == 0)
```

An output partition can generally be computed from a corresponding input partition.

Conceptually:

```
Input P1 ─────→ Output P1
Input P2 ─────→ Output P2
Input P3 ─────→ Output P3
```

This is a **narrow dependency**.

---

## 26. Wide dependency

Now consider:

```scala
pairs.reduceByKey(_ + _)
```

Values with the same key may exist in different partitions.

Spark may need to move data:

```
P1 ──┐
P2 ──┼──→ Shuffle → new partitions
P3 ──┘
```

This creates a **wide dependency**.

---

## 27. Why does this matter to lineage?

Because lineage can be viewed as a graph of dependencies.

Example:

```
             RDD 1
            /     \
       filter     filter
          |         |
        RDD 2     RDD 3
            \     /
              ...
```

Spark uses these dependencies to understand how to compute partitions.

The exact internal scheduling is handled by Spark's execution engine, but the conceptual lineage graph is fundamental.

---

## 28. DAG — Directed Acyclic Graph

You've probably heard this term in Spark.

DAG stands for: **Directed Acyclic Graph**

Spark can represent the computation as a graph of operations/dependencies.

Example:

```
RDD 1
  |
 filter
  ↓
RDD 2
  |
 map
  ↓
RDD 3
  |
reduceByKey
  ↓
RDD 4
  |
collect
  ↓
Result
```

The edges represent dependency relationships:

```
RDD1 → RDD2 → RDD3 → RDD4
```

There are no cycles in this computation graph, hence **acyclic**.

---

## 29. Why does Spark use a DAG?

Instead of executing every operation as a completely independent job, Spark can analyze the entire chain and organize execution.

Conceptually:

```
Your code
   |
   ↓
Transformations
   |
   ↓
DAG
   |
   ↓
Execution planning
   |
   ↓
Tasks
```

This is one of the reasons Spark's execution model differs from traditional MapReduce.

---

## 30. DAG vs Lineage

Don't confuse them.

**Lineage**

Focuses on: how an RDD was derived from its dependencies.

**DAG**

A broader graph representation of computation/dependencies used in Spark's execution planning.

For a simple RDD chain, they can look very similar conceptually.

### A safe viva answer

> RDD lineage records the dependency chain between RDDs, while the DAG represents the directed acyclic computation graph that Spark can use to plan execution.

---

## 31. Lazy Evaluation + DAG + Lineage

Now we can connect the whole story:

```
             Your Spark Code
                    |
                    ↓
          Transformations
                    |
                    ↓
             Lazy evaluation
                    |
                    ↓
        Dependency / Lineage
                    |
                    ↓
              DAG planning
                    |
                    ↓
                 Action
                    |
                    ↓
              Actual execution
                    |
                    ↓
              Task execution
```

This is the big picture.

---

Let's use:

```scala
val nums = sc.parallelize(1 to 10)

val result = nums
  .filter(_ % 2 == 0)
```

At this stage: **No final computation requested**

Then:

Now:


**Result:**

```
Array(20,40,60,80,100)
```

## 34. Job, Stage, Task — basic connection

## 37. Why is Spark often faster than disk-heavy MapReduce?

We're not revisiting Unit I, but this connection is useful.

Suppose an iterative workload repeatedly uses data:

```
Read
 ↓
Process
 ↓
Write
 ↓
Read again
 ↓
Process
 ↓
Write
```

MapReduce traditionally relies heavily on persistent storage between stages.

Spark can:

```

 ↓
Transform
 ↓
Cache/persist

```

This can substantially reduce repeated I/O for suitable workloads.

But remember the correct statement:

> Spark emphasizes in-memory reuse; it does not mean Spark never uses disk.

**Mistake 1**

**Mistake 2**

❌ No. Lineage stores dependency information used for recomputation.

**Mistake 3**

❌ No. Caching uses Spark's storage mechanism and cached data can be evicted.

**Mistake 4**

## 47. 🧠 PART 6 Rapid-fire Viva

**Q1. What is lazy evaluation?**
Deferring transformation execution until an action requires a result.

**Q2. Why does Spark use lazy evaluation?**
To avoid unnecessary computation and enable optimization of the overall computation.

**Q3. What is lineage?**
The dependency/history describing how an RDD is derived from previous RDDs.

**Q4. Why is lineage important?**
It enables Spark to recompute lost partitions and provides RDD fault tolerance.

**Q5. What happens when an RDD partition is lost?**
Spark can recompute the lost partition using its lineage.

Persisting an RDD's computed partitions so that reused data can potentially be accessed without recomputing the full lineage.

**Q7. What does `cache()` do?**
Requests persistence using the default caching storage level.

`cache()` uses the default storage level, while `persist()` allows a chosen storage level.

**Q10. What does `unpersist()` do?**
Requests removal of cached RDD data.

**Q11. What is DAG?**
Directed Acyclic Graph representing a directed, cycle-free computation/dependency graph.

**Q12. How are transformations and actions related to lazy evaluation?**
Transformations build the computation lazily; actions trigger its execution.

A dependency where an output partition depends on a limited set of input partitions, typically one.

**Q14. What is a wide dependency?**
A dependency where an output partition can depend on multiple input partitions, typically requiring data redistribution/shuffle.

They may require shuffle involving network transfer, serialization, memory and/or disk I/O.
